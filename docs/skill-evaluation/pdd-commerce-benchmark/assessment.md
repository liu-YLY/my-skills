# 电商交易域 Skill 纵向评测方案评估

> 评估对象：[电商交易域 Skill 纵向评测方案](benchmark-plan.md)
> 评估日期：2026-11-17
> 评估维度：可行性、必要性、收益、成本、风险
> 结论：**方案可行、必要，收益明确；建议按 P0 → P3 分阶段落地，先人工后 AI，不建议一上来做全自动评分。**

---

## 1. 结论摘要

| 维度 | 判断 | 核心理由 |
|---|---|---|
| 技术可行性 | **高** | 仓库已有 runner / judge / 汇总脚本、methodology v1.5、tier23 对照经验；新增工作主要是业务资产与评分卡，不涉及底层重构 |
| 数据可行性 | **高** | 需求文档、固定数据、must-cover、open findings 均可一次性编写并冻结；58 条 must-cover 已可机器校验引用 |
| 方法可行性 | **中高** | 评分卡与配对设计可复现；主要难点是人工评分一致性与需求歧义，已有 kappa、锚点、仲裁机制对冲 |
| 组织可行性 | **中** | 需要 2 名独立评审员与固定仲裁人；若无法保证独立性，结论只能降档为「未盲评」 |
| 必要性 | **高** | 现有 42 task 套件缺少真实连贯需求，且已暴露缺料与术语依赖问题；没有纵向基准，skill 改进容易被单点 prompt 过拟合 |
| 收益 | **中高** | 直接收益是 keep/revert 决策与高风险场景覆盖；长期收益是形成可复用的标注数据集与 AI judge 资产 |
| 成本 | **中** | 单次全量对照 60 份产物；H0 校准 240 次人工判定；主要成本在人工评分，不在运行 |
| 综合建议 | **推荐立项** | 先做 P0 小闭环，验证评分卡与输出契约，再扩到全量 |

一句话判断：**这套方案不是「再造一个评分表」，而是把「skill 是否真的让输出更好」变成可复跑、可归因、可积累的证据链。** 它的价值不在分数本身，而在把分数、净效应、成本、错误类型分开，避免用「分数上涨」替代「能力提升」。

---

## 2. 评估口径

本评估不预测具体提升幅度，也不估算日历工期。判断依据：

1. **可复现性**：同一输入、同一模型、同一评分卡，能否得到可解释的结果。
2. **归因能力**：结果变好/变坏时，能否区分是 skill、需求、评分卡、judge 还是环境造成的。
3. **决策价值**：能否支撑「保留 / 回滚 / 继续观察」的实际动作。
4. **成本可控性**：运行与人工评分是否可分批、可抽样、可自动化。
5. **风险可控性**：是否存在过拟合、分数虚高、judge 自证、数据污染等失效模式。

## 3. 可行性评估

### 3.1 技术可行性：高

已有基础：

- [methodology.md](../methodology.md) v1.5 已定义两层十维评分、§12 无效改进识别、§13 归因判定（A/A、配对、盲评、P/N/X/?、成本阈值）。
- [test-case-quality-eval-protocol.md](../test-case-quality-eval-protocol.md) 已定义 Tier 1/2/3 执行契约与 `partial` 标记。
- [tier23/](../tier23/) 已有 runner / judge / 汇总脚本与 84 份产物的实际对照经验。
- [scripts/skill-evals.py](../../../scripts/skill-evals.py) 可继续做输入校验与结果汇总。
- 被测 skill 的输入输出契约稳定：需求分析、测试点、用例均有明确格式要求。

本方案新增的是业务资产（PRD、must-cover、open findings）和评分卡，不需要改 skill 运行机制，也不需要新建评测平台。技术上属于「在现有评测骨架上增加一个纵向业务域」，不是从零搭建。

唯一需要新增的工程件是一个薄 runner 封装：现有 `scripts/skill-evals.py` 的 task 格式是单 prompt + expectations，不能直接承载多文件 PRD；薄封装负责读取 benchmark JSON、附加需求文档、调用 skill、写入 `runs.jsonl`。工作量小，风险低。

主要技术风险：

| 风险 | 说明 | 缓解 |
|---|---|---|
| must-cover 语义匹配 | 关键词匹配会把「提到」误判为「覆盖」 | 人工/AI judge 逐条附证据；0/0.5/1 三档；禁止纯关键词 |
| 输出格式不稳定 | 模型可能不按表格/块格式输出 | G0 结构闸门；P0 先跑 3 任务验证契约 |
| judge 同族偏好 | 同族模型偏好更符合 skill 规范的产物 | 强制换族；影子期；盲评 |
| 运行方差 | 单次生成波动大 | 3 次重复；A/A；固定参数 |

### 3.2 数据可行性：高

- 需求文档已编写并冻结，覆盖三条主链路，含 58 条 must-cover、8 条开放问题、固定测试数据。
- `benchmark-v1.json` 已通过 JSON 解析与引用一致性校验：10 个任务、58 条 must-cover、25 条 critical、8 条 open findings、10 条 review checks，任务引用无缺失。
- 需求中的金额、库存、优惠券、地址、支付结果均有固定数据，可复现。
- 开放问题被显式列出，避免「需求没写清但要求模型猜对」的不可判定争议。

数据层面的主要缺口：

- 尚无真实用户需求文档作为外部效度校验；当前 PRD 是借鉴拼多多的自拟需求，可能带有作者视角。
- 尚无历史版本的 120 份人工评分样本；H0 需要从零积累。
- 尚无 sealed 测试集；P0 需要先建立访问与版本控制。

这些缺口不影响 MVP，但限制了「结论可外推到真实业务」的强度。报告必须标注「评测输入为自拟 PRD」。

### 3.3 方法可行性：中高

方法上的关键设计是成立的：

1. **10 个任务单元 × 3 次重复 = 30 个配对样本**，达到 methodology §13.5 中「N=30 可检测中等效应」的最低门槛。
2. **绝对分与净效应分离**：评分卡衡量产物质量，配对胜负衡量 skill 的边际价值，避免「分数上涨但 no_skill 也上涨」的误判。
3. **A/A 前置**：先测噪声，再谈差异；避免把随机波动当改进。
4. **归因矩阵**：把低分拆成需求、oracle、skill、judge、环境五类，防止「改考卷让考生通过」。
5. **人工到 AI 的门槛**：kappa、S1 一致率、MAE、审计轮次，均有明确数值，不靠感觉切换。

方法上的主要难点：

- **评分主观性**：D3 可执行性、D6 可读性仍依赖判断；需要锚点与双评。
- **需求歧义**：开放问题虽已列出，但测试点是否应覆盖开放问题、如何计分，仍需在 P0 校准。
- **覆盖与正确的权衡**：覆盖率高但预期错误的产物，不能靠 D1 拿高分；G1/S1 封顶机制解决了一部分，但仍需评审员严格执行。
- **配对样本独立性**：同一任务的 3 次重复不是完全独立，符号检验的效力需在报告中说明；N=30 是最低门槛，不是充分条件。

### 3.4 组织可行性：中

需要的最小组织配置：

- 2 名独立评审员（不参与被测 skill 开发）。
- 1 名仲裁人（处理总分差 > 10 或 S1 分歧）。
- 1 名运行负责人（冻结资产、跑批次、落盘产物）。
- 1 名 skill 维护者（根据 S 类归因修改 skill，不修改 benchmark）。

风险：

- 评审员时间不可控，可能成为瓶颈。
- 评审员若与被测 skill 同团队，独立性不足，结论需降档。
- 若只有 1 名评审员，无法计算 kappa，只能做单评 + 抽检，结论强度下降。

缓解：

- P0 只做 3 个任务、18 份 pilot，降低首次投入。
- H1 之后 AI 影子分担评分量。
- H2 只审计 20% + 关键错误，逐步降低人工比例。
- 评审员使用统一评分表与锚点，减少沟通成本。

## 4. 必要性评估

### 4.1 现有评测体系解决了什么

现有 42 task 套件与 tier23 对照已经证明：

- 可以跑通 with/without 配对。
- 可以做盲评与产物落盘。
- 可以发现「有 skill 比无 skill 更好」的方向性差异（2026-11-03 报告：with_skill 165/219 vs no_skill 96/219，+31.5pp）。

### 4.2 现有体系没有解决什么

| 缺口 | 证据 | 后果 |
|---|---|---|
| 缺少连贯的真实需求 | 42 task 多为单点 prompt，无跨模块 PRD | 无法衡量需求理解、跨模块金额一致性、状态闭环 |
| 评测集缺料 | 2026-11-03 报告约 11 条评审 case 的附件是占位符或不存在文件 | 这些 case 无法产出有效判定，分数失真 |
| skill 术语依赖 | 约 29 条评审/安全 case 的 checks 依赖 skill 特有术语 | no_skill 天然低分，差距不能全部归因于生成质量 |
| 缺少纵向版本基线 | tier23 是一次性对照，不是固定业务基准 | 每次改动仍要重新设计输入，难以比较 |
| 缺少标注数据集 | 评分结果未形成结构化标签 | AI judge 无法校准，人工评分无法复用 |

### 4.3 不做的后果

如果不建立纵向 benchmark，可能出现三种失效：

1. **单点过拟合**：skill 针对 42 条 task 的措辞优化，分数上升，但面对真实 PRD 仍漏跨模块规则。
2. **无效改进被保留**：只改措辞、文件组织或输出长度，评分略升，但没有真实覆盖增益，违反 methodology §12。
3. **AI judge 无据可依**：没有稳定的人工标注集，AI 评分无法校准，容易变成「另一个模型的主观印象」。

### 4.4 必要性判断

**必要性高**，理由不是「多一个 benchmark」，而是：

- 它是 skill 迭代的**回归基线**：每次改规则，先问「在这份真实需求上是否更好」。
- 它是 AI judge 的**冷启动数据源**：人工评分先跑，才能让 AI 学会评分口径。
- 它是**反向调整的抓手**：低分测试点和用例能定位到具体规则缺口，而不是停留在「感觉不够好」。
- 它补上了现有套件最缺的**跨模块一致性**：登录态、购物车价格、订单金额、支付回调、退款状态必须在一条链路里闭环。

## 5. 收益评估

### 5.1 决策收益

| 收益 | 说明 | 可观测指标 |
|---|---|---|
| 保留/回滚有证据 | 版本对照给出配对胜负与 P/N/X/?，不靠主观判断 | 每轮对照的胜/平/负、p 值、结论档位 |
| 区分「分数涨」与「能力涨」 | 绝对分与净效应分开报告 | no_skill 是否同步上涨；配对 Δ 是否显著 |
| 发现隐性退化 | S1/S2 错误单列，不被总分掩盖 | S1 数量、critical recall |
| 控制成本倒挂 | 输出长度、token、轮次单独计量 | 成本指标是否超阈值 |

### 5.2 质量收益

- **高风险场景覆盖**：58 条 must-cover 中 25 条 critical，集中在认证安全、支付幂等、库存不超卖、优惠券单次使用、越权、退款闭环。
- **跨模块一致性**：购物车金额 → 确认订单页 → 支付金额三段一致；登录态过期后的购物车恢复；拼单失败后的库存/券/退款闭环。
- **可执行性提升**：评分卡强制前置条件、测试数据、步骤、可观察预期；禁止「准备相关数据」「功能正常」。
- **需求评审质量**：8 条开放问题 + 10 条风险检查，迫使评审输出影响与建议，而不是只列问题。

### 5.3 效率收益

- **复用现有工具链**：runner、judge、汇总脚本、协议均可复用，新增主要是资产与评分卡。
- **分批抽样**：P0 只跑 3 个任务；H2 只审计 20% + 关键错误；条目分析后淘汰饱和条目。
- **AI judge 逐步接管**：H1 影子、H2 初评、H3 常规，人工从 100% 降到争议与抽检。
- **资产复用**：同一份 PRD 可扩展出测试策略、状态机、性能测试、造数等任务，不需要每次重写输入。

### 5.4 资产收益

- **标注数据集**：每次运行的产物、评分、错误、仲裁结论都结构化落盘，形成可复用资产。
- **评分锚点库**：0/2/4 分样例可复用于新评审员培训与 AI judge 校准。
- **需求变体库**：未来可增加售后、优惠券叠加、跨境等变体，形成难度梯度。
- **组织记忆**：历史报告与失败案例保留，避免重复踩坑。

### 5.5 风险收益

- **提前发现资金/库存/权限类缺陷**：这些缺陷在真实业务中代价高，在 benchmark 中可低成本暴露。
- **降低「上线后才发现漏测」的概率**：must-cover 清单把关键场景前置。
- **减少无效迭代**：如果改动只涨措辞分，配对胜负会揭穿它，避免团队把时间投入无效优化。

### 5.6 收益判断

**收益中高，但需要时间积累才能完全兑现。** 首轮收益主要是决策质量与高风险覆盖；数据集与 AI judge 的复利效应要到 H1/H2 之后才明显。不能承诺「一次上线就大幅提升质量」，更合理的预期是：

- 第一轮：建立基线，发现 3-5 个明确的 skill 缺口。
- 第二轮：验证修复是否带来配对胜场，淘汰无效改动。
- 第三轮起：AI judge 分担评分，人工聚焦争议与基准演进。

## 6. 成本评估

### 6.1 一次性成本

| 项 | 内容 |
|---|---|
| 需求文档 | 已编写，636 行，含 58 条 must-cover 与 8 条开放问题 |
| Benchmark 资产 | 10 个任务、任务 prompt、输出契约、负向范围 |
| 评分卡 | 3 类任务权重、G0-G4 闸门、S1/S2/S3、judge JSON 契约 |
| 评审员培训 | 锚点、评分表、S1 清单、仲裁规则 |
| 工具适配 | 复用现有 runner/judge；新增产物目录与 schema |

### 6.2 持续性成本

| 项 | 数量/频率 | 说明 |
|---|---|---|
| 单次全量对照 | 60 份产物 | 10 tasks × 2 variants × 3 repeats |
| 含 reference | 90 份产物 | 增加旧版本对照 |
| H0 人工评分 | 240 次判定 | 120 份 × 2 人 |
| H1 AI 影子 | 120 份 AI + 120 份人工 | 人工为共识基线 |
| H2 审计 | 20% 抽样 + 100% 关键错误 | 逐阶段降低人工 |
| 基准维护 | 每次变更 | 升版本、双评分、更新 README |

### 6.3 成本判断

成本中等，主要成本在人工评分，不在运行。可控手段：

- P0 只跑 3 个任务，先验证再扩量。
- H0 先抽样 30 份预校准，kappa 达标再扩到 120 份。
- 条目分析淘汰饱和项，减少后续评分量。
- AI 影子与审计逐步替代全量人工。

如果组织无法保证 2 名独立评审员，建议降低目标：只做单评 + 抽检，结论标注「未独立」，不要强行发布「有效」结论。

## 7. 风险与前提

### 7.1 主要风险

| 风险 | 等级 | 影响 | 缓解 |
|---|---|---|---|
| 需求歧义 | 中 | 评分争议、不可判定 | 开放问题显式化；任务要求标注「待确认」；仲裁 |
| 人工评分不一致 | 中 | 分数不可比 | 双评 + kappa + 锚点 + 仲裁 |
| judge 同族偏好 | 中高 | 结论自证 | 换族、盲评、证据要求、影子期 |
| 过拟合 benchmark | 中高 | 分数上升但真实能力不升 | sealed 集、held-out 变体、禁止逐字复用 |
| 分数虚高 | 中 | 误判改进 | G1 封顶、覆盖下限、成本单列、配对胜场 |
| 运行方差 | 中 | Δ 不可解释 | A/A、3 次重复、固定参数 |
| 评测集缺料 | 低 | 无效判定 | P0 每任务先跑通；缺料即修 |
| 维护腐化 | 中 | 基准失效 | 版本化、季度复校、README 登记 |
| 组织投入不足 | 中 | 评审员瓶颈 | 分批、抽样、AI 影子 |

### 7.2 成立前提

1. **基准冻结**：一次对照期间不改需求、oracle、评分卡；要改就升版本并双评分。
2. **评审员独立**：不参与被测 skill 开发；无法满足时报告降档。
3. **judge 换族**：AI judge 与被测模型不同族；无法换族时标注「未换族」。
4. **产物落盘**：所有数字可追溯到产物与 SHA256。
5. **不逐字复用**：benchmark 原题/答案不得写进 skill few-shot。
6. **结论纪律**：N < 20 只用于止损；N ≥ 30 且胜场达标才可声称「有效」；未达标只能写「未证实」。

## 8. 替代方案比较

| 方案 | 成本 | 可复现性 | 真实度 | 数据积累 | 结论 |
|---|---|---|---|---|---|
| A. 继续只用现有 42 task 套件 | 低 | 高 | 中低 | 中 | 适合回归，不足以判断真实业务能力 |
| B. 每次人工临时评审 | 中 | 低 | 高 | 低 | 真实但不沉淀，无法版本比较 |
| C. 本方案：纵向 benchmark + 人工先行 + AI 迁移 | 中 | 高 | 高 | 高 | **推荐** |
| D. 引入外部通用 benchmark | 低 | 高 | 低 | 低 | 不覆盖拼多多式交易规则与中文业务约束 |

推荐 **C + A 并用**：

- C 负责「在真实需求上是否更好」。
- A 负责「触发、结构、回归是否坏」。
- B 作为 C 的补充，用于发现 C 未覆盖的新问题，但结论要回灌到 C 的资产中。

## 9. 分阶段建议

| 阶段 | 做什么 | 不做 | 通过条件 |
|---|---|---|---|

## 10. 最终判断

### 可行性

**可行。** 技术骨架已存在，新增资产已完成初版并可校验；主要不确定性在人工评分一致性与需求歧义，已有 kappa、锚点、仲裁、开放问题等机制对冲。

### 必要性

**必要。** 现有套件解决了「单点任务是否规范」，但没有解决「面对真实连贯需求是否更好」；没有纵向基准，skill 迭代容易退化为对 42 条 prompt 的过拟合。

### 收益

**明确，但需分阶段兑现。** 首轮收益是决策证据与高风险覆盖；中期收益是反向调整闭环；长期收益是标注数据集与 AI judge 的复利。

### 建议

1. **立项，按 P0 先跑小闭环**，不要直接全量。
2. **人工评分先行**，H0 不引入 AI judge。
3. **绝对分与净效应分开报告**，避免「分数上涨 = 能力提升」。
4. **基准冻结、变更双评分、结论按 N 与胜场定档**。
5. **把 benchmark 当作资产维护**：版本化、登记、季度复校、sealed 集防污染。

如果只能做一件事：**先跑 P0 的 3 个订单模块任务，验证「同一份需求下，with_skill 是否比 no_skill 写出更完整的支付/库存/退款用例」。** 这个最小闭环能最早暴露方案是否值得继续投入。
