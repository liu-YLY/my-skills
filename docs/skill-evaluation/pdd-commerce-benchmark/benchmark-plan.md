> 版本：1.0.0
> 日期：2026-11-17
> 状态：方案冻结，待首次执行

> 配套资产：[需求文档](requirements-pdd-auth-cart-order.md)｜[评分卡](scoring-rubric.md)｜[Benchmark 种子](benchmark-v1.json)｜[可行性评估](assessment.md)

## 1. 结论摘要

本方案建议按「人工评分先行、AI 评分影子运行、校准达标后切换」的路径落地，先做一个可复跑的纵向评测集（Vertical Benchmark），再用它判断每次 skill 改动是否真的带来提升。

核心设计：

- **固定输入**：一份冻结的拼多多风格交易需求文档，覆盖登录注册、购物车、购买三条主链路。
- **三类任务**：需求评审、测试点提取、测试用例编写；拆成 10 个任务单元，每单元默认重复 3 次，形成 30 个配对样本。
- **两层判定**：绝对质量分（评分卡）+ 相对净效应（有/无 skill 配对、盲评、符号检验）。
- **评分迁移**：H0 人工双评 → H1 AI 影子 → H2 AI 初评 + 人工审计 → H3 AI 常规评分，每一级都有量化门槛。
- **反向调整**：低分先归因到需求、oracle、skill、judge、环境五类；只有 benchmark 自身缺陷才改基准，skill 缺陷只改 skill，避免「改考卷让考生通过」。
- **防虚高**：结构闸门、关键错误封顶、覆盖下限、成本单列、基准变更双评分。

建议先执行 P0（资产冻结 + 3 任务 pilot + 2 名评审员校准），通过后再进入 P1 全量 10 任务。首次对照只用于止损和方向判断，不对外声称「提升」；达到 methodology §13 的 N ≥ 30 胜场门槛后，才发布效果结论。

## 2. 目标与非目标

### 2.1 目标

1. **判断 skill 改动的真实效果**：同一需求、同一模型、同一参数下，比较 with_skill 与 no_skill / 旧版本，回答「这次改动是正向、中性还是负向」。
2. **区分分数与净效应**：评分卡衡量产物质量，配对比较衡量 skill 的边际价值；两者并列报告，不互相替代。
3. **形成可积累的数据集**：每次运行的产物、评分、错误标签、仲裁结论都落盘，成为后续 AI judge 的训练/校准资产。
4. **驱动反向改进**：从低分测试点和用例中定位 skill 规则缺口，形成「发现问题 → 修改 skill → 复跑验证」的闭环。
5. **覆盖高风险交易场景**：认证安全、支付幂等、库存不超卖、优惠券单次使用、越权、退款闭环。

### 2.2 非目标

- 不替代现有 42 task 的横向评测套件；两者互补，横向查回归，纵向查真实业务效果。
- 不在第一阶段做全自动 AI 评分；人工校准未达标前，AI 只做影子评分。
- 不评测模型本身的能力差异；跨模型结果不可归因于 skill。
- 不把需求文档当作可直接上线的最终 PRD；它是评测输入，开放问题保留。
- 不追求「用例越多越好」；数量只作为成本指标，不作为质量分。

| [test-case-engineer SKILL.md](../../../plugins/testing/skills/test-case-engineer/SKILL.md) | 被测主 skill；本方案不修改其规则，只作为评测对象 |

### 3.1 为什么现有 42 task 套件不够

现有套件解决的是「单点任务是否按规范输出」，但存在三个结构性限制：

1. **输入碎片化**：42 条 task 多为单点 prompt，缺少一份连贯、真实、跨模块的需求文档，难以衡量需求理解与跨模块一致性。
2. **评测集缺料**：2026-11-03 报告记录约 11 条评审类 case 的附件是占位符或引用不存在的文件，导致这些 case 无法产出有效判定。
3. **术语依赖**：约 29 条评审/安全类 case 的 checks 依赖 skill 特有流程术语，no_skill 天然低分，差距不能全部归因于生成质量。

纵向 benchmark 用一份完整 PRD 补上「真实输入」这一层，并用 must-cover 清单把覆盖率变成可核对的证据。

## 6. 任务设计

### 6.1 为什么是 10 个任务单元

methodology §13.5 规定：N=30 时，21 胜（70%）才能支持中等效应的正向结论。为避免「3 个任务 × 3 次重复 = 9 个样本」不足以支撑结论，本方案拆成：

- 需求评审 3 个：账号、购物车、订单支付。
- 测试点 3 个：账号、购物车、订单支付。
- 测试用例 4 个：账号、购物车、订单支付、端到端主链路。

合计 10 个任务单元 × 3 次重复 = **30 个配对样本**。这正好达到「可检测中等效应」的最低样本量，同时保持每次运行的 token 成本可控。

### 6.2 任务清单

| ID | 类别 | 模块 | 输出重点 | must-cover |
|---|---|---|---|---:|
| REV-AUTH | 需求评审 | 账号 | 规则冲突、开放问题、认证安全风险 | 0（用 open_findings） |
| REV-CART | 需求评审 | 购物车 | 计价顺序、失效商品、跨模块金额一致性 | 0 |
| REV-ORDER | 需求评审 | 订单支付 | 支付幂等、库存、拼单退款、越权 | 0 |
| TP-AUTH | 测试点 | 账号 | 功能/边界/异常/状态/权限/安全 | 15 |
| TP-CART | 测试点 | 购物车 | 功能/边界/异常/状态/并发/数据一致性 | 14 |
| TP-ORDER | 测试点 | 订单支付 | 功能/状态/异常/并发/安全/权限 | 22 |
| TC-AUTH | 测试用例 | 账号 | 可执行步骤、可判定预期、固定数据 | 15 |
| TC-CART | 测试用例 | 购物车 | 同上 + 计价与失效处理 | 14 |
| TC-ORDER | 测试用例 | 订单支付 | 同上 + 支付/库存/拼单/退款 | 22 |
| TC-E2E | 测试用例 | 端到端 | 主链路 + 重复提交/回调/超时/并发 | 7 |

> `must-cover` 是评分用检查清单，不在任务 prompt 中直接展示给被测 skill。T3 用例任务只给需求文档，避免提前泄露答案；V1.1 可增加「给定黄金测试点」的隔离变体，用于区分测试点质量与用例写作质量。

### 6.3 隔离模式与流水线模式

| 模式 | 输入 | 用途 | 是否主判定 |
|---|---|---|---|
| 隔离模式（V1 默认） | 每个任务独立读需求文档 | 归因清晰，适合版本比较 | 是 |
| 流水线模式（可选） | T1 评审 → T2 测试点 → T3 用例 | 观察真实工作流中的误差传播 | 否，只作诊断 |

隔离模式避免「上游漏了一个规则，导致下游全部扣分」的级联归因错误。流水线模式用于回答「端到端使用 skill 是否更顺」，不用于声称单点能力提升。

## 7. 运行协议

### 7.1 变体与重复

| 变体 | 说明 | 用途 |
|---|---|---|
| `no_skill` | 不加载 skill，仅用户 prompt + 需求文档 | baseline，回答「是否值得存在」 |
| `with_skill` | 加载被测 skill | candidate，回答「当前版本是否更好」 |
| `reference` | 上一版本 / 精简版 / 竞品 skill | 回答「这次改动是否值得」 |

默认重复 3 次。全量对照输出数：

```text
10 tasks × 2 variants × 3 repeats = 60 份产物
10 tasks × 3 variants × 3 repeats = 90 份产物（含 reference）
```

### 7.2 A/A 噪声基线

正式对照前，用同一配置跑两次 A/A：

| 指标 | 通过条件 | 不通过动作 |
|---|---|---|
| 总分差 | ≤ 5 分 | 检查评分卡锚点、judge 温度、断言可判定性 |
| must-cover 一致率 | ≥ 90% | 检查语义判定是否稳定；必要时增加重复次数 |
| 结构闸门 | 两次都通过 | 修 runner 指令或输出契约 |

A/A 不通过时，**不得**进入 with/without 对照；此时任何 Δ 都不可解释。

### 7.3 盲评与去标识

- 产物文件名使用中性编号，例如 `S01`、`S02`，不包含 skill 名称、版本、variant。
- 去掉生成时间、模型名、skill 名、版本号、工具调用痕迹。
- 同一任务的 with/without 产物随机排序。
- judge 只看到需求文档、任务 prompt、产物和评分卡；不看到变体标签。
- 人工评审员不得参与被测 skill 的开发；若无法满足，报告必须标注「未独立」。

### 7.4 运行环境

| 项 | 要求 |
|---|---|
| 模型 | 同一批次内所有 variant 使用同一模型与参数 |
| 上下文 | 每次运行使用全新上下文，不继承上一次产物 |
| 提示 | 只使用 [benchmark-v1.json](benchmark-v1.json) 中的任务 prompt，不追加「请完整」「请按四阶段」等提示 |
| 输入 | 只附加需求文档；不附加 must-cover、open_findings、评分卡 |
| 记录 | token、耗时、输出字符数、工具调用数、失败原因 |
| 失败 | 空输出、截断、格式无法解析均记为 invalid，不计入分数 |

### 7.5 执行顺序

```text
1. 冻结资产并记录 SHA
2. 跑 A/A，确认噪声可接受
3. 跑 no_skill（3 次）
4. 跑 with_skill（3 次）
5. 跑 reference（可选，3 次）
6. 产物去标识、随机排序
7. 人工/AI 评分
8. 汇总覆盖率、关键错误、成本
9. 配对分析 + P/N/X/? 定档
10. 写报告并归档
```

## 8. 评分体系

### 8.1 两层判定

| 层 | 指标 | 回答的问题 | 是否受 skill 名称影响 |
|---|---|---|---|
| 绝对质量 | 评分卡总分 0-100、覆盖率、关键错误 | 这份产物有多好 | 否 |
| 相对净效应 | 配对胜/平/负、符号检验 | 相比 baseline 是否更好 | 否，盲评 |

**绝对分上升不等于 skill 有效**。如果 no_skill 也同步上升，说明是模型或题目变化；只有配对胜场达到门槛，才能声称 skill 带来提升。

### 8.2 评分卡

详见 [scoring-rubric.md](scoring-rubric.md)。要点：

- G0 结构闸门：不满足输出契约记 0。
- G1 关键正确性：S1 错误（认证绕过、金额/支付错误、超卖、越权、状态损坏）总分封顶 59。
- G2 覆盖下限：加权覆盖率 < 60% 封顶 59。
- G3 追溯下限：可追溯条目 < 50% 封顶 74。
- D1-D6 六维加权：覆盖、正确、可执行、风险异常、追溯优先级、结构可读。
- 成本指标单列：输出字符数、token、轮次、工具调用数，不进入质量分。

### 8.3 Must-cover 覆盖率

- 58 条 must-cover，按 `critical=3`、`high=2`、`medium=1` 加权。
- 每条按 0 / 0.5 / 1 命中，必须附证据。
- `critical_recall` 单独报告，不能被平均值掩盖。
- **聚合口径**：任务内按 must-cover 加权；跨任务报告用宏平均（每个任务等权），不按 58 条微平均，避免订单模块条目多而主导总分；`critical_recall` 单独做微平均报告。
- 覆盖率只衡量「有没有测到」，不衡量「写得好不好」；后者由 D2-D6 承担。

### 8.4 关键错误

S1 错误必须单列，不能只体现在总分里。报告必须给出：

- 错误类型
- 涉及需求 ID
- 产物中的位置
- 是否在 no_skill 中也出现
- 是否属于 skill 引入的退化

若 with_skill 的 S1 错误数高于 no_skill，直接判 X（消极），不再看总分。

### 8.5 净效应判定

按 methodology §13.5 / §13.6：

| 条件 | 结论 |
|---|---|
| 胜场达到门槛，成本在预算内 | P 积极 |
| 胜场未达门槛，置信区间含 50% | N 中性·未证实 |
| 0-1 胜（任意 N），或成本倒挂，或出现事实/安全错误 | X 消极 |
| A/A 噪声超限，或有效样本 N < 6 | ? 无法判定 |

N=30 时，至少 21 胜才能判 P；0-1 胜判 X；其余判 N。N < 20 的实验只用于止损，不得声称收益。

### 8.6 成本指标

| 指标 | 采集 | 默认阈值 |
|---|---|---|
| 输出字符数 | 产物 UTF-8 字符数 | 增幅 ≤ 30% |
| token 消耗 | 运行日志 | 增幅 ≤ 50% |
| 交互轮次 | 消息计数 | 不增加 |
| 工具调用数 | 日志计数 | 不增加 |

成本倒挂：胜率达标，但任一成本指标增幅超过阈值 2 倍，结论降级为 N，并单列成本数据。

### 8.7 报告必填字段

每份版本对照报告必须包含：

- benchmark 版本 + 需求 SHA256
- skill 版本 + 模型 + 参数
- judge 族系 + 是否盲评 + 是否换族
- A/A 结果
- N、胜/平/负、符号检验 p 值
- P/N/X/? 档位
- must-cover 覆盖率、critical recall
- S1/S2/S3 错误清单
- 成本指标
- 未评估范围与限制

缺任一项，报告不得发布效果结论。

## 9. 人工评分阶段（H0）

### 9.1 样本设计

| 项 | 设计 |
|---|---|
| 样本量 | 10 tasks × 3 variants × 4 repeats = 120 份产物 |
| 评审员 | 2 名，独立评分，互不沟通 |
| 盲评 | 产物去标识、随机排序 |
| 评分单位 | 每份产物按评分卡打 D1-D6、must-cover、错误 |
| 仲裁 | 总分差 > 10 或 S1 判定不一致时，由第三名评审员仲裁 |
| 记录 | 评分表、证据、置信度、备注 |

### 9.2 校准指标

| 指标 | 门槛 | 不通过动作 |
|---|---|---|
| 二次加权 kappa（维度分） | ≥ 0.70 | 补充锚点示例，明确 0/2/4 分边界 |
| S1 判定一致率 | ≥ 0.90 | 细化 S1 清单，增加证据要求 |
| must-cover 命中一致率 | ≥ 0.85 | 把模糊条目拆成可判定条目 |
| 总分 MAE | ≤ 8 分 | 检查权重与锚点是否偏斜 |

### 9.3 锚点示例

评分卡 §11 要求每个维度提供 0/2/4 分锚点。首批锚点从 H0 样本中挑选：

- 4 分：可直接作为团队模板。
- 2 分：方向正确但缺少关键条件或证据。
- 0 分：结构失败、关键错误或完全偏离需求。

锚点只用于校准评分员，不进入 skill 的 few-shot；避免 benchmark 污染。

## 10. 人工到 AI 的迁移

### 10.1 四阶段

| 阶段 | 评分方式 | 人工参与 | 进入条件 |
|---|---|---|---|
| H0 人工校准 | 2 名评审员独立评分 | 100% | kappa ≥ 0.70 |
| H1 AI 影子 | AI 与人工同时评分，AI 不参与决策 | 100% | AI 与人工共识 kappa ≥ 0.75；S1/S2 一致率 ≥ 0.90；MAE ≤ 0.5；≥ 120 样本 |
| H2 AI 初评 + 审计 | AI 给初评，人工审计 20% + 100% 关键错误 + 55-65 边界样本 | 20%-30% | 连续 3 轮审计通过；月度漂移 kappa ≥ 0.70 |
| H3 AI 常规 | AI 常规评分，人工处理争议 | 争议 + 抽检 | 季度锚点复校通过 |

### 10.2 数据集积累

每次运行写入以下记录：

- `runs.jsonl`：一次运行的元数据与产物指针。
- `scores.jsonl`：人工/AI 评分、维度分、must-cover、错误、置信度。
- `adjudications.jsonl`：双人分歧与仲裁结论。
- `manifest.json`：资产 SHA、模型、参数、环境。

目标积累量：

- H1 校准：≥ 120 个评分样本。
- H2 审计：≥ 300 个评分样本，覆盖 3 类任务、3 个模块、至少 2 个 skill 版本。
- H3 常规：每季度新增 ≥ 60 个样本，保持 judge 漂移可检测。

### 10.3 AI judge 要求

- 必须与被测模型不同族；无法换族时标注「未换族」，结论降级。
- 不读取 skill 名称、版本、生成时间、variant 标签。
- 输出必须符合 [scoring-rubric.md](scoring-rubric.md) §9 的 JSON 契约，逐条附证据。
- 温度 0；55-65 边界样本 3 次投票取中位数。
- 禁止用同一批样本同时调优 judge 和发布最终评估；保留 sealed 测试集。

### 10.4 切换与回退

- 任一月度锚点检查 kappa < 0.70，回退到 H2。
- 连续两次审计发现 S1 漏判，回退到 H1。
- 评分卡版本升级后，AI judge 必须重新校准，不能直接沿用旧阈值。

> V1 的 AI 评分是 rubric-based LLM-as-judge，不训练专用评分模型。只有当标注样本足以划分训练 / 验证 / sealed 三集，且 rubric judge 的 kappa 稳定后，才评估微调 reward model 是否值得；否则优先改 rubric 与证据要求。

## 11. 反向调整闭环

### 11.1 五步闭环

```text
运行 → 评分 → 归因 → 动作 → 复跑
  ↑                              │
  └──────── 记录与对比 ←─────────┘
```

### 11.2 归因矩阵

| 现象 | 归因 | 动作 | 是否修改 benchmark |
|---|---|---|---|
| 多个 skill 版本都漏同一规则，且需求文档没有写清 | 需求缺陷 R | 补充需求、升级版本、重算 SHA | 是 |
| 产物按需求是对的，但 oracle 判错 | Oracle 缺陷 O | 修 must-cover / 预期、双评分 | 是 |
| 评分卡锚点模糊，两个评审员分歧大 | Rubric 缺陷 O | 补锚点、拆条目、重新校准 | 是 |
| 需求明确，但 with_skill 仍漏 | Skill 缺陷 S | 修改 skill 规则/知识库，记录版本 | 否 |
| 同一产物两次评分差异大 | Judge 噪声 J | 增加重复、换 judge、加证据要求 | 否 |
| 产物被截断、读取失败、模型超时 | 环境问题 E | 重跑，不计入统计 | 否 |

**核心纪律**：只有 R / O 类问题才改 benchmark；S 类问题只改 skill。禁止为了让 skill 通过而降低 must-cover 或修改预期。

### 11.3 测试点/用例的反向调整

1. **聚类**：按 requirement_id 聚合漏测项，区分「单条规则漏」与「整类场景漏」。
2. **定位**：检查 skill 的阶段 1/2 是否读取了对应规则；检查知识库是否有反例或检查清单。
3. **决策**：
   - 若 skill 缺少规则：补 skill 的测试点框架、风险清单或写作规则。
   - 若需求缺少定义：补 PRD，升级 benchmark，重新基线。
   - 若 oracle 过严/过松：修 must-cover，双评分。
4. **复跑**：只改一个变量，配对复跑；报告新旧差异。
5. **回归**：确认修复没有引入新的 S1/S2 错误，成本没有倒挂。

### 11.4 防止「教坏考卷」

| 风险 | 防护 |
|---|---|
| 把 benchmark 原题/答案写进 skill few-shot | 禁止逐字复用；只允许抽象为规则 |
| 只优化 must-cover 清单 | 保留 sealed 任务与 held-out 需求变体 |
| 通过增加用例数量提高覆盖率 | 重复扣分；覆盖按条目而不是条数 |
| 通过拉长输出提高可读性分 | 长度不计分；成本单列 |
| 修改评分卡让旧版本变高分 | 变更需双评分，历史结论不改写 |
| judge 与被测同族 | 强制换族；无法换族时降档 |

### 11.5 条目分析

积累 ≥ 30 次运行后，对 must-cover 做条目分析：

- **难度**：所有 variant 的平均命中率。长期 > 95% 的条目区分度低，移入 sanity check，不再计入主分。
- **区分度**：with_skill 与 no_skill 的命中率差。长期接近 0 的条目不能证明 skill 价值，保留但不作为核心指标。
- **歧义**：两个评审员命中判定一致性 < 0.7 的条目，拆细或改写。
- **饱和**：所有版本都覆盖的条目，保留为回归底线，不参与「提升」结论。

| 阶段 | 交付物 | 退出条件 |

## 14. 成本与工作量

| 项 | 数量 | 说明 |
|---|---:|---|
| 单次全量对照产物 | 60 | 10 tasks × 2 variants × 3 repeats |
| 含 reference 的对照 | 90 | 10 tasks × 3 variants × 3 repeats |
| H0 校准评分 | 120 份 × 2 人 = 240 次判定 | 3 类任务、3 个模块、3 个 variant |
| H1 影子评分 | 120 份 × 1 AI + 120 份人工 | 人工为共识基线 |

工作量控制手段：

- P0 只跑 3 个任务，先验证评分卡与输出契约。
- H0 先抽样 30 份做预校准，kappa 达标后再扩到 120 份。
- H2 人工审计按 20% 抽样 + 关键错误全检，避免全量人工。
- 条目分析后淘汰饱和条目，减少后续评分量。

## 15. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 需求本身有歧义 | 评分争议、无法判定 | 第 14 节列开放问题；任务要求标注「待确认」；仲裁 |
| 人工评分主观 | 分数不可比 | 双评 + kappa + 锚点 + 仲裁 |
| AI judge 同族偏好 | 结论自证 | 换族、盲评、证据要求、影子期 |
| 过拟合 benchmark | 分数上升但真实能力不升 | sealed 集、held-out 变体、禁止逐字复用 |
| 分数虚高 | 误判改进 | G1 封顶、覆盖下限、成本单列、配对胜场 |
| 运行方差大 | Δ 不可解释 | A/A、3 次重复、固定参数、记录环境 |
| 评测集缺料 | 无效判定 | P0 校验每个任务可产出有效产物；缺料即修 |
| 维护成本高 | 基准腐化 | 版本化、季度复校、条目分析、README 登记 |
| 人工瓶颈 | 迭代慢 | H1/H2 逐步自动化；抽样审计 |
| 数据泄露/污染 | 评测失效 | 访问控制、sealed 集、评分与调优分离 |

## 16. Benchmark 自身的验收标准

同时满足才可进入正式对照：

1. 需求文档、benchmark JSON、评分卡均有版本号与 SHA256。
2. `benchmark-v1.json` 可解析；10 个任务、58 条 must-cover、8 条 open findings、10 条 review checks 引用一致。
3. 每个任务在 no_skill 下能产出符合输出契约的产物；否则修 prompt 或契约。
4. A/A 通过：总分差 ≤ 5，must-cover 一致率 ≥ 90%。
5. 2 名评审员 kappa ≥ 0.70；S1 一致率 ≥ 0.90。
6. 至少一份真实版本对照报告，包含 P/N/X/? 档位与完整证据。
7. 所有数字可追溯到落盘产物与 SHA256。
8. 新增文件已在 [docs/skill-evaluation/README.md](../README.md) 登记，无孤儿文件。

## 17. 结论与建议

1. **先做 P0，不要直接全量**：用 3 个订单模块任务验证「需求文档 → 输出契约 → 评分卡 → 双人评分」是否跑得通。
2. **人工评分先行**：H0 不引入 AI judge；先把锚点、kappa、S1 清单打磨稳定。
3. **绝对分与净效应分开**：报告同时给出质量分和配对胜负；不要把「分数从 70 到 80」直接写成「skill 提升」。
4. **基准冻结**：一次对照期间不改需求、oracle、评分卡；要改就升版本并双评分。
5. **反向调整只改该改的**：需求缺陷改需求，oracle 缺陷改 oracle，skill 缺陷改 skill；不能用改考卷替代改能力。
6. **与横向套件并用**：纵向 benchmark 查真实业务效果，42 task 套件查触发、结构与回归。
7. **达到门槛再宣称**：N ≥ 30 且胜场达标才写「有效」；否则只能写「未证实」或「需止损」。
