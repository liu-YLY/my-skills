## 1. 结论

P0-lite 的链路已经跑通：资产冻结 → runner packet → 7 份产物 → G0 结构校验 → 评分 → 配对汇总 → 报告。所有产物 G0 通过，评分脚本可复算，A/A 复跑分数差为 0。

但本批次**不能**用于判断 skill 是否提升，原因：

- 只跑了 1 次重复（方案要求 3 次）。
- 只有 1 名评审者（方案要求 2 名独立评审员）。
- 评审者与被测模型同源，未换族、未真正盲评。
- 有效配对数 N=3，小于 methodology §13.6 的 N≥6 门槛，结论档位只能是 `?`。

因此本报告只回答「工具链和评分卡能不能跑」，不回答「skill 是否更好」。

## 7. 观察

### 7.1 with_skill 的表现

- 需求评审覆盖了 3 条与本模块相关的开放问题（退款节假日、不可配送清单、拼单并发上限），并额外识别了关闭后回调、优惠券门槛口径冲突、0 元单等规则缺口。
- 测试点覆盖 22/22 条 must-cover，包含幂等、回调验签、并发、对账、权限等高风险项。
- 用例覆盖 22/22 条 must-cover，步骤含固定数据，预期多为可判定结果。

### 7.2 with_skill 仍存在的问题

- 用例任务没有为开放问题单独写「待确认」用例，只覆盖了已定义规则。
- `TP_ORDER_008` 的 0 元单预期仍带「待确认」分支，未给出唯一可判定结果。
- `TP_ORDER_044` 性能测试点缺少测量方法与阈值来源。
- 评审任务存在 1 条范围说明被当作问题条目，轻微拉低结构质量。

### 7.3 no_skill 的表现

- 需求评审能覆盖部分通用风险（支付安全、重复提交、库存不足），但漏掉拼单并发上限、金额三段一致、关闭后回调等订单域关键规则。
- 测试点覆盖主流程，但幂等、回调验签、并发、对账、券返还多为 0 或 0.5 命中。
- 用例多为「进入页面 → 操作 → 功能正常」式描述，缺少可判定预期，符合评分卡对 D3 的低分判定。

## 8. 反向调整动作

按 [benchmark-plan.md](../benchmark-plan.md) §11 的归因矩阵：

| 发现 | 归因 | 动作 | 是否改 benchmark |
|---|---|---|---|
| 用例任务未覆盖开放问题 | Skill 缺陷 S | 在 skill 的用例输出要求中补充「开放问题必须单列待确认用例」 | 否 |
| 0 元单预期带分支 | Skill 缺陷 S | 补充金额边界规则或明确写「按产品确认结果二选一」 | 否 |
| 性能测试点缺少测量方法 | Skill 缺陷 S | 在性能测试点模板中补测量方法与阈值来源 | 否 |
| 评审问题条目混入范围说明 | Skill 缺陷 S | 评审输出中把范围说明移到「边界说明」，不计入问题清单 | 否 |
| G3 追溯闸门误伤评审任务 | 工具缺陷 | 已在 `p0_score.py` 修正：评审任务不适用 G3 | 否 |
| 开放问题是否应计入 must-cover | 待观察 | P1 再决定是否新增条目，不在 P0 改基准 | 暂不 |

本批次**没有**修改需求文档、must-cover 或评分卡。P0 只改了一个工具 bug（G3 对评审任务误封顶）。

## 9. 未完成项与下一步

要满足方案定义的 P0 退出条件，还需要：

1. 2 名独立评审员对 18 份产物评分（3 任务 × 2 变体 × 3 重复）。
2. 计算二次加权 kappa；目标 ≥ 0.70。
3. 做真正的去标识与随机排序；评审员不参与 skill 开发。
4. 由独立 runner 重新生成产物，避免同源会话污染。
5. 复核 A/A：同配置两次，分数差 ≤ 5，must-cover 一致率 ≥ 90%。

在这些完成之前：

- 不发布「skill 提升」结论。
- 不把本批次分数写入版本对比或 keep/revert 决策。
- 不根据本批次修改 benchmark 的 must-cover / 开放问题。
