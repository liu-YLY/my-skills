# 电商交易域 Skill 评测评分卡

> 配套：[评测方案](benchmark-plan.md)｜[需求文档](requirements-pdd-auth-cart-order.md)｜[Benchmark 种子](benchmark-v1.json)
> 版本：1.1.0
> 变更：v1.1.0 新增 §6.4 用例业务可读性专项（R1-R4）与 3-5 秒快速理解检查；0-100 权重不变，R 分单独报告。
> 适用范围：需求评审、测试点提取、测试用例编写三类任务
> 原则：评分与净效应分开。评分回答「这份产物有多好」，净效应回答「相比不用 skill，是否真的更好」。本评分卡只负责前者。

---

## 1. 评分单位与输出

| 项 | 定义 |
|---|---|
| 评分单位 | 一次任务运行（task × variant × repeat）产出的一个完整产物 |
| 任务类别 | `review`（需求评审）、`test_points`（测试点）、`test_cases`（测试用例） |
| 评分者 | 人工评审员或 AI judge；必须记录 `rater_type`、`rater_id`、`rubric_version` |
| 总分 | 0-100，保留 1 位小数 |
| 诊断信息 | 必须同时输出维度分、gate 结果、must-cover 命中、错误清单、证据位置 |

评分不是唯一决策依据。是否保留一次 skill 改动，必须结合 [methodology.md](../methodology.md) §13 的配对净效应判定。

---

## 2. 评分总览

```text
产物
  │
  ├─ G0 结构闸门 ──失败──> 0 分，不进入后续评分
  │
  ├─ G1 关键正确性闸门 ──命中 S1──> 总分封顶 59
  ├─ G2 覆盖下限闸门 ──低于阈值──> 总分封顶 69 / 59
  ├─ G3 追溯下限闸门 ──低于阈值──> 总分封顶 74
  │
  ├─ D1 覆盖（Coverage）
  ├─ D2 正确（Correctness）
  ├─ D3 可执行（Executability）
  ├─ D4 风险与异常（Risk & Edge）
  ├─ D5 追溯与优先级（Traceability & Priority）
  └─ D6 结构与可读（Structure & Readability）
        │
        └─ 加权总分 − 错误扣分 = 最终分
```

最终分取「加权总分 − 扣分」与所有 gate 封顶值中的最小值。

## 3. 闸门定义

### 3.1 G0 结构闸门

任一条件不满足即 G0 失败，产物记 0 分：

| 任务 | G0 要求 |
|---|---|
| `review` | 包含需求理解、问题清单、风险清单、建议补充验收标准四类内容；问题条目有唯一 ID、涉及条款、影响、建议 |
| `test_points` | 包含 `TP_ID`、模块、关联需求 ID、维度、优先级、测试点描述、预期结果；ID 唯一 |
| `test_cases` | 每条用例以 `### TC_模块_功能_序号: 标题` 承载；含前置条件、测试数据、步骤、预期结果、优先级、关联测试点；禁止一张表罗列全部用例 |

结构失败不进入语义评分，但必须在报告中记录失败原因，不得用 0 分直接推断 skill 质量。

### 3.2 G1 关键正确性闸门

出现任一 S1 错误，总分封顶 59，并标记 `critical_error = true`。

S1 错误包括：

- 认证绕过：未登录、未绑定手机号、未勾选协议仍可完成登录或下单。
- 支付金额错误：客户端金额被信任、支付金额与订单应付不一致仍成功。
- 支付记录错误：同一订单生成多条成功支付记录，或重复扣款。
- 库存超卖：并发下库存扣减为负，或同一库存被重复售卖。
- 优惠券重复使用：同一优惠券被多个订单使用。
- 越权：用户可查看或操作他人订单、购物车、支付信息。
- 状态损坏：订单从终态回退，或支付成功后被关闭。
- 数据泄露：完整手机号、密码、验证码、支付凭证出现在日志或响应中。

### 3.3 G2 覆盖下限闸门

按 §5 计算加权覆盖率 `recall_weighted`：

| 加权覆盖率 | 处置 |
|---|---|
| ≥ 85% | 不封顶 |
| 70%–84% | 总分封顶 79 |
| 60%–69% | 总分封顶 69 |
| < 60% | 总分封顶 59 |

### 3.4 G3 追溯下限闸门

可追溯条目占比 = 带有效需求 ID 的测试点/用例数 ÷ 总条目数。

| 可追溯占比 | 处置 |
|---|---|
| ≥ 80% | 不封顶 |
| 50%–79% | 总分封顶 84 |
| < 50% | 总分封顶 74 |

### 3.5 G4 范围纪律

以下情况按条扣分，不设封顶，但最多扣 20 分：

- 把明确不在本期范围的售后、物流、发票、评价写成核心用例：每条 -5。
- 虚构需求中不存在的规则并作为确定预期：每条 -5。
- 把开放问题当成已定义规则：每条 -3。

范围纪律扣分与 S2/S3 扣分分开记录，避免重复扣分。

## 4. 维度与权重

每个维度按 0-4 分评分，加权公式：

```text
dimension_score = Σ(weight_i × score_i / 4)
total = dimension_score − penalties
final = min(total, gate_caps)
```

### 4.1 任务权重

| 维度 | `review` | `test_points` | `test_cases` |
|---|---:|---:|---:|
| D1 覆盖 | 20 | 30 | 30 |
| D2 正确 | 20 | 20 | 20 |
| D3 可执行 | 20 | 10 | 20 |
| D4 风险与异常 | 25 | 20 | 10 |
| D5 追溯与优先级 | 5 | 10 | 10 |
| D6 结构与可读 | 10 | 10 | 10 |
| 合计 | 100 | 100 | 100 |

### 4.2 维度定义

| 维度 | `review` 关注点 | `test_points` 关注点 | `test_cases` 关注点 |
|---|---|---|---|
| D1 覆盖 | 是否覆盖模块的全部功能、规则、状态、接口与开放问题 | 是否覆盖 must-cover 清单与模块关键规则 | 是否将给定测试点完整落地为用例 |
| D2 正确 | 结论是否与需求一致，是否虚构规则 | 测试点描述与预期是否符合需求 | 步骤、数据、预期是否符合需求 |
| D3 可执行 | 问题是否可定位、建议是否可执行 | 测试点是否可独立转化为用例 | 步骤是否可执行、预期是否可观察 |
| D4 风险与异常 | 是否识别资金、库存、并发、安全、隐私、异常路径 | 是否覆盖边界、异常、状态、并发、安全 | 是否覆盖失败语义、回滚、幂等、越权 |
| D5 追溯与优先级 | 问题是否引用条款，优先级是否合理 | 是否关联需求 ID，优先级是否合理 | 是否关联测试点，优先级是否合理 |
| D6 结构与可读 | 结构清晰、无重复、无空话 | 分组清晰、粒度一致、无重复 | 标题、步骤、预期可扫读，术语一致；业务语言优先；3-5 秒能理解测试目的 |

## 5. Must-cover 覆盖率

### 5.1 条目与权重

`benchmark-v1.json` 中的 `must_cover` 条目按优先级赋权：

| 优先级 | 权重 | 典型内容 |
|---|---:|---|
| `critical` | 3 | 支付幂等、库存不超卖、优惠券单次使用、越权、密码锁定、会话失效 |
| `high` | 2 | 主流程、核心规则、关键状态流转、金额计算 |
| `medium` | 1 | 次要提示、展示、兼容性、非关键边界 |

### 5.2 命中判定

每条 must-cover 按 0 / 0.5 / 1 三档：

| 档位 | 判定 |
|---|---|
| 1 | 产物明确覆盖该行为，且预期结果可判定；证据可定位到条目 ID、步骤或预期 |
| 0.5 | 提到了相关概念，但缺少关键条件、预期或可执行步骤 |
| 0 | 未覆盖，或只出现关键词但没有对应测试行为 |

禁止用关键词匹配代替语义判断。每条命中必须附证据摘录或位置。

### 5.3 加权覆盖率

```text
recall_weighted = Σ(hit_i × weight_i) / Σ(weight_i)
```

`critical` 条目单独统计 `critical_recall`，不参与平均掩盖。

聚合口径：

- 任务内按 must-cover 加权。
- 跨任务报告使用**宏平均**（每个任务等权），不把 58 条条目直接混在一起微平均，避免订单模块条目多而主导总分。
- `critical_recall` 单独做微平均报告，不与总覆盖率混算。

### 5.4 覆盖维度分映射

| `recall_weighted` | D1 分数 |
|---|---:|
| ≥ 95% | 4 |
| 85%–94% | 3 |
| 70%–84% | 2 |
| 50%–69% | 1 |
| < 50% | 0 |

`review` 任务的 D1 按 `open_findings` 命中率与模块规则覆盖共同判定，详见 §6.1。

## 6. 三类任务的专项规则

### 6.1 需求评审（`review`）

评审任务不使用完整 must-cover 清单，使用：

- `open_findings`：8 条开放问题，每条按「是否识别 + 影响分析 + 建议决策 + 需确认问题」四要素判定，命中 1 / 部分 0.5 / 未命中 0。按任务 focus 与 requirement_ids 过滤，只计本模块相关条目。
- `review_checks`：每个模块的高风险检查项，例如支付幂等、库存超卖、优惠券并发、登录防枚举、隐私脱敏、退款路径。按任务 focus 过滤，分母只计本模块条目。
- 规则冲突与缺失定义：按产物中的问题条目质量评分，不要求与 oracle 逐字一致。

D1 覆盖评分：

```text
review_coverage = 0.5 × open_finding_rate + 0.5 × risk_check_rate
```

映射同 §5.4。

额外扣分：

- 把开放问题写成确定规则：每条 -3。
- 只列问题、不给影响或建议：每条 -2，最多 -10。
- 把非本期范围（售后、物流、发票）作为主要缺陷：每条 -5。

### 6.2 测试点（`test_points`）

- 以 must-cover 覆盖率为核心，D1 权重 30。
- 测试点必须能独立转化为用例；一个测试点包含多个独立验证目标时，按「粒度不合格」扣 D3。
- 重复测试点（同一规则、同一条件、同一预期）每条扣 2 分，最多扣 10。
- 只写「正常/异常/边界」而无具体条件与预期，按 0.5 命中或 0 命中处理。

### 6.3 测试用例（`test_cases`）

- 以 must-cover 覆盖率为核心，D1 权重 30。
- 每条用例必须可执行：前置条件、测试数据、步骤、预期结果四者齐全。
- 预期结果必须可观察、可判定；出现「正常」「正确」「合理」「符合预期」作为唯一判定词时，该条 D3 不得高于 2。
- 一条用例混合多个独立验证目标时，D3 不得高于 2。
- 步骤中不得出现「准备相关数据」「执行对应操作」等不可执行描述；出现则 D3 不得高于 1。
- 用例数量不作为得分项；长度不计入质量分，只作为成本指标单独报告。

### 6.4 用例业务可读性专项评审（R1-R4）

测试用例除了「覆盖对、预期对」，还必须让人快速看懂。`test_cases` 任务增加一组独立可读性子项，不改变 0-100 权重，单独报告：

| 子项 | 关注点 | 0 分 | 2 分 | 4 分 |
|---|---|---|---|---|
| R1 业务贴合 | 是否使用业务语言描述业务行为 | 技术实现语言或与业务无关 | 部分业务语言，夹杂实现细节 | 标题、步骤、预期均使用 PRD 业务术语，能直接对应业务规则 |
| R2 精准简洁 | 是否无废话、无歧义、长度可控 | 大量空话、重复、模糊指代 | 基本清楚，但有冗余或含糊 | 一句话说清场景、动作、关键预期；无多余修饰 |
| R3 无自创晦涩词 | 是否出现 PRD 未定义的黑话、缩写、生造词 | 多处自创词，读者需猜 | 少量自创词但可理解 | 术语与 PRD 一致；必要缩写首次出现有解释 |
| R4 3-5 秒理解 | 只看标题与预期首句，能否在 3-5 秒内说出「测什么、为什么、预期是什么」 | 无法复述测试目的 | 能复述部分，但需回看步骤 | 3-5 秒内能完整复述测试目的与关键预期 |

#### 3-5 秒快速理解检查

1. 每份用例集随机抽取 5 条，至少覆盖 2 个优先级。
2. 评审员只看标题、关联需求 ID、预期结果首句，不看步骤。
3. 计时 3-5 秒后复述三件事：测什么、为什么测、预期是什么。
4. 三项都能复述记 `pass`，两项记 `partial`，一项及以下记 `fail`。
5. 通过率映射 R4：≥80% → 4；60%-79% → 3；40%-59% → 2；20%-39% → 1；<20% → 0。

#### 计分与联动

- `R = (R1 + R2 + R3 + R4) / 4`，保留 1 位小数，单独报告。
- `R < 2` 时 D6 最高 2 分；`R < 1` 时 D6 最高 1 分。
- R 分不直接改变 0-100 总分，避免可读性权重压过覆盖与正确性。
- 报告中同时给出「总分」与「R 分」，并列出 R4 抽查的 5 条用例编号。

#### 反例与正例

| 类型 | 示例 | 问题 |
|---|---|---|
| 反例 | `验证订单相关功能正常` | 没有场景、没有预期，3-5 秒无法复述 |
| 反例 | `订单域支付幂等穿透校验` | 「幂等穿透」是自创黑话，读者需猜 |
| 反例 | `测试支付` | 范围过大，无法判断测什么 |
| 正例 | `同一 Idempotency-Key 重复提交 60 秒内只生成一个订单` | 场景、条件、预期一句话说清 |
| 正例 | `支付金额与服务端应付不一致时拒绝支付` | 业务语言，3 秒可理解 |
| 正例 | `拼单 24 小时未成团自动退款并释放库存` | 场景 + 触发条件 + 预期 |

## 7. 错误严重度与扣分

| 级别 | 定义 | 处理 |
|---|---|---|
| S1 | 认证绕过、金额/支付记录错误、超卖、重复扣款、越权、状态损坏、敏感数据泄露 | G1 封顶 59，必须单列 |
| S2 | 业务规则错误、关键状态缺失、优惠/运费计算错误、超时/退款路径错误 | 每条 -5，最多 -25 |
| S3 | 文案、格式、次要优先级、非关键边界遗漏 | 每条 -1，最多 -10 |

同一问题不得同时按 G4、S2、S3 重复扣分；按最严重级别记一次。

## 8. 计算示例

假设 `test_cases` 产物：

- D1=3、D2=3、D3=2、D4=3、D5=3、D6=4。
- 加权分：30×3/4 + 20×3/4 + 20×2/4 + 10×3/4 + 10×3/4 + 10×4/4 = 22.5 + 15 + 10 + 7.5 + 7.5 + 10 = 72.5。
- 发现 1 个 S2（-5）、2 个 S3（-2）：72.5 - 7 = 65.5。
- `recall_weighted = 78%`：G2 封顶 79；`traceability = 85%`：G3 不封顶。
- 最终分：min(65.5, 79) = 65.5。
- 结论：需明显补全，不可作为基线；同时记录 S2 的具体条目，供反向调整使用。

## 9. Judge 输出契约

AI judge 与人工评分统一使用以下 JSON 结构：

```json
{
  "run_id": "REV-AUTH__with_skill__r1",
  "task_id": "REV-AUTH",
  "task_type": "review",
  "rubric_version": "1.0.0",
  "rater_type": "human",
  "rater_id": "R1",
  "gate_results": {
    "G0": true,
    "G1": false,
    "G2": true,
    "G3": true,
    "G4": true
  },
  "dimensions": {
    "D1": { "score": 3, "evidence": ["问题清单第 2 条"] },
    "D2": { "score": 3, "evidence": ["与 BR-AUTH-08 一致"] },
    "D3": { "score": 2, "evidence": ["建议缺少回退路径"] },
    "D4": { "score": 3, "evidence": ["覆盖支付幂等与库存并发"] },
    "D5": { "score": 3, "evidence": ["引用条款 ID"] },
    "D6": { "score": 4, "evidence": ["结构清晰，无重复"] }
  },
  "must_cover": [
    { "id": "MC-AUTH-08", "hit": 1, "evidence": "第 3 条：连续 5 次错误锁定 15 分钟" }
  ],
  "readability": {
    "R1": 4,
    "R2": 3,
    "R3": 4,
    "R4": 4,
    "r4_pass_rate": 1.0
  },
  "errors": [
    { "severity": "S2", "description": "未覆盖第 3 次失败触发图形验证码", "evidence": "问题清单第 5 条" }
  ],
  "penalties": 5,
  "total_score": 72.5,
  "confidence": "high",
  "notes": "未评估账号注销的合规保留期限"
}
```

要求：

- 每个维度分必须附证据，禁止只给分数。
- `must_cover` 只记录本任务相关的条目；未覆盖条目也要列出 `hit: 0`。
- `test_cases` 必须额外输出 `readability`（R1-R4、r4_pass_rate），并列出 3-5 秒抽查的 5 条用例编号。
- `confidence` 取 `high` / `medium` / `low`；低置信度必须说明原因。
- AI judge 不得读取 skill 名称、版本号、生成时间或另一 variant 的产物。

## 11. 人工到 AI 的迁移门槛

| 阶段 | 评分方式 | 进入下一阶段的条件 |
|---|---|---|
| H0 人工校准 | 2 名评审员独立评分 | 二次加权 kappa ≥ 0.70；低于阈值先修锚点与评分卡 |
| H1 AI 影子 | AI 与人工同时评分，AI 不参与决策 | 与人工共识的二次加权 kappa ≥ 0.75；S1/S2 判定一致率 ≥ 0.90；MAE ≤ 0.5；各维度偏差 ≤ 0.5；累计 ≥ 120 个评分样本 |
| H2 AI 初评 + 人工审计 | AI 给初评，人工审计 20% 随机样本 + 100% 关键错误 + 全部分数位于 55-65 的样本 | 连续 3 轮审计通过；月度漂移检查 kappa ≥ 0.70 |
| H3 AI 常规评分 | AI 常规评分，人工只处理争议与基准演进 | 每季度用固定锚点复校；kappa < 0.70 回退 H2 |

补充要求：

- 二次加权 kappa 使用 0-4 维度分计算，不用总分计算。
- R1-R4 业务可读性子项单独校准；R4 的 3-5 秒复述一致率目标 ≥ 0.80。
- 两名评审员对同一条用例的「测什么/为什么/预期」复述不一致时，进入仲裁并回看标题与预期首句。
- AI judge 必须与被测模型不同族；无法换族时，报告必须标注「未换族」并降低结论档位。
- AI judge 温度设为 0；对 55-65 边界样本采用 3 次投票取中位数。
- 人工评分样本必须覆盖三类任务、三个模块、至少两个 skill 版本，避免分布偏斜。
- 禁止用同一批样本同时做 judge 调优和最终评估；保留 sealed 测试集。

## 12. 防分数虚高规则

1. **长度不计分**：输出字数、用例条数、测试点数量不作为质量加分项；只作为成本指标。
2. **重复扣分**：同义重复条目按重复处理，不因数量多而提高覆盖率。
3. **虚构扣分**：把需求没有的规则写成确定预期，按 S2 或 G4 扣分。
4. **关键错误一票封顶**：S1 出现即封顶 59，不能被其他维度高分抵消。
5. **覆盖下限**：覆盖率低于阈值直接封顶，避免「写得漂亮但没测到」。
6. **成本单列**：输出字符数、token、轮次、工具调用数单独报告，不进入质量分。
7. **绝对分不等于提升**：版本间比较必须使用配对设计；只有配对胜场达到 [methodology.md](../methodology.md) §13.5 门槛，才能声称提升。
8. **基准变更双评分**：评分卡或 oracle 变更后，必须对历史产物重新评分，分别报告「口径变化」与「skill 变化」。
