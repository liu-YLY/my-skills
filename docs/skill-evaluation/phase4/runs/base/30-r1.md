# 420 条测试用例评审方案（8 模块 / 3 人 / 1 周）

## 一、基本信息

| 项 | 内容 |
|---|---|
| 用例规模 | 420 条，8 个模块（均值 52.5 条/模块） |
| 评审人 | 3 人 |
| 周期 | 下周 5 个工作日 |
| 模式 | 评审模式 + 规模化（>100 条）+ 评审方案（面向干系人） |
| 目标 | L1 全量必评、其余分层抽样；输出意见表 + 建议清单 + 度量报告 |

## 二、分层评审策略（L1–L5）

| 层级 | 范围 | 评审方式 | 依据 |
|---|---|---|---|
| L1 | 全部 P0 + 各模块主流程 Happy Path | 全量逐条评审，不允许抽样 | 覆盖核心流程不可用风险 |
| L2 | P1 中涉资金/权限/状态机/跨模块联动 | 全量；其余 P1 按 ≥50% 抽样 | 高影响异常路径 |
| L3 | P2/P3 | 按 ≥20% 抽样，覆盖核心场景 | 影响可控、有替代路径 |
| L4 | 本次改动模块、历史高频缺陷模块 | 定向加评，提高抽样比例 | 风险集中原则 |
| L5 | 汇总 | 输出度量报告与残留风险 | review-mode R3 |

> 若存在 git diff，仅评审变更用例（增量子模式），其余标注未评审。

## 四、评审执行（R1–R3）

- **R1 解析**：按模块解析 ID / 标题 / 优先级 / 类型 / 步骤 / 预期结果 / 前置条件；确认需求文档、测试点清单是否存在。无需求 → 标注「溯源维度降级，仅检查内部一致性」。
- **R2 十维度**：覆盖度、优先级合理性、字段规范、可执行性、冗余、溯源、可维护性、可自动化、测试数据依赖、语义一致性。每条意见引用「用例 ID + 字段 + 原文 + 命中证据」；`candidate` 与 `confirmed` 分开输出，候选项不计入扣分。
- **语义一致性**：每模块抽取 SemanticFacts 后调 MCP `check_semantic_conflicts`（前置条件矛盾 / 同输入异预期 / 依赖闭环）。MCP 不可用则降级为「AI 规则核对（未经过 MCP 校验）」，并标注。

## 五、通过标准与度量

- 已确认 P0 → 整体评级 **D**。
- 无确认 P0：A ≥95% 且问题密度 <0.5；B ≥80%；C ≥60%；D <60%。
- 报告展示 `assessed_dimensions` 与 `not_assessed`，并分列候选问题。

## 六、交付物

1. 按模块的评审意见表
2. 改进建议清单（P0/P1/P2 分级）
3. 评审度量报告（通过率、问题密度、评级、维度分布、严重等级分布）
4. 残留风险与未评审清单
5. 文件化：≥20 条或评级 C/D → `docs/review-reports/{YYYYMMDD}-{module}-batched.md`

## 七、风险与依赖

- 无需求文档：溯源维度降级，意见表标注。
- 单模块 >100 条：按批次拆分，每批 ≤50 条。
- SemanticFacts 抽取失败：跳过第 10 维度并标注原因。
- 评审人时间冲突：优先保 L1 全量，L2/L3 顺延并声明风险。

- 确认各模块用例数与优先级分布，填入分工表
- 确认 MCP review-checker 是否可用
