# 登录改版用例评审方案

**评审对象**：登录改版用例集 vX.X（共 N 条，P0/P1/P2 分布见度量报告）
**参会**：产品、UI、前端、后端、QA
**方式**：AI 规则核对 + 人工确认（可选 MCP 增强模式）

## 一、会议目标（对齐三件事）

1. **测试思路共识**：范围边界、风险分级、分层策略、准入准出标准
2. **需求覆盖度共识**：需求条目 → 测试点 → 用例可双向追溯，缺口有理由
3. **问题闭环**：形成评审意见表，明确修订责任人与复审时间

## 二、角色关注点

| 角色 | 重点 |
|------|------|
| 产品 | 业务规则、验收标准、边界定义、裁剪合理性 |
| UI | 布局/视觉/文案/弱网与加载态、设计稿一致性 |
| 前端 | 交互逻辑、兼容性、字段校验、埋点 |
| 后端 | 接口鉴权、会话/令牌、并发、异常码、性能 |
| QA | 覆盖完整性、可执行性、优先级依据、自动化 |

## 三、测试思路讲解（约 10 分钟）

- **分层**：功能、UI、安全、性能、兼容、可用性按需选择，按主要验证目标定类型，不按技术实现
- **优先级三步法**：① 失败的业务影响（核心流程/资金/数据/权限）；② 发生可能性、频率、历史缺陷、替代路径；③ 定 P0–P3，高风险写明依据，不从类型自动推导
- **范围闸门**：焦点项全覆盖；非焦点只留冒烟；服务故障类默认不写，除非需求明确要求容错/降级/重试
- **登录专项**：账号密码/验证码/第三方登录、会话与登出、多端互踢、记住登录、权限边界、错误提示、限流与安全
- **覆盖基线**：至少 1 条 Happy Path；改动字段做三点边界；明确的角色做权限差异；明确的条件做联动；辅助操作覆盖取消/返回/刷新

## 四、需求覆盖度汇报（核心，约 20 分钟）

**汇报顺序**：

1. **覆盖矩阵**（主表）：需求 ID/条目 → 测试点编号 → 用例 ID → 优先级 → 状态
2. **覆盖率口径**：按需求条目覆盖率 = 已覆盖条目 / 需求总条目；另按场景类型（正向/反向/边界/权限/异常）统计，避免“数量够但类型偏”
3. **未覆盖清单**：逐条给出「需求条目 + 未覆盖原因 + 风险等级 + 裁剪说明」，不得以“需求没写”直接略过
4. **追溯核查**：用例填写了 `test_point_id`/需求 ID 的，现场抽查能否反查；完全缺省仅作观察项
5. **结论**：给出“可交付/有条件交付/不可交付”结论与残余风险，不输出总分

**矩阵示例**：

| 需求 ID | 需求条目 | 测试点 | 用例 ID | 优先级 | 状态 |
|---|---|---|---|---|---|
| REQ-LOGIN-01 | 账号密码登录 | TP-01 | TC_LOGIN_001 | P0 | 已覆盖 |
| REQ-LOGIN-07 | 连续失败锁定 | TP-07 | — | — | 未覆盖（低优先级，待确认） |

## 五、评审流程（R1 → R2 → R3，约 30 分钟）

- **R1 解析**：确认用例 ID/标题/优先级/步骤/预期/前置条件完整；无需求文档时标注「溯源维度降级」
- **R2 十维度**：覆盖度、优先级合理性、字段规范、可执行性、冗余、溯源、可维护性、可自动化、测试数据依赖、语义一致性；每条意见引用「用例 ID + 字段 + 原文证据 + 判定规则」
- **CHECKPOINT**：先展示意见表与候选项（`candidate` 不计入扣分），再决定是否授权修订
- **R3 输出**：意见表 + 改进建议清单 + 度量报告（通过率、问题密度、评级、维度分布）

## 六、议程与时间

| 环节 | 时长 |
|---|---|
| 测试思路与范围边界 | 10 min |
| 需求覆盖度汇报与质询 | 20 min |
| 分维度评审与问题确认 | 20 min |
| 优先级与修订范围决策 | 10 min |

## 七、输出物与跟进

- 评审意见表、改进建议清单、度量报告
- 用例文件化：`docs/review-reports/{YYYYMMDD}-login-full.md`（≥20 条或评级 C/D 触发）
- 修订走授权后的生成模式，复审仅覆盖受影响维度，输出前后对比与残留问题

## 八、风险与纪律

- 用例 >100 条：切换大规模评审，分批 L1–L5，至少完成强制全量清单
- 格式无法解析：只评可解析部分并标注「评审不完整」
- **AI 评审不构成人工审核**，不写「人工核对已完成」
- 未授权不直接改用例；只引用规则指出问题，业务规则变更回溯产品确认
