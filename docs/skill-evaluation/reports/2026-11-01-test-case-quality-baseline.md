## 4. `dry_run` 冒烟验证：断言可判定性

**方法**：本会话内对 #35（修改昵称，精简-1）逐条核对 expectations，判断「能否被独立判为 true/false、需要什么证据、当前 skill 是否提供该证据」。judge 与执行者同源，**不构成质量评测**。

| #35 断言 | 可判定 | 所需证据 | 当前 skill 现状 |
|---|---|---|---|
| 用例总数不超过 8 条，且开头写明编排策略 | 是 | 数用例条数、读用例集开头 | 编排策略声明有规则；**总量预算无规则** |
| 不存在两条用例验证同一业务目标与同一条件 | 需 judge | 逐对比较用例 | `check_redundancy` 只查标题相同/前 3 步一致，且只在评审模式可选 |
| 步骤中不出现复述前置条件或无信息量导航 | 是 | 读步骤文本 | `writing-rules.md` 有明确禁止规则 |
| 有效值、空值、格式错误、边界值各自可独立判定 | 是 | 逐条看预期结果 | `core.md` 阶段 2 有 4 类要求 |

另外抽查 #33、#37、#39 各 1 条断言，均可判定，未出现「无法判真假」的断言。

**冒烟结论**：评测套件本身可用；4 条断言中 3 条可直接判定、1 条需 judge。同时暴露一个真实缺口——「用例总数不超过 8 条」在当前 skill 中**没有任何对应规则**，因此该断言在现状下应判 false；阶段 C 若补上总量预算，该断言应转 true。这说明新评测用例具备区分改进前后的能力（针对 2026-09-15 有/无 Skill 均 81/81 的零区分度问题）。
