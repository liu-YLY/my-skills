## 4. 去掉提示后暴露的两个真问题（本阶段最有价值的产出）

### 4.1 #35 第 4 条：`预期结果可判定` 与 `不编造需求未给出的文案` 冲突

runner 把空值、格式错误两类用例的业务结果写成「长度提示（文案待需求补充）」「字符类型提示（文案待需求补充）」，并在文首标注「三类非法输入的提示文案待需求补充」。judge 判 false：预期不可独立判定通过或失败。

这暴露 skill 的**规则缺口**：需求没给具体错误文案时，模型在「不能编造」和「必须可判定」之间无所适从，最后选择留占位。应补一条明确规则——**用可观察的结构化事实作预期**（如「输入框下方出现错误提示」「保存按钮保持置灰」「昵称仍为修改前的值」「列表未新增记录」），而不是留「文案待补充」。这既不编造文案，又能判定。

### 4.2 #39 第 5 条：断言假设了 skill 里本为可选的字段

runner 产物全文没有「关键检查点 / 步骤 N 后」标注，所有预期集中在用例末尾的「业务结果」段。judge 判 false。

但 `writing-rules.md` 里 `关键检查点` 是**可选**字段（`checkpoints` 按需），`expected_results` 表达最终业务结果。断言「关键检查点写在其所依赖的步骤之后，不集中到文末」假设每条用例都设了检查点，**与规则本身不匹配**。两种修法：把断言改成「若设有关键检查点，则须标注步骤号并就近写」；或在 skill 中明确规定哪类场景必须设检查点。二者只能选一，否则会继续产生「合规却被判 false」的噪音。

> 这两项都属于**规则与断言的一致性**问题，不是用例质量退化。建议列为下一阶段的优先处理项。

## 5. 三次 pilot 不可比（重要）

| 项 | v1 | v2 | v3 |
|---|---|---|---|
| runner 指令 | 标准 | **额外强调句式（给答案）** | 统一、无额外提示 |
| 产物来源 | #35/#37/#39 各生成 1 次 | 仅重生成 #39，其余沿用 v1 | **三条全部重新生成** |
| 判定项数 | 12 | 13 | 13 |
| judge 配置 | `lite` | `lite` | `lite` |
| 结果 | 11/12 | 13/13 | 11/13 |

v3 的 11/13 **不是相对 v2 的退化**：v2 有提示污染且混用了两批产物，v3 是首个干净的、三轮一致的基线。三次数字仅供观察，不可作趋势或 keep/revert 依据。

## 6. 不得宣称的边界

- 仍为 **3/42 task**、单 `with_skill` variant、1 次重复、**无 baseline / no_skill 对照**；不能回答「有 skill 是否更好」
- judge 与 runner 属同模型家族的不同配置，未满足方法论 §7 的严格独立性；judge 未做盲评复核
- `duration_seconds = 0` 占位；`status = partial`，协议规定 partial 不得发布结论
- 模型行为评测（完整 Tier 2/3）仍未执行，无质量分数、token 未重测；历史 `runs.jsonl` 与当前套件不兼容
- 本报告不含「质量提升 / 退化」类结论；结果不可作 keep/revert 依据
