### 3.1 runner 指令：污染识别与修正（过程如实记录）

历史 v3 / v4 的 runner 指令**未落盘**，本阶段按「统一、无额外提示」口径重构，**未逐字复用**。首次指令里写了「完整地按 skill 的四阶段流程生成」，产物自述将其解读为「用户明确要求完整流程」，命中 SKILL.md 的默认模式例外，使 #35 从 v4 的快速模式切到默认模式（384 行 / 9901 字符）。

这属于**无意提示污染**，已弃用该批产物，改用中性指令（不提「完整」「四阶段流程」，模式一律由 SKILL.md 路由决定）重跑覆盖：#35 回到快速模式（291 行 / 6227 字符），#37 / #39 为默认模式。最终 v5 产物以重跑版为准。

### 3.2 runner 输入不完整

两次 runner 均报告 `knowledge/writing-examples.md` 与 `knowledge/review-mode.md` 读取被审批超时拦截，产物「信息来源」已自行标注。前者为「拿不准格式时查阅」的可选项、后者属本次未触发的评审模式，但**runner 实际输入与 v3 / v4 不完全相同**，进一步限制跨次可比性。

## 5. 本阶段主要产出：配对证据（唯一干净的因果证据）

**v5 的 13/13 不能归因于断言改写**：`case-35-v5.txt` L5 明确写「共 8 条，符合单字段纯校验 ≤8 条预算」，产物恰好落在预算内，因此 #35 第 1 条在**旧口径**（≤8 硬门槛）下同样会判 `true`。分数从 12/13 升到 13/13，主要来自产物重新生成后的条数变化，不是口径修好的证明。

真正证明「合规却被判 false」被消除的是**同一份产物、两个口径**的配对判定：

| 产物 | 事实 | 旧口径（≤8 硬门槛） | 新口径（软预算对齐） |
|---|---|---|---|
| `case-35-v4.txt`（阶段 J 产物，文件未改动） | 10 条；L71 写明「超出单字段纯校验 ≤8 条软预算」及具体超出理由（遵循单一验证目标、不堆叠多个验证目标），并写明「按用户旅程编排」；L239 复述理由 | **false**（阶段 J 实判） | **true**（本阶段 judge 复核） |

judge 给出的新口径证据：L71 的超出理由是具体、非空泛的，且编排策略声明在开头；rubric 列出的三种 `false`（未写明理由 / 无编排策略声明 / 理由空泛）均不适用。

> 这一配对中**唯一变量是断言口径**，产物字节完全未变，因此可以直接归因：K1 的改写消除了「按 skill 软预算规则合规、却被硬门槛断言判 false」的噪音。这是本阶段唯一可作因果归因的结论，且仅限这一条断言。

## 6. 其它观察（如实记录，不作质量结论）

- **产物篇幅波动明显**：#35 291 行 vs v4 的 239 行、#37 587 vs 458、#39 512 vs 325；平均字符数 11245 vs 9296。runner 输入与模型调用均非逐字复现，单次生成不稳定，说明「1 次重复」不足以支撑任何趋势判断，多轮重复属完整 Tier 2/3 范畴。
- **判定质量偏差**：judge 对 #39 第 2 条（长句 ≤40 字）给出的证据主要基于「标题不含中文逗号」，未逐段核对正文长句。该条 `true` 的证据强度弱于其它条目；因 judge 未做盲评复核，本报告不把它当作可读性质量结论。
- **runner 输入不完整**：见 §3.2。

## 8. 不得宣称的边界

- 仍为 **3 条 case**、单 `with_skill` variant、1 次重复、**无 baseline / no_skill 对照**；不能回答「有 skill 是否更好」
- judge 与 runner 属同模型家族的不同配置，未满足协议 §4 的严格独立性；judge 未做盲评复核，§6 已记录一处判定证据偏弱
- `duration_seconds = 0` 占位；`status = partial`，协议 §7 规定 partial 不得发布结论
- runner 输入不完整（两个 knowledge 文件读取被拦截）、指令未逐字复现，详见 §3
- 完整 Tier 2/3 仍未执行，无质量分数、token 未重测；历史 `runs*.jsonl` 与当前套件不兼容
- 本报告不含「质量提升 / 退化」结论；结果不可作 keep/revert 依据
- 本阶段**未改 skill 生成规则**、未升版本（仍 v9.11.0）、未推送、未建 PR；K1 改的是评测集断言
