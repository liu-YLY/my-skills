# 阶段 Q：修复评测集缺料后的完整对照结果

> 日期：2026-11-03
> 基线：分支 `feat/test-case-eval-pilot`，冻结套件 v6（SHA `a8fcdc82…`，54 cases / 219 checks）
> 触发：用户选择「修评测集缺料」，为 11 条评审类 case 内嵌真实用例
> 边界：仍为方向性观察（缺 3 次重复、缺 old 对照、`status=partial`）

## 1. 本阶段做了什么

阶段 P 的完整对照发现：约 11 条评审类 case 的 prompt 里，`[附用例]` 是占位符、或引用不存在的文件（`testing-tm-cases/`、`feat/order`），导致 runner 无法真正执行评审、judge 无法有效判定，这两类 case 的分数被系统性压低且不能归因于 skill。

本阶段为这 11 条 case（#3/#7/#8/#9/#11/#13/#14/#16/#19/#20/#21）**内嵌了真实用例文本**，每条内嵌内容精确匹配其 checks 期望的「问题特征」（如 #11 含明显合格与不合格的 P0 用例、#16 含字段缺失与冗余、#20 含步骤耦合与模糊断言等）。

冻结套件从 v5 更新到 **v6**（SHA `a8fcdc82…`），checks 数不变（219），仅 11 条 prompt 变化。

## 2. 修复前后对照

| 指标 | 修复前（v5） | 修复后（v6） |
|---|---:|---:|
| with_skill | 165/219 = 75.3% | **181/219 = 82.6%** |
| no_skill | 96/219 = 43.8% | **104/219 = 47.5%** |
| 差异 | +31.5pp | **+35.2pp** |

**关键观察**：

1. **with_skill 提升最明显（+7.3pp）**：这 11 条 case 补料后，runner 能真正解析并执行评审，skill 的评审流程（R1/R2/R3、失败模式、度量报告、修订闭环）得以完整展现，通过率从被压制的状态回升。这验证了「缺料」确实是导致 with_skill 被系统性低估的原因。

2. **no_skill 也小幅提升（+3.7pp）**：裸模型同样能从内嵌用例中受益（有了真实内容可评），但因为裸模型没有 skill 的流程术语，check 里那些「触发失败模式#N」「10 维度」「CHECKPOINT R3」等仍无法满足，所以提升有限。

3. **差异进一步拉开到 +35.2pp**：修复后 with_skill 的优势更真实、更可信——因为消除了「双方都被评测集缺料拖累」的噪音。

## 3. 仍存在的判定口径问题（如实记录）

重判过程中，judge 揭示了两个「checks 本身 vs skill 规则」的细节偏差，属于评测集/断言层面仍需关注的点，不是本轮修复范围：

- **#13 第 6 条（评级阈值）**：skill 的 review-mode.md 有「存在已确认 P0 → 整体评级 D」的规则，而 check 写的是「A:≥95%且密度<0.5 / B:≥80% / C:≥60% / D:<60%」。runner 按「有 P0 即 D」判，judge 按 check 的字面阈值判，两者不一致——这是**断言与 skill 规则的口径冲突**，类似阶段 J/K/M 修的同类问题，需后续单独处理。
- **#7/#19 的「抽样评审」标注**：skill 在规模化评审里，当采用「全量分批（S2）」策略时**不实际抽样**，因此产物不出现「抽样评审」字样是合理的；但 check 期望标注「抽样评审」。这反映 check 假设了「>100 条必然抽样」，与 skill 的「S2 全量优先、S3 抽样兜底」设计不符。

这两处是下一轮「断言-规则一致性」排查的候选，本轮如实记录、未擅自改动。

## 4. 诚实边界

- 仍 1 次重复、缺 old（v9.10.0）对照、`status=partial`，是**方向性观察，不是可发布结论**。
- runner 用 reasoning 深度思考配置，未单独剥离 skill 边际增益。
- 29 条评审/安全类 case 的差距仍很大程度来自「裸模型没有 skill 流程术语」。
