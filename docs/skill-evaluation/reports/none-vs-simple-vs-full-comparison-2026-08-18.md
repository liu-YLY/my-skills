# 无 skill vs 简单 skill vs 全量 skill 效果对比实验报告

> 测评方法：[methodology.md](../methodology.md) v1.4（B3.6 baseline 对照扩展为三条件 × 双任务）
> 测评日期：2026-08-18
> 测评问题：**「过度的 skill 往往比没有 skill 效果更差」这一流行观点是否成立？**

## 一、实验设计

### 1.1 三条件

| 条件 | 构成 | 说明 |
|---|---|---|
| **A. 无 skill（baseline）** | 无任何规则文档，凭模型自身能力 | 对照基准 |
| **B. 简单 skill** | 单文件约 30 行：角色 + 一行一用例表格格式 + 5 条编写规则（优先级/具体值/可判定/场景覆盖）+ 直接输出 | 典型"30 分钟能写出来"的最小 skill，无阶段流程/知识库/Fallback/模式 |
| **C. 全量 skill** | test-case-engineer v8.4.0（入口 136 行 + core 495 行 + 10 个知识文件，四阶段/5 模式/31 条 Fallback） | 被测对象 |

> 简单 skill 原文以内联方式注入子 agent（30 行全文见附录），保证可复现。

### 1.2 双任务（同一 judge 同轮执行）

| 任务 | 类型 | 设计意图 |
|---|---|---|
| **T1 优惠券**（满减两档+9折封顶+限领3张+单订单单券，用例 8-12 条） | 复杂规则型：多约束、边界、资金风险 | 全量 skill 应发挥优势的场景 |
| **T2 修改昵称**（2-20 字符/中英数/立即生效/跨用户可见，不限用例数） | 简单功能型：单字段纯校验 | **"过度 skill 反而更差"假说应在此显形**：流程开销是否得不偿失 |

T1 的 A/C 两格复用 2026-08-17 报告 B3.6 full_test 数据（同模型/同指令/同会话条件），B 格与 T2 三格均为本轮新跑。每格 N=1。

### 1.3 局限声明

- 每格单次试验、单一 judge（与执行模型同族，存在自评偏差风险），结论为方向性证据而非统计结论
- 输出体量为估算字符数；评分中"信噪比"含主观权重

## 四、假设检验

### H1：「过度 skill 比没有 skill 更差」——**不成立**

两个任务上全量 skill 总分均最高（T1 +12、T2 +5），未出现在任一任务上整体劣于 baseline 的情况。**但其合理内核被数据证实为三条真实的"税"**：

1. **过程税**：T2 简单功能上，需求理解文档/测试点表/假设清单/效率报告等中间产物约占产出 40%+，输出体量是 baseline 的 2 倍；
2. **粒度税**：块状全字段格式（~25 行/条）使同等产出预算下用例数仅为 baseline 的 55%（22 vs 40），UI/兼容/输入法等 P2/P3 广度被"核心业务优先"原则主动牺牲（4+3 项独有检查点丢失）；
3. **保守税**：不确定边界倾向归入"待确认"而非落例——300 封顶临界、敏感词/唯一性均被 defer，而 baseline 直接落例（T1 的 TC08、T2 的 TC307）。这是 skill"不确定规则不落用例"设计的副作用。

### H2：「简单 skill 必然优于无 skill」——**不成立**

T1 上 +2（格式纪律小胜），T2 上 **-4（反而更差）**：在模型先验很强的常见场景（昵称校验），简单 skill 的僵化单表格式束缚了 baseline 自发的分类组织与广度展开。简单 skill 的稳定收益只有格式一致性，无风险发现增益（T2 高阶风险 1 分 vs baseline 7 分）。

### H3：「skill 价值与任务复杂度正相关」——**成立**

全量 skill 对 baseline 的领先从 T1 的 +12 收窄到 T2 的 +5；其独有价值（并发/越权/状态机/追溯/需求缺口管理）在复杂任务上是决定性的，在简单任务上部分被"广度让步 + 过程税"抵消。

## 五、结论与建议

**结论**："过度 skill 更差"在本实验中不成立——它混淆了"成本真实存在"与"净效果为负"。全量 skill 的真实画像是：**简单任务上优势收窄但未反转，复杂任务上不可替代**（baseline 在 T1 完全缺失并发/状态机/资损风险识别）。

**对 test-case-engineer 的改进建议**（针对三条税）：

| 优先级 | 建议 | 针对 |
|---|---|---|
| P1 | 模式自动路由：入口增加复杂度判定规则（如"单字段纯校验类功能 → 默认快速模式"），避免简单功能走全量四阶段 | 过程税（本次 T2 实测走了默认模式） |
| P2 | P2/P3 批量用例允许紧凑表格模式（保留 ID/优先级/步骤/预期 4 列），核心 P0/P1 才用块状全字段 | 粒度税 |
| P2 | 已识别但需求未确认的边界，允许落例并标注"判定口径待确认（两种预期并列）"，而非全部 defer | 保守税（300 临界类） |

## 附录：简单 skill 对照组原文（30 行）

```markdown
---
name: simple-test-writer
description: 需要编写测试用例时使用。根据功能描述输出覆盖正常、异常、边界场景的测试用例。
---
# 简单测试用例编写 Skill
你是一位测试工程师，帮助用户为指定功能编写测试用例。
## 用例格式
用 Markdown 表格输出，每条用例一行：
| 用例ID | 标题 | 优先级 | 前置条件 | 步骤 | 预期结果 |
## 编写规则
1. 优先级：P0 核心流程 / P1 重要功能与校验 / P2 边界与异常
2. 标题：一句话说明测试点和预期
3. 步骤：写具体操作和具体输入值（如"输入 21 个字符的昵称"），不要写"输入有效值"这类模糊描述
4. 预期结果：写可判断通过/失败的具体表现（如页面提示文案、跳转结果、数据变化）
5. 场景覆盖：至少覆盖正常流程、异常输入、边界值（长度上限/下限及两侧）、权限差异（如功能涉及角色）
## 输出要求
- 直接输出用例表格，无需额外流程
- 用例数量与功能复杂度匹配
```
