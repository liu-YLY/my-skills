增量用例评审报告（非 Git 场景）
主题：对一批测试用例做增量评审，用例文件不在 git 仓库中

════════════════════════════════════════════
一、执行前提核验（如实说明）
════════════════════════════════════════════
1. 本需求要求对"这批用例"做增量评审，但未随需求提供以下任一输入：
   - 基线版本用例（改动前）
   - 当前版本用例（改动后）
   - 两者的目录路径或文件清单
2. 且用例文件不在 git 仓库中，无法通过 git diff 获取增量。
3. 结论：输入数据缺失，无法产出针对真实用例的逐条增量结论。
   下文给出"非 git 场景"的标准增量评审方法、评审维度与报告模板，待输入齐备即可执行。

════════════════════════════════════════════
二、非 git 场景的增量识别方法
════════════════════════════════════════════
由于用例不受版本库管理，需先人工/工具化定位增量，可选方式：

方式 1  目录对拍（推荐）
        diff -ruN 基线目录/ 当前目录/
        得到新增、删除、修改的文件清单与逐行差异。

方式 2  文件时间戳/清单比对
        按文件修改时间或维护一份《用例清单》对比版本号，
        识别本次交付相对上次评审新增/变更的用例文件。

方式 3  评审痕迹比对
        若此前留存过评审记录，将"已评审范围"与"本次交付范围"求差集。

方式 4  需求变更反向定位
        按本次迭代的需求/缺陷编号，反查受影响的用例集合，锁定增量范围。

════════════════════════════════════════════
三、增量评审维度
════════════════════════════════════════════
1  正确性：变更后步骤与业务逻辑一致，预期与步骤严格对应。
2  完整性：前置条件、输入数据、步骤、预期四要素齐全。
3  可执行性：不依赖缺失的环境或未提供的桩数据。
4  断言质量：预期具体、可判定，不含"正常/成功/正确"等模糊表述。
5  步骤耦合：单步骤单动作，步骤与预期一一对应。
6  边界与异常：等价类、边界值、异常输入、并发/幂等覆盖充分。
7  变更影响：改动是否影响被复用/引用的其他用例。
8  一致性：编号、命名、层级与整体规范一致。

问题等级：严重 / 一般 / 轻微（定义同标准评审）。

五、输出说明
