模式：评审模式 + 评审方案子模式（评审会参会方包含产品/UI/前端/后端，且要求「评审方案/覆盖度汇报」）

说明：本方案负责把测试思路与覆盖度组织成可宣讲、可决策的材料，重点落在「需求追溯」与「覆盖度」。单条用例的质量判定仍按 review-mode.md R2 十维度；对外只过缺口、风险与待确认项，不逐条读用例。

---

## 用例评审方案

**评审对象**：登录改版
**评审类型**：干系人评审（stakeholder review，产品/UI/前端/后端/测试）
**评审日期与时长**：2026-11-02 之后择日，60–90 分钟
**参会角色**：产品、UI、前端、后端、测试（主持人、记录员由测试侧担任）

---

### 一、范围

- 本次覆盖：登录改版涉及的登录主链路、输入校验、锁定与安全、会话与跳转（具体需求项以 PRD 为准）
- 本次不覆盖：第三方登录、扫码登录、短信验证码登录（若不在本期改版范围，需产品当场确认并记录理由）
- 依赖与假设：短信网关为 mock，真机验证需联调阶段补测；需要 3 个测试账号与 1 个锁定测试账号

---

### 二、测试思路（业务语言版）

| 要讲的内容 | 讲法 |
|-----------|------|
| 测试范围 | 「本期只测登录主链路与安全校验，不做压力测试，压测由性能专项覆盖」 |
| 分层策略 | 「接口层验规则（错误码、锁定计数），UI 层验交互（提示、跳转、掩码），E2E 只保留主流程」 |
| 设计方法 | 「密码长度用边界值：7 位、8 位、20 位、21 位各一条」 |
| 状态流转 | 「锁定：连续错 5 次进锁定态，锁定期间即使密码正确也拒绝，这是重点确认项」 |
| 风险与优先级 | 「认证失效会导致账号安全风险，所以 P0；文案调整是 P2」 |
| 已知限制 | 「短信验证码为 mock，真实下发需联调阶段补测」 |

---

### 三、覆盖度（P3，重点）

**覆盖度画像**（需求项与场景数需以 PRD 回填，下为口径与占位）：

| 指标 | 公式 | 本次值 | 说明 |
|------|------|--------|------|
| 需求覆盖率 | 已覆盖需求项 / 需求项总数 | 待回填 | 部分覆盖按 0.5 计或单列，口径在方案中写明 |
| 场景覆盖率 | 已覆盖场景 / 识别场景 | 待回填 | 按正向、异常、边界、权限、并发分类统计 |
| 高风险覆盖率 | 已覆盖高风险场景 / 高风险场景总数 | 目标 100% | 锁定、会话安全、密码校验应 100% |
| 用例可追溯率 | 有需求 ID 的用例 / 用例总数 | 待回填 | 衡量孤儿用例 |
| 不测范围占比 | 不测需求项 / 需求项总数 | 待回填 | 逐项给出理由 |

**覆盖类型矩阵**（逐类回答「需求要不要、我们做没做」，缺口必须给处置）：

| 类型 | 需求是否要求 | 已设计 | 缺口与处置 |
|------|-------------|--------|-----------|
| 正向流程 | 是 | 是 | - |
| 异常与错误处理 | 是 | 部分 | 补网络异常、服务端 5xx 各 1 条 |
| 边界值 | 是 | 是 | - |
| 权限与角色 | 是 | 部分 | 未登录访问受保护页已覆盖；不同角色登录态差异待确认是否本期范围 |
| 并发与幂等 | 部分 | 部分 | 已覆盖高频登录频率限制，幂等由后端确认接口约定 |
| 安全 | 是 | 部分 | SQL 注入、暴力破解已覆盖；CSRF 待前端确认是否适用 |
| 兼容性 | 否 | - | 不在本期范围 |
| 性能 | 否 | - | 由性能专项覆盖，本次不重复 |

**原则**：缺口必须给出处置（补用例 / 接受风险 / 移出范围），不能只列「未覆盖」。

### 七、议程与出口准则

**议程（60 分钟干系人评审）**：

| 时间 | 内容 | 主讲 | 产出 |
|------|------|------|------|
| 0–5 分钟 | 背景、目标、本次范围 | 主持人 | 对齐目标 |
| 5–15 分钟 | 测试范围与不测范围 | 测试 | 范围确认 |
| 15–30 分钟 | 测试思路与设计方法 | 测试 | 方法确认 |
| 30–45 分钟 | 覆盖度画像与需求追溯矩阵 | 测试 | 缺口确认 |
| 45–55 分钟 | 待确认问题与风险 | 各角色 | 结论或行动项 |
| 55–60 分钟 | 结论、行动项、下次检查点 | 主持人 | 会议记录 |

**时间盒规则**：单条问题讨论超 5 分钟未收敛，转为行动项会后跟进。

**出口准则（全部满足才算评审结束）**：
- [ ] 所有 P0 待确认项已有结论
- [ ] 覆盖缺口均有处置（补用例 / 接受风险 / 移出范围）
- [ ] 行动项均有负责人与截止时间
- [ ] 风险接受有记录人

**结论三态**：通过（无 P0 待确认、缺口有处置）/ 有条件通过（存在不影响执行的待确认或补测项）/ 不通过（需求不一致、关键场景未覆盖或风险不可接受）。
