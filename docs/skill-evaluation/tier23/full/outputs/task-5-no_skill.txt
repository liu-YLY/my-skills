测试用例评审报告

评审对象：测试登录功能（单条用例）
已知缺陷：缺 ID、缺步骤、缺预期结果

一、评审结论

不通过。该用例仅有一条笼统的标题"测试登录功能"，属于不可执行的无效用例。

二、缺陷逐项分析

1. 缺 ID（用例编号）
- 现状：无任何编号，无法唯一标识、追踪、归档。
- 影响：执行时无法登记结果，缺陷无法定位到用例，回归无法按编号筛选。
- 整改：补充统一编号，如 Login_001 或按团队规范命名。

2. 缺步骤（测试步骤）
- 现状：仅有"测试登录功能"一句，未说明操作路径与输入数据。
- 影响：不同测试人员执行结果不一致，无法复现。
- 整改：补充可执行的逐步步骤，如"打开登录页 → 输入账号 → 输入密码 → 点击登录"。

3. 缺预期结果
- 现状：未说明登录成功的判定标准。
- 影响：无法判断通过/失败，验收无依据。
- 整改：补充明确、可断言的预期，如"登录成功，跳转首页，显示用户信息"。

4. 附加缺陷（隐含问题）
- 缺少前置条件：未说明账号是否已注册、环境是否就绪。
- 缺少优先级：无法用于执行排期与回归取舍。
- 粒度不当："登录功能"范围过大，应拆分为手机号登录、邮箱登录、错误密码、空值、锁定等多个独立用例。

三、整改后示例

用例编号：Login_001
标题：登录-已注册手机号与正确密码登录成功
优先级：P0
前置条件：已存在已注册且状态正常的手机号账号
测试步骤：
1. 打开登录页，切换到"手机号登录"
2. 输入已注册手机号
3. 输入正确密码
4. 点击"登录"按钮
预期结果：登录成功，跳转到首页，页面顶部显示当前用户昵称

四、批量评审建议

若同类用例普遍缺 ID、步骤、预期结果，建议：
1. 制定用例编写模板（编号、标题、优先级、前置条件、步骤、预期结果为必填）。
2. 对存量用例批量补全，并增加必填项校验。
3. 建立用例评审准入规则：三要素不全的用例不得进入执行阶段。
