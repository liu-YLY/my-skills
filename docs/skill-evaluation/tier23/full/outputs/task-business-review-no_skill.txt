用例组评审意见

评审对象
- 用例 A：已登录且拥有订单 42，查看订单 42 应显示详情。
- 用例 B：未登录，查看订单 42 应提示登录。
- 共同属性：测试点均为 TP_VIEW，优先级均为 P1。
- 共同步骤：打开订单页、输入 42、提交查询。
- 预期：各一条。
- 依据范围：除上述描述外，无其他需求或覆盖基线。

一、确定问题（Definite Issues）

1. 测试点标识冲突
A 与 B 同用测试点 TP_VIEW，但两者覆盖的是不同场景：A 是「已登录 + 有权限」的正向查看，B 是「未登录」的鉴权拦截。二者本质不同，共用同一测试点会导致追踪、统计与回归定位混淆。应拆分，例如 TP_VIEW（已登录查看）与 TP_AUTH（未登录拦截）。

2. 前置条件缺失
A 声称「拥有订单 42」，但未说明如何准备该数据：订单 42 必须真实存在且归属当前登录用户，否则 A 无法验证「显示详情」。
B 声称「未登录」，但未说明如何进入并保持未登录态（如清除会话/Token、无 Cookie、退出登录）。

3. 步骤不足以支撑预期
两条步骤均为「打开订单页、输入 42、提交查询」，但：
- A 缺少「订单 42 属于当前用户」的确认步骤，未体现输入的是订单号还是别的编号。
- B 缺少在未登录态下「提交查询」会被如何拦截（跳转登录页 / 弹窗提示）的操作描述。

4. 预期过于笼统
A 预期「显示详情」未列出详情应包含的关键字段或至少「订单号=42 的详情页正常渲染」。
B 预期「提示登录」未指明提示形式（跳转登录页、弹出登录框、Toast 文案）及后续行为。

5. 数据唯一性与边界未定义
「42」作为订单号，未说明其类型（纯数字、字符串）、是否存在前导零、非法值（非数字、不存在、超长）如何处理，导致 A、B 之外的大量分支未定义。

二、候选问题（Candidate Issues）

1. 优先级设置可能不合理
A 与 B 均标 P1。通常「未登录拦截」属鉴权关键路径，P1 合理；但 A 的「已登录查看详情」若为核心主流程也可 P1。建议据业务影响分别评估，而非无差别 P1。

2. 步骤可合并公共部分
两条用例的「打开订单页、输入 42、提交查询」相同，仅登录态不同。可抽取公共步骤或使用参数化用例，减少维护成本（非缺陷，属优化）。

3. 缺少反例与安全场景
- 已登录但订单 42 不属于当前用户（水平越权/IDOR）。
- 订单 42 不存在。
- 已登录但无查看权限。
这些是否属本需求范围未说明，若不在范围内应显式声明排除。

4. B 未明确「未登录」是通过何种方式实现
未说明是「从未登录」还是「已退出登录」，二者会话残留行为可能不同。

三、未评估范围（Not Assessed）

1. 鉴权与越权安全：已登录用户查看他人订单（IDOR/水平越权）、垂直越权（低权限查看高权限订单）。
2. 数据有效性：订单号非法（非数字、负值、超大、特殊字符）、订单不存在、已删除订单。
3. 并发与性能：并发查询、大数据量下列表/详情响应。
4. 多端与多通道：移动端、不同浏览器、接口直调 vs UI 操作。
5. UI/可用性：提示文案、错误码、无障碍、国际化。
6. 数据一致性与缓存：订单 42 数据变更后详情是否实时刷新。
7. 权限模型扩展：除「登录/未登录」外是否存在角色权限、数据范围权限。

评审结论
- 当前 2 条用例可执行性不足，需先补全前置条件、明确预期、拆分测试点后方可作为有效基线。
- 建议优先修复确定问题 1–5，再据业务需要决定是否纳入候选问题中的安全反例。
