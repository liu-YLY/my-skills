# judge 指令与盲评协议（Tier 2/3 小规模对照）

> judge 角色由**你**在 opencode 客户端担任，**必须切成与 WorkBuddy 当前模型不同的另一个模型**。判定前请确认已切换。

## 通用判定原则

1. 每条 check 单独判 `true` / `false`，并附产物中的证据位置（行号或原文片段）。
2. 只在产物文本里找证据；不得依据 skill 规则「应该怎么写」推断产物「写了什么」。
3. 证据不足、表述含糊、需要猜测的判 `false` 并注明「证据不足」，不给同情分。
4. 一条 check 含多个条件时，全部条件满足才判 `true`。
5. **不读任何 skill 指令文件**，只读产物、本判定口径与 checks 文本，避免「知道期望答案」造成偏差。
6. 你是独立 judge，与 runner 模型不同；请在结果开头注明你实际使用的模型名称。

## 待判定的 13 条 check（按 case 分组，顺序即数组顺序）

### case A（4 条）
1. 用例总数不超过 8 条，或超出 8 条时在开头写明超出的具体理由；并写明所采用的编排策略
2. 不存在两条用例验证同一业务目标与同一条件
3. 步骤中不出现复述前置条件的确认动作或无信息量导航
4. 有效值、空值、格式错误、边界值各自的用例可独立判定通过或失败

### case B（4 条）
1. 阶段 1 输出列出 5 条可测需求条目作为覆盖分母
2. 输出需求到测试点到用例的对应关系，5 条均有对应用例
3. 无对应用例的条目单独列出并写明原因，不混入已覆盖统计
4. 覆盖结论不只用用例条数表达

### case C（5 条）
1. 仅看标题即可说出被测对象、触发条件与预期行为，且不以「验证」「测试」开头
2. 按中文逗号切分后每个构件不超过 40 字，URL 与字段名等行内代码不计入字数
3. 每一步只含一个决策点，不出现「输入 A 并点击 B」式多动作
4. 同一动作全文使用同一动词，同一控件全文使用界面原文
5. 若设有关键检查点，每项标注所依赖的步骤号并就近写；未设检查点时业务结果须完整可判定

> 注：盲评时产物以中性编号 S1–S6 呈现，真实映射在 `blind-map.json`，判定期间 judge 不可见。判定完成后由 WorkBuddy 揭开。judge 需自己根据每份产物内容，判断它对应 13 条 check 里的哪一组（A=4 条 / B=4 条 / C=5 条），因为盲评副本不标注 case 身份。

## 盲评协议

- 6 份产物以 **S1–S6 中性编号**呈现（其中 3 份是 with_skill，3 份是 no_skill，但 judge 不知道哪份属于哪组，也不知道哪份对应哪条 case）。
- judge 逐份、逐条判定，只写 `true`/`false` + 证据，**不猜测、不标注**「这份像是用了 skill」或「这份像是 case 39」。
- 判定某份产物时，先看它的内容判断属于 A/B/C 哪一组（4/4/5 条），再按对应 check 判定；判断不清的按「证据不足」处理并在结果里注明。

## 结果输出格式（每份产物一段）

```
产物编号：A1
1. true/false —— 证据位置
2. true/false —— 证据位置
...
N. true/false —— 证据位置
```

判定完成后，把结果（或整份输出）交回，由 WorkBuddy 按 `blind-map.json` 映射回 `(case_id, variant)` 并回填 `judge-results.jsonl`。
