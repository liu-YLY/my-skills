## 阶段顺序与共同约定

| 阶段 | 主要交付 | 完成后能够做什么 |
| --- | --- | --- |
| S0 设计与计划 | 两份可审阅文档、来源和当前恢复点 | 明确实施范围与接续方法 |
| S1 需求分析质量 | 原有需求分析流程的针对性修订与行为证据 | 重要预期有来源，关键规则进入测试点 |
| S2 用例与评审质量 | 编写、校验、独立评审和修订的完整衔接 | 发现业务遗漏、错误预期及不可执行步骤 |

每阶段开始先读本计划的恢复点、对应阶段和上一阶段收尾，再核对实际分支、提交与未提交差异。先记录本阶段范围以及采用哪些前序经验，完成后记录改了什么、实际验证结果、失败与下一步。

恢复点和阶段收尾维护在本计划末尾，证据放在现有 `docs/skill-evaluation/` 体系并登记其 README；不另建第二套评测框架。维护记录不进入普通测试任务的必填流程。

遵守用户本轮提供的 AGENTS 约定：仅本地分支、验证和提交，不 push、PR、合并或发布。新阶段按实际情况 fetch 并从最新 main 建分支；需依赖前序未合并提交时，只带入本计划已验收的必要提交，不夹带旧分支其他增量或自动合并 main。

单个审阅增量不超过 400 行。超出时按可独立验证的功能拆分，每个提交的入口、引用和依赖都闭合；不提交残缺模板。阶段实施完成不等于已获准进入业务环境或写外部工单。

## S1：先提高需求分析质量

### 开始前继承什么

读取 v9.14.0 的阶段 1、资料发现规则和需求模板，记录信息收集、来源判断、输出终点之间的重复或冲突。按需读取旧分支 R5 调查和恢复记录，不默认采用该分支的代码或历史评分。

先冻结三个短材料任务：简单需求；需求与已确认澄清/代码不一致；邀请或权限业务存在重要角色与状态条件。材料放在仓库评测目录，明确标为隔离样本。冻结业务必要结果及基线产物后再修改。

### 修改范围

- 主要修改 `test-case-engineer/test-case-engineer-core.md` 的需求理解及衔接段落，`knowledge/project-knowledge.md` 的来源与资料读取规则，必要时同步 SKILL 入口。
- 让原文、澄清、实现和运行结果分开；关键规则可定位，并对应测试点。明确只要求需求分析时的停止位置。
- 合并重复义务，简单需求保留必要内容，复杂需求才展开相应字段；不新建需求分析 skill 或另一套必填报告。
- 未决规则只阻塞依赖它的场景；不用源码或旧用例补猜验收预期。

### 验证与完成条件

基线与候选版使用相同材料，分别检查规则依据、业务条件、必要测试点和未决项处理；至少包含一条生成摘要容易遗漏的原文规则。检查简单任务是否因新规则增加无效阅读和追问。

每项问题引用原始材料和输出位置。样本中不再出现无依据的确定预期，关键规则能传给测试点，相关待确认项保留，独立内容继续；没有观察到改进的修改删除或保留待验证，不以新增字段数量验收。

收尾向 S2 交付：采用的来源规则、必要测试点、已证实缺口、未决项及实际使用的固定版本。

## S2：提高用例编写质量，闭合评审修订

### 开始前继承什么

读取 S1 结果及现有 `writing-rules.md`、`scope-discipline.md`、`review-rubric.md`、评审 agent。核对脚本、语义评审和全面评审的职责，避免重复执行三套检查。

### 修改范围

- 沿用现有用例块格式、编号和脚本。主要在原写作规则中处理前置不足、步骤无法到达目标、结果与动作不对应等具体问题；没有证据支持的规则暂不修改。
- 在原范围规则中核验固定数量、单侧边界和责任归属是否误裁必要场景；用有业务依据的反例决定是否调整，不把简化等同于固定减条数。
- 让独立评审者读取原文、最新澄清、测试点和用例，补上“原文规则是否进入测试点”的核对；不只验测试点到用例的映射。
- 明确作者修订、脚本重跑、独立问题复核和争议交付。工作流默认做一次独立语义评审；已有单项 skill 的评审触发边界不无故扩大。
- 缺少独立评审能力时保存可接续的评审材料与缺口，不把作者自检标成独立完成。

### 验证与完成条件

使用 S1 产物和一份预先植入错误的用例，包含遗漏关键原文规则、错误预期、不可达入口、相互矛盾的前置，以及一条应保留的正常用例。评审者不能提前获得问题答案。

验证其能找到关键问题并给出原文依据，也能保留正确场景；修订后的用例可操作、结果可判定，追溯关系仍在。脚本 0 error 与语义结论分开记录，误报与无法评估项保留。

若修改脚本，执行其现有测试和针对真实缺口的回归；未修改脚本时不另写重复实现的测试。收尾交付实际修订、检出与误报记录、未决争议和供 S3 使用的资料清单。

## S3：增加工作流入口和跨聊天接续

### 修改范围

- 新增 `plugins/testing/skills/test-workflow/SKILL.md` 和 `assets/task.md`；复用 S1/S2 规则，不把专业方法全文复制进工作流。
- 只管理需求分析、用例编写与评审、执行、缺陷复验四个环节，支持从任意环节开始和指定终点。
- 在 bundle 中只补明确工作流请求的转交及不回调约定；单一测试请求保持原来路由。
- 建立一个任务入口，登记现有产物、规则变化、当前进度和下一步；没有既有产物时才按设计默认创建。
- 同步现有安装清单、版本、README、安装检查与评测输入；不另建安装工具。对齐 CONTRIBUTING 中已落后的固定知识文件数量要求，按职责提供资源，不为凑数创建文件。S4 尚未交付时，对执行/复验能力缺失如实保留受阻状态。

### 验证与完成条件

做三个隔离接续演练：分析完成后换聊天编写；评审有未决问题后换聊天修订；仅要求已有用例评审时直接进入评审。后继执行者只拿任务路径和必要工具，不继承聊天历史。

另检查规则中途改变、多任务目录、缺失文件、已有格式，以及单项请求不会被误拉入全流程。核对每个结论来自实际可读文件，后继执行者不要求重复讲已有背景。

在临时安装目录验证必需文件和相对引用。新建空上下文核对实际加载的文件与版本，记录工具限制；不把元数据分类或链接校验称为宿主真实触发。安装副本更新到用户日常环境另按后续具体授权处理。

完成条件：一个任务入口足够接续，当前有效工作被复用，指定终点被遵守，安装依赖闭合；暂不可执行的环节有明确缺口。

## S4：接入执行与缺陷复验

### 开始前继承什么

沿用 S3 的任务入口、评审结论位置和缺失能力清单。实施时重新读取本机 executor、bug-reporter 及其引用资料，记录实际来源版本；设计时的目录存在不等于当前内容已验证。

### 分成可独立审阅的增量

1. 纳入 `test-case-executor` 的可移植基础执行、结果记录与必要资产，所有引用同时闭合；项目专属适配按实际需要单独提供，不携带固定个人绝对路径或凭据。
2. 纳入 `bug-reporter` 的记录与复验通用部分，保留写回和状态流转的具体授权边界。执行以用例为依据，缺陷记录引用执行证据，复验回填同一关联记录。
3. 更新工作流能力发现、安装内容和对应检查，必要时再补边界数据或特定项目适配；不为完整复制本机所有资料突破 400 行限制。

`test-doc-organizer` 作为可选能力，第一版不迁入、不构成运行依赖。根因定位仅在需要时使用既有 bug-analyzer，不自动扩成代码修复任务。

### 验证与完成条件

先用本地隔离业务样本演练一条完整路径：执行发现已知缺陷、保存原始证据、整理缺陷、切换修复版本、复验并更新结果；样本及缺陷性质明确标为合成，不记作真实产品缺陷。

补验部分数据组完成、采集失败、业务结果未知和环境前置失效。中断后用新上下文续跑，核对不会重复提交结果未知的动作；复验只有实际完成后才记通过。

完成条件：执行与复验的输入、结果、证据和任务入口互相可查，缺能力或缺条件时保留真实状态；临时安装不依赖用户本机 skills 路径。真实业务环境尚未试用时明确标记，不以隔离演练替代验收。

## S5：综合回归，选择一项真实任务试用

先使用设计中的六类样本回归，重点观察需求理解、用例质量和接续行为，不再追加流程表单。简单任务与专项任务都要包含，避免只在复杂样本上判断流程是否过重。

需要声称质量改善时，开跑前冻结基线/候选提交、相同模型和工具条件、业务必要结果、重复规模及评审口径。按现有评测方法区分配对比较、独立判定与普通演练；模型或独立评审工具不具备时保留限制，不启动无边界反复追分。

对需求理解错误、关键遗漏、不可执行用例、误报分别说明；上下文重复说明、重复操作、无效阅读及用时作为另一组观察。质量保持且省负担可以记为效率收益，不写成质量明显提升。

真实试用由后续指定的一项范围清楚的需求开始，优先完成分析与用例评审。进入执行前再核对环境、部署、测试数据及授权；没有这些条件时，交付“隔离回归完成、真实执行待试用”，继续完成可独立验证的部分。

最终同步现有使用说明，提供开始、只做一段、继续任务和复验四类示例。保留仍适用的旧产物，不批量迁移历史用例，不自动改写以前的通过率或审核状态。

完成条件：所有必要质量问题有明确处置，静态检查与实际行为证据分别可查，试用范围及未验证部分明确；交付本地分支、原子提交和实际结果。静态或隔离验证只能完成其对应子项，真实业务试用未完成时 S5 不标为全部完成。

## 每阶段怎样验证和恢复

按改动选择现有检查，不要求所有阶段一律全量运行：

```text
python3 scripts/check-version-sync.py
python3 scripts/check-knowledge-count.py
python3 scripts/check-md-links.py
python3 scripts/check-skill-consistency.py
python3 scripts/check-project-inventory.py
python3 scripts/skill-evals.py
python3 -m pytest scripts/tests
python3 -m pytest plugins/testing/skills/test-case-engineer/scripts/test_validate_cases.py
git diff --check
```

版本、资源、链接和评测输入检查是静态验证。`skill-evals.py` 默认只验证评测输入，`--results` 用于复核已有结果，不负责发起模型运行或独立判定。运行前核对当前脚本参数和依赖；PowerShell 等工具缺失时记录真实跳过项，命令非零退出后先查原因，不继续提交或宣称通过。

新增文档另做定向链接检查；新增运行入口需做实际行为和安装演练。新证据在 `docs/skill-evaluation/README.md` 登记；来源题面、输出、评审意见及结论需要能互相定位，敏感资料不进入仓库。

每阶段在本计划追加下面三段即可，不为记录另建复杂系统：

- **开始与范围：** 实际分支、起始提交、工作区、前序经验、本次修改与停止点。
- **结果与经验：** 实际文件、命令及退出结果、行为证据、失败与调整、仍未验证内容。
- **收尾与下一步：** 本地提交、干净状态、阶段完成判断、下一阶段必须继承的问题。自身提交通过 Git 历史查找，避免为填写自身 SHA 反复生成提交。

上下文丢失后从“当前恢复点”接续，并回读上一阶段收尾。计划、设计、静态检查、隔离演练、真实业务执行和部署验收的状态分别保存；不得把预计能完成写成已经完成。
