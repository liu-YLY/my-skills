# 旧分支改动迁入与评测资料清理计划

将 `feat/change-impact-evidence` 中仍有用的方法和工具改进，逐项改写到当前版本。以当前分支的去说教、深瘦身和脚本校验成果为基础，每项验证后单独提交，最后再清理旧分支及其评测资料。

本轮只沉淀并提交这份计划。实际迁移、模型对比和清理均留待后续执行。用户已明确同意后续清理旧本地分支、旧评测资料及相关 Codex 检查点；清理必须在有价值内容迁入、验证及提交后进行。

## 为什么采用逐项迁入

旧分支有尚未进入当前版本的内容，包括 PR 固定快照、实际负载口径、按风险分层、同根因检查等。当前版本又已经完成新的用例写作规则、校验器和上下文精简，两边各有需要保留的部分。

直接合并旧分支会把大量评测归档、旧流程及失效引用一并带回；只删除旧分支则会丢掉未处理的方法改动。本计划采用“核对当前缺口 → 改写必要内容 → 定向验证 → 单项提交 → 最后清理”。这落实用户要求的“以新分支为基础调整，避免破坏其他改动的效果”。

迁移顺序是本次规划建议；后续可根据新发现调整顺序，但应记录原因，不为完成清单而增加不需要的默认流程。

## 分步实施与验证

每个阶段开始时重新核对工作区、当前 HEAD、已迁入内容及上一阶段结论。后续如另开实现分支，从本计划所在分支的最新 HEAD 派生，并确认包含 `a0a2805`、`74d201f`、`57caa85`；不能从缺少这些改动的旧 main 重新开始。此处按用户明确指定的新基线执行。

### 先保存现状，建立可比较的基线

- 固定实际实现前的 SHA、相关文件清单和已有回归结果；运行现有仓库检查，失败项先区分既有问题与新增问题。
- 核对 V-01～V-03 的现存材料，并为下面每项准备一个能观察目标缺口的最小样本及普通任务对照。
- 记录当前模型、工具、输入及运行设置。静态检查、模型产物与真实业务执行分别报告。
- 保留现有预算及业务保护项；基线信息齐备后开始第一个实现增量。

### 先迁入独立的压缩读取能力

- 修改 `scripts/skill-evals.py` 及相应单测；保留当前纯文本读取和统计语义。
- 覆盖正确压缩文件、截断、哈希不匹配、解压后长度不匹配，以及原有未压缩产物。
- 测试使用临时生成的小文件，不依赖旧评测归档中的 `prepare.py`，也不带回大型数据。
- 定向测试通过后单独提交。这是维护工具改善，不宣称业务用例质量提升。

### 再补 PR 快照与关系核验

- 在当前 change-impact 的入口和知识中改写旧方法，版本说明与示例同时同步。
- 用本地临时 Git 材料验证：工作树与 PR 不同、fork 同名分支、元数据不足、符号同名但绑定不同、删除后旧引用等情形。
- 预期是分析固定版本、候选有核对依据、无法取得上下文时明确降级；用户活跃分支和文件保持原样。
- 普通 diff 任务仍能直接完成，不默认创建工作区或扫描全仓。模型前后对比与静态检查分别保留证据，再提交。

### 校准测试分层与契约条件

- 同时检查 strategy 的入口、`test-pyramid.md`、`strategy-templates.md`、README 和 quickstart，消除固定比例与新规则并存的问题。
- 比较无 UI 的后端服务、不可控第三方 API、双方可协作的消费者/提供者三个样本。
- 预期是每层投入解释对应风险与成本，契约方法满足采用条件；不因“微服务”三个字强制工具，也不把 mock 通过写成外部提供者履约。
- 保留现有风险矩阵、准入准出及不确定规则处理；无关文档不重写。

### 补齐性能测试的负载口径

- 修改当前 performance 对应段落，区分负载形状与到达方式，交代计划发起、实际发起、完成和未能发起的计数及时间窗。
- 用闭环系统变慢、发压端不足和跨时间窗完成请求的短样本验证解释；普通负载方案不扩大为复杂诊断。
- 不执行真实压测、不编造 SLA 或容量结论。预算仅余 9 字符，先整理重复说明，再判断是否需要条件读取。

### 按独立缺口处理同根因、性质和断言

- 同根因：比较真同类、已有守卫、同名误报三类位置；给定根因只要求扩搜时，直接完成该任务。
- 性质与反例：用一组仅设计任务和一组已授权实际验证任务，观察是否尊重范围，并能说明有效输入域和回放条件。
- 断言：在可运行的合成目标中，先正常通过，再引入单个业务错误，观察对应测试是否失败；人工用例只保留可观察业务差异。
- 三项分别判断价值、修改和提交，不作为一个大增量。没有新的必要缺口时允许不迁入，并记录理由。

### 汇总回归，再决定交付

- 重新检查当前业务保护项、相关普通任务以及已准备好的 V-01～V-03 回归材料；不要把静态零报错当成业务覆盖和可执行性已经通过。
- 对方法改动使用冻结的新任务做前后比较，检查事实正确性、必要覆盖、可操作性、无关负担与实际读取量。历史题用于回归，不为旧票数追分。
- 若使用独立盲评，隐藏版本标签和性能信息，保留原始判断；题目、模型或配置不一致时说明可比性限制。
- 只观察到效率改善就按效率改善报告。没有观察到新的价值时接受持平，停止继续堆规则。

## 每项怎样提交、暂停与回退

- 一个提交只处理一种行为或配套同步；不能把旧评测归档混入功能提交。PR 拆分遵守当前仓库规模约束，提交不代表已授权推送或发布。
- Skill 行为变化需同步入口、版本、人类说明、索引及必要样例，沿用当前结构；不因旧版本号更大就直接覆盖当前文件。
- 出现必要业务遗漏、引用断裂、脚本语义退化、预算超限或未授权执行时，暂停该增量，保留证据后缩小或撤回。
- 未提交修改只撤销自己本次的相关内容；已提交问题采用针对性修正或反向提交，不重写其他提交历史。
- 每次接续只读本计划、上次增量记录和当前差异；无需反复加载全部旧评测原件。

实施时按影响范围选择检查，以下是当前仓库已有命令，记录实际输出，不引用旧通过数量：

```bash

python3 scripts/check-md-links.py
python3 scripts/check-knowledge-count.py
```

代码增量另运行对应工具、MCP 或校验器的现有测试。文档同步仅做文档和结构检查；模型效果比较按上述阶段安排，不为一个文档提交启动全量模型评测。

## 最后清理旧分支、评测资料及相关检查点

清理范围已获用户明确授权，本轮尚未执行。后续必须先满足以下条件：

- 每项旧改动已有“迁入并提交 / 当前已覆盖 / 不采用及理由”的记录，当前分支能独立接续，不依赖旧文件。
- 当前功能、文档同步、预算与相应验证已记录；需要保留的历史结论、评测局限和必要最小材料已沉淀到新分支。
- 旧原始资料不再作为独立改动、未完成测试或唯一复跑材料的来源；若仍有依赖，先迁出必要部分并说明去向。

满足条件后按以下顺序执行：

1. 重新枚举旧分支独有提交、所有 Git 引用、reflog、工作树、索引和相关 Codex 检查点，不能沿用本轮对象数量直接删除。
2. 确认当前不在旧分支，删除本地 `feat/change-impact-evidence`；不删除不属于本计划的其他分支或远程引用。
3. 检查每个相关检查点的完整内容。若还保留其他工作的独有文件或恢复状态，先保全这些内容，再处理对应引用；不清空所有 `refs/codex/`。
4. 针对本次旧资料核对 reflog 等残余引用，再回收符合清理范围的无引用对象；不全局清空 reflog、不直接按目录名删除被引用的 Git 对象。
5. 核对当前 HEAD、其他分支、项目文件与索引，运行 Git 完整性检查，并记录实际释放空间及仍被其他引用保留的资料。

仅删除分支不会立即释放整批数据。本轮核查发现相关评测对象也被 Codex 检查点引用；对象去重、压缩和其他引用都会影响实际空间，清理时重新测量，不承诺按文件内容总量回收。

本计划不包含 Cursor 索引清理，也不包含其他评测项目或远程历史改写。此前单独授权的 71 个无引用对象已清理，与本阶段分别记录。
