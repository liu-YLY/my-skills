# 测试技能与评测工具改进计划

修正测试分层、PR 版本采集和性能统计口径中的具体缺口，同时保持现有用例的可读性、范围控制、机器校验和按需加载效果。

先建立基线，依次实施测试分层与契约、PR 版本固定、性能统计口径。其余技能先运行旧版样本，按实际结果决定是否调整。

## 目标与实施边界

保留当前去说教、自包含前置、未定规则隔离、范围裁剪、测试点与用例脚本校验。方法改进不得增加每次任务都要执行的通用流程，也不改变共享数据契约、bundle 路由和 MCP 降级约定。

test-case-engineer 已于前一轮优化，本次仅用现有成果做回归对照。实施范围限于本地技能与离线验证。

## 实施前先建立比较基线

- 在独立功能工作区以最新 main 为起点，记录 SHA 和允许修改的文件，保留原工作区。
- 运行现有仓库检查，记录当前失败项、上下文大小和版本同步状态，防止把既有问题归因于本次改动。
- 准备三类业务回归：邮箱激活有效期、支付回调幂等、Webhook 配置。保存独立题面、已知规则、未定项和判据，确保能够重新执行。
- 为每项改动准备一个能暴露目标缺口的最小样本，以及一个不需要专项方法的普通任务对照。题面只表达目标，不提示解法。
- 固定模型、工具、材料和运行设置；静态检查、模型产物质量和真实业务执行分别记录。

## 实施顺序

### 按风险选择测试层和契约方法

**目的：** 让测试策略解释“为什么在这一层验证”，并适应无 UI、第三方不可控和团队协作方式不同的项目。

**修改位置：** `plugins/testing/skills/test-strategy-engineer/` 下的入口、`knowledge/test-pyramid.md`、`knowledge/strategy-templates.md`、README 和 `integrations/quickstart.md`。

**具体做法：**

- 根据风险在哪一层可观察、现有覆盖和执行成本决定测试投入。比例作为示意，不强制各层齐备、固定配额或 ±5% 偏差。
- 按需要隔离不确定或高成本外部依赖，不要求替换所有确定性组件。
- 消费者可识别、双方可协作且能准备提供方状态时，考虑消费者驱动契约。分别核对真实消费者对 mock 响应的处理和提供者重放。
- 面对不可控第三方，检查公开规范、本方适配和实际使用分支。mock 通过只支持本方在该假设响应下的处理，不能证明第三方已经履约。
- 同步入口、模板、README、示例与继续执行规则，消除相互矛盾的指引；保留现有风险矩阵和准入准出处理。

| 验收样本 | 需要观察到的结果 |
| --- | --- |
| 无 UI 的后端服务 | 不补造 UI 测试，所选层能够观察对应风险 |
| 不可控第三方 API | 给出本方可执行的规范、适配和集成验证，结论边界清楚 |
| 消费者与提供者可协作 | 说明采用条件、双方版本、前置状态及实际验证范围 |

### 固定 PR 版本

**目的：** 分析用户指定的 PR 时，能够解释对应版本的业务影响，避免工作区差异和符号误匹配导致错误结论。

**修改位置：** `plugins/testing/skills/change-impact-analyzer/` 下的 `SKILL.md`、`knowledge/diff-modes.md`、`knowledge/cross-impact-analysis.md`，以及配套说明和样例。

**具体做法：**

- 核对服务实例、仓库、PR 编号及 fork 的 head 身份，固定 base、head、merge-base 和元数据来源。
- 优先只读固定 Git 对象；需要目录上下文时使用版本匹配的隔离工作区。分析过程中不切换用户活跃分支，不混入本地脏文件。
- 资料不足时基于已取得的 diff 继续，明确缺少哪些上下文。PR 更新后，保持原快照或完整重新采集，不能混用两个版本。
- 沿用已有的反向定位和正向核验。用样本检查别名绑定、删除或改名前的调用方，只补实际漏判。
- 记录实际读取范围和停止原因；普通 diff 任务仍直接完成，不默认创建工作区或扫描全仓，也不自动执行被分析项目的脚本。

| 验收样本 | 需要观察到的结果 |
| --- | --- |
| 工作树与 PR 内容不同，且包含未提交修改 | 使用固定 PR 版本；用户分支和文件没有变化 |
| fork 与主仓库存在同名分支 | 使用正确仓库的 head，不以分支名称代替身份核对 |
| 元数据或源码不可取得 | 继续可确定的 diff 分析，明确结论缺口 |
| 同名符号、别名、删除及改名 | 命中有具体关系依据；无法确认的保留为候选 |

### 明确负载到达方式与统计单位

**目的：** 性能方案能够说明计划施加和实际施加的负载，避免将发压端不足误认为系统容量上限。

**修改位置：** `plugins/testing/skills/performance-test-engineer/knowledge/load-models.md`、`knowledge/metrics-framework.md`，以及必要的入口和样例说明。

**具体做法：**

- 区分阶梯、峰值、疲劳等负载形状与开放、封闭到达方式。
- 分别记录请求、事务、迭代和并发用户；只有具备每次迭代的请求数等依据时才换算。
- 在同一统计窗口中区分计划发起、实际发起、完成与未能发起的数量，说明跨窗口完成的口径。
- 解释闭环系统变慢导致发起量下降，以及发压端资源或调度不足的情况。复用已有发压端 CPU、目标和实际到达率检查。
- 保留证据不足状态，不填写无依据的 SLA、容量阈值或确定根因。

**验收：** 使用闭环响应变慢、发压端不足、跨窗口完成请求三个短样本，能够正确说明计数、单位和结论边界；普通负载设计任务不扩大为完整诊断。本阶段不运行真实压测。

## 先验证或暂缓的项目

| 项目 | 推进条件 |
| --- | --- |
| 同根因扩搜 | 先跑旧版样本，区分真同类、有效守卫与同名误报。出现实际漏判时再定向修正。 |
| 性质验证与反例 | 先跑旧版设计样本，检查能否从确认规则识别顺序风险并写出可执行的观察项。有实际遗漏再补，暂不扩展自动执行和缩减流程。 |
| 压缩评测产物 | 暂缓。仓库目前没有压缩结果或引用，等出现明确的产物存储需求再评估。 |

## 如何保护已有改动的效果

- 每次只修改一个明确缺口，按项目分别验证和提交。
- 先替换误导规则与重复说明，专项细节按需读取。对比入口、常用路径的字符数与估算 token，目标是不增加普通任务的读取量。按 [上下文预算](../../../scripts/context-budget.json) 检查，保留必要业务规则。
- 需要变更预算时，说明新增价值、实际读取量和普通任务成本，单独评估，不与方法调整混在一起。
- 保留当前前置自包含、说教噪音拦截、结果字段、汉字与分号限制、范围裁剪、未定项隔离及测试点/用例校验。
- 行为变化同步入口、版本、README、模板、知识索引和必要样例；只改实际受影响内容，避免不同文件给出相反指引。
- 出现必要业务遗漏、脚本退化、引用断裂、预算超限或越权执行时，暂停该增量，缩小或撤回自己的修改。已提交问题采用针对性修正或反向提交，不重写其他提交历史。

## 验证与完成条件

每项改动均需保存修改前后的同条件结果，比较事实正确性、必要覆盖、可操作性、无关负担和实际读取量。专项样本验证能力，普通任务验证是否增加无关流程。

使用独立盲评时，隐藏版本标签与性能信息，保留原始判断。模型、题面或配置不同则说明可比性限制；只观察到效率改善就按效率改善报告，没有新价值时接受持平。

按影响范围运行当前仓库已有检查并记录实际结果：

```bash
python3 scripts/check-version-sync.py
python3 scripts/check-skill-consistency.py
python3 scripts/check-md-links.py
python3 scripts/check-knowledge-count.py
python3 scripts/check-project-inventory.py
python3 scripts/check-context-budget.py --target
```

代码增量另运行对应工具、MCP 或校验器测试。文档检查通过只表示结构与引用有效；模型产物质量仍由样本对比判断。

阶段完成需同时满足：目标样本达到预期、相关普通任务没有实质退化、已有用例与共享契约不受破坏、检查和同步事项完成，并已形成独立提交及可接续记录。三项实施后运行三类业务样本并汇总结果，区分模型产物、静态检查和真实业务执行。
