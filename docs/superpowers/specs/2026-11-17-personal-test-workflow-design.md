# 个人测试工作流设计

日期：2026-11-17（Asia/Singapore）。状态：设计提案，待审阅；尚未实现工作流。

这次改造把需求分析、用例编写与评审、测试执行、缺陷复验串起来。优先解决需求理解失真、重要场景遗漏、用例难以执行的问题，再用落盘记录减少重复交代上下文，让新聊天能接着做。

日常使用只增加一个工作流入口和一个任务进度入口。已有需求文档、用例、执行台账仍在原位置维护；不要求每次测试先填写一套新表单。

## 这次设计基于什么

- 用户已明确：重点是需求分析和用例质量，流程尽量简单；本轮只交付详细设计与分阶段改造计划。
- 仓库基线为 `main/origin/main` 的 `848b613`，`testing-bundle` v3.6.0、`test-case-engineer` v9.14.0。设计文档在新分支 `feat/test-workflow-design` 编写。
- 原分支 `feat/change-impact-evidence` 的 69 个本地提交保留，未合并到本分支。其恢复入口和 R5 调查可通过该分支读取；旧整合计划的状态不因本设计改变。
- 本机另有 `test-case-executor`、`bug-reporter`、`test-doc-organizer`，位于 `~/.agents/skills/`；它们尚未纳入本仓库，不能作为可移植安装已经具备的能力。

现有用例工程师已包含需求分析、测试点、编写、自检、脚本校验和语义评审。新增工作流负责选定下一步、传递资料和保存进度；专业规则继续在原 skill 中维护。

## 目标和第一版边界

第一版完成以下目标：

- 已确认需求、实现现状、运行观察和推测能够区分，重要预期能找到依据。
- 必要业务规则能对应到测试点和用例，评审能发现错误预期、遗漏及不可执行的步骤。
- 任一环节可以直接进入；用户指定本次做到哪里，就停在哪里。
- 换聊天后能找到最新产物、未决问题及下一步，不重做仍然有效的工作。
- 执行失败、证据不足和未执行分别保留；缺陷复验能关联原用例与当前版本。

第一版不建设网站、数据库、任务调度服务或新浏览器框架。项目级策略、性能、状态机、离线造数仍按实际需要调用，均不是普通任务必经步骤。本轮不修改业务环境、外部工单或本机安装副本。

## 采用哪种改造方式

| 方式 | 能解决什么 | 主要代价 | 本稿选择 |
| --- | --- | --- | --- |
| 直接把全部流程加入 testing-bundle | 入口少一个 | 路由与任务管理混在一起，单独写用例也容易带入整套流程 | 保持其路由职责 |
| 新增 test-workflow，复用专业 skills | 统一任务衔接，保留单项能力独立使用 | 需要明确入口边界和一个接续记录 | 推荐，本稿据此设计 |
| 建设带状态存储的执行平台 | 可集中调度和展示任务 | 开发、部署及维护范围大，不能直接解决需求和用例质量 | 第一版不采用 |

这是根据用户目标提出的实现选择，尚未视为用户批准实施。

## 用户会怎样使用

```text
需求分析 → 用例编写与评审 → 测试执行 → 缺陷复验
               ↑                │          │
               └── 规则或用例需要修订 ──────┘
```

一次请求即可开始，也可以只做其中一段：

```text
按测试工作流处理这份需求，先完成需求分析和用例评审，暂不执行。
继续 /项目目录/本次任务/任务.md，完成尚未执行的用例。
只复验这个缺陷，沿用关联用例和上次记录。
```

工作流先识别已有资料和本次终点，直接调用负责该环节的 skill。只写用例时不运行测试；已有合格用例时直接进入执行，不重新分析整份需求。普通环节衔接连续推进；影响结论的关键规则不清、范围变化或缺少具体操作授权时才询问。

单独的用例、影响分析、根因分析请求仍直达原 skill。`testing-bundle` 只为明确的工作流启动或续跑请求转交一次；`test-workflow` 不再回调 bundle，避免来回路由。

## 怎样保存上下文

### 每个任务只有一个进度入口

优先沿用业务项目已有目录。没有约定时，默认在业务项目的 `docs/testing/<任务名>/` 保存以下内容：

```text
任务.md             当前范围、资料位置、完成情况、未决项、下一步
需求与用例.md       无既有文档时才创建，合并需求分析、测试点和用例
执行记录.md         进入执行后且无既有台账时才创建
evidence/           有实际证据时才创建
```

只有 `任务.md` 是工作流新增的固定入口。需求、用例和执行记录有现成位置时，只登记引用，不复制为另一套文件。缺陷优先关联现有工单；没有平台时把缺陷草稿放在执行记录的对应条目下，不另建必填缺陷台账。

稳定的项目路径、用例格式和工具约定优先读取业务项目现有 AGENTS 或文档索引；没有时首次写入任务入口，后续复用。第一版不增加必填 `project.yaml`、全局任务数据库或第二份项目知识库。

### 各类事实只维护一处

| 内容 | 维护位置 | 任务入口保存什么 |
| --- | --- | --- |
| 需求原文与已确认澄清 | 原文及需求分析中的规则记录 | 来源位置、版本或日期及最近变化 |
| 测试点与范围取舍 | 既有测试点清单 | 文件位置、当前是否可用 |
| 用例及其审核状态 | 既有用例文件 | 当前版本、评审结论位置 |
| 实际执行与证据 | 执行台账和证据文件 | 本轮范围、结果位置、剩余工作 |
| 缺陷与复验 | 原工单或本地缺陷条目 | 缺陷关联及下一步 |

任务入口只保存接续所需摘要，不抄写全部业务规则、用例和日志。建议起始内容如下，已有等效字段时沿用：

```markdown
# 本次测试任务

## 本次目标
项目与任务目录：实际位置
本次范围与终点：例如完成需求分析和用例评审
执行范围：本轮是否执行、目标环境，以及已明确的操作边界

## 最新资料
需求及澄清：实际位置与版本或日期
分析与测试点：实际位置
用例与评审：实际位置及当前状态
执行与缺陷：已有记录位置；未开始时直接说明

## 当前进度
已完成：实际完成且仍有效的工作
待处理：具体问题、影响的规则或用例、缺少什么
下一步：可直接开始的一项工作
最近更新：时间，以及本次改变了哪些判断
```

证据细节和账号现状保留在现有台账，入口登记位置。凭据只引用受控存放位置，不抄入进度、设计或共享报告。

## 怎样提高需求分析质量

需求分析继续由 `test-case-engineer` 的阶段 1 承担，集中修订已有流程，不另加一个需求分析 skill。

1. **先说清业务变化。** 说明谁在什么条件下做什么，变化前后有什么不同，受影响的上下游是什么；区分本次焦点、直接回归和范围外内容。
2. **把重要预期绑定来源。** 区分需求原文、适用范围明确的已确认澄清、代码现状及运行观察。记录实际读过的位置与版本；原文不可读时保留缺口，不仅凭标题或旧摘要推断。
3. **沿业务操作找缺口。** 对有关角色、入口、初始状态、输入限制、状态变化及副作用逐项判断；只在相关规则存在时展开超时、重试、第三方失败等专项内容。
4. **把分析交给后续使用。** 规则对应已有测试点编号，用例追溯测试点。没有现成标识时，只为需要跨环节引用的规则补短标识，不给每句话编号。

分析结果保留功能变化、关键规则与依据、必要测试点、待确认问题。简单需求可合并为一份短文；复杂需求沿用现有详细结构，不机械输出十二组空字段。

多来源冲突时先判断是否属于同一版本、对象和场景。适用范围明确的最新用户澄清保留原措辞与生效范围；不能判断谁有效时列出差异。源码用于解释实现和发现风险，不能替产品决定未定预期，旧用例也不是天然正确答案。

### 分析什么时候可以进入编写

编写前在同一份分析里核对三件事：重要结果有依据；关键业务条件已进入测试点；剩余问题影响哪些场景已经明确。这个检查不增加单独审批或报告。

依赖未决规则的场景保留为待确认，其余场景继续。评审时要回到原始资料检查测试点是否漏项，不能只检查“已有测试点都有用例”。用户本次只要分析时，到此交付并保存接续点。

例如，以下是虚构材料：需求只写“邀请成员”，讨论又补充“未激活的邀请也占名额”，代码只统计已激活成员。分析应分别记录澄清与实现差异，加入“未激活邀请占名额”的测试点；不能直接以代码现状编写通过预期。缺少名额上限时，保留依赖该数值的边界场景，不猜一个上限。

## 怎样提高用例编写与评审质量

### 编写围绕可以判定的业务结果

复用现有 `writing-rules.md` 和 v9.14.0 的用例块格式，保留用例编号、必要前置、具体动作、可观察结果及需求追溯。输入示例、角色状态和操作入口要足以执行；只在改变数据或共享状态时补必要恢复说明。

同一业务目标的数据变体可以参数化，不同状态或副作用不能为减少条数而混成一个无法定位的结果。优先级由业务影响决定，不按固定比例分配，不为凑维度生成无依据的场景。

范围取舍继续由 `scope-discipline.md` 维护。需要重点检验其中固定数量、单侧边界及责任归属规则会不会误裁必要覆盖；若真实样本证明存在问题，在原处修订并回归，不在工作流另写一套相反规则。

### 复用现有两类检查

| 检查 | 继续由谁负责 | 工作流需要补什么 |
| --- | --- | --- |
| 格式和确定性规则 | `validate_cases.py` | 保存真实执行结果；有错误先修复再检查 |
| 业务语义与覆盖 | `test-case-reviewer`、`review-rubric.md` | 让评审者同时获得原始需求、最新澄清、测试点和当前用例 |

当前脚本校验是必做步骤；脚本不可用时沿用原有降级说明，记录未校验，不称为校验通过。脚本通过只说明其检查的规则通过，不代表业务覆盖或执行通过。

工作流中的“编写与评审”默认包含一次独立语义评审，复用 J1–J9，不额外叠加十维度评审会。用户要求全面评审或评审会材料时才使用 `review-mode.md` 的对应流程。

评审者使用独立上下文，读取原始材料和当前产物，不读取生成者的推理或自评分。既检查测试点到用例的对应，也检查需求到测试点的遗漏。意见必须指出原文位置、受影响用例及具体问题；缺少原始资料时注明无法评估的范围。

生成者修订后重跑脚本，评审者复核相关问题及必要关联场景。同一问题一轮修订后仍无新增依据、资料缺失或双方判断冲突时，保留争议与缺口交付，不无限互审。明确的错误预期、关键遗漏和不可执行步骤未解决前，不标记为可进入正式执行；缺口不影响的用例可以先行。

运行环境没有独立评审能力时，先完成作者自检并保存待评审资料，标记“独立评审未完成”；新聊天可只接评审环节，不把同一上下文的自检冒称独立评审。AI 评审、真人审核和业务执行状态分别保留。

## 怎样换聊天继续

新聊天只需给任务入口位置。已有项目索引唯一指向当前任务时可直接读取；有多个候选任务时只确认目标，不重新询问已落盘的业务背景。

1. 读取任务入口、当前环节对应 skill 和最新相关产物，按需展开原文及证据，不全量重读历史聊天。
2. 核对本次终点、资料版本、环境和已有操作授权；任务记录保存的是授权依据，不自行扩大或恢复已经失效的授权。
3. 对照最近变化定位受影响规则、测试点和用例；只把相关分析、评审及结果标为需要更新，保留历史记录。
4. 从下一步继续。已经完成且条件未变的工作直接复用；请求结果未知时先查实际状态，不重复提交业务动作。
5. 重要结论、规则澄清、评审修订和执行结果产生后及时落盘；主动暂停或交付前更新任务入口，不把持久化留到聊天结束时才做。

第一版采用单写入者维护台账。即使使用子 agent 评审，主执行者负责合并意见；不引入并发修改同一任务记录的机制。文件未保存或目标文件不可读时，明确接续缺口，不承诺仅凭聊天记忆自动恢复。

## 执行与缺陷复验怎样衔接

执行消费用例、已确认规则、账号数据位置和已获授权的环境，不自行改写业务预期。通过、失败、受阻、未执行分别记录；受阻再说明是规则、数据、工具还是授权缺口。部分数据组完成不能判整条通过，截图缺失也不能直接判产品失败。

接入本机 `test-case-executor` 的通用部分前，将入口实际引用的模板与参考资料一并纳入仓库，闭合依赖并检查项目专属路径。不能仅复制 SKILL.md，或把 `~/.agents/skills/` 写成安装后的必备路径。特殊业务造数继续读目标项目的操作约定，离线造数不等于获准写业务数据库。

执行发现问题后，`bug-reporter` 消费用例、实际结果、预期依据和原始证据，形成可复现记录。工单写回、状态流转按具体授权进行；只整理记录时不自动发工单、改状态或启动代码修复。

复验先核对修复部署和当前前置，再执行原触发场景及必要关联场景。已有可用记录时先复用；开发说已修、代码已合入或工单已关闭都不能替代复验。需求澄清导致预期变化时，先更新规则和相关用例，再重新判断旧结果的适用范围。

`test-doc-organizer` 可用于整理交付文本，第一版不把它作为运行依赖；没有时按项目格式汇总实际结果。最终结论由执行证据决定，不能因文字整理改变结果。

## 改动落在哪里

| 位置 | 计划中的职责 |
| --- | --- |
| `plugins/testing/skills/test-case-engineer/` | 先修需求分析、来源判断、测试点与用例质量，统一原有指令 |
| `plugins/testing/agents/test-case-reviewer.md` 及 `review-rubric.md` | 补足对照原始资料、需求遗漏核对和评审后修订的衔接 |
| `plugins/testing/skills/test-workflow/SKILL.md` | 新增工作流入口，按当前任务调用能力并维护接续点 |
| `plugins/testing/skills/test-workflow/assets/task.md` | 提供一个可沿用已有格式的任务入口模板 |
| `plugins/testing/skills/test-case-executor/`、`bug-reporter/` | 分阶段纳入可移植的执行与复验能力，必需依赖闭合后才接入 |
| testing-bundle 及现有安装清单、说明、检查 | 同步入口边界、版本及实际安装内容 |

保持规则单处维护，工作流引用规则而不复制。第一版不创建通用交接 JSON、自动状态机或新增 MCP 服务。既有业务文件不批量搬迁、重新编号或改写历史执行结果。

现有 CONTRIBUTING 仍写有固定知识文件数量，而实际资源检查已按引用有效性判断。新增入口按职责提供必需资源，后续同步这处旧交付约定；不为满足旧数量补造文件。

## 怎样判断改造有用

| 任务样本 | 必须观察到的结果 |
| --- | --- |
| 简单字段或开关需求 | 重点规则和必要反向场景保留，步骤与结果可直接执行，没有额外完整策略流程 |
| 需求、澄清、代码存在差异 | 原文可回查，未定预期不被代码覆盖，独立场景仍能继续 |
| 邀请、权限或额度业务 | 关键角色、状态及业务边界进入测试点和用例，隐藏入口不被当成服务端授权已验证 |
| 植入遗漏与错误预期的用例 | 评审能从原始需求发现漏项，并对具体预期给出有依据的意见 |
| 在分析、评审或部分执行后换聊天 | 读取落盘资料即可继续，不要求重讲背景，不重放已完成业务 |
| 缺陷复验、工具缺失或结果未知 | 保留真实状态及具体缺口，先核实际状态，不虚报通过或重复业务动作 |

每阶段先用少量固定材料检验具体行为，再决定是否保留改动。需要判断质量提升时，比较同一任务在基线和候选版的产物，保持模型、资料和工具条件一致；将关键业务错误、遗漏、执行可行性与阅读负担分别说明。

静态链接、脚本校验、隔离样本、新聊天演练和真实业务试用分别报告。没有业务环境或部署证据时，执行与复验只能记为隔离验证或待试用；不能把文档齐全、用例更多、分数提高或请求更少当作质量提升的证明。
