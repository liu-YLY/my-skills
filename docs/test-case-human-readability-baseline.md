# 人类易读性（L2）标准调查

> 调查日期：2026-10-31
> 归属任务：T1（执行计划见 [2026-10-31-test-case-readability.md](superpowers/plans/2026-10-31-test-case-readability.md)）
> 范围：只研究「人读起来是否轻松、能否快速找到并正确使用信息」，不重复 L1 的术语准确性与可判定性（见 [test-case-readability-baseline.md](test-case-readability-baseline.md)）

---

## 0. 结论摘要

1. **易读性首先是结构问题，不是用词问题。** ISO 24495-1:2023 的约 485 条指引中，只有约 7% 涉及词汇选择，其余是内容相关性、可查找性、结构与可用性。把可读性等同于"术语准确 + 句子通顺"，会漏掉八成问题。
2. **可读性是可检验的用户结果，不是文风偏好。** ISO 的四原则是「读者拿到需要的 / 能找到 / 能理解 / 能用」，对应到用例就是：信息齐全、结构可扫读、句子可解析、执行人能照做。
3. **中文技术文本有可执行的句长阈值。** 业界通行规范：逗号分隔的构件宜 ≤20 字，20–29 可接受，30–39 需语义明确，**>40 字不可接受**；整句 ≤100 字。这是惯例而非国标，适合做软预算。
4. **扫读是默认行为。** NN/g 与 plainlanguage.gov 的实证：79% 用户扫读而非逐字读，页面平均只有 18% 的文字被读到。用例的标题、步骤首词、预期首词决定读者能否跳过无关内容。
5. **认知负荷理论给出三条可落地约束**：分块（chunking）、避免注意力分割（相关信息就近放置）、删除冗余（同一信息不从两个入口重复进入）。
6. **精确与易读不冲突。** Plain language 要求保留必要术语与具体值，只是要求「首次出现时解释、句式可解析」。简化不等于模糊。

## 1. 关键概念：易读性包含什么

| 维度 | 通俗解释 | 反面表现 |
|------|----------|----------|
| 相关性 | 只给读者需要的信息 | 大段背景、复述需求、解释常识 |
| 可查找 | 能快速定位到要看的那一行 | 关键条件埋在长段落中间 |
| 可理解 | 句子能一次解析，术语不挡路 | 40 字长句、三重定语、括号套括号 |
| 可使用 | 读完能直接照做 | 信息齐但顺序乱、结果与步骤对不上 |

> ISO 的定义：一段沟通若其**措辞、结构和设计**清晰到目标读者能轻松找到、理解并使用信息，才叫 plain language。注意它把 wording / structure / design 三者并列，且结构权重最高。

## 2. 标准与证据

### 2.1 ISO 24495-1:2023（国际标准，语言中立）

四原则：

1. **Readers get what they need**（相关）——先识别读者与阅读目的，只给所需内容
2. **Readers can easily find what they need**（可查找）——用标题标示内容，补充信息分离
3. **Readers can easily understand what they find**（可理解）——常用词、清晰简洁的句子与段落、保持连贯
4. **Readers can easily use the information**（可用）——在编写中评估、与读者一起评估

对用例的落点：
- 读者至少有三类：执行人、评审人、业务方。用例要同时让三类人各取所需（执行人看步骤与结果，评审人看标题与追溯，业务方看业务背景与结果）。
- 「补充信息分离」对应元信息块（优先级/类型/追溯）与正文分离，不混进步骤。

### 2.2 WCAG 2.2 SC 3.1.5（无障碍，AAA）

- 要求阅读难度不高于**初中**水平（约 7–9 年级）；做不到时须提供简化版本。
- 实现要点：短句、常用词；专有名词与技术术语可豁免，但需保证可理解。
- 对用例的落点：业务方阅读的字段（标题、业务背景、业务结果）应避免堆叠内部术语；必须使用的术语首次出现时用一句解释。

### 2.3 中文技术文档写作规范（业界惯例，非国标）

句长：
- 逗号分隔的构件宜 ≤20 字；20–29 可接受；30–39 须语义明确；**>40 字不可接受**
- 含逗号的整句 ≤100 字（或正文 3 行以内）

句式：
- 一句一个动词、一句一个意思；简单句/并列句优先于复合句
- 主动语态优先；肯定句优先于双重否定
- 动词直接使用，不套「进行」「作出」「予以」
- 代词「其 / 该 / 此 / 这」必须有唯一指代；否则重复名词
- 名词前修饰语不超过两层

段落：
- 一段一个主题，首句为主题句；一段 ≤4 行（最多 7 行）

> 这些阈值来自中文技术写作社区长期实践，不是国家标准；作为软预算使用，不用于机械扣分。

### 2.4 标点与数字（国家标准）

- **GB/T 15834-2011 标点符号用法**：中文正文用全角标点；并列引号/书名号之间通常不加顿号；序次语层级为「一、→（一）→ 1. →（1）」。
- **GB/T 15835-2011 出版物上数字用法**：计量与编号用阿拉伯数字；概数用汉字（"十几个""三四个月"）；同一场合遵循「同类别同形式」；数值范围用「~」或「—」。
- 对用例的落点：步骤里的数量、版本、金额、时间格式统一；不要中文句子里混半角逗号；范围写法统一。

### 2.5 扫读行为（NN/g、plainlanguage.gov）

- 79% 用户扫读新页面，仅 16% 逐字读（1997）；页面平均只有 18% 的文字被读到（2008，45,237 次浏览）。
- 扫读路径以 F 型为主：先横向读顶部，再向下扫左侧首词。
- 有效做法：信息前置（front-loading）、信息性小标题、项目符号、加粗关键词、一段一个意思、倒金字塔。

对用例的落点：
- 标题前 6–10 字要承载区分信息（对象 + 条件），不要以「验证」「关于」开头。
- 步骤首词用动词（输入/点击/选择），执行人扫左列即可定位动作。
- 预期结果首词写「位置」（页面/接口/表），再写值或状态。

### 2.6 认知负荷理论（Sweller）

三类负荷：
- **内在负荷**：任务本身复杂度，不能消除，只能分块管理
- **外在负荷**：表达与设计带来的额外负担，应尽量消除
- **相关负荷**：用于建立理解的投入，应保留

三条可用约束：
1. **分块**：把长流程拆成有意义的阶段，而不是一次给 12 步
2. **避免注意力分割**：相互依赖的信息要就近放置（预期结果紧跟对应步骤，别放到文末）
3. **避免冗余**：同一信息不要从两个入口重复进入（前置条件写过的不在步骤复述）

### 2.7 精确性与易读性的边界

- Plain language 不等于删信息：具体值、业务规则、错误码必须保留。
- WCAG 明确技术术语可豁免阅读等级，但要求可理解。
- 结论：**先保可判定，再降阅读成本**；不得为了短句把「HTTP 422 / PHONE_INVALID」简化成「报错」。

## 3. 可检验判据（供 T2–T6 落地）

> 分级：S = 标准/国标要求；P = 行业惯例；R = 研究结论。阈值均为软预算，用于提示与评审，不作硬性扣分。

### 3.1 句子层

| # | 判据 | 级别 | 检查方法 |
|---|------|------|----------|
| S1 | 逗号分隔的构件 ≤30 字，>40 字必须改写 | P | 按逗号切分计数 |
| S2 | 单条步骤/预期 ≤100 字 | P | 字符计数 |
| S3 | 一句只表达一个动作或一个事实 | P/R | 数动词与「并/同时/然后」 |
| S4 | 主动语态；不写「被…所…」 | P | 检索「被」+「所」 |
| S5 | 动词直用，不写「进行/作出/予以 + 名词」 | P | 检索「进行」「作出」「予以」 |
| S6 | 名词前修饰 ≤2 层，括号嵌套 ≤1 层 | P | 人工判读 |
| S7 | 代词「其/该/此」指代唯一，否则重复名词 | P | 人工判读 |

### 3.2 段落与结构层

| # | 判据 | 级别 | 检查方法 |
|---|------|------|----------|
| P1 | 标题前 6–10 字承载对象与条件 | P/R | 读前 10 字能否定位 |
| P2 | 元信息与正文分离，固定顺序 | S/P | 结构检查 |
| P3 | 步骤首词为动词，预期首词为位置 | P/R | 首词检查 |
| P4 | 相关信息就近：预期与对应步骤不跨段 | R | 结构检查 |
| P5 | 不使用整段叙述替代步骤列表 | P | 段落长度检查 |
| P6 | 单个信息块 ≤7 项；超出则分阶段 | R | 计数 |

### 3.3 术语与格式层

| # | 判据 | 级别 | 检查方法 |
|---|------|------|----------|
| T1 | 同一对象同一称呼，同一动作同一动词 | P | 术语一致性扫描 |
| T2 | 术语首次出现有解释或上下文 | S | 人工判读 |
| T3 | 全角标点，不中英混用 | S | 检索半角 , ; : ( ) |
| T4 | 数字与单位遵循 GB/T 15835，同场合同形式 | S | 人工判读 |
| T5 | 版本、金额、时间、范围写法统一 | P | 模式检索 |

### 3.4 可用性验证

| # | 判据 | 级别 | 检查方法 |
|---|------|------|----------|
| U1 | 未参与编写的人能按用例独立执行 | S | 读者测试（1 人 1 条） |
| U2 | 执行人卡点能指向具体句子 | R | 记录停顿与回读位置 |

## 4. 与现有 skill 的差距（指向后续任务）

| 差距 | 现状 | 对应任务 |
|------|------|----------|
| 没有句长与句式约束 | 只有「一句话一个事实」的原则，无阈值 | T2 |
| 没有结构可扫读规范 | 有字段顺序示例，但未规定首词、就近、分块 | T3 |
| 没有认知负荷约束 | 拆分只看业务目标，不看信息块数量 | T4 |
| 术语一致无机制 | 仅 Tag 有受控词表 | T5 |
| 无读者验证 | 自检只问「能否判 Pass/Fail」 | T7 |

## 5. 不建议引入的做法

| 做法 | 原因 |
|------|------|
| 用 Flesch-Kincaid 等英文公式给中文用例打分 | 公式基于英文音节/词数，中文需分词，结果不可比 |
| 把 20/40 字做成硬性门禁 | 中文业务对象名长短差异大，硬卡会逼出缩写与歧义 |
| 为短句删掉具体值或错误码 | 违反可判定性；Plain language 不要求删必要信息 |
| 全面口语化 | 用例是工作文档，需要稳定术语，不是聊天 |
| 引入「易读性评分」单一数字 | 会把多维问题压缩成一个伪精确指标 |
