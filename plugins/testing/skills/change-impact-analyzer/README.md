# Change Impact Analyzer Skill

> 变更影响分析师技能包，v1.5.1。
> 从代码改动点总结影响范围和测试内容，需求与现有用例均为可选输入。

## 核心能力

- **四阶段工作流**：收集输入 → 变更解析 → 测试内容与可选交叉分析 → 生成报告
- **七种 diff 模式**：工作区 / 暂存区 / 分支对比 / 单 Commit / Commit 范围 / Revision Range / PR Diff 或外部 Patch
- **只读采集**：记录比较基线、SHA、状态和已读/未读范围；不执行外部转换，按风险分组处理大 diff。当前不附带采集脚本
- **跨层影响链路追踪**：沿「页面 → 组件 → API → Controller → Service → Model/DB → 缓存/MQ/外部系统」串联上下游，找出间接影响
- **前后端契约两侧检查**：接口契约变更同时检查两侧，不只看变更的一端
- **可选材料**：仅代码即可生成范围与测试内容；有用例再检查断言和缺口，有需求再对照实现。Mode A/B 只区分有无需求
- **风险三档清单**：高/中/低风险具体场景清单 + 「降低风险必须有证据」硬约束
- **P0/P1/P2 优先级**：明确哪些问题必须在发布前发现
- **结构化测试场景**：前置、操作、观察项、预期来源和变更证据；无法确认的业务预期保留待确认
- **业务工作表优先**：实际业务操作 → 为什么受影响/边界 → 测试内容 → 测试方式与证据 → 优先级，主调用链写在业务场景下，详细源码放技术追溯
- **完整业务方案模板**：使用 [业务影响与测试范围模板](templates/business-impact-test-scope.md)，从业务范围、改动链和测试点展开到测试方式、数据准备、适用发布阶段、验收与技术追溯；简单改动仍用简表，正文使用清楚的操作和结果描述
- **提交与版本核对**：定位工单相关提交和补充修正，区分最终净变化、过渡风险、服务依赖与实际部署状态
- **验证方式选择**：业务入口、单元/组件、真实数据库、跨服务与迁移验证对应各自证明目标；检查部分失败和相关恢复路径
- **独立证据状态**：实现情况、测试覆盖、执行结果分开，自动化存在不构成免回归依据
- **灵活用例输入**：支持 Markdown/CSV/JSON/YAML，可指定文件路径或目录；无基线则既有覆盖未评估

## 与 testing 生态的关系

| 维度 | change-impact-analyzer | test-case-engineer | bug-analyzer |
|------|----------------------|-------------------|--------------|
| 方向 | 代码改动 → 影响范围与测试内容 | 正向（需求 → 用例） | 逆向（Bug → 根因） |
| 输入 | diff/patch/前后片段/改动点，需求与用例可选 | 需求文档/代码变更 | Bug 现象/日志 |
| 输出 | 影响报告（行为变更 + 覆盖缺口 + 影响链路 + 风险结论 + 必测内容 + 回归范围） | 测试用例 | 根因报告 + 防御性测试点 |
| 协作 | 发现缺口后转交 test-case-engineer 补充用例 | — | — |

## 适用场景

| 场景 | 说明 |
|------|------|
| ✅ 开发提测前 | 分析当前分支相对 main 的变化，提前知道哪些模块要准备数据、是否有需求遗漏 |
| ✅ 测试分析阶段（Mode B） | 需求 + 代码变更一起输入，检查需求覆盖、实现冲突、超范围修改 |
| ✅ 代码合并前 | 对 PR Diff 做风险扫描，重点检查公共组件/接口契约/权限/DB/配置/发布顺序 |
| ✅ 发布前 | 按 P0/P1/P2 重新确认测试完成情况，把高风险遗漏优先补齐 |
| ✅ PR/MR 前检查 | 分析分支改动对现有用例的影响 |
| ✅ 回归风险评估 | 检查 commit 范围的变更是否破坏用例 |
| ✅ 覆盖缺口分析 | 找出改动功能中未被用例覆盖的部分 |

> 完整正式用例集请使用 test-case-engineer；本 skill 直接交付变更相关场景。Bug 根因分析请使用 bug-analyzer。

## 不能替代的边界

代码变更无法完整还原真实产品需求，本 skill **不能替代**：需求评审、测试人员的业务判断、开发代码评审、真实环境验证、最终发布决策。它更适合作为「测试分析助手」，整理代码事实、影响链路、风险和待确认问题，减少遗漏，但不替人做最终判断。

## 敏感信息与脱敏

代码 Diff 可能包含接口地址、业务数据、密钥、用户信息等敏感信息。优先在受信任的本地环境中分析；报告对外分享前必须脱敏；涉及密钥/凭据的变更点只标注「涉及敏感字段」，不复制具体值。

## 核心工作流

```
阶段 1: 收集输入 → 阶段 2: 变更解析 → 阶段 3: 测试内容与可选交叉分析 → 阶段 4: 生成报告
```

### 阶段 1: 收集输入

**目标**：获取可核对的变更依据与可选需求/用例。

- 确认 diff 范围（七种模式：工作区 / 暂存区 / 分支对比 / 单 Commit / Commit 范围 / Revision Range / PR Diff 或外部 Patch）
- 接受 patch、前后片段或具体改动点；只读核对源码及基线，不宣称读取不可达材料
- 有用例时加载（Markdown/CSV/JSON/YAML），没有则既有覆盖未评估，继续交付范围与测试内容
- Mode B 下额外加载需求文档/验收标准/任务说明

披露比较范围与材料来源；已明确时直接继续，仅关键歧义、范围扩大或授权改变时询问。

### 阶段 2: Diff 解析

**目标**：从 diff 中提取结构化变更清单。

- 提取变更文件列表（路径/类型/行数）
- 排除构建产物；依赖升级、行为配置、测试依赖和断言变化分别分析
- 解析每个文件的变更详情（函数/接口/字段/业务逻辑）
- 跨层影响链路追踪（页面 → 组件 → API → Controller → Service → Model/DB → 缓存/MQ）
- 前后端契约两侧检查（接口契约变更同时检查对端）

每个行为改动点关联 change_id、前后变化、关系证据和来源版本；上下游不可达时保留候选影响。

### 阶段 3: 测试内容与可选交叉分析

**目标**：从改动点形成可操作测试场景，有已读用例时再交叉对照。

**3.0 变更固有风险参考清单**：高/中/低风险具体场景，硬约束「降低风险必须有证据」。

**3.1 第一轮 — 行为变更影响**：
- 直接引用匹配（高置信度）：用例文本包含变更的函数名/API路径/字段名
- 模块关联匹配（中置信度）：用例关键词与变更文件模块路径一致
- 依赖链匹配：核对相关源码中的实际调用、注册或字段消费；import 只作线索

**3.2 第二轮 — 覆盖缺口**：
- 检查每个变更点是否有用例覆盖
- 在已检查基线内无覆盖的标记为缺口；没有基线或不可达则未评估

**3.3 Mode A / Mode B 双模式**：
- Mode A（默认）：输出三分（代码事实/影响推断/待确认问题），避免把推断当事实
- Mode B：需求对照实现，分别输出实现情况、测试覆盖和执行结果，识别疑似超范围实现

### 阶段 4: 生成报告

**目标**：先输出工作表，复杂变更再按下面结构追加详情；仅用户要求写文件时保存报告。

报告正文：分析基线 → 实际业务影响、条件与主调用链 → 测试内容及方式 → 共用数据准备、相关迁移/故障验证 → 回归建议与待确认。文件/函数/提交、风险依据和 Mode B 需求矩阵按需附在技术追溯部分。

## 使用方式

### 快速开始

```
用户：帮我分析一下当前改动对测试用例的影响，用例在 docs/test-cases.md
```

### 无旧用例的影响范围与测试内容

```
用户：根据当前分支的代码改动点总结影响范围和测试内容，没有需求文档和旧用例。
AI：读取改动与相关调用方 → 输出工作表、回归建议和待确认 → 既有覆盖未评估，不编造业务预期。
```

### 分支对比

```
用户：对比 main 和 feat/order-cancel 分支的改动，检查对 order 相关用例的影响
```

### Commit 范围

```
用户：检查 commit abc1234 的改动是否影响了 regression 用例
```

### Mode B 需求对照

```
用户：对照 docs/requirement.md，分析 main...当前分支的代码改动，输出需求覆盖情况和测试范围
```

### 外部 Patch

```
用户：分析这个 patch 对现有用例的影响，patch 内容如下：
diff --git a/src/api/user.ts ...
```

## 反例与黑名单

| # | 反模式 | 替代做法 |
|---|--------|---------|
| 1 | 不披露分析范围 | 说明 diff 基线、用例来源及未评估文件 |
| 2 | 混淆测试依赖和业务变化 | 基础设施标为测试依赖，测试断言标为覆盖证据，不能一刀切跳过 |
| 3 | 所有变更都标记"高风险" | 严格按风险参考清单打标，低风险也要标注 |
| 4 | 降低风险没有证据就下调等级 | 必须给出「调用方数量/契约一致性/自动化覆盖」等具体证据 |
| 5 | Mode A 把推断当事实陈述 | 必须区分代码事实/影响推断/待确认问题，推断需标注置信度 |
| 6 | 验收标准凭空创造 | 测试范围可推断，但验收标准不能臆测，必须列入待确认问题 |
| 7 | 测试场景写"验证 XX 是否正常" | 必须用 `[P级][类型] 前置→操作→预期—证据` 结构 |
| 8 | 只看变更一侧不查契约对端 | 接口契约变更必须同时检查前后端两侧 |
| 9 | 报告只列问题不给建议 | 每个问题附带建议操作 |
| 10 | 强行解析 Excel 格式 | 提示转换为 CSV/Markdown |
| 11 | 把整个仓库塞给模型 | 完整目录按风险分组，定向读取并披露未评估范围 |
| 12 | 报告对外分享前未脱敏 | 替换接口路径/用户 ID/密钥等敏感信息 |
