# 反例与黑名单

> **何时阅读**：贯穿阶段 1-4 执行时查阅；阶段 4 输出前按第 4 节自检。
> **覆盖范围**：核心 7 条 / 扩展 7 条 / 触发时机 / 自检清单 / 失败模式。
> **设计依据**：SkillLens 实证——只写"应该做 X"没有"不要做 Y"会降低 judge 准确率。

## 1. 核心反模式（7 条）

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|--------|------------|---------|
| 1 | 不披露分析范围直接给结论 | 范围错误会让后续所有结果无效，浪费 token | 披露 diff 基线、用例来源和未评估文件；已明确范围无需重复确认 |
| 2 | 把测试基础设施变更全部跳过，或把用例变更当成被测代码变更 | 基础设施会改造数、断言或环境；用例变更属于覆盖证据，不是被测变化 | 阶段 2 分开记录：基础设施标「测试依赖」，业务断言变更标「覆盖证据」，都不跳过 |
| 3 | 把所有变更都标为"高风险" | 虚高风险让报告失去参考价值，P0-P2 失去校准基准 | 严格按风险三档打标，低风险也要标注 |
| 4 | 静默修改变更清单或分析范围 | 用户无法追查判断变化的原因 | 保留 change_id，新证据修正判断时说明依据；范围扩大或授权改变时询问 |
| 5 | 报告中只列问题不给建议 | 用户需要可落地的行动项 | 每个问题附建议操作（修改/补充用例/验证确认）、涉及 ID 和优先级 |
| 6 | 对 Excel 格式强行解析 | 合并单元格、公式、版本差异容易丢失或乱码 | 提示转换为 CSV/Markdown 或粘贴内容；坚持使用时标「格式推断，仅供参考」 |
| 7 | 忽略重命名/移动文件的语义 | 用例中旧路径引用可能失效，职责变化影响链路 | 阶段 2 识别 `R` 并保留 old/new 路径，阶段 3 检查用例路径引用 |

## 2. 扩展项（7 条）

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|--------|------------|---------|
| E1 | 降低风险没有证据就下调等级 | "开发说改动很小"不构成低风险证据，凭印象下调会漏掉高风险 | 必须给出「调用方数量/契约一致性/自动化覆盖」等具体证据 |
| E2 | Mode A 把推断当事实陈述 | 会让用户误以为代码已验证，导致决策失误 | 区分代码事实/影响推断/待确认问题，推断标置信度 |
| E3 | 验收标准凭空创造 | 会以假需求指导测试 | 验收标准不明确时列入「待确认问题」，不给臆测答案 |
| E4 | 测试场景写"验证 XX 是否正常" | 不可执行，无法判定 pass/fail | 用 `[P级][类型] 前置→操作→预期—证据` 结构（见 [report-template.md](report-template.md) 第 3 节） |
| E5 | 只看变更一侧不查契约对端 | 会漏掉对端未同步修改的问题 | 契约变更必须同时检查前后端两侧（见 [cross-impact-analysis.md](cross-impact-analysis.md) 第 2 节） |
| E6 | 把整个仓库塞给模型 | 上下文超限会淹没关键变更点 | 先获取完整变更目录和版本，再按风险定向读取（见 [diff-modes.md](diff-modes.md) 第 3 节） |
| E7 | 报告对外分享前未脱敏 | diff 可能含接口地址、密钥、用户信息 | 替换接口路径/用户 ID/密钥；涉及密钥只标"涉及敏感字段" |

## 3. 触发检查时机

| 阶段 | 必查 |
|------|------|
| 阶段 1（收集输入 / 范围披露） | 核心 1、扩展 E6 |
| 阶段 2（Diff 解析 / 清单自检） | 核心 2、3、7；扩展 E1、E5、E6 |
| 阶段 3（交叉分析） | 核心 4；扩展 E2、E3、E5 |
| 阶段 4（生成报告 / Excel 用例） | 核心 3、5、6；扩展 E4、E7 |

## 4. 输出前自检

- [ ] 基线、可选材料来源和未评估范围已披露，只有阻塞歧义才询问？（核心 1）
- [ ] 测试基础设施标「测试依赖」，业务断言变更标「覆盖证据」？（核心 2）
- [ ] 风险等级有证据支撑，不是全部"高风险"？（核心 3、E1）
- [ ] 清单修正有证据、理由和稳定 change_id？（核心 4）
- [ ] 每个问题都附了建议操作和优先级？（核心 5）
- [ ] Excel 用例未强行解析，重命名语义已处理？（核心 6、7）
- [ ] Mode A 下推断与事实已区分，验收标准没有凭空创造？（E2、E3）
- [ ] 测试场景采用 `[P级][类型] 前置→操作→预期—证据` 结构？（E4）
- [ ] 每条预期有需求/契约/确认规则来源，无依据部分保留待确认？
- [ ] 每个业务都解释了操作、调用链、本次变化和后果，触发/跳过条件及直接/间接/候选影响已区分？
- [ ] 多提交的最终净变化、撤回项和各服务依赖已核对，部署状态未由仓库版本代替？
- [ ] 测试方式对应证明目标，Mock/页面提示/源码未替代真实持久化或外部副作用证据？
- [ ] 失败前的部分更新和恢复路径已检查，没有假定失败即全部回滚或自动幂等？
- [ ] 实现、覆盖、执行状态分开；无用例标未评估，自动化存在未当作免回归证据？
- [ ] 契约两侧都已检查，未把整个仓库塞给模型，报告已脱敏？（E5、E6、E7）

## 5. 失败模式速查

| 阶段 | 触发条件 | 一线修复 | 仍失败兜底 |
|------|---------|---------|-----------|
| 阶段 1 | 不在 git 仓库 | 有 patch/片段/改动点则直接解析 | 缺少变更依据时询问，不声称读取源码 |
| 阶段 1 | diff 为空 | 核对比较基线、已提交分支改动与未跟踪文件 | 已跟踪无差异才报告无变更；未读文件单列 |
| 阶段 1 | diff 过大（>5000 行） | 完整目录按风险分组，优先关键行为与依赖 | 标注采样及每组未读范围，不据此排除回归 |
| 阶段 1 | 无旧用例或指定用例不可达 | 保留既有覆盖未评估，有已读基线才对照 | 仍交付代码影响和测试内容，不虚构用例或覆盖率 |
| 阶段 1 | 用例格式无法识别 | 提示确认格式 | 按纯文本推断，标注「格式推断」 |
| 阶段 2 | 无法识别函数/类名 | 跳过函数级解析 | 标注「minified，仅文件级」 |
| 阶段 2 | 非文本文件混入 diff | 按扩展名过滤 | 报告标注跳过数量 |
| 阶段 3 | 用例格式不规范 | 自然语言理解，标注低置信度 | 标记「无法分析」单独列出 |
| 阶段 3 | 交叉结果为空 | 检查模块覆盖 | 输出覆盖缺口清单 |
| 阶段 4 | 输出目录不存在 | 用户要求写文件时创建目录 | 未要求写文件则在对话交付 |
