# 阶段 3 交叉分析操作细则

> 有已读用例基线时加载，承载阶段 3 两轮交叉分析；没有基线时按 [cross-impact-analysis.md](cross-impact-analysis.md) 生成影响范围与测试内容，既有覆盖保持未评估。

## 1. 第一轮：行为变更影响分析

**分析策略**：

对变更清单中的每个变更点，按以下优先级匹配测试用例：

1. **直接引用匹配**（高置信度）：用例中直接提到了变更的函数名、接口路径、字段名。判定规则：用例文本包含变更点的精确标识符（函数名/API路径/字段名），不区分大小写
2. **模块关联匹配**（中置信度）：用例标题或步骤中提到的业务模块与变更文件的模块路径一致。判定规则：变更文件路径含 `user` → 匹配用例中含「用户/user」关键词的；变更文件路径含 `order` → 匹配用例中含「订单/order」关键词的
3. **依赖链匹配**：在相关源码核对实际调用、路由注册或字段消费；仅有 import 线索标潜在关联，不能只查 diff 中新增的 import。依据充分的依赖关系可确认影响，不因间接关系固定判低置信度。

**影响程度判定**：

| 程度 | 判定条件 |
|------|---------|
| 高 | 用例预期直接依赖变化契约或规则，需核对需求后决定更新用例或修复实现，不能让旧断言迁就疑似缺陷 |
| 中 | 用例的操作步骤可能受变更影响，建议验证 |
| 低 | 变更在同一模块但不直接影响用例核心路径，建议关注 |

**输出格式**：每个问题包含变更文件、变更内容、影响程度、受影响用例列表（用例 ID + 标题 + 具体影响说明）。

**关联证据边界**：精确标识符、模块关键词、import关系只提供匹配线索；文字相似不证明具体业务结论失效。候选关联与已确认关联分列，保留来源和版本；只有可核对的契约依赖或结构化追溯映射才确认影响。

## 2. 第二轮：覆盖缺口分析

**分析策略**：

对变更清单中的每个变更点，检查：
1. 是否有用例直接测试了该变更的功能
2. 是否有用例间接覆盖了该变更的路径
3. 检查断言是否覆盖变化条件，而非只有同名标题或相关文件；在已读基线范围内均无覆盖时标缺口。部分基线只能说「已检查用例中未发现」，不能断言全库没有。

为每个变更点分别记录 `coverage_status` 与 `execution_status`，标用例/断言位置、基线完整度和执行证据版本。没有用例基线、无法解析断言、用例不可达时保持「未评估」。已有测试代码或过去通过的记录不证明当前代码已通过。

**风险等级判定**：

| 等级 | 判定条件 |
|------|---------|
| 高 | 新增核心业务功能/接口，或修改了关键业务逻辑，无任何用例覆盖 |
| 中 | 修改了非核心功能的参数/返回值，或新增了辅助功能，无用例覆盖 |
| 低 | 有契约与依赖证据支持的内部重构/格式调整，可复用现有回归；未经验证不能直接认定行为未变 |

**输出格式**：每个缺口包含变更文件、变更内容、风险等级、建议的补充用例方向。
