# 跨层影响分析

> **何时阅读**：阶段 2 输出结构化变更清单、阶段 3 生成测试内容时加载；第 5 节仅在有用例基线时阅读。
> **覆盖范围**：链路追踪 / 契约两侧检查 / 风险三档 / Mode A/B / 两轮交叉分析 / 定向复核。

## 1. 跨层影响链路追踪

**目标**：不止停留在「改了哪些文件」，而是沿调用链把上下游串起来，找出间接影响。真实影响往往不在改动文件本身：后端改了返回字段，问题可能出在前端旧解析、历史数据、缓存旧结构、另一个调用页面或仍断言旧结果的自动化用例。

### 1.1 链路方向（自上而下）

```
页面或路由 → 组件和状态 → API 请求（方法/路径/参数/返回值）
→ 后端 Controller → Service 业务逻辑
→ Model 和数据库（schema/默认值/历史数据）→ 缓存、消息队列或外部系统
```

### 1.2 追踪策略

- 对每个变更点向上找**调用方**（谁会触发），向下找**依赖方**（它调用了什么）。
- 识别三类范围：同接口多调用方、公共方法多业务方、数据流下游（DB 字段追到所有读写接口、缓存键、消息体）。
- 每条关系记录 `change_id`、调用/消费位置（文件与行或符号）、来源版本和 `confirmed/candidate`；在完整相关源码中核对调用、路由注册或字段消费，不能只搜索 diff 中的 import。
- 记录已查入口与停止位置。动态调用、消息消费、配置开关或跨仓库对端不可达时列待核实；「未找到调用方」不等于「没有调用方」。
- 只提供 patch/改动说明时限定到给定材料；缺失上下游形成候选影响，不虚构路径或组件。

### 1.3 输出格式（追加到变更清单）

```yaml
impact_chains:
  - change_id: "CH-001"
    change_ref: "src/api/user.ts::getUser"
    chain:
      - {layer: frontend, nodes: ["pages/user-profile"], relation: consumes_response, confirmation: confirmed, source_refs: ["pages/user-profile:42@head-sha"]}
      - {layer: api, nodes: ["GET /api/user/:id"], relation: defines, confirmation: confirmed, source_refs: ["src/api/user.ts::getUser@head-sha"]}
      - {layer: service, nodes: ["UserService.getProfile"], relation: implements, confirmation: confirmed, source_refs: ["UserService::getProfile@head-sha"]}
      - {layer: model, nodes: ["users.avatar (nullable)"], relation: reads_from, confirmation: confirmed, source_refs: ["users::avatar@head-sha"]}
      - {layer: cache, nodes: ["user:profile:{id}"], relation: cached_as, confirmation: candidate, source_refs: []}
    indirect_risks:
      - "历史用户 avatar 为空，前端需处理 null 展示"
      - "缓存未失效会返回旧结构，需确认失效策略"
```

### 1.4 从调用关系解释实际业务影响

每条业务影响都应回答「为什么要测这个入口」。先反向找真实调用方，再正向核对该入口的完整相关路径；页面、业务 API、定时任务或消息回调都可作为入口。只有后端材料时保留已知业务动作，页面路径和按钮名称标待核实。

按以下顺序写一条可追溯的说明：

`业务操作 → 实际调用链 → 本次改动及前后差异 → 触发条件 → 数据/错误传播 → 用户或业务后果`

- **影响性质与确认状态分开**：直接影响是该入口实际执行变化分支；间接回归是入口依赖受影响的上游结果或共享数据；候选影响表示关系未核实，不能当成已确认必测范围。
- **记录边界**：写清新建/已有记录、空/非空、开关、角色、版本等决定是否执行改动的条件；跳过变化分支不等于整个入口无需回归。
- **逐调用方核对语义**：共享读方法可能在不同入口只用于判空、解密展示或外部比对，不能把某入口写成它新增了支付字段解密。
- **检查失败前后状态**：沿错误返回和事务范围确认哪些写入/外部调用已发生、哪些后续动作未发生；失败响应不能证明全部回滚。
- **解释排除理由**：有完整已读路径证明不消费本次变化时才排除；同字段、同模块、同方法名或 import 仅作检索线索。
- **保留依据**：每条链关联 `change_id`、源码符号/位置、版本和 `confirmed/candidate`；业务后果标代码事实或影响推断。

示例：新用户提交新手引导 → 初始化套餐 → 创建基础账单 → 本次新增非空姓名加密 → 加密失败提前返回 → 套餐初始化未继续。影响发生在提交引导时，不能笼统写成「注册接口失败」；已有记录跳过创建、空姓名跳过加密，是不同的条件分支。

## 2. 前后端契约两侧检查

接口契约变化必须同时检查两侧，不能只看变更的一端。任一端变更时逐项确认对端：

| 变更侧 | 检查项 |
|--------|--------|
| 前端改了请求参数 | 后端是否接收新字段名？旧版客户端是否还发旧字段？是否需兼容两种字段？参数缺失返回什么状态码？日志/监控是否还能记录用户信息？其他调用方是否也用这个接口？ |
| 后端改了返回字段 | 前端是否按新字段解析？历史数据是否含新字段？缓存里是否还是旧结构？另一个页面是否也调用？自动化用例是否仍断言旧结果？ |
| 后端改了业务规则 | 前端是否需同步交互（禁用按钮、隐藏入口）？权限校验是否需要同步？状态机是否一致？ |
| DB schema 变更 | 历史数据是否需迁移？默认值是否兼容旧代码？读写该字段的接口是否都已更新？ |

示例：请求体从 `{"userId": 1001}` 改为 `{"user_id": 1001}`，只看前端只会得出「参数名调整」；还需确认后端是否接收 `user_id`、旧客户端是否仍发 `userId`、是否需兼容两种字段、缺失时状态码、日志监控可用性和其他调用方。

```yaml
contract_checks:
  - interface: "POST /api/orders"
    changed_side: "frontend"
    checklist:
      - {item: "后端是否同步接收 user_id", status: "confirmed", evidence: "src/api/orders.ts:23 已读取 user_id"}
      - {item: "旧版客户端兼容性", status: "unknown", evidence: "需确认是否仍需支持 userId"}
```

## 3. 变更固有风险三档清单

每个变更点在阶段 2 标注的 `risk` 依据下表。不是所有变更都值得相同测试成本。

| 等级 | 判定条件（高风险任一命中即高） |
|---|---|
| 高 | 登录和权限；支付、金额计算、订单关键状态和履约规则；删除或破坏性操作；敏感数据；数据库迁移；公共接口不兼容；事务和并发；大范围公共组件；发布配置和部署顺序 |
| 中 | 核心业务流程；接口字段扩展；状态管理；表单校验；缓存和重试；有明确调用范围的共享服务 |
| 低 | 独立页面文案；不改接口的内部重构；影响范围较小的展示调整 |

🔴 **硬约束 · 降低风险必须有证据**：

- 「开发说改动很小」不是低风险证据；「公共方法只有一个调用方、契约未变、已有自动化覆盖主要分支」才是。
- 覆盖不足或影响范围不清时不能无依据下调；确认契约不兼容、权限缺失或历史数据处理不当时按具体影响提级。
- 业务影响等级与证据不确定性分别说明；信息不足先标待核实，不因模块名称或未知项数量把所有改动升为高风险。

**用途**：阶段 2 的 `risk` 赋值；阶段 3 行为影响校准（高风险即使无现成用例也应追间接影响）与覆盖缺口校准（有基线时高风险缺口优先验证）；阶段 4 的 P0/P1/P2 划分。

## 4. Mode A / Mode B 双模式

是否有需求材料决定 Mode A/B；是否有现有用例是独立维度。

### 4.1 模式判定

- **Mode A**（默认）：有 diff、patch、前后代码片段或可定位改动点，无需求/验收/任务/Bug 材料；现有用例可选。
- **Mode B**：另有需求文档、验收标准、任务说明或 Bug 描述；现有用例仍可选。
- 用例基线单列来源、版本、可达性、已读范围与完整程度；无用例或文件不可达时跳过该项对照，不能把未评估写成未覆盖。

### 4.2 Mode A：只有代码，没有需求文档

**输出三分原则**，避免把推断当成事实：

| 类别 | 定义 | 表述规范 |
|------|------|---------|
| 代码事实 | 能直接观察到的变化（新增接口参数、删除状态判断、改默认值、新增权限校验） | 直接陈述 |
| 影响推断 | 由调用关系推出的潜在影响（接口被两个页面调用、历史数据可能为空） | 标注置信度（高/中/低）并说明依据 |
| 待确认问题 | 代码无法回答的问题（状态 2 是否允许退款、旧客户端是否须兼容） | 以问号结尾，不臆测答案 |

🔴 **硬约束**：测试范围可以推断，但**验收标准不能凭空创造**。不写「产品需求就是允许状态 2 的用户退款」，改写「从状态判断变化推断，状态 2 可能被纳入退款范围，置信度中等，需确认实际业务规则」。

### 4.3 从改动点生成测试内容（两种模式共用）

按 `before → after → 触发条件 → 影响对象` 拆分行为改动点；对每点说明业务入口、直接/间接影响、风险理由和建议验证。纯移动/重构也要核对导入、注册与契约，再决定复用哪些回归。

- 测试场景至少关联 `change_id`，包含前置、操作、观察项、可判定预期及预期来源。
- 只展开相关维度：条件分支取边界两侧，契约变化查调用两侧，状态变化查合法/拒绝分支，副作用查数据与事件一致性；不从模块名称补出不存在的权限、重试或消息规则。
- 金额场景区分公式的数学参考值与实际货币表示/舍入断言；整数输入也可能产生小数或浮点误差，不能据此宣称无需舍入规则。
- 预期来源区分 `requirement/contract/confirmed_rule/pending` 并记录具体引用；代码证据另列为当前观察行为，不自动成为验收标准。旧用例只作历史基线，变更后是否有效需核对。
- 只知 `timeout=10 → 20` 时，能报告数值变化并建议检查配置读取和超时前后行为；单位、默认值、重试与 SLA 均待确认，不能写成「超过 20 秒返回 504」。

### 4.4 按证明目标选择测试方式与数据

先写要证明的结果，再选触发方式和观察证据；不要给每条业务套全部测试层。这里只形成建议，不执行测试、造数或故障注入。

| 证明目标 | 适合的方式与观察项 | 证据边界 |
|----------|------------------|----------|
| 用户能完成操作、契约保持 | 实际页面/业务 API 触发，检查响应、重新查询和业务最终状态 | 接口通过不证明页面交互；页面提示不证明持久化或外部副作用 |
| 条件、空值、类型转换、错误传播、调用次数 | 单元/组件测试，必要时 Mock 依赖，断言分支与后续调用 | Mock 不证明真实数据库、消息消费或第三方处理 |
| 零值更新、列投影、事务、历史数据 | 真实测试数据库集成测试，操作前后查询目标行及关联记录 | 源码更新列、sqlmock 或加密方法通过不能证明数据已正确落库 |
| 跨服务、支付、消息或异步状态 | 集成/测试环境验证，用业务关联标识核对事件、账单、外部记录和最终状态 | 单次日志或成功提示不能证明无重复处理；外部不可达则列未验证层 |
| 迁移、回填、开关与版本兼容 | 按上线阶段检查 schema、读写、存量数据、配置和服务依赖 | 停写某路径不证明存量已清理；仓库/依赖版本不证明部署版本 |

- 数据按改动条件划分：已有/新建、历史/新格式、空/非空/冲突/异常，以及实际存在的开关与服务版本组合；不照抄领域无关矩阵。
- 加密/字段迁移可选历史明文、双写一致、仅密文、明密文冲突、均空、密文异常；按字段核对优先级、清空、类型与失败策略。
- 失败场景检查「失败前已发生什么 → 失败时保留什么 → 恢复后如何继续」。存在重试/消息重投链路时补恢复与重复触发观察项；幂等、补偿和回滚规则无来源则待确认。
- 报告区分业务验证、底层分支/数据库验证、迁移发布验证；所需环境、权限或造数方式未明确时标待确认，不编造可执行命令。

### 4.5 Mode B：需求与代码对照

先拆解需求 → 对照实现 → 有已读用例时核对断言 → 有执行记录时核对版本和结果。三项状态独立，不用测试覆盖状态代替实现结论。

| 维度 | 状态及判定 |
|------|---------|
| 实现情况 | 符合 / 冲突 / 未发现实现 / 待确认；检索不足或权限可能在中间件时保留待确认 |
| 测试覆盖 | 已覆盖 / 部分覆盖 / 未覆盖 / 未评估；有已读断言并匹配变化条件才认定覆盖，缺基线则未评估 |
| 执行结果 | 当前版本通过 / 失败 / 未执行 / 历史证据待复核；记录代码版本、环境、范围与结果来源 |

示例：需求「只有管理员可以删除项目」，已查路由、中间件与服务，确认普通成员可删除；用例清单无权限拒绝断言、无执行记录 → 实现「冲突」、覆盖「未覆盖」、执行「未执行」，风险 high；建议 `[P0][安全/权限]` 场景，具体状态码待契约确认。

**疑似超范围实现**（Mode B 独有）：除检查「需求有没有实现」，还要识别代码是否超出需求。例如需求只改订单列表展示，代码同时放开了订单导出权限——不一定是 Bug，但缺需求依据且可能影响用户行为，必须单独标记，交产品/开发/测试确认。

```yaml
requirement_traceability:
  - requirement_id: "REQ-001"
    requirement: "只有管理员可以删除项目"
    implementation_evidence: "已查路由/中间件/服务，普通成员路径没有拒绝条件"
    test_evidence: "无用例覆盖权限拒绝"
    implementation_status: "冲突"
    coverage_status: "未覆盖"
    execution_status: "未执行"
    risk: "high"
out_of_scope_changes:
  - change: "订单导出接口去除了角色校验"
    related_requirement: "无（需求只要求修改订单列表展示）"
    risk: "high"
    action: "需产品/开发确认是否为预期改动"
```

## 5. 有用例基线时的两轮交叉分析

有已读用例基线时执行；没有基线时按第 4.3 节交付影响范围与测试内容，既有覆盖保持未评估。

### 5.1 第一轮：行为变更影响分析

对每个变更点按优先级匹配用例：

1. **直接引用**（高置信度）：用例直接提到变更的函数名、接口路径或字段名（精确标识符，不区分大小写）。
2. **模块关联**（中置信度）：用例标题/步骤的业务模块与变更文件模块路径一致（如 `user` → 「用户/user」）。
3. **依赖链**：在相关源码核对实际调用、路由注册或字段消费；仅有 import 线索标潜在关联，不能只查 diff 中新增的 import。

| 影响程度 | 判定条件 |
|---------|---------|
| 高 | 用例预期直接依赖变化契约或规则，需核对需求后决定更新用例或修复实现，不能让旧断言迁就疑似缺陷 |
| 中 | 操作步骤可能受变更影响，建议验证 |
| 低 | 变更在同一模块但不直接影响用例核心路径，建议关注 |

**输出**：变更文件、变更内容、影响程度、受影响用例列表（用例 ID + 标题 + 具体影响说明）。

**证据边界**：精确标识符、模块关键词、import 关系只提供匹配线索，文字相似不证明业务结论失效。候选关联与已确认关联分列，保留来源和版本；只有可核对的契约依赖或结构化追溯映射才确认影响。

### 5.2 第二轮：覆盖缺口分析

对每个变更点检查：是否有用例直接测试该功能、是否间接覆盖该路径、断言是否覆盖变化条件而非只有同名标题或相关文件。在已读基线内均无覆盖时标缺口；部分基线只能说「已检查用例中未发现」，不能断言全库没有。

为每个变更点分别记录 `coverage_status` 与 `execution_status`，标用例/断言位置、基线完整度和执行证据版本。没有基线、无法解析断言、用例不可达时保持「未评估」。已有测试代码或过去通过的记录不证明当前代码已通过。

| 风险等级 | 判定条件 |
|---------|---------|
| 高 | 新增核心业务功能/接口，或修改关键业务逻辑，无任何用例覆盖 |
| 中 | 修改非核心功能参数/返回值，或新增辅助功能，无用例覆盖 |
| 低 | 有契约与依赖证据支持的内部重构/格式调整，可复用现有回归；未验证不能直接认定行为未变 |

**输出**：变更文件、变更内容、风险等级、建议补充用例方向。

## 6. 来源变更与定向复核（可选追溯输入）

- 消费 `traceability.sources`（id/location/version/availability）、`artifacts`（id/kind/version）和 `links`（upstream/downstream/confirmation/source/source_refs），保留原 source/evidence_type。
- sources availability 为 available/unreachable/missing/unknown；links confirmation 为 confirmed/candidate。使用显式稳定产物 ID，不以列表下标或展示编号建立长期关联。
- 先核对 source_refs 指向可达且明确版本的来源及关联依据，未满足时保留 uncorroborated_links；再定位来源/需求 ID 与变更版本，沿有依据的 confirmed 链找风险、模型/场景、用例和执行证据；只把受影响结论标「需复核」，保留旧版本/证据，不能宣布旧测试已失败。
- candidate 链只形成候选影响清单，记录需核对的规则/调用依赖；不得把关键词同名升级为 confirmed。
- 来源不可达只报取证缺口；业务结果未知另报状态，两者不能互相替代。无追溯图时按 Mode A/B 继续，关系未评估而不是假装无影响。
- 同一产物被多条路径命中只记录一次复核项，附全部依据；只复核变更项的受影响范围，不重跑无关流程。

示例：优惠上限从 30 改为 20，REQ-COUPON-CAP→SC-CAP→TC-COUPON-BOUNDARY 有 confirmed 关系，只复核对应优惠边界断言；无关联证据的登录用例保持原状态，同模块其他用例最多进入 candidate，不自动失效。
