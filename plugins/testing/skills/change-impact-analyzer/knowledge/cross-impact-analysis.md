# 跨层影响分析

> **何时阅读**：阶段 2 输出结构化变更清单 + 阶段 3 交叉分析时加载本文件。
> **覆盖范围**：跨层影响链路追踪 / 前后端契约两侧检查 / 变更固有风险三档清单 / Mode A 与 Mode B 双模式规则。

## 1. 跨层影响链路追踪

**目标**：不止停留在「改了哪些文件」，而是沿调用链把上下游串起来，找出间接影响。

变更点的真实影响往往不在改动文件本身，而在调用链上下游。例如开发只改了后端返回字段，但真正出问题的地方可能是：前端仍按旧字段解析、历史数据没有新字段、缓存里还是旧结构、另一个页面也调了这个接口、自动化用例仍断言旧结果。

### 1.1 链路追踪方向（自上而下）

```
页面或路由
    ↓
组件和状态
    ↓
API 请求（方法 / 路径 / 参数 / 返回值）
    ↓
后端 Controller
    ↓
Service 业务逻辑
    ↓
Model 和数据库（schema / 默认值 / 历史数据）
    ↓
缓存、消息队列或外部系统
```

### 1.2 追踪策略

- 对每个变更点，沿链路向上找**调用方**（谁会触发它），向下找**依赖方**（它调用了什么）
- 识别**同接口多调用方**场景：同一接口被订单详情页和退款页同时调用，任一端变化都需要两侧回归
- 识别**公共方法多业务方**场景：公共组件/工具方法被多处引用，变更影响范围需逐个评估
- 识别**数据流下游**场景：DB 字段变化要追到所有读写该字段的接口、缓存键、消息体
- 每条关系记录 `change_id`、调用/消费位置（文件与行或符号）、来源版本和 `confirmed/candidate`；在完整相关源码中核对实际调用、路由注册或字段消费，不能只搜索 diff 中的 import。
- 记录已查入口与停止位置。动态调用、消息消费、配置开关或跨仓库对端不可达时列为待核实；「未找到调用方」不等于「没有调用方」。静态调用成立不证明运行时条件已满足。
- 只提供 patch/改动说明时限定到给定材料；缺失的上下游形成候选影响，不虚构路径或组件。

### 1.3 输出格式（追加到变更清单）

```yaml
impact_chains:
  - change_id: "CH-001"
    change_ref: "src/api/user.ts::getUser"
    chain:
      - layer: "frontend"
        nodes: ["pages/user-profile", "pages/admin-user-list"]
        relation: "consumes_response"
        confirmation: "confirmed"
        source_refs: ["pages/user-profile:42@head-sha", "pages/admin-user-list:65@head-sha"]
      - layer: "api"
        nodes: ["GET /api/user/:id"]
        relation: "defines"
        confirmation: "confirmed"
        source_refs: ["src/api/user.ts::getUser@head-sha"]
      - layer: "service"
        nodes: ["UserService.getProfile"]
        relation: "implements"
        confirmation: "confirmed"
        source_refs: ["UserService::getProfile@head-sha"]
      - layer: "model"
        nodes: ["users.avatar (nullable)"]
        relation: "reads_from"
        confirmation: "confirmed"
        source_refs: ["UserService::getProfile@head-sha", "users::avatar@head-sha"]
      - layer: "cache"
        nodes: ["user:profile:{id}"]
        relation: "cached_as"
        confirmation: "candidate"
        source_refs: []
    indirect_risks:
      - "历史用户数据 avatar 为空，前端需处理 null 展示"
      - "缓存未失效会返回旧结构，需确认失效策略"
```

## 2. 前后端契约两侧检查

**目标**：接口契约变化必须同时检查两侧，不能只看变更的一端。

### 2.1 检查清单（任一端变更时都要逐项确认对端）

| 变更侧 | 检查项 |
|--------|--------|
| 前端改了请求参数 | 后端是否同步接收新字段名？旧版客户端是否还在发旧字段？接口是否需要兼容两种字段？参数缺失时返回什么状态码？日志/监控是否还能记录用户信息？其他调用方是否也用这个接口？ |
| 后端改了返回字段 | 前端是否按新字段解析？历史数据是否包含新字段？缓存里保存的还是旧结构吗？另一个页面是否也调了这个接口？自动化用例是否仍断言旧结果？ |
| 后端改了业务规则 | 前端是否需要同步调整交互（如禁用按钮、隐藏入口）？权限校验是否需要同步？状态机是否一致？ |
| DB schema 变更 | 历史数据是否需要迁移？默认值是否兼容旧代码？读写该字段的接口是否都已更新？ |

### 2.2 示例

前端把请求体从 `{"userId": 1001}` 改为 `{"user_id": 1001}`，只看前端代码会得出「参数名调整」的结论。完整检查还需确认：后端是否同步接收 `user_id`、旧版客户端是否还会发送 `userId`、接口是否需要同时兼容两种字段、参数缺失时返回什么状态码、日志和监控是否还能记录用户信息、其他调用方是否也使用这个接口。

### 2.3 输出格式（追加到变更清单）

```yaml
contract_checks:
  - interface: "POST /api/orders"
    changed_side: "frontend"
    checklist:
      - item: "后端是否同步接收 user_id"
        status: "confirmed | missing | unknown"
        evidence: "src/api/orders.ts 第 23 行已读取 user_id"
      - item: "旧版客户端兼容性"
        status: "unknown"
        evidence: "需确认是否仍需支持 userId"
```

## 3. 变更固有风险三档清单

每个变更点在阶段 2 标注的 `risk` 字段，依据下表打标。**不是所有变更都值得投入相同的测试成本**，修改一段页面文案与修改支付金额计算逻辑，测试策略不能一样。

### 3.1 高风险（任一命中即高风险）

- 登录和权限
- 支付、金额计算、订单关键状态和履约规则
- 删除或破坏性操作
- 敏感数据
- 数据库迁移
- 公共接口不兼容
- 事务和并发
- 大范围使用的公共组件
- 发布配置和部署顺序

### 3.2 中风险

- 核心业务流程
- 接口字段扩展
- 状态管理
- 表单校验
- 缓存和重试
- 有明确调用范围的共享服务

### 3.3 低风险

- 独立页面文案
- 不改变接口的内部重构
- 影响范围较小的展示调整

### 3.4 🔴 硬约束 · 降低风险必须有证据

- 「开发说改动很小」**不是**低风险证据
- 「这个公共方法只有一个调用方，接口契约没有变化，已有自动化覆盖了主要分支」**才是**降低风险的证据
- 覆盖不足或影响范围不清时不能无依据下调；确认契约不兼容、权限缺失或历史数据处理不当时按具体影响提级
- 业务影响等级与证据不确定性分别说明；信息不足先标待核实，不因模块名称或未知项数量把所有改动升为高风险。

### 3.5 本清单用途

- 阶段 2 变更清单的 `risk` 字段赋值
- 阶段 3 行为变更影响校准（高风险变更即使无现有用例直接引用，也应主动追间接影响）
- 阶段 3 覆盖缺口校准（有基线且已确认的高风险变化缺口优先验证；无基线仍为未评估）
- 阶段 4 必测内容的 P0/P1/P2 优先级划分（详见 [report-template.md](report-template.md)）

## 4. Mode A / Mode B 双模式

根据是否有需求材料选择 Mode A/B；是否有现有用例是独立维度，不影响从改动点交付影响范围和测试内容。

### 4.1 模式判定

- **Mode A**（默认）：有 diff、patch、前后代码片段或可定位改动点，无需求/验收/任务/Bug 材料；现有用例可选。
- **Mode B**：另有需求文档、验收标准、任务说明或 Bug 描述；现有用例仍可选。
- 用例基线单列来源、版本、可达性、已读范围与完整程度；没有用例或指定文件不可达时，跳过该项用例对照，不能把未评估写成未覆盖。

### 4.2 Mode A：只有代码，没有需求文档

**适用场景**：没有正式需求文档、只有开发口头描述、需求已过期、临时修复线上问题、只能拿到代码 Diff。

**输出三分原则**：根据代码变化推断业务意图时，必须明确区分以下三类信息，**避免 AI 把推断当成事实**。

| 类别 | 定义 | 示例 | 表述规范 |
|------|------|------|---------|
| 代码事实 | 代码中能直接观察到的变化 | 新增了一个接口参数；删除了一个状态判断；修改了数据库字段默认值；新增了一次权限校验 | 直接陈述，无需修饰 |
| 影响推断 | 根据调用关系推断出来的潜在影响 | 该接口被订单详情页和退款页同时调用；状态判断变化可能影响退款入口；新字段可能导致历史数据为空 | 必须标注置信度（高/中/低），并说明推断依据 |
| 待确认问题 | 代码本身无法回答的问题 | 状态 2 是否允许退款？老版本客户端是否必须兼容？新字段为空时产品希望展示什么？这次修改是否需要处理历史数据？ | 必须以问号结尾，不能给出臆测答案 |

🔴 **硬约束**：
- 测试范围可以根据代码推断，但**验收标准不能凭空创造**
- 不能直接说「产品需求就是允许状态 2 的用户退款」
- 必须写成「从状态判断变化推断，状态 2 可能被纳入退款范围，置信度中等，需要确认实际业务规则」

### 4.2.1 从改动点生成测试内容（两种模式共用）

按 `before → after → 触发条件 → 影响对象` 拆分行为改动点；对每点说明业务入口、直接/间接影响、风险理由和建议验证。纯移动/重构也要核对导入、注册与契约，再决定复用哪些回归。

测试场景至少关联 `change_id`，包含前置、操作、观察项、可判定预期及预期来源。只展开相关维度：条件分支取边界两侧，契约变化查调用两侧，状态变化查合法/拒绝分支，副作用查数据与事件一致性；不从模块名称补出不存在的权限、重试或消息规则。

金额场景区分公式的数学参考值与实际货币表示/舍入断言；整数输入也可能产生小数或浮点误差，不能据此宣称无需舍入规则。精度、容差或展示格式没有来源时保留待确认。

预期来源区分 `requirement/contract/confirmed_rule/pending`，记录具体引用；代码证据另列为当前观察行为，不自动成为业务验收标准。旧用例可用作历史基线，变更后是否仍有效需核对；纯改动说明未核对源码时保留来源状态。

例如只知 `timeout=10 → 20`：能报告数值变化，建议检查超时配置读取与超时前后行为；单位、默认值、重试与 SLA 均待确认，不能写成「超过20秒返回504」。无旧用例时仍交付这些内容，既有覆盖标「未评估」。

### 4.3 Mode B：需求与代码对照

**适用场景**：用户同时提供了需求文档、验收标准、任务说明或 Bug 描述。

**分析流程**：先拆解需求 → 对照实现 → 有已读用例时核对断言 → 有执行记录时核对版本和结果。三项状态独立，不用测试覆盖状态代替实现结论。

```
需求
  ↓
实现证据
  ↓
测试证据
  ↓
覆盖状态
```

### 4.4 实现、覆盖与执行状态

| 维度 | 状态及判定 |
|------|---------|
| 实现情况 | 符合 / 冲突 / 未发现实现 / 待确认；检索范围不足或权限可能在中间件时保留待确认 |
| 测试覆盖 | 已覆盖 / 部分覆盖 / 未覆盖 / 未评估；有已读断言并匹配变化条件才认定覆盖，缺基线则未评估 |
| 执行结果 | 当前版本通过 / 失败 / 未执行 / 历史证据待复核；记录代码版本、环境、范围与结果来源 |

### 4.5 Mode B 示例

需求「只有管理员可以删除项目」，已检查路由、中间件与服务调用，确认普通成员可以删除；提供的完整用例清单没有权限拒绝断言，未提供执行记录：

```yaml
requirement: "只有管理员可以删除项目"
implementation_evidence: "已新增 DELETE /api/projects/:id 接口"
permission_evidence: "已检查路由/中间件/服务，普通成员路径没有拒绝条件"
test_evidence: "无用例覆盖权限拒绝场景"
implementation_status: "冲突"
coverage_status: "未覆盖"
execution_status: "未执行"
risk: "high"
suggested_test:
  - "[P0][安全/权限] 普通成员账号调用删除接口 → 应拒绝且项目数据不变；具体状态码待接口契约确认"
```

### 4.6 疑似超范围实现识别（Mode B 独有）

除检查「需求有没有实现」外，还要识别代码改动是否超出需求范围。

例如：需求只要求修改订单列表展示，但代码同时放开了订单导出权限。这不一定就是 Bug，也可能是必要的技术调整，但因为缺少明确需求依据、又可能影响用户行为，所以必须**单独标记**让产品、开发、测试一起确认。

### 4.7 Mode B 输出格式（追加到分析结果）

```yaml
requirement_traceability:
  - requirement_id: "REQ-001"
    requirement: "只有管理员可以删除项目"
    implementation_evidence: "已检查路由/中间件/服务，普通成员路径没有拒绝条件"
    test_evidence: "无用例覆盖权限拒绝"
    implementation_status: "冲突"
    coverage_status: "未覆盖"
    execution_status: "未执行"
    risk: "high"
out_of_scope_changes:
  - change: "订单导出接口去除了角色校验"
    related_requirement: "无（需求只要求修改订单列表展示）"
    risk: "high"
    action: "需产品/开发确认是否为预期改动"
```

## 5. 来源变更与定向复核（可选追溯输入）

- 消费 `traceability.sources`（id/location/version/availability）、`artifacts`（id/kind/version）和 `links`（upstream/downstream/confirmation/source/source_refs），保留原source/evidence_type。
- sources availability为available/unreachable/missing/unknown；links confirmation为confirmed/candidate。使用显式稳定产物ID，不以列表下标或SM展示编号建立长期关联。
- 先核对source_refs指向可达且明确版本的来源及关联依据，未满足时保留uncorroborated_links；再定位来源/需求ID与变更版本，沿有依据的confirmed链找风险、模型/场景、用例和执行证据；只把受影响结论标「需复核」，保留旧版本/证据，不能宣布旧测试已失败。
- candidate链只形成候选影响清单，记录需要核对的规则/调用依赖；不得将关键词同名升级为confirmed。
- 来源不可达只报告取证缺口；业务结果未知另报状态，两者不能互相替代。无追溯图时按现有Mode A/B继续，关系未评估而不是假装无影响。
- 同一产物被多条路径命中只记录一次复核项，附全部依据；只复核变更项的受影响范围，不重跑无关完整流程。

示例：优惠上限从30改为20，REQ-COUPON-CAP→SC-CAP→TC-COUPON-BOUNDARY有confirmed关系，
只复核对应优惠边界断言；无关联证据的登录用例保持原状态。同模块其他用例最多进入candidate，不自动失效。
