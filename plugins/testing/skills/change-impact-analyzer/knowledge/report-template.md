# 报告模板

> **何时阅读**：阶段 4 交付影响范围和测试内容时加载；默认按实际业务给工作表，复杂变更再展开详情。
> **覆盖范围**：格式与写作 / 工作表与详情 / P0-P2 / 场景模板 / 输出。完整 Mode B 示例见 [report-example.md](report-example.md)。

## 0. 选择格式与写作要求

- 用户要完整、面向测试人员的业务影响与测试方案时，加载 [业务方案模板](../templates/business-impact-test-scope.md)，按其业务顺序交付；本文件结构用于补充风险、回归和需求对照，不要求先堆技术清单。
- 简单改动或只要简表时用第 1 节工作表；不要为填模板扩写无关的迁移、支付、状态机或故障场景。用户已有指定格式时保留其格式并补齐信息。
- 正文先说谁做什么、哪里受影响、为什么、怎么操作和检查什么。业务标题用“保存账单资料”“导出订单”等动作；函数、字段、SHA 和完整路由放改动链或技术追溯。
- 改动链先用业务语言串起关键步骤，再给方法名和出处；方法第一次出现时说明它做什么，不能只有一串函数名。
- 一个段落说清一个原因或一个条件。合并重复说明，保留会改变结论的角色、数据状态、版本、开关、失败顺序和跳过条件。
- 用具体操作和结果替换“验证正常”“保障一致性”“完成闭环”；没有规则依据时写实际观察项和待确认。
- 术语确有作用时保留并就近解释（如“重投（再次发送同一个事件）”）；未知写“待确认”或“尚未验证”，不把可能改成确定。
- 交付前从测试人员角度检查：不翻源码，能否知道哪些业务要测、为什么、要什么数据、从哪操作、在哪检查结果、哪些结论不确定？

## 1. 工作表与报告详情

简单变更交付分析基线、业务工作表、回归建议和待确认即可；完整业务方案按第 0 节模板组织。工作表引用 CH/TS 标识，详情补证据与执行准备，不重复抄写同一场景。无用例时保留既有覆盖「未评估」，不能省略影响范围和测试内容。

```markdown
# 变更影响分析报告

> 生成时间：YYYY-MM-DD HH:mm
> 分析范围：[diff 描述]
> 代码版本：[base/head SHA 或材料版本；本地改动另注明]
> 用例基线：[来源/版本/完整程度；无或不可达则未评估]
> 分析模式：Mode A / Mode B

## 影响范围与测试内容工作表

| 实际业务操作 | 为什么受影响及边界 | 测试内容 | 测试方式与结果证据 | 优先级 | 依据与待确认 |
|---------------|-------------------|----------|--------------------|--------|-------------|
| 普通成员删除项目 | CH-001：已查路由/中间件/服务，成员进入删除；直接影响 | TS-001：成员尝试删除，检查拒绝及数据不变 | 业务 API 触发，核对响应和项目/关联数据 | P0 | 需求要求管理员；状态码待契约确认 |

工作表中的测试项在下面详情展开；短报告可直接在单元格写前置、操作、预期来源和观察项。

## 1. 分析范围

明确本次分析的是：当前工作区 / 暂存区 / 某个 Commit / 分支差异 / PR / 外部 Patch。
同时说明哪些模块已深入检查，哪些内容没有读取或无法验证。

## 2. 改动与需求摘要

区分三类信息（Mode A 默认输出，Mode B 追加需求对照）：
- 有直接代码证据的变化
- 根据代码推断的影响（标注置信度；不能把实现反推成需求）
- 需求与实现的匹配结论（Mode B）

## 3. 影响链路（技术追溯，可置于业务正文之后）

用表格串联：业务入口 → 前端 → 接口 → 后端 → 数据库或外部依赖。
并说明属于直接影响、间接回归、兼容性风险，还是部署和数据风险。

| 变更点 | 业务入口 | 前端 | 接口 | 后端 | 数据/外部 | 影响类型 |
|--------|---------|------|------|------|----------|---------|
| getUser 返回新增 avatar | 用户资料页 | pages/user-profile | GET /api/user/:id | UserService.getProfile | users.avatar | 直接影响 |
| 状态判断放开 state=2 | — | — | — | OrderService.refund | — | 间接回归 |

## 4. 风险结论

列出风险等级、判断原因和对应验证方式。高风险必须给出具体证据，不能仅靠"开发说改动很小"下调。

| 变更点 | 风险等级 | 判断原因 | 验证方式 |
|--------|---------|---------|---------|
| 删除接口未限制成员 | 高 | 已核对完整调用路径，成员没有拒绝条件；涉及权限+删除 | 权限拒绝场景必测 |
| 订单列表新增展示字段 | 低 | 仅展示调整，接口契约不变，无历史数据问题 | 界面回归 |

## 5. 按实际业务展开必测内容

每条场景采用统一结构（详见第 3 节测试场景模板）：

### [P0][API/权限] 普通成员无法删除他人项目

- **为什么受影响**：成员发起删除 → 路由/中间件未拒绝 → 删除服务；CH-001 使成员进入删除路径，直接影响权限与数据。已查路径之外的入口不据此宣称同样受影响。
- **前置条件**：普通成员账号已登录，拥有目标项目查看权限，但没有删除权限。
- **操作**：调用 `DELETE /api/projects/{id}`。
- **预期结果及来源**：
  - 拒绝删除（已确认需求：仅管理员可删除）；具体状态码待接口契约确认
  - 项目记录未被删除
  - 关联数据保持不变
- **观察项**：响应状态/错误体、项目及关联数据；未提供审计规则，不把日志内容写成验收标准。
- **测试方式与证据边界**：实际业务 API 验证拒绝结果和数据未变；单元测试可验证拒绝分支不调用删除服务，但不能替代数据库结果核对。
- **变更证据**：CH-001，路由/中间件/服务已读位置与代码版本。

## 6. 回归范围

回归范围拆成三类：

- **核心回归**：本次改动直接影响的功能和接口
- **定向回归**：通过链路追踪发现的间接影响（同接口多调用方、公共方法多业务方、数据流下游）
- **可不回归**：有明确隔离证据、与本次改动无关联的部分；注明排除理由和适用范围
- 已有自动化优先复用验证，标明需执行哪些断言；复用已有结果时核对代码/依赖/配置版本、环境及覆盖范围。用例存在或历史通过不能作为免验证依据。

| 回归类型 | 范围 | 原因 |
|---------|------|------|
| 核心回归 | 用户资料页、GET /api/user/:id | 直接修改 |
| 定向回归 | 退款页（同接口多调用方） | 间接影响 |
| 可不回归 | 订单导出（独立模块，无关联） | 隔离证据明确 |

## 7. 需求追踪矩阵（Mode B 独有）

Mode B 下逐条展示需求、实现情况、测试覆盖和执行结果；Mode A 跳过本节。

| 需求 ID | 实现证据与情况 | 测试证据与覆盖 | 执行结果与版本 | 风险 |
|---------|----------------|----------------|----------------|------|
| REQ-001：仅管理员可删除 | 已核对路由/中间件/服务，普通成员可删除；冲突 | 已读完整用例无拒绝断言；未覆盖 | 未执行 | 高 |

若仅未在一个文件看到权限判断，实现保持待确认，继续核对中间件；没有用例基线则测试覆盖为未评估。

疑似超范围实现单独列出：

| 变更点 | 关联需求 | 风险 | 后续动作 |
|--------|---------|------|---------|
| 订单导出去除角色校验 | 无 | 高 | 需产品/开发确认 |

## 8. 待确认与限制

可选追溯输入存在时，在本节列来源版本、confirmed 受影响结论、candidate 关联及最小复核动作；保留旧执行证据，区分来源不可达、业务结果未知和当前未执行。只定向复核受影响产物，不宣称整套用例失效。

把无法从代码确认的问题明确列出，而不是让 AI 自己补全答案。

- 状态 2 是否允许退款？（需产品确认）
- 老版本客户端是否必须兼容旧字段？（需客户端团队确认）
- 新字段为空时产品希望展示什么？（需设计确认）
- 本次修改是否需要处理历史数据？（需 DBA 确认）

### 报告限制说明

- 本报告基于代码变更推断，无法还原完整产品需求
- 涉及灰度开关、运营后台配置、第三方系统状态的内容需另行确认
```

## 2. P0 / P1 / P2 优先级划分

**优先级不是减少测试**，而是在时间有限时明确哪些问题必须在发布前发现。

| 优先级 | 定义 | 常见场景 |
|--------|------|---------|
| **P0** | 不通过就不建议发布 | 核心业务不可用；金额计算错误；数据可能丢失；权限可被绕过；数据库迁移失败；公共接口破坏性变化 |
| **P1** | 覆盖本次改动的核心行为 | 新增功能主流程；主要异常分支；核心状态转换；前后端契约；直接受影响的关联页面 |
| **P2** | 次要回归和低概率边界 | 非核心浏览器兼容；次要页面展示；较低概率异常；与改动距离较远但存在关联的流程 |

## 3. 测试场景模板

每条必测内容必须采用以下结构，**不能只写"验证 XX 是否正常"这种不可执行的描述**。

```
[优先级][测试类型]

前置条件：
- 数据准备、账号、权限、环境状态

为什么受影响与边界：
- 业务操作 → 已核对调用链 → 本次变化 → 触发/跳过条件 → 业务后果
- 直接影响 / 间接回归；调用关系未核实则标候选，不编造完整链

操作：
- 具体的执行步骤、入口、接口调用

预期结果及来源：
- 已确认需求/契约/规则的具体引用；代码观察行为另列
- 无业务依据时标待确认，不自行填写状态码、默认展示、重试次数

观察项：
- 状态码 / 页面状态 / 数据结果 / 事件 / 权限 / 回滚，按本次变化选择

测试方式与结果证据：
- 触发方式、所需数据/环境、观察位置、能证明的结果与未验证层
- 有部分更新/异步副作用时检查失败后的状态，相关恢复/重复触发规则待确认

证据：
- change_id、改动前后行为、调用关系、文件位置和来源版本

覆盖与执行（有材料时）：
- 已读用例及断言 / 覆盖状态 / 执行记录及版本；无基线则未评估
```

**反例（禁止）**：验证订单功能是否正常；验证接口是否正确；验证权限是否生效。

**正例**：

```
[P0][API/权限]

前置条件：
- 普通成员账号已登录，拥有目标项目查看权限，但没有删除权限。

操作：
- 调用 DELETE /api/projects/{id}

预期结果及来源：
- 拒绝删除（需求确认仅管理员可删除）；状态码待接口契约确认
- 项目记录未被删除
- 关联数据保持不变

证据：
- CH-001，路由/中间件/服务的已读位置与版本；未提供审计规则，不编造日志断言。
```

**业务组织与测试准备**：

- 业务名称用用户实际做的事，如「提交新手引导」「保存账单资料」，不以 `Upsert`、字段或服务名代替；未知入口如实标待核实。
- 同一业务可关联多个 CH，同一 CH 可影响多个业务。合并相同操作与结果，保留会改变结论的条件、版本或失败策略。
- 共用账号、数据状态和开关集中列准备表，注明服务版本和来源；迁移/回填/开关/回滚仅在相关时按阶段补充。
- 每项说明是业务验证、底层分支/数据库验证还是迁移发布验证。所有建议默认「未执行」；只有匹配当前版本、环境与范围的记录才标通过。

## 4. 报告输出

- **默认交付**：对话中的工作表与必要详情；仅用户要求写文件时使用 `docs/change-impact-report.md`
- **自定义路径**：用户可通过参数指定输出路径
- **文件名建议**：包含日期，如 `change-impact-report-2026-07-08.md`
