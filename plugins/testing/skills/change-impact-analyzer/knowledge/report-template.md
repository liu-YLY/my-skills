# 报告模板

> **何时阅读**：阶段 4 交付影响范围和测试内容时加载；默认按实际业务给工作表，复杂变更再展开详情。
> **覆盖范围**：工作表与可选详情 / P0/P1/P2 / 场景与预期来源 / 需求、覆盖、执行的独立状态。

## 0. 选择格式与写作要求

- 用户要完整、面向测试人员的业务影响与测试方案时，加载 [业务方案模板](../templates/business-impact-test-scope.md)。默认按其业务顺序交付；本文件后面的结构用于补充风险、回归和需求对照，不要求先堆技术清单。
- 简单改动或用户只要简表时，用第 1 节工作表；不要为了填模板扩写无关的迁移、支付、状态机或故障场景。用户已有指定格式时保留其格式，补齐相关信息。
- 模板参考[加密合规2-测试](https://app.notion.com/p/3f95974a71f78008ab42dcb3d9f29cf5)的组织方式，不将其中的业务数量、字段、系统或验收断言推广为所有项目的规则。
- 正文先说谁做什么、哪里受影响、为什么、怎么操作和检查什么。业务标题用“保存账单资料”“导出订单”等动作；函数、字段、SHA 和完整路由放必要的改动链或技术追溯，不代替业务解释。
- 改动链先用业务语言串起关键步骤，再给方法名和出处；方法第一次出现时说明它做什么。不能只有一串函数名，让读者自己推断后果。
- 一个段落说清一个原因或一个条件。合并重复说明，保留会改变结论的角色、数据状态、版本、开关、失败顺序和跳过条件；不能为了短而删掉边界。
- 用具体操作和结果替换“验证正常”“保障一致性”“完成闭环”。例如“保存后重新打开，检查页面和数据库是否都是新值”；没有规则依据时写实际观察项和待确认，不把例句当成统一验收标准。
- 专业术语确有作用时保留并就近解释，如“重投（再次发送同一个事件）”；不要把术语删掉后丢失故障或恢复条件。未知就写“待确认”或“尚未验证”，不通过润色将可能改成确定、设计改成已通过。
- 交付前从测试人员角度检查：不翻源码，能否知道哪些业务要测、为什么要测、需要什么数据、从哪操作、在哪里检查结果，以及哪些结论还不能确定？

## 1. 分析范围

明确本次分析的是：当前工作区 / 暂存区 / 某个 Commit / 分支差异 / PR / 外部 Patch。
同时说明哪些模块已经深入检查，哪些内容没有读取或无法验证。

## 2. 改动与需求摘要

区分三类信息（Mode A 默认输出，Mode B 追加需求对照）：
- 有直接代码证据的变化
- 根据代码推断的影响（标注置信度；不能把实现反推成需求）
- 需求与实现的匹配结论（Mode B）

## 3. 影响链路（技术追溯，可置于业务正文之后）

用表格串联：业务入口 → 前端 → 接口 → 后端 → 数据库或外部依赖。
并说明属于直接影响、间接回归、兼容性风险，还是部署和数据风险。

| 变更点 | 业务入口 | 前端 | 接口 | 后端 | 数据/外部 | 影响类型 |
|--------|---------|------|------|------|----------|---------|
| getUser 返回新增 avatar | 用户资料页 | pages/user-profile | GET /api/user/:id | UserService.getProfile | users.avatar | 直接影响 |
| 状态判断放开 state=2 | — | — | — | OrderService.refund | — | 间接回归 |

## 4. 风险结论

列出风险等级、判断原因，以及对应的验证方式。高风险必须给出具体证据，不能仅靠"开发说改动很小"下调。

| 变更点 | 风险等级 | 判断原因 | 验证方式 |
|--------|---------|---------|---------|
| 删除接口未限制成员 | 高 | 已核对完整调用路径，成员没有拒绝条件；涉及权限+删除 | 权限拒绝场景必测 |
| 订单列表新增展示字段 | 低 | 仅展示调整，接口契约不变，无历史数据问题 | 界面回归 |

## 5. 按实际业务展开必测内容

每条场景采用统一结构（详见第 3 节测试场景模板）：

### [P0][API/权限] 普通成员无法删除他人项目

- **为什么受影响**：成员发起删除 → 路由/中间件未拒绝 → 删除服务；CH-001 使成员进入删除路径，直接影响权限与数据。已查路径之外的入口不据此宣称同样受影响。
- **前置条件**：普通成员账号已登录，并拥有目标项目的查看权限，但没有删除权限。
- **操作**：调用 `DELETE /api/projects/{id}`。
- **预期结果及来源**：
  - 拒绝删除（已确认需求：仅管理员可删除）；具体状态码待接口契约确认
  - 项目记录未被删除
  - 关联数据保持不变
- **观察项**：响应状态/错误体、项目及关联数据；未提供审计规则，不把日志内容写成验收标准。
- **测试方式与证据边界**：实际业务 API 验证拒绝结果和数据未变；单元测试可验证拒绝分支不调用删除服务，但不能替代数据库结果核对。页面入口未读则页面表现待核实。
- **变更证据**：CH-001，路由/中间件/服务已读位置与代码版本。

## 6. 回归范围

回归范围拆成三类：

- **核心回归**：本次改动直接影响的功能和接口
- **定向回归**：通过影响链路追踪发现的间接影响（同接口多调用方、公共方法多业务方、数据流下游）
- **可不回归**：有明确隔离证据、与本次改动无关联的部分；注明排除理由和适用范围
- 已有自动化优先复用验证，标明需执行哪些断言；若复用已有执行结果，核对代码/依赖/配置版本、环境及覆盖范围。用例存在或历史通过不能作为免验证依据。

| 回归类型 | 范围 | 原因 |
|---------|------|------|
| 核心回归 | 用户资料页、GET /api/user/:id | 直接修改 |
| 定向回归 | 退款页（同接口多调用方） | 间接影响 |
| 可不回归 | 订单导出（独立模块，无关联） | 隔离证据明确 |

## 2. P0 / P1 / P2 优先级划分

为每条必测内容标注优先级，**优先级的意义不是减少测试**，而是在时间有限时明确哪些问题必须在发布前发现。

| 优先级 | 定义 | 常见场景 |
|--------|------|---------|
| **P0** | 不通过就不建议发布 | 核心业务不可用；金额计算错误；数据可能丢失；权限可以被绕过；数据库迁移失败；公共接口发生破坏性变化 |
| **P1** | 覆盖本次改动的核心行为 | 新增功能主流程；主要异常分支；核心状态转换；前后端接口契约；直接受到影响的关联页面 |
| **P2** | 次要回归和低概率边界 | 非核心浏览器兼容；次要页面展示；较低概率异常；与改动距离较远但存在一定关联的流程 |

## 3. 测试场景模板

每条必测内容必须采用以下统一结构，**不能只写"验证 XX 是否正常"这种不可执行的描述**。

```
[优先级][测试类型]

前置条件：
- 数据准备、账号、权限、环境状态

为什么受影响与边界：
- 业务操作 → 已核对调用链 → 本次变化 → 触发/跳过条件 → 业务后果
- 直接影响 / 间接回归；调用关系未核实则标候选，不编造完整链

操作：
- 具体的执行步骤、入口、接口调用

预期结果及来源：
- 已确认需求/契约/规则的具体引用；代码观察行为另列
- 无业务依据时标待确认，不自行填写状态码、默认展示、重试次数等

观察项：
- 状态码 / 页面状态 / 数据结果 / 事件 / 权限 / 回滚，按本次变化选择

测试方式与结果证据：
- 触发方式、所需数据/环境、观察位置、能证明的结果与未验证层
- 有部分更新/异步副作用时检查失败后的状态，相关恢复/重复触发规则待确认

证据：
- change_id、改动前后行为、调用关系、文件位置和来源版本

覆盖与执行（有材料时）：
- 已读用例及断言 / 覆盖状态 / 执行记录及版本；无基线则未评估
```

### 3.3 业务组织与测试准备

- 业务名称用用户实际做的事，如「提交新手引导」「保存账单资料」「更换支付方式」，不以 `Upsert`、字段或服务名代替业务标题；未知入口如实标待核实。
- 同一业务可关联多个 CH，同一 CH 可影响多个业务。合并相同操作与结果，保留条件、版本或失败策略会改变结论的分支。
- 共用账号、数据状态和开关集中列准备表，注明服务版本和来源；迁移/回填/开关/回滚仅在相关时按阶段补充。
- 每项说明是业务验证、底层分支/数据库验证还是迁移发布验证。所有建议默认「未执行」；只有匹配当前版本、环境与范围的记录才标通过。

- **预期结果**：
  - 接口返回 403

### [P0][API/权限] 订单导出权限范围待核实

- **为什么受影响及边界**：订单管理导出 → 导出接口 → 移除角色中间件 → 导出服务；直接影响入口限制，是否应允许成员待确认。

### [P1][兼容性] 历史用户空头像的读取与展示

- **为什么受影响及边界**：历史用户访问资料 → 查询接口 → users.avatar 空值 → 资料展示；空值消费路径需回归，默认占位策略未知。

- **操作**：登录该历史用户，访问 `/profile` 页面。
- **预期结果**：具体空值展示与接口行为待确认，不默认要求占位符或某个状态码。
- **观察项**：页面渲染、响应状态、空值传递与报错情况。
- **测试方式**：历史空值账号访问页面并检查接口响应；组件测试覆盖空值分支，不能代替实际页面验证。
- **证据**：users.avatar 为新增 nullable 字段，历史数据无值。
