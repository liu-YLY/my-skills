# 快速上手

> **何时阅读**：首次使用本 skill 或需快速了解触发方式与协同调用时查阅。
> **覆盖范围**：SKILL_ROOT 路径 / 触发示例 / testing-bundle 协同 / 单独安装边界。
> **可跳过条件**：已熟悉本 skill 触发与层间转交规则。

## SKILL_ROOT

`SKILL_ROOT` 为当前实际读取的 `SKILL.md` 所在目录。源码目录及运行时安装目录均有效；命令执行时使用该实际绝对路径，不硬编码仓库或个人目录。

## 快速触发示例

### 示例 1：电商下单接口性能测试方案（正向，plan）

**用户输入**：我们有一个电商下单接口，日常 QPS 约 500，大促峰值预计 3000 QPS，SLA 要求 P99 响应时间 ≤ 800ms，请帮我设计性能测试方案

**执行**：
- 阶段 1 需求与指标：保留用户峰值 3000 QPS 与 P99 RT ≤800ms；业务 TPS 与请求 QPS 映射、错误定义及错误率目标未提供，标待确认。
- 阶段 2 负载与场景：按峰值时段设计开放到达，列请求目标、实际发起及完成量；容量另按有效稳态档观察；疲劳可选，时长按业务周期确认。
- 交付前自检：披露方案、假设和待确认项；仅用户要求逐阶段审阅、缺资料、改变范围或未授权执行压测时暂停。
- 阶段 3/4：本例为正向方案设计，无性能数据，不适用。

**输出摘要**：
- 负载模型：峰值测试（验证大促瞬时峰值）+ 容量测试（验证本环境持续吞吐边界，区分 QPS 与业务 TPS）。
- 场景清单：基线（单用户基线）→ 阶梯递增（3000 QPS 验证达标）→ 峰值（按保护条件停止）→ 可选疲劳（持续采集，不由固定 4h 证明泄漏）。
- 指标阈值表：用户目标为峰值 3000 QPS 与 P99 RT ≤800ms；P999/错误率/CPU/内存阈值待确认，不套模板值。

### 示例 2：TPS 上不去 + CPU 低的瓶颈定位（diagnose）

**用户输入**：线上接口 TPS 上不去，加压到 800 就开始报超时，CPU 才 40%，请帮我定位瓶颈

**执行**：
- 阶段 3 瓶颈定位：现象收集（加压到 800 开始超时、总体 CPU 40%；800 的单位、实际 TPS 及 RT 分布待补）。
- 按最强证据选择起点，交叉核对：
  - 应用层：GC 频率、线程状态、连接池占用、慢 SQL。
  - 资源层：USE 方法补齐单核、runqueue、IO、网络证据；同时核对发压机；总体 CPU 40% 不能排除单核、队列或停顿。
  - 架构层：DB 连接池规格、缓存命中、限流配置。
- 阶段 4 归属与转交：候选为连接池、单核/GC、发压机及依赖；证据不足不宣布瓶颈。

**输出摘要**：
- 已知现象不能确认瓶颈归属；连接池、单核/GC、发压机及依赖均为待验证候选。
- 最小补采：同时间窗目标/实际到达率、RT/错误分类、单核/队列、连接池占用/等待与依赖；不补造占用 100%。
- 先验证候选：对比连接池等待与 DB 查询、发压调度和单核热点；证据支持后才建议对应优化。
- 转交：若证据指向 N+1/错误 join/连接未释放等代码缺陷 → bug-analyzer；缺索引、资源不足、配置问题留在本 skill。

### 示例 3：P95 RT 陡增但 CPU/内存正常（diagnose）

**用户输入**：我们的系统最近加压测试时发现 P95 响应时间在并发 500 时从 200ms 陡增到 2s，但错误率没变，CPU/内存都正常，请分析原因

**执行**：
- 阶段 3 瓶颈定位：现象收集（P95 陡增、CPU/内存总体正常、错误率不变）。
- 按最强证据核对应用/资源/依赖：GC 停顿、线程阻塞/锁等待、磁盘 await、网络重传、缓存命中、DB 锁等待、限流、发压机。
- 对照 [knowledge/bottleneck-patterns.md](../knowledge/bottleneck-patterns.md) 六类瓶颈模式形成可证伪候选。

**输出摘要**：
- 候选清单（按证据优先级，均未确认）：磁盘 IO 饱和、锁竞争、缓存命中下降、GC 停顿。
- 每项给最小验证：iostat/await、线程 dump、缓存命中率、GC 日志与堆快照。
- 转交：仅当线程 dump 显示死锁、GC 日志/堆快照显示泄漏、或链路显示 N+1 等代码缺陷 → bug-analyzer；资源/配置类留在本 skill。

## 与 testing-bundle 协同调用

本 skill 是 `testing-bundle` 的子 skill（性能测试方向）。bundle 负责意图判断与路由，本 skill 负责性能测试执行。

**协同流程**：

```
用户：帮我设计性能测试方案
testing-bundle → 意图判断：性能测试 → 路由到 performance-test-engineer
performance-test-engineer → 按 plan 路径执行阶段 1~2
```

**路由规则**（由 testing-bundle 执行，本 skill 不感知）：

| 用户意图 | 路由目标 |
|----------|----------|
| 性能测试 / 负载测试 / 压力测试 / 瓶颈定位 / 容量评估 | performance-test-engineer |
| 功能用例生成 | test-case-engineer |
| 功能 Bug 根因分析 | bug-analyzer |

**层间转交**（本 skill 与 bug-analyzer，由 bundle 衔接）：

| 转交方向 | 触发条件 | 携带内容 |
|----------|----------|----------|
| 本 skill → bug-analyzer | 证据指向代码逻辑缺陷（死锁、N+1/错误 join、内存泄漏、连接未释放、死循环、正则回溯） | 瓶颈定位报告 + 已收集性能数据 + 怀疑代码模块 |
| bug-analyzer → 本 skill | 根因指向资源/架构瓶颈（连接池不足、扩容需求、缓存未命中、DB 分库分表、限流缺失） | 根因报告 + 资源/架构层怀疑点 |

## 单独安装时的能力边界

本 skill 单独安装（无 testing-bundle）时，行为边界如下：

| 能力 | testing-bundle 下 | 单独安装 |
|------|-------------------|----------|
| 入口路由 | bundle 自动判断意图并路由 | 用户直接调用本 skill |
| 与 bug-analyzer 转交 | bundle 自动衔接两 skill | 用户手动衔接：复制本 skill 输出的瓶颈定位报告，作为 bug-analyzer 输入 |
| 与 test-case-engineer 协同 | bundle 可调度 | 用户手动衔接 |

**单独使用触发方式**：用户直接给出性能测试 / 瓶颈定位相关输入即可触发，无需 bundle 介入。

**转交需手动衔接的场景**：本 skill 阶段 4 判定证据指向代码逻辑缺陷时，输出转交提示（含瓶颈定位报告 + 怀疑代码模块）。现有授权包含代码诊断且下游可用时携带上述材料继续转交；下游不可用时交付可复用材料并说明手动转交路径，不声称已执行转交。
