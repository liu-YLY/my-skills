# 瓶颈模式知识库

> **何时阅读**：定位阶段需要识别瓶颈类型、选择优化方向时查阅。
> **覆盖范围**：CPU / IO / 网络 / 锁 / 连接池 / GC 六类模式、传导链、反例。

## 层边界声明（必读）

本库聚焦资源/架构层。锁竞争、GC 停顿、慢 SQL（缺索引/全表扫描）、连接池不足等先按资源/架构层排查；只有证据指向代码逻辑缺陷时才转交 `bug-analyzer`。

| 层级 | 范围 | 典型问题 | 处理方 |
|------|------|----------|--------|
| 资源/架构层 | CPU/IO/网络/锁/连接池/GC 等系统级饱和或架构问题 | 慢 SQL（缺索引）、锁竞争、堆配置不当、带宽打满 | 本库 |
| 代码逻辑层 | 代码逻辑缺陷 | 死锁、N+1/错误 join、内存泄漏、连接未释放、死循环、正则回溯 | bug-analyzer |

**判断规则**：先排查发压机、测试数据、限流、网络与共享依赖；按同时间窗最强证据选起点，交叉核对资源、应用与代码。资源饱和可由代码缺陷引起，不能仅凭饱和决定归属；本表数字为排查示例。

## 1. CPU 飙升

| 现象 | 定位指标 | 根因候选 | 优化方向 | 转交 |
|------|---------|---------|---------|------|
| CPU >80%、runqueue > 核数×1（持续）、上下文切换激增 | CPU 总体+单核、runqueue、上下文切换、火焰图 | 死循环、正则回溯、序列化开销、GC 频繁、计算密集 | 算法优化、缓存、异步化、水平扩容 | 死循环/正则回溯等逻辑缺陷 → 转交 |

定位：`top`/`mpstat` 区分 sys/user；sys 高查上下文切换和系统调用，user 高用火焰图定位热点；先排除 GC 假性飙升，再判断算法问题或代码缺陷。

## 2. IO 等待

| 现象 | 定位指标 | 根因候选 | 优化方向 | 转交 |
|------|---------|---------|---------|------|
| iowait 高、磁盘队列深、RT 抖动 | iowait%、IOPS、带宽、队列深度、iostat | 慢 SQL、缺索引、日志同步写、磁盘性能差、随机 IO 多 | 加索引、读写分离、缓存、SSD、异步日志 | SQL 逻辑错误（N+1）→ 转交 |

定位：`iostat -x 1` 区分 IOPS 或带宽瓶颈、看 await；慢 SQL 用 `pt-query-digest`/慢日志定位；缺索引/全表扫描属本库，N+1/错误 join 转 bug-analyzer。

## 3. 网络延迟

| 现象 | 定位指标 | 根因候选 | 优化方向 | 转交 |
|------|---------|---------|---------|------|
| RT 高但 CPU/IO 低、跨机房慢 | 网络延迟、带宽、重传率、TCP 连接数 | 跨机房调用、带宽打满、DNS 慢、连接复用差、防火墙 | 就近部署、连接池、CDN、压缩、批量化 | 一般不转交 |

定位：`ping`/`traceroute`/`mtr` 区分网络层与应用层；重传高查带宽/网卡，DNS 慢查解析；应用层 RT 高而网络正常时查连接复用与序列化。

## 4. 锁竞争

| 现象 | 定位指标 | 根因候选 | 优化方向 | 转交 |
|------|---------|---------|---------|------|
| CPU 不高但 TPS 上不去、线程等待长 | 线程阻塞时间、锁等待、synchronized/lock 竞争 | 粗粒度锁、锁范围大、热点竞争、死锁 | 锁细化、无锁结构、分段锁、乐观锁、异步化 | 死锁等代码缺陷 → 转交 |

定位：`jstack`/`arthas` 抓线程 dump，统计 BLOCKED；锁等待长而 CPU 低是典型特征；粗锁细化、热点分段。锁竞争本身按本库优化；只有线程 dump 指向死锁或锁用法代码缺陷时才转交。

## 5. 连接池耗尽

| 现象 | 定位指标 | 根因候选 | 优化方向 | 转交 |
|------|---------|---------|---------|------|
| 请求排队、连接超时、TPS 到顶后错误率飙升 | 连接池使用率、等待线程数、连接持有时间 | 池过小、连接泄漏、慢查询占连接、未释放 | 扩容、查泄漏、慢查询优化、超时配置 | 连接泄漏（未 close）→ 转交 |

定位：监控 active/idle/wait，wait 持续增长即耗尽；长持有查慢查询/未释放，短持有但池小则扩容；连接不归还查代码未 close 路径并转交。

## 6. GC 停顿

| 现象 | 定位指标 | 根因候选 | 优化方向 | 转交 |
|------|---------|---------|---------|------|
| 周期性 RT 陡增、TPS 周期下跌、日志无异常 | GC 频率/耗时、堆占用、Full GC 次数 | 堆太小、对象创建过快、内存泄漏、大对象、FGC 频繁 | 扩堆、调 GC 参数、减少对象创建、对象池 | 内存泄漏 → 转交 |

定位：`jstat -gc`/GC 日志看 YGC/FGC 频率与耗时；FGC 频繁且耗时长是候选，需对齐停顿与 RT 时间窗并做可恢复对照；堆上涨核对 GC 后存活量与保留链。堆配置/GC 参数属本库，有泄漏证据再转交。

## 瓶颈传导链

一个瓶颈未及时处理会引发连锁反应，必须沿链追溯根因，否则治标不治本。

| 传导链 | 起点 → 中间 → 终点 | 治标风险 |
|--------|---------------------|----------|
| 1 | GC 停顿 → 请求堆积 → 连接池耗尽 → 错误率飙升 | 只扩连接池不解决 GC，延迟复发 |
| 2 | 慢 SQL → 连接占用久 → 连接池耗尽 → 上游超时级联 | 只调超时阈值不优化 SQL，问题转移 |
| 3 | 锁竞争 → 线程阻塞 → CPU 看似低 → 误判容量足继续加压 | 加压加剧锁竞争，TPS 反降 |
| 4 | 网络抖动 → 重试风暴 → 下游请求翻倍 → 下游 CPU 飙升 | 只扩下游不治理重试，越扩越崩 |
| 5 | 日志同步写 → IO 队列深 → 请求线程阻塞 → RT 整体抬升 | 只扩磁盘不改异步日志，IO 仍饱和 |

分析：从最终错误倒推，每步问「为什么会这样」；每环节要有指标证据，禁止跳跃；最早可观测环节不必是真根因，核对上下游、反证与对照，缺链路时保留候选并补采。

## 反例

- 把代码逻辑缺陷当性能瓶颈（如 NPE 导致错误率上升）→ 转 bug-analyzer。
- 只看单一指标下结论（CPU 高就断定 CPU 瓶颈）→ 排除 GC 假性飙升，多指标交叉验证。
- 修了连接池但根因是慢 SQL → 沿传导链追溯起点，对起点优化。
- 没有指标就断定「加机器/拆服务」→ 先用资源层指标证明饱和，再做架构判断。
- 看到 RT 高就加缓存 → 先定位网络/锁/IO/GC 根因，再选方案。
- 发现瓶颈直接说「扩容解决」→ 扩容是缓解不是定位，必须给出根因和根治方案。

## 协作

- 需生成压测用例验证优化效果 → 输出性能测试点清单，转交 test-case-engineer。
- 根因涉及代码逻辑缺陷 → 转交 bug-analyzer，附已定位的资源层证据。
