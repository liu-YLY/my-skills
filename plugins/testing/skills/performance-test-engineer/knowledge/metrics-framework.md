# 指标体系

> **何时阅读**：设计压测方案、采集性能数据、判定瓶颈位置时。
> **覆盖范围**：吞吐 / RT / 错误率 / 资源利用率四项指标、阈值参考、相互关系、采集建议。

**证据口径**：文中数字均为工具或排查示例；除非有业务合同、已批准目标或同环境历史基线，不作为达标承诺或容量硬门槛。报告逐项标来源，缺依据标「待确认」。

## 1. 四项核心指标

### 1.1 负载与吞吐

- 分列请求数/秒（RPS；查询类可用 QPS）、业务事务数/秒（TPS）、迭代数/秒和并发用户数，标注计量对象与统计边界。
- 同一时间窗分列计划发起、实际发起、未发起和完成；封闭方式通常只有并发目标，计划发起可不适用。
- 区分按完成时间统计的总吞吐与按发起批次追踪的完成量：本窗完成可含上窗发起，本窗发起也可能在下窗结束。缺数标未知，未发起和在途不计作服务端失败。

### 1.2 响应时间 RT

| 分位数 | 含义 | 用途 |
|--------|------|------|
| P50 | 中位数 | 典型用户体验 |
| P95 | 95 分位 | 大多数用户体验的下限 |
| P99 | 99 分位 | 长尾体验，SLA 核心指标 |
| Max | 最大值 | 最差体验，易受噪声干扰 |

采集位置：客户端含网络往返、序列化和发压机调度开销，用于评估真实体验；服务端为纯处理时间，用于定位自身瓶颈。

观察：P99 与 P50 差距 >3 倍提示长尾，追查 GC、锁竞争或慢查询；RT 陡增是异常观测点，需核对发压机、排队与依赖证据，不能单独定承载上限；分位数发散是排队开始的信号。

### 1.3 错误率

定义：失败请求数 / 总请求数。采集：压测工具断言 + 服务端日志 + APM 错误追踪。

| 类型 | 表现 | 责任方 |
|------|------|--------|
| 业务错误 | HTTP 4xx（参数错、鉴权失败、业务拒绝） | 调用方 / 业务逻辑 |
| 系统错误 | HTTP 5xx（空指针、依赖崩溃、OOM） | 服务提供方 |
| 超时 | 客户端 / 网关 / 数据库超时 | 多方定位 |
| 断言失败 | 压测脚本断言未通过（字段缺失/值错） | 接口契约问题 |

观察：首次非零错误只触发分类排查；测试数据 4xx、限流 429 或下游波动不能直接定容量。先超时后 5xx 是资源耗尽的典型演变；单机集中查负载不均，全机同步查数据、网关、限流或共享依赖。

### 1.4 资源利用率

至少覆盖 CPU、内存、磁盘 IO、网络，关注总体与单核、GC 频率与停顿、IOPS/带宽/await、重传率。四类资源的 USE 检查项、采集命令与示例阈值见 [use-method.md](use-method.md) §2，本文件不重复。

观察：利用率 80%/90% 仅为排查示例，须结合持续时长、队列/等待与基线；饱和度信号包括 CPU runqueue > 核数（持续）、iowait >20%、GC STW 持续上升；总体 CPU 不高但单核 100% 提示串行化候选（锁、单线程模型）。

## 2. 指标阈值参考

以下为讨论起点，正式 SLA 以业务合同或已批准目标为准；未确认时不得据此宣布达标或失败。

| 业务类型 | P99 RT | 错误率 | CPU 利用率 | 备注 |
|---------|--------|--------|-----------|------|
| 互联网应用（C 端） | ≤ 500ms | ≤ 0.1% | ≤ 70% | 用户体验优先 |
| 互联网应用（B 端） | ≤ 1s | ≤ 0.5% | ≤ 75% | 容忍度略高 |
| 金融交易 | ≤ 200ms | ≤ 0.01% | ≤ 60% | 强一致 + 低延迟 |
| 物联网/设备上报 | ≤ 2s | ≤ 1% | ≤ 80% | 海量低频 |
| 内部管理后台 | ≤ 2s | ≤ 1% | ≤ 80% | 低优先级 |

## 3. 指标间关系

### 3.1 Little's Law

**L = λW**：L 为系统内平均并发数，λ 为到达率（请求/秒），W 为平均响应时间（秒）。

仅在稳定、无持续队列积累的同一系统边界内，用平均到达率和平均停留时间估算平均在途数；不能将 P99、线程数或活跃用户数直接代入。例如实测 1,000 请求/秒、同边界平均停留 0.2 秒，对应约 200 个平均在途请求。

### 3.2 RT 陡增与 TPS 上限

TPS 平台期与 RT 上升提示排队候选，不保证线性增长；发压能力、限流、数据或依赖同样可造成平台期，须交叉验证。

- **异常观测点**：首次出现陡增、错误或平台期，记录并排查。
- **SLA 边界**：按已确认目标、流量配比、统计窗口和失败定义识别超限档。
- **容量边界**：对发压能力、业务数据、限流、网络和依赖完成反证，重复验证最大通过档与首个失败档；只报告该环境下的区间、持续时长和限制，未测到失败档则仅报已验证下界。

### 3.3 错误率与资源饱和

资源饱和后错误率突增是过载信号，典型演变：利用率上升 → RT 陡增 → 超时 → 5xx（连接池/OOM/线程打满）。因果需同时间窗证据，不能只看错误总数。

## 4. 采集建议

| 维度 | 要求 |
|------|------|
| 采样频率 | 持续采集完整加压过程；常规资源示例 1Hz，按短时事件尺度与开销调整；请求量、错误分类及 RT 分布保留统计，抽样/聚合披露损失；瞬时耗尽补事件或日志 |
| 采样窗口 | 保存全过程原始数据，按预热、稳态、加压和恢复分段报告；不固定删除前后 10% 来掩盖异常 |
| 冷启动排除 | 稳态容量单列实际预热条件；冷启动体验属于目标时必须另报，不能丢弃 |
| 多机采样 | 分布式系统分机器采样并汇总，禁止只看一台 |
| 时间对齐 | 压测工具与服务端日志时间戳 NTP 同步，偏差 <1s |

## 5. 反例

| 反例 | 正确做法 |
|------|---------|
| 只看平均值不看分位数 | 同时报告 P50/P95/P99/Max |
| 忽略冷启动数据 | 保留原始数据并分列冷启动与稳态，不按固定比例删除 |
| 只看一台机器的资源 | 分机器采样，单机利用率单独报告 |
| TPS 到顶后继续加压看 RT | 按预定终止条件停止并记录异常点，排除发压/限流/数据/依赖后再验证容量区间 |
| 混淆客户端 RT 与服务端 RT | 两端分别采集，定位瓶颈时对照差异 |
| 用压测机 CPU 占用判断服务负载 | 监控发压机 CPU、调度滞后、目标/实际到达率；先验证发压瓶颈再调整 |
| 错误率只看总数不分类型 | 按状态码 + 超时 + 断言失败分类统计 |
