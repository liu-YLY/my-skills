# 指标体系

> **何时阅读**：设计压测方案、采集性能数据、判定瓶颈位置时查阅。
> **覆盖范围**：吞吐量 / 响应时间 / 错误率 / 资源利用率 四项核心指标的定义、采集、阈值与相互关系。

**证据口径**：下文数字均为工具或排查示例，除非有业务合同、已批准目标或同环境历史基线，不作为达标承诺或容量硬门槛。报告逐项标来源；缺依据时标待确认。

## 1. 四项核心指标

### 1.1 TPS / QPS（吞吐量）

| 属性 | 说明 |
|------|------|
| **定义** | 单位时间内系统处理的请求数（事务/秒 或 查询/秒） |
| **采集方式** | 压测工具原生统计（JMeter Summary Report / Wrk / Locust Stats）；APM 全量采集 |
| **关键观察点** | 随并发上升的拐点；稳态值（持续 N 分钟不下降）；加压后不再增长的顶点 |
| **单位选择** | TPS 面向事务（含多步），QPS 面向单次查询；同一报告内禁止混用 |

### 1.2 响应时间 RT（延迟）

| 分位数 | 含义 | 用途 |
|--------|------|------|
| **P50** | 中位数 | 反映典型用户体验 |
| **P95** | 95 分位 | 反映大多数用户体验的下限 |
| **P99** | 99 分位 | 反映长尾用户感受，是 SLA 核心指标 |
| **Max** | 最大值 | 反映最差体验，但易受噪声干扰 |

| 采集位置 | 含义 | 适用场景 |
|----------|------|----------|
| **客户端采集** | 包含网络往返、序列化、压测机调度开销 | 评估真实用户体验 |
| **服务端采集** | 纯处理时间（从接收请求到发出响应） | 定位服务自身瓶颈 |

| 关键观察点 | 说明 |
|------------|------|
| **P99 与 P50 差距** | 差距 > 3 倍即存在长尾问题，需追查 GC / 锁竞争 / 慢查询 |
| **随并发的陡增点** | RT 陡增是异常观测点；核对负载机、排队与依赖证据，不能单独定承载上限 |
| **分位数发散** | 高并发下 P99 远离 P50，是排队效应开始的信号 |

### 1.3 错误率

| 属性 | 说明 |
|------|------|
| **定义** | 失败请求数 / 总请求数 |
| **采集方式** | 压测工具断言统计 + 服务端日志 + APM 错误追踪 |

**错误分类**：

| 类型 | 表现 | 责任方 |
|------|------|--------|
| 业务错误 | HTTP 4xx（参数错、鉴权失败、业务规则拒绝） | 调用方 / 业务逻辑 |
| 系统错误 | HTTP 5xx（空指针、依赖崩溃、OOM） | 服务提供方 |
| 超时 | 客户端超时 / 网关超时 / 数据库超时 | 多方定位 |
| 断言失败 | 压测脚本断言未通过（响应体字段缺失/值错） | 接口契约问题 |

| 关键观察点 | 说明 |
|------------|------|
| **突增并发阈值** | 首次非零错误仅触发分类排查；测试数据4xx、限流429或下游波动不能直接定容量上限 |
| **错误类型切换** | 先出现超时、后出现 5xx，是资源耗尽的典型演变 |
| **错误分布** | 单机集中可疑负载不均；全机同步也可能是数据、网关、限流或共享依赖故障，需验证 |

### 1.4 资源利用率

| 资源 | 指标 | 关键观察点 |
|------|------|------------|
| **CPU** | 总体利用率 + 单核利用率 | 单核100%与总体30%提示局部热点候选；核对profiling与队列，总体80%仅排查示例 |
| **内存** | 已用 / 可用 + GC 频率与耗时 | Full GC每分钟1次或STW200ms仅排查示例，须对齐RT和停顿窗口 |
| **磁盘 IO** | IOPS + 吞吐带宽 + await | await20ms或util80%仅排查示例，结合存储基线、队列和延迟验证 |
| **网络** | 入站带宽 + 出站带宽 + 重传率 | 重传1%或带宽90%仅线索，核对丢包/限速/队列与同窗口流量 |

| 采集工具 | 适用场景 |
|----------|----------|
| node_exporter + Prometheus | Kubernetes / 容器化环境，持续采集 |
| top / htop | 快速查看 CPU 与内存，单机定位 |
| iostat -x 1 | 磁盘 IO 详细指标（await、util、svctm） |
| sar -n DEV 1 | 网络流量与重传，历史回溯 |
| pidstat 1 | 进程级 CPU / 内存 / IO 归因 |

| 关键观察点 | 说明 |
|------------|------|
| **利用率阈值** | 80%/90% 是排查示例；结合持续时长、队列/等待与基线确认，不能由利用率单独判饱和 |
| **饱和度信号** | CPU runqueue > 核数 × 1（持续）、iowait > 20%、GC STW 持续上升 |
| **单核打满** | 总体 CPU 不高但单核 100% → 串行化瓶颈（锁、单线程模型） |

## 2. 指标阈值参考表

以下是业务类型的讨论起点，正式 SLA 以业务合同或已批准目标为准；未确认时不得据此宣布达标/失败：

| 业务类型 | P99 RT | 错误率 | CPU 利用率 | 备注 |
|---------|--------|--------|-----------|------|
| 互联网应用（C 端） | ≤ 500ms | ≤ 0.1% | ≤ 70% | 用户体验优先 |
| 互联网应用（B 端） | ≤ 1s | ≤ 0.5% | ≤ 75% | 容忍度略高 |
| 金融交易 | ≤ 200ms | ≤ 0.01% | ≤ 60% | 强一致 + 低延迟 |
| 物联网/设备上报 | ≤ 2s | ≤ 1% | ≤ 80% | 海量低频 |
| 内部管理后台 | ≤ 2s | ≤ 1% | ≤ 80% | 低优先级 |

## 3. 指标间关系

### 3.1 Little's Law

公式：**L = λW**

| 符号 | 含义 | 单位 |
|------|------|------|
| L | 系统内平均并发数 | 个 |
| λ | 到达率（吞吐量） | 请求/秒 |
| W | 平均响应时间 | 秒 |

**应用场景**：稳定、无持续队列积累的同一系统边界中，以平均到达率和平均停留时间估算平均在途数；不能将 P99、线程数或活跃用户数直接代入。

**示例**：
```
目标：TPS = 1000，RT = 0.2s
推算：L = 1000 × 0.2 = 200
结论：在上述稳态假设下平均在途请求约200；实际发压用户数还受思考时间、客户端调度和重试影响，不能保证压出1000 TPS
```

### 3.2 RT 陡增与 TPS 上限

TPS 平台期与 RT 上升提示排队候选，不保证线性增长；以下仅为示意。发压能力、限流、数据或依赖同样可造成平台期，须交叉验证。

- 异常观测点：首次出现陡增、错误或平台期，记录并排查。
- SLA 边界：按已确认目标、流量配比、统计窗口和失败定义识别超限档。
- 容量边界：对发压能力、业务数据、限流、网络和依赖完成反证，重复验证最大通过档与首个失败档；只报告该环境下的区间、持续时长和限制，未测到失败档则仅报已验证下界。

```
并发 100  → TPS 500, RT 200ms  （正常）
并发 200  → TPS 1000, RT 200ms （线性扩展）
并发 400  → TPS 1000, RT 400ms （顶点，开始排队）
并发 800  → TPS 1000, RT 800ms （纯排队，TPS 已封顶）
```

### 3.3 错误率与资源饱和

资源饱和后错误率突增是典型过载信号。常见演变顺序：

1. 资源利用率上升至 > 80%
2. RT 开始陡增（排队）
3. 出现超时（客户端或网关）
4. 出现 5xx（连接池耗尽、OOM、线程打满）

## 4. 采集建议

| 维度 | 要求 |
|------|------|
| **采样频率** | 持续采集完整加压过程；常规资源示例1Hz，按短时事件尺度与开销调整；请求数量、错误分类及RT分布保留统计，抽样/聚合须披露损失；瞬时耗尽补事件或日志 |
| **采样窗口** | 保存全过程原始数据，按实测稳态、预热、加压和恢复分段报告；不固定删除前后10%来掩盖异常 |
| **冷启动排除** | 稳态容量单列实际预热条件；冷启动体验属于目标时必须另报，不能丢弃 |
| **多机采样** | 分布式系统分机器采样 + 汇总，禁止只看一台 |
| **时间对齐** | 压测工具时间戳与服务端日志时间戳必须 NTP 同步，偏差 < 1s |

## 5. 反例（不要这样做）

| 反例 | 后果 | 正确做法 |
|------|------|----------|
| 只看平均值不看分位数 | 平均 100ms 可能掩盖 P99 = 2s 的长尾问题 | 同时报告 P50 / P95 / P99 / Max |
| 忽略冷启动数据 | 把预热期的高 RT 当成系统性能差 | 保留原始数据并分列冷启动与实测稳态，不按固定比例删除 |
| 只看一台机器的资源 | 漏掉负载不均导致的单点瓶颈 | 分机器采样，单机利用率单独报告 |
| TPS 到顶后继续加压看 RT | 误以为系统"变慢"，实际是过载排队 | 按预定终止条件停止并记录异常点，排除发压/限流/数据/依赖后再验证容量区间 |
| 混淆客户端 RT 与服务端 RT | 网络开销被算进处理时间，误判服务慢 | 两端分别采集，定位瓶颈时对照差异 |
| 用压测机 CPU 占用判断服务负载 | 压测机自身瓶颈被当成服务瓶颈 | 监控发压机CPU、调度滞后、目标/实际到达率；70%仅示例线索，先验证发压瓶颈再调整 |
| 错误率只看总数不分类型 | 4xx 业务错误与 5xx 系统错误混为一谈，无法定位 | 按状态码 + 超时 + 断言失败分类统计 |
