# Test Case Engineer Skill

> AI 赋能的测试用例工程师技能，自动生成高质量测试用例。当前版本 v8.5.0。v8.0.0 起由原 test-engineer 拆分而来，专注正向用例生成。

## 简介

Test Case Engineer 是一个 AI 驱动的测试技能，扮演资深测试工程师角色，能够：

- **需求分析**：深入理解需求文档，提取业务规则和测试点
- **测试点提取**：系统性扫描 7 个维度，确保测试覆盖无遗漏
- **用例生成**：AI 生成 70%-90% 的基础用例，人工审核补充
- **用例评审**：10 维度评审已有用例的质量与覆盖度
- **产品知识库**：按产品维度沉淀业务知识，增强测试针对性

> Bug 根因分析能力已迁移至独立的 bug-analyzer skill。

## 适用场景

| 场景 | 说明 |
|------|------|
| 编写测试用例 | 从需求文档自动生成完整测试用例 |
| 评审测试用例 | 检查用例质量和覆盖度 |
| 需求分析 | 提取业务规则和测试点 |
| 测试策略设计 | 确定测试范围和优先级 |

> Bug 根因分析、缺陷定位请使用 bug-analyzer skill。

## 核心工作流

```
阶段 1: 理解需求 → 阶段 2: 提取测试点 → 阶段 3: 编写用例 → 阶段 4: 自检补全
```

每个阶段设有 CHECKPOINT，需用户确认后才能进入下一阶段。完整的四阶段流程、失败模式与 Fallback、CHECKPOINT 详情见 [test-case-engineer-core.md](test-case-engineer-core.md)。

**模式选择**：

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| 默认 | 完整四阶段流程 | 正式测试用例编写 |
| 快速 | 压缩阶段 1/4 | 时间紧迫、快速出测试点 |
| 回归验证清单 | 跳过阶段 1/2，直接输出回归验证清单 | 纯重构无行为变更 |
| 探索式 | 额外输出探索章程 | 新功能探索、风险评估 |
| 评审 | 10 维度评审，可选调用 review-checker MCP Server | 评审已有测试用例的质量与覆盖度 |

> 评审模式独立于四阶段生成流程，详见 [knowledge/review-mode.md](knowledge/review-mode.md)。

> **增量评审前置条件**：增量评审子模式需在 git 仓库内执行，依赖 `git diff` 提取变更用例。若用例文件不在 git 仓库中，将自动降级为全量评审。

## 使用方式

### 快速开始

1. **确定模式**：根据场景选择默认/快速/回归验证清单/探索式/评审模式
2. **提供输入**：
   - 需求文档（Word/PDF/Markdown）
   - 或用户描述
   - 或代码变更
3. **执行流程**：
   - 按阶段 1→2→3→4 顺序执行（默认模式）
   - 每个阶段完成后等待用户确认
   - 遇到问题查阅对应知识库文件

### 示例对话

```
用户：我有一个用户登录功能需要测试，需求如下：用户通过手机号+验证码登录...

AI（test-case-engineer）：
## 阶段 1: 需求理解

**功能概述**：用户通过手机号+验证码登录系统

**用户角色**：
- 普通用户
- 管理员

**业务规则**：
1. 手机号格式为 11 位数字
2. 验证码为 6 位数字，有效期 5 分钟
3. 支持记住登录状态 7 天

[展示给用户确认后继续阶段 2...]
```

## 常见问题

### Q: 如何快速生成测试用例？
A: 使用快速模式，提供需求文档或描述，AI 会自动生成测试点清单和基础用例。

### Q: AI 生成的用例质量如何保证？
A: AI 生成 70%-90% 基础用例，人工审核后补充业务特有逻辑，最终输出标记来源。用例编写铁律详见 [knowledge/writing-rules.md](knowledge/writing-rules.md)。

### Q: 如何处理复杂业务逻辑？
A: 阶段 1 深入理解需求，阶段 2 提取所有测试点，阶段 3 AI 生成 + 人工补充。

### Q: 如何分析 Bug 根因？
A: 请使用 bug-analyzer skill，它提供五步定位法 + 鱼骨图 + 5 Whys 根因分析。

### Q: 纯重构代码变更需要写测试用例吗？
A: 使用回归验证清单模式，直接基于变更范围输出回归验证清单，无需编写完整测试用例。
