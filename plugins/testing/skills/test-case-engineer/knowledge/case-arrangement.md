# 用例组织：分层、输出类型与编排

> **何时阅读**：阶段 2 确定分层与输出类型时；阶段 3 输出完整用例集前必读。
> **覆盖范围**：五层定义与默认重心 / 编排组占比 / 默认输出类型 / 上游 strategy 映射 / 编排与排序 / 用例集预算与去重。

## 测试分层

| 分层 | 典型目标 | 谁主导 | 本 Skill 常见产出 |
|------|----------|--------|-------------------|
| 单元/组件 | 函数/类边界、分支、异常 | 开发 | 测点提示（输入边界、异常路径） |
| 集成 | 多模块/DB/消息队列联调 | 开发/测试 | 关键路径的接口级或环境级步骤 |
| API/服务 | HTTP/RPC 行为与契约 | 测试（或开发） | 请求/响应/状态码/错误码可断言的用例 |
| 契约/消费者-提供者 | Schema 与版本兼容 | 视团队 | 字段、版本号、破坏性变更相关测试点 |
| E2E/功能验收 | 完整用户旅程、多端 | 测试 | 默认可执行场景用例（默认重心） |

**默认重心**：产出可执行的场景级用例，重心为 E2E/功能验收（含必要 UI 步骤）。需求明确后端/接口时重心必须上移到 API，禁止用纯 UI 步骤代替服务侧验证。

**禁止混层**：接口用例不能只写「打开页面点击」而无请求/断言；E2E 用例不能堆砌底层字段而无操作上下文；应拆条或分组，保持每条用例分层一致。

**分层选择**：需求仅接口/无界面 → API（+契约按需）为主；强依赖浏览器/多端 → E2E 为主，API 作辅助或回归子集；重构无行为变更 → 回归清单，禁止强行补全所有分层；不确定 → 在「存疑点」列出并标注分层列。

## 编排组占比（L1/L2-A/L2-B/L3）

| 分层 | 名称 | 关注点 | 目标占比 |
|------|------|--------|----------|
| L1 | 单元层 | 核心算法、复杂计算 | 0–10% |
| L2-A | 业务场景层 | 跨接口业务闭环、状态机 | 30% |
| L2-B | 接口契约层 | API 参数校验、DB 读写、第三方 | 30% |
| L3 | UI/E2E 层 | 用户旅程、交互、端到端 | 40% |

**动态调整**：核心业务逻辑型 L2 70% / L3 30%；数据集成型 L2 80% / L3 20%；纯交互/UI 型 L2 20% / L3 80%。

**选择决策**：核心算法/复杂计算 → L1；跨接口业务闭环 → L2-A；API/数据/第三方 → L2-B；UI/交互/体验 → L3。

## 默认输出类型

默认只输出功能用例（`type: functional`）；performance / security / compatibility 仅在需求明确要求时追加，并在功能用例后独立成组。触发条件见 [test-standards.md](test-standards.md)「用例类型」。

## 与上游 strategy 分层映射

| strategy 三层 | 本文件五层 |
|---|---|
| 单元 | 单元（1:1） |
| 接口 | 集成 + API + 契约（按需求特征分配） |
| UI | E2E/验收（1:1） |

L1/L2-A/L2-B/L3 是五层的编排分组视角：L1=单元；L2-A=集成/API（业务闭环）；L2-B=API/契约；L3=E2E/验收。占比是编排目标，不是分层硬约束。收到上游比例时先按上表换算；无上游输入时用默认占比。

## 编排与排序

用例输出必须遵循统一编排顺序，禁止随机罗列；默认策略一。

| 条件 | 策略 |
|------|------|
| 单一功能/页面/模块，预计 ≤50 条 | 策略一：用户旅程编排 |
| 可划出 ≥3 个功能模块，或 >50 条，或涉及多角色/多页面/跨系统 | 策略二：模块化分组编排（组内仍按策略一） |

**策略一（默认）**：按入口与到达 → 初始状态与默认值 → 创建 → 查询与展示 → 编辑 → 删除 → 恢复（仅需求存在时）→ 辅助操作排列。需求仅覆盖部分阶段时按实际裁剪，保持相对顺序；阶段内先正向后反向，同级按 P0→P3；用例 ID 功能缩写与阶段对应（ADD/QUERY/EDIT/DEL/RESTORE），同阶段序号连续。

**策略二（需求庞大时）**：按功能内聚性划分模块（同数据实体、状态联动、同一条操作路径、同角色/页面族），模块间按依赖拓扑排序，无依赖按主用户旅程先后；组内按策略一。模块以分组标题呈现，粒度以「共享前置数据、可连续执行」为宜；用例 ID 模块缩写与分组对应；跨模块端到端流程置于依赖模块之后独立成组。

**通用排序**：功能用例在前，非功能类型独立成组追加末尾；阶段 4 补充的用例按归属插入对应位置，禁止整体追加末尾；用例集开头声明所用编排策略。

## 用例集预算与等价合并

预算按「用例集」计，不按模块/批次分别计数；参数化/紧凑表格组内每行仍算 1 条。

| 复杂度 | 判定依据 | 预算 |
|--------|----------|------|
| 单字段纯校验 | 单字段、无联动、无状态机、无资金 | ≤8 |
| 常规单功能 | 单功能、少量规则、单角色主流程 | ≤15 |
| 多功能多状态 | 多规则约束、状态机、资金/权限/并发、跨模块 >2 处 | ≤25 |

超出预算时在用例集开头写明理由（风险、监管、多角色等），不把预算当硬性扣分或质量门槛。

**合并优先于新增**：同一业务目标与条件的等价场景合并为参数化组；同一操作触发的多个紧密结果用关键检查点汇总，不拆条；合并后无法指出「哪一步、哪个字段」导致失败时才拆分。

**输出前去重**：逐对检查标题、前置条件与关键输入；等价的合并，仅条件/数据不同的改为参数化行，不因来源不同保留重复。

**与紧凑表格**：writing-rules 的紧凑表格用于同构 P2/P3 数据组；本节预算与去重适用于所有优先级。

**与阶段 2 裁剪**：core.md 的「裁剪说明」记录未落用例的维度/字段及理由；本节约束最终总数。裁剪不等于删需求，未覆盖测试点仍须单列并写明原因。
