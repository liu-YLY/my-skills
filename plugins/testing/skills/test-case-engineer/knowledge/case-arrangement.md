# 用例组织：分层、编排与数量预算

> **何时阅读**：阶段 2 定分层与预算、阶段 3 排定输出顺序前必读。

## 一、测试分层与编排占比

| 编排层 | 对应测试层（映射上游 strategy 三层） | 典型验证目标 | 默认占比 |
|--------|--------------------------------------|--------------|----------|
| **L1** | 单元/组件（= strategy 单元） | 核心算法、复杂计算边界 | 0–10% |
| **L2-A** | 集成 / API 业务闭环（∈ strategy 接口） | 跨接口流转、状态机、幂等并发 | 30% |
| **L2-B** | API 契约 / 数据层（∈ strategy 接口） | 参数校验、落库/缓存、第三方契约 | 30% |
| **L3** | E2E / 功能验收（= strategy UI） | 完整用户旅程、关键交互（默认重心） | 40% |

- **按系统形态动态调整**：核心后端逻辑型 `L2 70% / L3 30%`；数据集成/纯接口型 `L2 80%–100%`（禁拿纯 UI 点击代替接口契约验证）；纯交互 UI 型 `L2 20% / L3 80%`；纯重构无行为变更走回归验证清单，不强凑各层。
- **禁止混层**：接口用例必须有请求与响应/数据断言；E2E 用例必须有用户业务上下文，不堆砌底表字段。
- **默认输出类型**：默认只出 `functional`；仅当需求明确要求性能/安全/兼容指标时才追加对应类型，并在功能用例末尾独立成组（见 [test-standards.md](test-standards.md)）。

## 二、编排与排序策略

禁止随机罗列用例，用例集开头须声明所用编排策略（阶段 4 补入的用例必须插入对应业务阶段，禁堆在文末）：

1. **策略一：用户旅程编排（默认，单一功能/模块且 ≤50 条）**
   - 阶段顺序：`入口与到达 → 初始状态与默认值 → 创建(ADD) → 查询展示(QUERY) → 编辑(EDIT) → 删除(DEL) → 恢复(RESTORE，仅需求有时) → 辅助操作`（按实际涉及阶段裁剪，保持先后）。
   - 阶段内排序：**先正向后反向，同级按 P0 → P3**；ID 功能缩写与阶段一致且序号连续。
2. **策略二：模块化分组编排（≥3 个子模块、>50 条或多角色跨系统）**
   - 按实体/路径内聚分组（以共享前置、可连续执行为粒度），模块间按依赖拓扑排序，组内仍按策略一；跨模块端到端闭环置于依赖模块之后独立成组。

## 三、用例集预算与等价去重

预算按整份用例集计（紧凑表格/参数化组内每行有独立 ID 时仍计 1 条）：

| 需求复杂度 | 判定特征 | 建议总预算 |
|------------|----------|------------|
| **单字段纯校验** | 单字段、无联动、无状态机、无资金 | **≤ 8 条** |
| **常规单功能** | 单功能主流程 + 少量校验与异常规则 | **≤ 15 条** |
| **多功能多状态** | 多规则耦合、状态机、资金/权限/并发、跨模块 >2 处 | **≤ 25 条** |

- 超预算须在文首写明高风险/多角色等客观理由，不为凑数扩写，也不把预算当硬扣分线。
- **合并与去重**：输出前逐对核查标题、前置与关键输入——同一规则的等价输入合并为参数化或 `数据组：`，同一动作的多层结果用检查点/分号合并，删除因多轮补点产生的重复用例；未落用例的维度留在阶段 2「裁剪说明」。
