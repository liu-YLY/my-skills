# 规模化评审方案

> 本文件定义用例数量过大时的评审组织方案。单条用例的判定规则仍以 [review-mode.md](review-mode.md) R2 表为唯一权威源，本文件不重复维护。

**边界**：review-mode.md 管「单条用例怎么判」，本文件管「大量用例怎么分批、怎么抽样、怎么分工、怎么收敛」。

## 触发条件

满足以下任一条件进入规模化评审：

- 用例总数 > 100 条（强制进入，与 review-mode.md 失败模式阈值一致）
- 用例总数 50–100 条且用户要求评审方案/排期（可选进入）
- 跨 3 个以上模块或多文件批量评审
- 用户明确要求「评审方案」「评审计划」「评审排期」「用例太多评不完」
- 存在明确的时间或人力约束

用例总数 ≤ 50 条时不进入本方案，直接按 review-mode.md R1-R3 单批全量执行。

## 工作流（5 步）

```
L1 规模画像 → L2 选策略 → L3 定抽样与分工 → L4 输出评审方案 → L5 分批执行与聚合
```

## L1 规模画像（强制先做）

不允许凭用例数量直接选策略，必须先输出画像。缺少的字段标注「未知」，不得填 0 或猜测。

| 指标 | 说明 | 用途 |
|------|------|------|
| 用例总数 N | 可解析的用例条数 | 决定策略 |
| 模块数 M | 从用例 ID 模块段或文件结构提取 | 决定批次划分 |
| 单模块最大条数 | 识别超大批次 | 是否需要二次切分 |
| 优先级分布 | P0/P1/P2/P3 条数 | 识别强制全量范围 |
| 类型分布 | 功能/异常/边界/权限/并发等 | 识别类型缺口 |
| 可解析率 | 能提取 ID/标题/步骤/预期的比例 | 决定是否降级 |
| 需求或测试点基线 | 有 / 无 | 溯源维度是否可执行 |
| 变更范围 | 增量评审时的 diff 用例数 | 决定是否叠加增量策略 |

画像结论用一句话给出，例如：「N=420，M=8，单模块最大 96 条，P0 68 条，无优先级字段，需求基线存在」。

## L2 选评审策略

| 编号 | 条件 | 策略 | 覆盖方式 |
|------|------|------|---------|
| S1 | N ≤ 50 | 单批全量 | 全量 |
| S2 | 50 < N ≤ 300，且无时间约束 | 全量分批 | 全量，每批 ≤ 50 条 |
| S3 | N > 300，或存在时间/人力约束 | 分层抽样 | 强制全量清单全查 + 其余分层抽 20% |
| S4 | 迭代场景，有明确 diff 范围 | 增量评审 | 变更用例全量 + 覆盖度按全量统计 |
| S5 | 高风险模块占比 ≥ 1/3 | 混合 | 高风险模块全量，其余模块抽样 |

策略可叠加，例如 S4 + S3：变更用例全量评审，未变更部分分层抽样，覆盖度与优先级分布按全量统计。选择结果必须写明依据，不能只写编号。

## L3 强制全量清单（不可抽样）

以下用例必须全量评审，不进入抽样池：

- P0 用例
- 涉及资金、权限、数据安全、主流程的用例
- 新增模块或大改模块的全部用例
- 上次评审判定为 C/D 的模块
- 跨模块联动的用例
- 用户明确指定的重点范围

**原则**：抽样降低的是工作量，不是风险。强制全量清单的条数必须与抽样条数分列，不得合并成一个「本次评审 N 条」。

## L3.1 抽样方案（可复现）

- **分层键**：模块 × 优先级
- **每层样本数**：`k = max(ceil(层内条数 × 20%), 1)`
- **抽样方法**：对 `hash(用例ID + sample_seed)` 升序取前 k 条，不使用运行时随机数
- **种子**：`sample_seed` 默认评审日期（`YYYYMMDD`），写入方案；同一种子必须得到同一批样本
- **上限**：单批样本 ≤ 50 条，超出时先加大批次或做二次分层抽样，并记录两级种子
- **同组归并**：同一 `test_point_id` 下超过 5 条的等价用例，抽 1 条代表，其余标记「同组未评审」，不计入通过率

抽样产出必须同时给出三份清单：

1. 样本清单（将被评审的用例 ID）
2. 未评审清单（未抽中的用例 ID）
3. 强制全量清单（L3 中的用例 ID）

三份清单相加必须等于用例总数 N，用于自检是否漏算。

## L3.2 维度分工

可机器判定的维度不抽样，需要业务判断的维度才抽样。抽样只用于后者，避免「省了人工、漏了确定性」。

| 维度 | 执行方式 | 覆盖范围 |
|------|---------|---------|
| 字段规范 | 确定性校验 | 全量 |
| 溯源 | 确定性校验（有基线时） | 全量 |
| 语义一致性 | 确定性校验（facts 抽取） | 全量 |
| 可执行性 | 确定性结构检查 + 人工 | 结构全量，语义判断抽样 |
| 冗余 | 相似度扫描 + 人工核实 | 扫描全量，核实抽样 |
| 覆盖度 | 统计 + 人工核对 | 统计全量，缺口核对抽样 |
| 优先级合理性 | 分布统计 | 全量统计，异常个案抽样 |
| 可维护性 | 人工 | 抽样 |
| 可自动化 | 人工 | 抽样 |
| 测试数据依赖 | 人工 | 抽样 |

## L4 输出评审方案

方案是交付物，必须包含以下 7 个部分，缺一不可。

| 部分 | 内容 |
|------|------|
| 1 规模画像 | L1 的结果 |
| 2 策略与依据 | L2 的策略编号 + 选择理由 |
| 3 批次计划 | 批次表：批次号 / 模块 / 优先级 / 条数 / 策略 / 负责人 / 工作量 |
| 4 抽样计划 | 分层矩阵、每层抽样数、`sample_seed`、三份清单 |
| 5 维度分工 | L3.2 的执行方式表 |
| 6 执行日程 | 异步预检 → 分批评审 → 汇总评审，标注每段的产出 |
| 7 收敛指标与退出条件 | 通过率、问题密度、未评审条数、系统性问题数 |

### 评审方案模板

```markdown
## 规模化评审方案

**评审范围**：[文件/模块/全量]
**评审日期**：[YYYY-MM-DD]
**策略**：[S2 全量分批 / S3 分层抽样 / S4 增量 / 组合]
**依据**：[一段话，引用规模画像中的关键数字]

### 规模画像

| 指标 | 值 |
|------|----|
| 用例总数 | N |
| 模块数 | M |
| 单模块最大条数 | x |
| 优先级分布 | P0 x / P1 x / P2 x / P3 x |
| 可解析率 | x% |
| 需求基线 | 有 / 无 |

### 批次计划

| 批次 | 模块/范围 | 优先级 | 条数 | 策略 | 负责人 | 产出 |
|------|----------|--------|------|------|--------|------|
| B1 | order | P0 | 40 | 全量 | - | 意见表 + 度量 |
| B2 | order | P1/P2 | 50 | 抽样 20% | - | 意见表 |

### 抽样计划（S3 时必填）

- 分层键：模块 × 优先级
- 抽样比例：20%，每层最少 1 条
- sample_seed：`YYYYMMDD`
- 样本清单：[文件/列表]
- 未评审清单：[文件/列表]
- 强制全量清单：[文件/列表]
- 三清单合计：x + y + z = N

### 维度分工

[引用 L3.2 表，标注本次实际执行方式]

### 执行日程

| 阶段 | 时间 | 内容 | 产出 |
|------|------|------|------|
| 异步预检 | D0 | 机器跑确定性维度，全量 | 预检问题清单 |
| 分批评审 | D1-Dn | 各批 R2 + 意见表 | 批次意见表 |
| 汇总评审 | D+1 | 聚合、系统性问题、度量 | 评审报告 |

### 收敛指标与退出条件

- 已评审用例数 / 未评审用例数
- 通过率（仅以已评审用例为分母）
- 问题密度（已确认问题数 / 已评审用例数）
- 系统性问题数（同一维度问题占比 ≥ 30%，或同类问题跨 ≥ 3 个模块）
- 退出条件：强制全量清单 100% 完成，且无未处置的 P0
```

## L5 分批执行与聚合

- 每批独立走 review-mode.md R1-R3，输出批次意见表与批次度量，不跨批复用结论
- 聚合阶段必须做四件事：
  1. 合并同一用例在不同批次的问题，避免重复计数
  2. 识别系统性问题：某维度问题数 ≥ 该批问题总数 30%，或同类问题出现在 ≥ 3 个模块
  3. 重算整体度量：分母只算已评审用例，未评审用例单列
  4. 输出未评审范围声明：哪些模块/优先级未覆盖，可能的风险是什么
- 任何一批未完成时，标注「未评审」，不得用其他批次的结论推断

## 失败模式与 Fallback

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 无用例优先级字段 | 按模块 + 标题关键词粗分组 | 按模块均匀抽样，标注「优先级未知，抽样不按风险加权」 |
| 用例 ID 不规范，无法提取模块 | 按文件/章节结构切分批次 | 按解析顺序每 50 条一批，标注「批次按位置划分，非业务闭环」 |
| 单模块 > 50 条 | 按业务子流程再切 | 按测试点分组合并批次，标注「同模块跨批」 |
| 抽样后单批样本 > 50 | 加大批次或做二次分层抽样 | 记录两级种子，标注「二次抽样」 |
| 无需求或测试点基线 | 溯源维度标注「未评估」 | 跳过溯源，度量报告标「未评估：溯源」 |
| 时间不足以覆盖强制全量清单 | 按 P0 → 主流程 → 其余顺序削减 | 其余写入未评审清单，明确告知风险与覆盖缺口 |
| 用户要求抽样但仍要整体结论 | 结论限定在已评审范围内 | 输出「已评审部分评级 + 未评审范围声明」，不给全量评级 |

## 反例（不要做什么）

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|--------|-------------|----------|
| 1 | 抽样后宣称「已完成全量评审」 | 结论超出实际证据范围 | 明确拆分已评审/未评审，评级只在已评审范围内成立 |
| 2 | 把 P0 或主流程用例放入抽样池 | 高风险场景被统计概率漏掉 | 强制全量清单独立执行 |
| 3 | 抽样不记录种子 | 下次无法复现同一批样本，评审结论不可追溯 | 固定 seed 并使用确定性哈希排序 |
| 4 | 分批后不做聚合 | 跨批重复问题虚高，系统性问题被掩盖 | L5 四步聚合强制执行 |
| 5 | 按文件行数或顺序切批，而非业务闭环 | 单批内上下文割裂，评审人无法判断业务等价性 | 按模块/业务子流程切分 |
| 6 | 用未评审用例的「未发现问题」计入通过率 | 通过率虚高，掩盖覆盖缺口 | 分母只算已评审用例 |
| 7 | 对字段规范、溯源等机器可判定维度也抽样 | 省不下多少人工，却留下确定性遗漏 | 机器维度全量，只对业务判断维度抽样 |
