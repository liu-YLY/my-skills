# 需求评审模式

> **何时阅读**：输入为 PRD / 需求文档 / 用户故事，且用户要求「需求评审 / PRD 评审 / 评审需求 / 需求文档检查 / 找需求问题」时必读。
> **与用例评审的边界**：本模式评审「需求是否可开发、可测试、可验收」，不评已有用例；已有用例评审见 [review-mode.md](review-mode.md)。
> **原则**：只基于原文评审，不虚构需求；每条问题必须可回查；先报确认问题，再列候选与待确认。

## 10 维度检查

| # | 维度 | 判定问句 |
|---|------|----------|
| 1 | 完整性 | 角色、入口、前置条件、主流程、异常、后置状态是否齐全？缺哪一项会导致无法设计用例？ |
| 2 | 一致性 | 同一对象/规则/数值/状态在多处是否冲突？以哪一处为准？ |
| 3 | 明确性 | 每个规则是否有具体值、范围、文案或判定条件？「快速」「友好」「合理」能否判定？ |
| 4 | 可测性 | 是否给出可观察证据、验收口径或指标？执行人能否据此判 pass/fail？ |
| 5 | 状态与流程 | 状态集合、合法/非法转换、终态、幂等、并发是否定义？ |
| 6 | 权限与角色 | 角色矩阵、可见/可操作差异、越权与授权边界是否定义？ |
| 7 | 数据与校验 | 字段类型、长度、唯一性、边界、默认值、精度、时区是否定义？ |
| 8 | 异常与容错 | 失败、超时、重试、降级、部分成功、结果未知、补偿是否定义？ |
| 9 | 非功能 | 性能、容量、安全、兼容、可观测、合规是否给出可验收要求？ |
| 10 | 范围与追溯 | 范围边界、依赖、上下游、版本/迁移、验收责任是否明确？ |

> 10 维度是检查清单，不是问题数量下限；无问题的维度写「已检查，未发现问题」，无法检查的写「未评估 + 原因」。

## 严重级别

| 级别 | 定义 | 处置 |
|---|---|---|
| P0 | 阻断核心流程、资金/数据/权限风险，或矛盾导致无法实现/验收 | 必须澄清后才能开发或进入用例设计 |
| P1 | 主要路径、关键规则缺失或不可测，影响用例设计或发布判断 | 本次迭代内澄清 |
| P2 | 次要路径、文案/体验/可维护性问题，影响可控 | 可排期澄清 |
| P3 | 建议优化，不阻断开发与验收 | 记录即可 |

级别按「失败影响 × 发生可能性 × 影响范围」判定，不按问题类型自动推导；纯措辞/排版问题不得标 P0/P1，除非改变判定结果。

## 问题 schema（强制）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | `RR-001` 起连续编号，唯一 |
| `location` | 是 | 章节/行号/全文，如 `§3.2`、`req.md:L42`、`全文` |
| `quote` | 是 | 原文逐字引用，不改写；矛盾用 `原文A / 原文B` 两段 |
| `type` | 是 | 模糊 / 矛盾 / 缺失 / 不可测 / 权限 / 状态 / 数据 / 兼容性 / 非功能 / 依赖 / 文案冲突 / 安全 / 体验 |
| `severity` | 是 | P0 / P1 / P2 / P3 |
| `impact` | 是 | 受影响的流程、测试点、用例或发布判断 |
| `problem` | 是 | 一句话说明问题，不与建议混写 |
| `question` | 是 | 待确认问题或建议；建议值必须标「建议值，待确认」 |
| `status` | 是 | `confirmed`（原文可直接证实）/ `candidate`（需业务确认或存在多种解释） |

**硬约束**：

- `quote` 必须能在 PRD 原文中回查；回查不到即视为无效问题。
- 一条问题只描述一个问题；不要把缺失、矛盾、不可测混在一条。
- 不虚构数值、文案、时限、角色；需要举例时标「示例，非需求」。
- 缺需求与无法验证分开：缺失写「未定义」，不可测写「已定义但无判定口径」。
- `candidate` 不计入 P0–P3 分布、召回率和问题密度，单独列出待确认。
- 报告统计数必须与问题表一致；维度分布之和必须等于 confirmed 问题数。

## 报告模板

```markdown
# 需求评审报告

**评审对象**：[PRD 名称/版本]
**评审日期**：[YYYY-MM-DD]
**评审范围**：[章节/全文]
**结论**：[可进入用例设计 / 需澄清后进入 / 不可进入]
**问题统计**：confirmed N（P0 x / P1 y / P2 z / P3 w）；candidate M

## 问题清单

| ID | 位置 | 原文 | 类型 | 级别 | 影响 | 问题 | 待确认/建议 | 状态 |
|----|------|------|------|------|------|------|-------------|------|
| RR-001 | §2 vs §4 | `5 张 / 10 张` | 矛盾 | P0 | 优惠券上限无法确定，影响上限与叠加测试点 | 两处数量上限不一致 | 以哪一版为准？建议值待确认 | confirmed |
| RR-002 | 全文 | `快速响应` | 不可测 | P1 | 无法设计响应时间用例 | 未定义时限或指标 | 目标响应时间是多少？ | confirmed |

## 维度覆盖

| 维度 | 已检查 | 问题数 | 未评估原因 |
|------|--------|--------|------------|
| 完整性 | 是 | 1 | - |
| 一致性 | 是 | 1 | - |

## 未评估项

- [缺少的信息/无法检查的维度及原因]

## 原文回查

- RR-001：§2「单个订单最多使用 5 张优惠券」；§4「上限为 10 张」
- RR-002：全文「系统应快速响应」
```

## 输出规则

1. 先给结论与统计，再给问题清单；P0/P1 在前，同级按原文顺序。
2. 每条问题必须含位置 + 原文 + 类型 + 级别 + 影响 + 问题 + 待确认；缺任一项视为不合格。
3. 不输出「建议重写整份 PRD」这类无法执行的结论；建议必须指向具体条款。
4. 需求评审完成后，问题清单作为阶段 1 的输入：confirmed 问题进「原文问题清单」，candidate 进「待确认项」，不重复评审。
5. 需要进入用例设计时，按 [SKILL.md](../SKILL.md) 的模式选择进入默认/快速模式；本模式不直接产出测试用例。
6. 输出前运行 `python $SKILL_ROOT/scripts/validate_requirement_review.py <报告.md> --prd <PRD.md>`；0 error 方可交付。
