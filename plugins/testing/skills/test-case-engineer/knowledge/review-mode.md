# 评审模式

> 本文件定义评审模式完整工作流（从 core.md 拆分）。阶段 4 自检是对自己生成的用例做覆盖度自检；评审模式是对他人/已有用例做全面质量评审，两者独立，不互相替代。

## 触发条件

满足任一即进入评审模式，不走四阶段生成流程：

- 输入包含已有用例（文件路径 / 直接粘贴 / 目录引用），且使用「评审/review/检查质量」等触发词
- 用户明确要求「评审这些用例」「检查用例质量」
- 输入仅有用例、无需求文档 → 进入评审模式（溯源维度降级）
- 用例总数 >100 条，或用户要求评审方案/排期 → 叠加 [large-scale-review.md](large-scale-review.md)

## 评审工作流（3 步）

```
步骤 R1 解析输入 → 步骤 R2 10 维度评审 → 🔴 CHECKPOINT 步骤 R3 输出意见表+建议清单+度量报告
```

### 步骤 R1：解析输入

- 解析已有用例的结构：ID / 标题 / 优先级 / 类型 / 步骤 / 预期结果 / 前置条件
- 支持格式：Markdown（表格或 `### TC-xxx` 标题）/ CSV（按列解析）/ JSON（按字段解析）；Excel 提示转为 CSV/Markdown 或对话粘贴
- 有需求文档 → 解析需求要点用于溯源；无需求 → 标注「溯源维度降级，仅检查用例内部一致性」
- 用户指定「增量评审」→ 仅解析 git diff 中变更的用例（见 [review-reference.md](review-reference.md)「增量评审子模式」）

### 步骤 R2：10 维度评审

> v8.2 新增可维护性 / 可自动化 / 测试数据依赖（均为 P2 建议）；第 10 维度「语义一致性」由 skill 抽取 SemanticFacts 后调 MCP `check_semantic_conflicts` 确定性判定。

| 维度 | 检查点 | 判定规则 | 依据 |
|------|--------|----------|------|
| 覆盖度 | 需求要求的适用场景 | 仅对 `required_scenarios` 明确要求的类型检查缺失；缺少基线或 scenario 未标注时不确认缺口，不从标题猜测 | 需求与风险依据 |
| 优先级合理性 | 业务风险与回归必要性 | 核对业务风险依据，比例只描述分布，不设固定扣分阈值 | test-standards.md |
| 字段规范 | 必填字段、有效检查点、可读性 | 必填内容缺失、检查点引用越界 → P0；标题词语与长度仅为待核实提示；可读性问题统一按 P2 提示，需人工确认 | writing-rules.md / readability.md |
| 可执行性 | 具体操作与可判定结果 | 明确占位操作 → P0；结果仅有模糊结论 → P1；步骤与结果不要求数量相等，不按步骤数扣分 | writing-rules.md |
| 冗余 | 是否覆盖同一业务目标和条件 | 同标题、相同前三步或同测试点数量较多仅列候选线索；核实业务等价性后才确认 | 用例与需求 |
| 溯源 | 已提供的需求或测试点基线 | 基线存在时，编号缺失或不在清单 → P0；没有基线则未评估 | 需求文档（若有） |
| 可维护性 | 依赖与定位稳定性 | 未声明的跨用例依赖、绝对坐标提示 → P2，需结合实际可执行方式确认 | 执行约定 |
| 可自动化 | 断言与数据准备 | 模糊断言或缺少可用造数方案 → P2；人工用例不因没有自动化实现而降级 | 执行约定 |
| 测试数据依赖 | 数据成本与可获得性 | 生产或第三方数据依赖没有替代方案时提示核实，不要求全部场景使用 mock | 数据来源 |
| 语义一致性 | 内部矛盾、上下文、依赖闭环 | 单用例同 subject/state 同时肯定和否定 → P0；不同上下文不作冲突；同输入不同结果先列 candidate；依赖闭环 → P1 | 经核对的 SemanticFacts |

**可读性检查（字段规范子项）**：只评「读起来是否费力」，不改变判定口径；全部按 P2 提示，候选项不计入问题密度。

- 标题脱离步骤能否定位对象、条件与预期
- 单句超过 40 字，或一步含两个以上动作
- 同一对象、同一动作出现多种叫法
- 预期结果首词不是位置，或检查点集中到文末、需要回读

机器只能检查输入事实与结构；业务语义结论必须引用原文、条件或执行证据。`candidate` 与 `confirmed` 分开输出，候选项不计入扣分、问题密度和通过率。

**评审主体与审核来源**：本 Skill 执行 AI 评审；独立或降级模式写「AI 规则核对（未经过 MCP 校验）」，不能写「人工核对」「人工推理」或「人工审核已完成」。增强模式分列 AI 分析与 MCP 复核。只有确实提供真人审核记录及来源时才署真人审核；AI 评审不构成人工审核，也不把审核状态改为 reviewed。用例来源与人工审核状态按 [writing-rules.md](writing-rules.md) 独立记录。

### 步骤 R3：输出

交付评审意见表、改进建议清单、评审度量报告；模板见 [review-reference.md](review-reference.md)。仅评审请求不自动修改用例；用户已授权修订时按授权范围继续，不重复询问。

## MCP 增强（可选）

> 安装配套 [review-checker MCP Server](https://github.com/liu-YLY/my-skills/blob/main/plugins/testing/mcp-servers/review-checker/README.md) 后，R2 与 R3 可调用确定性校验，不依赖 LLM 推理这些本该确定的事；未安装时降级为纯 LLM 推理。

源码链接仅用于定位；安装版本需匹配当前 Skill 契约，并核对 `tools/list` 参数 Schema。旧服务不支持新可选字段时省略字段、保留评审说明，不能把远程旧版本视为本次能力已交付。

| 模式 | 触发条件 | 行为 | 输出标记 |
|---|---|---|---|
| 增强模式 | MCP 可用 | skill 推理 + MCP 确定性校验与度量计算 | `✓ MCP 增强模式` |
| 独立模式 | MCP 未安装 | 纯 LLM 推理执行 R2/R3 | `⚠ 独立模式（未校验）` |
| 降级模式 | MCP 调用失败 | 回退独立模式并记录原因 | `⚠ 降级模式（MCP 失败：原因）` |

| 评审步骤 | MCP 工具 | 用途 |
|---|---|---|
| R2 10 维度 | `review_test_cases(case_set)` | 执行确定性正则/阈值校验，返回 Issue 列表 |
| R3 度量报告 | `generate_report(case_set)` | 计算通过率/问题密度/评级/维度与严重等级分布 |
| R2 第 10 维度 | `check_semantic_conflicts(facts)` | 3 类确定性冲突检测（前置条件矛盾/同输入异预期/依赖闭环） |

**评级阈值**：

- 空集合：未评估，`pass_rate: null`；不评 A，也不作为失败集合
- 已确认 P0：整体评级 D（含集合级问题）；以下分级仅适用于无已确认 P0
- A：通过率 ≥95% 且问题密度 <0.5；B：≥80%；C：≥60%；D：<60%

**调用约定**：

- 新用例 `expected_results` 用字符串数组，兼容字符串输入，不迁移历史用例；可选 `checkpoints` 每项含 `after_step`（从 1 开始）与结果数组
- `required_scenarios` 仅填需求明确要求的类型；缺省为未评估，空数组表示已确认无类型要求
- `Issue.confirmation` 为 `confirmed`/`candidate`；`generate_report` 的 `issues` 与统计只含确定问题，候选项放 `candidate_issues`
- 同时展示 `assessed_dimensions` 与 `not_assessed`；结构检查 A 级不代表需求已全量验证
- SemanticFacts 可补充 `context`；未知极性用 `unknown`，不补成肯定事实
- 增强模式：R2 调 `review_test_cases` 复核，差异标「待确认」；R3 调 `generate_report`
- 独立模式：按 R2 规则自行推理，首行标 `⚠ 独立模式（未校验）`
- 降级模式：记录失败原因后回退独立模式
- 第 10 维度：增强模式先抽取 SemanticFacts（提示词见 [prompt-strategy.md](prompt-strategy.md)），再调 `check_semantic_conflicts`，核对全部用例后与其他 Issue 合并传入 `generate_report(..., semantic_reviewed=True)`；未完成保持 False。独立模式自行抽取并执行 3 类规则，标 `⚠ 独立模式（语义一致性未校验）`；降级模式跳过第 10 维度并标注原因

## 评审修订闭环

```
步骤 V1 核对修订授权与范围 → V2 转交生成模式修订 → V3 复审受影响维度 → V4 输出修订报告
```

- **V1**：用户已明确要求修订时直接执行授权范围，不重复确认；用户圈定需修订的用例 ID 与问题，可只修 P0；明确「不修订」的用例须在报告标注原因
- **V2**：按修订范围读取 core.md 与 writing-rules.md 的必要规则，定向逐条修订，不重跑与当前问题无关的完整四阶段；必须携带评审上下文（schema 见 [review-reference.md](review-reference.md)），不得脱离评审意见重新生成
- **V3 强制复审**：仅复审受影响维度。title → 字段规范/冗余/可维护性；steps → 可执行性/冗余/可维护性/可自动化/语义一致性；expected_results → 字段规范/可执行性/可自动化/语义一致性；priority → 优先级合理性；preconditions → 可维护性/测试数据依赖/语义一致性；新增用例 → 覆盖度/优先级/溯源/可维护性/可自动化/测试数据依赖/语义一致性；删除用例 → 覆盖度/溯源/语义一致性。复审发现新问题则在授权内继续修订，超出范围回 V1 询问
- **V4**：输出修订前后对比 + 复审结果 + 修订度量（修订条数/复审通过率/残留问题数）

完成授权范围内修订与复审后交付修改证据及残留问题，不重复请求已有授权。

## 补充用例 ID

评审发现缺失用例需补充时，遵循 [writing-rules.md](writing-rules.md)「补充用例 ID 生成规则」：`TC_{模块}_{功能}_{三位序号}`，模块/功能缩写从已有用例提取，序号 = 同模块+功能最大序号 +1；禁止不规范格式、序号跳跃与缩写不一致。

## 失败模式与 Fallback

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 用例格式不规范无法解析 | 列出已识别字段，提示补充后重新评审 | 仅评审可解析部分，标注「格式不规范，评审不完整」 |
| 无需求文档 | 仅检查内部一致性，标注「溯源维度降级」 | 跳过溯源，在意见表标注「未评审：溯源（缺需求文档）」 |
| 用例数量 >100 | 进入 [large-scale-review.md](large-scale-review.md)，按 L1–L5 输出方案 | 至少完成强制全量清单（P0/主流程），其余写入未评审清单并声明风险 |
| facts 数量 ≠ 用例数 | 重试抽取，强调「必须为每条用例产出 facts」 | 跳过第 10 维度，标注「语义一致性降级：facts 抽取不完整（N/M）」 |
| facts JSON 不合法 | 用 JSON 修复提示词二次修复 | 跳过第 10 维度，标注「语义一致性降级：facts 解析失败」 |
| subject 归一化失败 | 补充同义词示例重试 | 仅严格字符串匹配，漏报在建议中提示「疑似同概念但归一化不一致，建议人工复核」 |
| 用例无 test_point_id | 保留单用例内部矛盾检查，跨用例核对实际上下文 | 不以编号前缀或 unknown 组推定相同业务场景 |
| 用例数 >100 且抽取成本高 | 按模块分批抽取，每批 ≤50 条 | 分层抽样，标注「语义一致性抽样检测」 |

## 评审反例（不要做什么）

| # | 反模式 | 替代做法 |
|---|--------|----------|
| 1 | 直接修订用例而不输出意见表 | 先输出意见表+建议清单，修订走授权后的生成模式 |
| 2 | 评审意见使用模糊词 | 引用具体用例 ID + 字段 + 问题描述 |
| 3 | 跳过 CHECKPOINT 直接修订 | 展示意见表；未授权修订时仅交付意见 |
| 4 | 问题无依据地全打同一优先级 | 按业务影响、执行阻断程度、修订必要性逐条分级；分布只观察 |
| 5 | 评审越界擅自改业务规则 | 只引用规则、指出问题；业务规则变更须回溯需求并由产品确认 |
| 6 | 主观化、不引用判定规则 | 每条意见引用 R2 判定规则 + 用例 ID + 字段 + 命中证据 |
| 7 | 评审遗漏维度 | R2 覆盖全部 10 维度；无需求时溯源降级但不得跳过；用维度分布自检 |
| 8 | 语义一致性全靠 LLM 主观判断 | 先抽 SemanticFacts，再由 MCP 确定性判定；意见引用冲突类型 + 冲突对 evidence |

## 评审方案 / 规模化 / 增量

- 面向产品/UI/前后端等干系人的评审材料与会议组织见 [review-plan.md](review-plan.md)；R2 十维度判定仍是质量结论，评审方案只翻译结论
- 用例过大时的组织方案见 [large-scale-review.md](large-scale-review.md)；它只决定「评哪些、分几批、谁来评」，不改变单条判定标准
- 增量评审的触发、R1–R3 差异与失败模式见 [review-reference.md](review-reference.md)「增量评审子模式」

## 评审报告文件化

满足任一触发：用户要求保存/输出到文件/沉淀结果；评审用例 ≥20 条；整体评级 C 或 D。

命名：`docs/review-reports/{YYYYMMDD}-{module}-{mode}.md`，`mode` 为 `full`/`batched`/`incremental`/`sampled`；`module` 从用例 ID 模块段提取（`TC_order_*` → `order`）。内容结构见 [review-reference.md](review-reference.md)。

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 目录不存在 | 创建后写入 | 对话中输出完整报告，提示手动保存 |
| 模块名无法提取 | 提示用户指定 | 用 `unknown` |
| 同日同模块同模式已存在 | 文件名追加序号（`-02`） | 覆盖前提示用户确认 |
