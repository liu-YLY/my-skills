# 评审模式

> 本文件从 test-case-engineer-core.md 拆分，定义评审模式完整工作流。

> **与阶段 4 自检的边界**：阶段 4 自检是 AI 对**自己生成**的用例做覆盖度自检；评审模式是对**他人/已有**的用例做全面质量评审。两者独立，不互相替代。

## 触发条件

满足以下任一条件**必须**进入评审模式，不走四阶段生成流程：
- 用户输入包含已有用例（文件路径 / 直接粘贴 / 目录引用），且使用「评审/review/检查质量」等触发词
- 用户明确要求「评审这些用例」「检查用例质量」
- 输入仅有用例无需求文档 → 进入评审模式（溯源维度降级，见失败模式表）

## 评审工作流（3 步）

```
步骤 R1 解析输入 → 步骤 R2 10 维度评审 → 🔴 CHECKPOINT 步骤 R3 输出意见表+建议清单
```

**步骤 R1：解析输入**
- 解析已有用例的结构（ID/标题/优先级/类型/步骤/预期结果/前置条件）
- **支持格式**：Markdown（`.md`，提取表格或 `### TC-xxx` 标题）/ CSV（`.csv`，按列解析 ID/标题/步骤/预期结果）/ JSON（`.json`，按结构化字段解析）/ Excel（`.xlsx`/`.xls`，提示用户转为 CSV/Markdown 或对话粘贴）
- 若提供需求文档 → 解析需求要点，用于溯源维度
- 若无需求文档 → 标注「溯源维度降级，仅检查用例内部一致性」
- 若用户指定「增量评审」→ 仅解析 git diff 中变更的用例（详见「增量评审子模式」）

**步骤 R2：10 维度评审**

> **维度扩展说明**：v8.2.0 在原 6 维度基础上新增 3 维度（可维护性/可自动化/测试数据依赖），覆盖用例的全生命周期质量。新增维度均为 P2 级（建议改进，非阻塞）。v8.2 新增第 10 维度「语义一致性」（跨用例前后语义冲突检测：前置条件矛盾/同输入异预期/依赖闭环），由 skill 抽取 SemanticFacts 后调 MCP `check_semantic_conflicts` 确定性判定。

| 维度 | 检查点 | 判定规则 | 依据 |
|------|--------|----------|------|
| 覆盖度 | 需求要求的适用场景 | 仅对 `required_scenarios` 明确要求的类型检查缺失；缺少基线或 scenario 未标注时不确认缺口，不从标题猜测 | 需求与风险依据 |
| 优先级合理性 | 业务风险与回归必要性 | 人工核对依据，比例只描述分布，不设固定扣分阈值 | test-standards.md |
| 字段规范 | 必填字段与有效检查点 | 必填内容缺失、检查点引用越界 → P0；标题词语与长度仅为待核实提示 | writing-rules.md |
| 可执行性 | 具体操作与可判定结果 | 明确占位操作 → P0；结果仅有模糊结论 → P1；步骤与结果不要求数量相等，不按步骤数扣分 | writing-rules.md |
| 冗余 | 是否覆盖同一业务目标和条件 | 同标题、相同前三步或同测试点数量较多仅列候选线索；核实业务等价性后才确认 | 用例与需求 |
| 溯源 | 已提供的需求或测试点基线 | 基线存在时，编号缺失或不在清单 → P0；没有基线则未评估 | 需求文档（若有） |
| 可维护性 | 依赖与定位稳定性 | 未声明的跨用例依赖、绝对坐标提示 → P2，需结合实际可执行方式确认 | 执行约定 |
| 可自动化 | 断言与数据准备 | 模糊断言或缺少可用造数方案 → P2；人工用例不因没有自动化实现而降级 | 执行约定 |
| 测试数据依赖 | 数据成本与可获得性 | 生产或第三方数据依赖没有替代方案时提示核实，不要求全部场景使用 mock | 数据来源 |
| 语义一致性 | 内部矛盾、上下文、依赖闭环 | 单用例同 subject/state 同时肯定和否定 → P0；不同上下文不作冲突；同输入不同结果先列 candidate；依赖闭环 → P1 | 经核对的 SemanticFacts |

机器只能检查输入事实与结构；业务语义结论必须引用原文、条件或执行证据。`candidate` 与 `confirmed` 分开输出，候选项不计入扣分、问题密度和通过率。

**步骤 R3：输出评审意见表 + 改进建议清单 + 评审度量报告**

**评审输出**：交付意见表、建议和度量报告。仅评审请求不自动修改用例；用户已授权修订时按授权范围继续，不重复询问。

## MCP 增强（可选）

> **与 state-machine-test-engineer 的 MCP 增强对称**：安装配套 [review-checker MCP Server](../../../mcp-servers/review-checker/README.md) 后，R2 评审与 R3 度量报告可调用确定性机器校验，不依赖 LLM 推理这些本该确定的事。未安装时降级为纯 LLM 推理。

### 三模式

| 模式 | 触发条件 | 行为 | 输出标记 |
|---|---|---|---|
| **增强模式** | MCP 可用 | skill 自身推理 + 调用 MCP 做确定性校验与度量计算 | `✓ MCP 增强模式` |
| **独立模式** | MCP 未安装 | skill 纯 LLM 推理执行 R2/R3 全流程 | `⚠ 独立模式（未校验）` |
| **降级模式** | MCP 调用失败 | 自动回退到独立模式，记录失败原因 | `⚠ 降级模式（MCP 失败：原因）` |

### 工具映射

| 评审步骤 | MCP 工具 | 用途 |
|---|---|---|
| R2 10 维度评审 | `review_test_cases(case_set)` | 将 R2 表判定规则执行为确定性正则/阈值校验，返回 Issue 列表 |
| R3 度量报告 | `generate_report(case_set)` | 计算通过率/问题密度/整体评级（A/B/C/D）/10 维度分布/严重等级分布 |
| R2 第 10 维度 | `check_semantic_conflicts(facts)` | 接收 skill 侧 LLM 抽取的 SemanticFacts，执行 3 类确定性冲突检测（前置条件矛盾/同输入异预期/依赖闭环） |

**评级阈值**（与下方「评审度量报告模板」完全对齐）：
- 空集合：未评估，`pass_rate: null`；不评 A，也不作为失败集合
- 已确认 P0：整体评级 D，包含集合级问题；以下分级仅适用于无已确认 P0 的情况
- A: 通过率 ≥ 95% 且 问题密度 < 0.5
- B: 通过率 ≥ 80%
- C: 通过率 ≥ 60%
- D: 通过率 < 60%

### 调用约定

- 新用例 `expected_results` 使用字符串数组；兼容字符串输入，不迁移历史用例。可选 `checkpoints` 每项含 `after_step`（从 1 开始）和结果数组。
- `required_scenarios` 仅填需求明确要求的适用类型；缺省为未评估，空数组表示已确认无类型要求。
- `Issue.confirmation` 为 `confirmed` 或 `candidate`；`generate_report` 返回的 `issues` 和统计只含确定问题，候选项放 `candidate_issues`。
- 同时展示 `assessed_dimensions` 与 `not_assessed`；结构检查的 A 级不代表需求已全量验证。
- SemanticFacts 可补充 `context`（角色、环境、配置等）；未知极性使用 `unknown`，不补成肯定事实。

- **增强模式**下，skill 在 R2 步骤调用 `review_test_cases` 复核 LLM 推理结果，差异项标「待确认」；在 R3 步骤调用 `generate_report` 生成度量报告
- **独立模式**下，skill 按 R2 表规则自行推理，输出首行标注 `⚠ 独立模式（未校验）`
- **降级模式**下，记录 MCP 失败原因后回退到独立模式流程
- **第 10 维度特殊约定**：增强模式下 skill 先调 LLM 抽取 SemanticFacts（提示词见 [prompt-strategy.md](prompt-strategy.md)），再调 `check_semantic_conflicts(facts)`，核对全部用例的事实完整性后，与其他 9 维度 Issue 合并传入 `generate_report(..., semantic_reviewed=True)`；未完成时保持 False；独立模式下 skill 自行抽取并执行 3 类规则，输出标注 `⚠ 独立模式（语义一致性未校验）`；降级模式（facts 数量不符或解析失败）跳过第 10 维度并标注降级原因

## 评审意见表模板

```markdown
## 用例评审意见表

**评审范围**：[用例文件/模块]
**评审日期**：[YYYY-MM-DD]
**用例总数**：N 条
**整体评级**：[A 优秀 / B 合格 / C 需改进 / D 不合格]

| 维度 | 问题数 | 严重等级 | 典型问题 | 建议改进 |
|------|--------|---------|---------|---------|
| 覆盖度 | 2 | P0 | TC_005-TC_008 缺少异常类型（type=异常 的用例为 0 条） | 新增异常场景用例：网络断开/超时/依赖服务不可用 |
| 优先级合理性 | 0 | 未评估 | 缺少业务影响依据，当前只统计分布 | 补充业务风险说明 |
| 字段规范 | 1 | P0 | TC_002 expected_results 为空 | 补充最终业务结果 |
| 可执行性 | 1 | P1 | TC_004 仅写「功能正常」 | 改为可观察业务结果 |
| 冗余 | 0 | 候选 | TC_009 与 TC_010 前三步一致，尚未核实业务目标 | 核对条件及结果，不直接合并 |
| 溯源 | 1 | P0 | TC_011 的 test_point_id 不在测试点清单中 | 核对需求，补充对应测试点或删除该孤儿用例 |
| 语义一致性 | 1 | P0 | TC_003 内同一状态同时被肯定和否定 | 核对原文及抽取事实 |
```

## 评审度量报告模板

> **与生成模式效率度量对称**：生成模式在阶段 4 输出「效率度量报告」（AI 生成占比/工时节省率），评审模式在 R3 输出「评审度量报告」，使评审效果可量化、可对比、可追踪。

```markdown
## 评审度量报告

| 指标 | 本次值 | 说明 |
|------|--------|------|
| 用例总数 | N 条 | 评审范围内的用例总数 |
| 问题用例数 | M 条 | 至少有 1 个已确认问题的用例数 |
| 通过率 | (N-M)/N * 100% | 通过率 = 无问题用例 / 总用例 |
| 问题总数 | K 个 | 已确认问题数，候选问题单独展示 |
| 问题密度 | K/N | 平均每条用例的问题数（基准：< 0.5 优秀 / 0.5-1.0 合格 / > 1.0 需改进） |
| 整体评级 | [A/B/C/D/未评估] | 空集合未评估；已确认 P0 为 D；否则采用上述阈值，并标注实际评审范围 |

**维度分布**：

| 维度 | 问题数 | 占比 | 主要严重等级 |
|------|--------|------|-------------|
| 覆盖度 | x | x% | P0 |
| 优先级合理性 | x | x% | P1 |
| 字段规范 | x | x% | P0 |
| 可执行性 | x | x% | P1 |
| 冗余 | x | x% | P2 |
| 溯源 | x | x% | P0 |
| 可维护性 | x | x% | P2 |
| 可自动化 | x | x% | P2 |
| 测试数据依赖 | x | x% | P2 |
| 语义一致性 | x | x% | P0 |

**严重等级分布**：

| 严重等级 | 问题数 | 占比 | 处置建议 |
|---------|--------|------|---------|
| P0 | x | x% | 必须修订后方可执行 |
| P1 | x | x% | 建议本次迭代修订 |
| P2 | x | x% | 可纳入下个迭代修订 |

**评审结论**：[一段话总结评审发现，指出最严重的 1-2 个系统性问题及改进方向]
```

**度量报告使用场景**：
- 同模块多次评审的趋势对比（通过率是否提升、问题密度是否下降）
- 跨模块横向对比（识别问题集中的模块，作为后续测试设计重点）
- 评审改进措施的成效验证（如培训后某维度问题占比是否下降）

## 评审修订闭环

> **目的**：定义从评审结论到修订完成的完整链路，确保修订有据可查、修订后必须复审、上下文不丢失。

### 修订流程（4 步）

```
步骤 V1 核对修订授权与范围 → 步骤 V2 转交生成模式修订 → 步骤 V3 复审受影响维度 → 步骤 V4 输出修订报告
```

**步骤 V1：核对修订授权与范围**
- 用户已明确要求修订时直接执行已授权范围，不重复请求确认
- 用户基于评审意见表 + 改进建议清单，圈定本次需修订的用例 ID 列表与对应问题
- 用户可选择性修订（如仅修订 P0 问题，P1/P2 留待下迭代）
- 明确「不修订」的用例须在修订报告中标注原因

**步骤 V2：转交生成模式修订**
- 按修订范围读取 core.md 与 writing-rules.md 中必要的生成规则，定向逐条修订；不重跑与当前问题无关的完整四阶段
- 修订时必须携带评审上下文（见下方 schema），不得脱离评审意见重新生成

**步骤 V3：复审受影响维度**
- **强制复审**：修订后的用例必须重新走 R2 评审，但仅复审「受影响维度」
- 受影响维度判定：
  - 修订了 title → 复审「字段规范」「冗余」「可维护性」
  - 修订了 steps → 复审「可执行性」「冗余」「可维护性」「可自动化」「语义一致性」
  - 修订了 expected_results → 复审「字段规范」「可执行性」「可自动化」「语义一致性」
  - 修订了 priority → 复审「优先级合理性」
  - 修订了 preconditions → 复审「可维护性」「测试数据依赖」「语义一致性」
  - 新增用例 → 复审「覆盖度」「优先级合理性」「溯源」「可维护性」「可自动化」「测试数据依赖」「语义一致性」
  - 删除用例 → 复审「覆盖度」「溯源」「语义一致性」
- 若复审发现新问题 → 在授权范围内继续修订；超出范围时回到 V1 询问

**步骤 V4：输出修订报告**
- 输出修订前后对比 + 复审结果 + 修订度量（修订条数 / 复审通过率 / 残留问题数）

**修订交付**：完成授权范围内的修订和复审后，输出修改证据及残留问题；不重复请求已有授权。

## 补充用例 ID 生成规则（强制）

评审模式下发现缺失用例需要补充时，**必须**遵循 [writing-rules.md](writing-rules.md)「补充用例 ID 生成规则（强制）」——ID 格式 `TC_{模块}_{功能}_{三位序号}`、模块/功能缩写从已有用例提取、序号 = 同模块+功能最大序号 + 1，禁止不规范格式（`TC_001`）、序号跳跃与缩写不一致。本处不再重复维护规则正文，以 writing-rules.md 为唯一权威源。

## 评审模式失败模式与 Fallback

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 用例格式不规范（缺字段/结构混乱）无法解析 | 列出已识别字段，提示用户补充缺失字段后重新评审 | 仅评审可解析部分，标注「格式不规范，评审不完整」 |
| 无需求文档（溯源维度无法执行） | 仅检查用例内部一致性（步骤与预期是否对应），标注「溯源维度降级」 | 跳过溯源维度，在意见表中标注「未评审：溯源（缺需求文档）」 |
| 用例数量过大（>100 条） | 按模块/优先级分批评审，每批 ≤50 条 | 分层抽样：按优先级（P0/P1/P2/P3）× 模块交叉分层，每层抽 20%（最少 1 条），记录抽样种子（如 `seed=20260722`）确保可复现，标注「抽样评审」 |
| LLM 抽取的 facts 数量 ≠ 用例数 | 重试抽取，提示词强调"必须为每条用例产出 facts" | 跳过第 10 维度，标注「语义一致性降级：facts 抽取不完整（N/M）」 |
| LLM 抽取的 JSON 格式不合法 | 用 JSON 修复提示词二次修复 | 跳过第 10 维度，标注「语义一致性降级：facts 解析失败」 |
| subject 归一化失败（同概念不同字符串） | 提示词中补充同义词表示例重试 | 仅做严格字符串匹配，漏报在评审意见表"建议"中由 LLM 补充提示「TC_A 与 TC_B 的 subject 疑似同概念但归一化不一致，建议人工复核」 |
| 用例无 test_point_id | 保留单用例内部矛盾检查，跨用例核对实际上下文 | 不以编号前缀或 unknown 组推定相同业务场景 |
| 用例数 >100（抽取成本高） | 按模块分批抽取，每批 ≤50 条 | 分层抽样抽取（同抽样规则），标注「语义一致性抽样检测」 |

## 评审模式反例（不要做什么）

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|--------|-------------|----------|
| 1 | **直接修订用例而不输出意见表** | 用户无法理解评审结论，失去评审透明度 | 必须先输出意见表+建议清单，修订走用户授权修订后的默认生成模式 |
| 2 | **评审意见使用模糊词** | 用户无法定位具体问题 | 引用具体用例 ID + 具体字段 + 具体问题描述 |
| 3 | **跳过 CHECKPOINT 直接修订** | 违反用户确认原则，用户无法控制修订方向 | 展示意见表并按现有修订授权继续；未授权修订时仅交付意见 |
| 4 | **评审问题无依据地全打同一优先级** | 失去优先级指导价值，用户无法聚焦 | 按业务影响、执行阻断程度和修订必要性逐条分级；分布只作观察，不设固定占比 |
| 5 | **评审越界：擅自改业务规则** | 评审的职责是检查用例质量，不是改业务规则；擅自改规则会让用例脱离需求意图 | 评审意见只引用规则、指出问题，业务规则变更须回溯需求文档并由产品确认后，再通过修订闭环走生成模式修订 |
| 6 | **评审主观化：不引用判定规则** | 「感觉这个用例不好」「这个步骤写得不清楚」等主观判断无法复核，也无法转化为机器可校验的规则 | 每条评审意见必须引用 R2 表中对应的判定规则（如「最终业务结果缺失」「检查点引用不存在的步骤」），并给出具体用例 ID + 字段 + 命中证据 |
| 7 | **评审遗漏维度** | 只评覆盖度和字段规范、跳过优先级合理性/可执行性/冗余/溯源/可维护性/可自动化/测试数据依赖，导致系统性问题被掩盖 | R2 必须覆盖全部 10 维度；溯源维度在无需求文档时按失败模式 #2 降级，但不得直接跳过；度量报告的维度分布表用于自检 10 维度是否均有产出 |
| 8 | **语义一致性维度全靠 LLM 主观判断** | LLM 直接说"这两条用例冲突"无法复核，也无法转化为机器可校验规则 | 必须先抽取 SemanticFacts（结构化），再由 MCP 确定性规则判定；评审意见必须引用具体冲突类型规则（如"命中类型①：subject 相同且 polarity 互斥"）+ 给出冲突对 evidence |

## 增量评审子模式

> **目的**：迭代场景下仅评审本次新增/修改的用例，避免全量重复评审。借鉴 change-impact-analyzer 的 diff 模式。

### 触发条件

满足以下任一条件进入增量评审：
- 用户明确要求「增量评审」「只评审改动的用例」「评审本次新增」
- 用户提供 git diff 范围 + 用例文件路径（如「评审 feat/order 分支相对 main 的用例改动」）

### 工作流

增量评审复用标准评审的 R1-R3 流程，但 R1 的解析范围不同：

```
R1 解析 diff 用例 → R2 10 维度评审（仅针对变更用例）→ 🔴 CHECKPOINT R3 输出增量评审意见
```

**R1 差异**：

> **安全提示**：执行 git diff 前，必须遵守 [../integrations/quickstart.md](../integrations/quickstart.md)「安全约束」章节的 git diff 范围安全规则。

1. 执行 `git diff <range> -- <用例文件路径>` 提取变更内容
2. 从 diff 中识别新增（`+`）和修改的用例（按用例 ID 匹配前后版本）
3. 仅将变更用例纳入 R2 评审范围；未变更用例不评审

**R2 差异**：
- 覆盖度/优先级合理性维度：基于**全量用例**统计比例（变更用例可能影响整体分布），但仅对**变更用例**输出问题
- 冗余维度：变更用例须与**全量用例**比对（变更用例可能与未变更用例重复）
- 字段规范/可执行性/溯源维度：仅检查变更用例

**R3 差异**：
- 评审意见表标注「增量评审」+ diff 范围
- 度量报告的「用例总数」= 变更用例数，非全量用例数

### 增量评审失败模式

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 用例文件不在 git 仓库中 | 提示用户确认路径，或改用全量评审 | 降级为全量评审，标注「增量模式不可用，已转全量」 |
| diff 中无用例变更（用例文件未修改） | 提示用户本次无用例变更，确认是否评审全量 | 终止评审，输出「无用例变更」结论 |
| 变更用例无法从 diff 中提取结构（如格式损坏） | 列出 diff 中可识别的用例 ID，提示用户确认 | 仅评审可解析的变更用例，标注「部分变更用例无法解析」 |

## 评审报告文件化

> **目的**：将评审产出沉淀为文件，支持历史对比与趋势分析。默认输出到 `docs/review-reports/` 目录。

### 触发条件

满足以下任一条件触发文件化：
- 用户明确要求「保存评审报告」「输出到文件」「沉淀评审结果」
- 评审用例数 ≥20 条（规模化评审建议留存）
- 评审度量报告整体评级为 C 或 D（需改进/不合格，建议留存用于追踪改进）

### 文件命名规则

```
docs/review-reports/{YYYYMMDD}-{module}-{mode}.md
```

- `YYYYMMDD`：评审日期
- `module`：被评审模块（从用例 ID 的模块段提取，如 `TC_order_*` → `order`）
- `mode`：`full`（全量评审）/ `incremental`（增量评审）/ `sampled`（抽样评审）

**示例**：`docs/review-reports/20260722-order-incremental.md`

### 文件内容结构

```markdown
# 用例评审报告 · {模块} · {YYYY-MM-DD}

## 元信息
- 评审日期：{YYYY-MM-DD}
- 评审模式：{全量/增量/抽样}
- 评审范围：{用例文件路径 / git diff 范围}
- 用例总数：N 条
- 整体评级：{A/B/C/D}

## 评审意见表
{R3 输出的评审意见表}

## 改进建议清单
{R3 输出的改进建议清单}

## 评审度量报告
{R3 输出的评审度量报告}

## 修订记录（若有）
{若进入修订闭环，V4 输出的修订报告}

## 历史对比（若有同类报告）
- 上次评审：{日期} {评级} {通过率} {问题密度}
- 本次评审：{日期} {评级} {通过率} {问题密度}
- 趋势：{通过率变化} {问题密度变化} {评级变化}
```

### 文件化失败模式

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| `docs/review-reports/` 目录不存在 | 创建目录后写入 | 在对话中输出完整报告，提示用户手动保存 |
| 模块名无法从用例 ID 提取（如 ID 格式不规范） | 提示用户指定模块名 | 用 `unknown` 作为模块名 |
| 同日同模块同模式已存在报告文件 | 在文件名追加序号（如 `-02`） | 覆盖旧文件前提示用户确认 |
