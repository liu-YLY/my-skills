# 评审方案（面向需求相关方）

> 本文件定义如何把「测试思路 + 用例覆盖度」组织成一份可宣讲、可决策的评审方案，面向产品、UI、前端、后端等需求相关方。
>
> **边界**：本文件管「评审会上讲什么、要谁确认什么、结论怎么闭环」；单条用例的质量判定见 [review-mode.md](review-mode.md)，用例数量过大时的分批与抽样见 [large-scale-review.md](large-scale-review.md)。

## 触发条件

满足以下任一条件进入评审方案模式：

- 用户要求「评审方案」「评审会材料」「向产品/UI/前后端说明测试思路」「覆盖度汇报」
- 评审会参会方包含产品、UI、前端、后端等非测试角色
- 需要输出可宣讲的评审材料，而不只是问题清单

**与另外两个子模式的关系**：评审方案决定「讲什么」，review-mode R2 决定「质量怎么判」，规模化评审决定「分几批评、抽哪些」。三者可以组合：先在内部完成 R2 与规模化评审，再把结论整理成对外评审方案。

## 工作流（6 步）

```
P1 定评审类型与角色 → P2 建需求追溯矩阵 → P3 算覆盖度 → P4 写测试思路 → P5 组材料与议程 → P6 结论与闭环
```

## P1 评审类型与角色

评审类型参考 ISO/IEC 20246 / IEEE 1028 的划分，按正式程度从小到大选择：

| 类型 | 适用场景 | 参会方 | 产出 | 建议时长 |
|------|---------|--------|------|---------|
| 桌前检查（desk check） | 个人自查、小范围改动 | 作者本人 | 自查问题清单 | 30 分钟 |
| 走查（walkthrough） | 作者主讲，干系人跟随理解 | 作者 + 相关方 | 理解确认 + 问题清单 | 60 分钟 |
| 同行评审（peer review） | 同级测试或开发互评 | 测试/开发同行 | 技术问题与改进项 | 60–90 分钟 |
| 干系人评审（stakeholder review） | 需求相关方确认范围与覆盖 | 产品/UI/前后端/测试 | 范围确认 + 覆盖确认 + 行动项 | 60–90 分钟 |
| 正式评审（inspection） | 高等级、强监管或重大版本 | 主持人 + 评审组 + 记录员 | 正式记录 + 签字确认 | 90–120 分钟 |

**角色分工**（干系人评审必配）：

| 角色 | 职责 | 本次要确认的内容 |
|------|------|-----------------|
| 主持人 | 控节奏、守时间盒、裁定结论 | 是否达到出口准则 |
| 作者（测试） | 讲测试范围、思路、覆盖度 | 回答覆盖缺口与不测理由 |
| 记录员 | 记录问题、结论、行动项 | 记录完整可追溯 |
| 产品 | 确认需求理解与验收口径 | 需求是否完整、一致、可测 |
| UI | 确认交互与视觉覆盖 | 异常态、空态、加载态是否覆盖 |
| 前端/后端 | 确认技术可行性与数据一致性 | 接口契约、并发、兼容、依赖 |
| 测试负责人 | 确认范围与优先级 | 风险是否可接受 |

## P2 需求追溯矩阵（RTM）

对外评审的核心材料。每一条需求都要能回答「测了没有、哪条用例测的」。

| 需求 ID | 需求描述 | 测试点 ID | 用例 ID | 覆盖状态 | 备注 |
|---------|---------|----------|---------|---------|------|
| REQ_001 | 手机号 + 验证码登录 | TP_001 | TC_login_001~004 | 已覆盖 | - |
| REQ_002 | 连续错误 5 次锁定 30 分钟 | TP_002 | TC_login_010 | 部分覆盖 | 解锁后重试未覆盖 |
| REQ_003 | 登录失败提示国际化 | - | - | 未覆盖 | 待确认是否本期范围 |
| REQ_004 | 第三方登录 | - | - | 不测 | 本期不上线，需产品确认 |

**覆盖状态枚举**：`已覆盖` / `部分覆盖` / `未覆盖` / `不测`。

**两条强制规则**：

- 每条需求至少关联 1 条用例；无关联的必须标「未覆盖」或「不测」并写明理由
- 每条用例至少回溯到 1 条需求；回溯不到的标「孤儿用例」，在评审会上确认是否删除或补充需求

## P3 覆盖度画像

覆盖度必须用「需求/场景」口径，不能用用例条数或执行通过率替代。

| 指标 | 公式 | 本次值 | 说明 |
|------|------|--------|------|
| 需求覆盖率 | 已覆盖需求项 / 需求项总数 | x% | 部分覆盖按 0.5 计或单列，口径需在方案中写明 |
| 场景覆盖率 | 已覆盖场景 / 识别出的场景 | x% | 按正向、异常、边界、权限、并发、兼容分类统计 |
| 高风险覆盖率 | 已覆盖高风险场景 / 高风险场景总数 | x% | P0/P1 场景应 100% |
| 用例可追溯率 | 有需求 ID 的用例 / 用例总数 | x% | 衡量是否存在孤儿用例 |
| 不测范围占比 | 不测需求项 / 需求项总数 | x% | 必须逐项给出理由 |

**覆盖类型矩阵**（逐类回答「需求要不要、我们做没做」）：

| 类型 | 需求是否要求 | 已设计 | 缺口与处置 |
|------|-------------|--------|-----------|
| 正向流程 | 是 | 是 | - |
| 异常与错误处理 | 是 | 部分 | 补网络异常 2 条 |
| 边界值 | 是 | 是 | - |
| 权限与角色 | 是 | 否 | 待确认是否本期范围 |
| 并发与幂等 | 是 | 部分 | 仅覆盖重复提交 |
| 兼容性 | 否 | - | 不在本期范围 |
| 性能与安全 | 否 | - | 由性能/安全专项覆盖，本次不重复 |

**原则**：缺口必须给出处置（补用例 / 接受风险 / 移出范围），不能只列「未覆盖」三个字。

## P4 测试思路说明（业务语言版）

面向非测试角色时，必须用业务语言讲，每一项「一句话结论 + 一个具体例子」，不堆测试术语。

| 要讲的内容 | 讲法要求 | 示例 |
|-----------|---------|------|
| 测试范围 | 先讲不测什么，再讲测什么 | 「本期只测登录主链路，不做压力测试，压测由性能专项覆盖」 |
| 分层策略 | 说明各层各管什么，避免重复 | 「接口层验规则，UI 层验交互，E2E 只保留 5 条主流程」 |
| 设计方法 | 用需求语言解释方法 | 「手机号长度用边界值：10 位、11 位、12 位各一条」 |
| 规则组合 | 讲清规则之间的约束 | 「满减、封顶、限领三个规则用判定表组合，共 8 种有效组合」 |
| 状态流转 | 讲清非法跳转 | 「订单从待支付不能直接到已完成，这类跳转单独覆盖」 |
| 风险与优先级 | 说明为什么这些先测 | 「支付失败会导致资损，所以 P0；文案调整是 P2」 |
| 数据与环境 | 说明依赖与造数方式 | 「需要 3 个测试账号和 1 个沙箱商户号」 |
| 已知限制 | 如实说明假设 | 「短信网关为 mock，真机验证需联调阶段补测」 |

**禁止**：只报用例条数、只讲正向流程、用「已充分覆盖」这类不可验证的结论。

## P5 材料与议程

### 会前材料清单（建议提前 1 个工作日发出）

1. 一页纸摘要：范围、结论、待确认项（不超过 1 页）
2. 需求追溯矩阵（P2）
3. 覆盖度画像与类型矩阵（P3）
4. 待确认问题清单，按角色归属
5. 风险与不测范围说明
6. 用例明细（附录或链接，不要求会上逐条读）

### 议程模板（60 分钟干系人评审）

| 时间 | 内容 | 主讲 | 产出 |
|------|------|------|------|
| 0–5 分钟 | 背景、目标、本次范围 | 主持人 | 对齐目标 |
| 5–15 分钟 | 测试范围与不测范围 | 测试 | 范围确认 |
| 15–30 分钟 | 测试思路与设计方法 | 测试 | 方法确认 |
| 30–45 分钟 | 覆盖度画像与追溯矩阵 | 测试 | 缺口确认 |
| 45–55 分钟 | 待确认问题与风险 | 各角色 | 结论或行动项 |
| 55–60 分钟 | 结论、行动项、下次检查点 | 主持人 | 会议记录 |

**时间盒规则**：单条问题讨论超过 5 分钟未收敛，转为行动项会后跟进，不在会上展开细节。

## P6 结论与闭环

### 结论三态

| 结论 | 判定条件 | 后续动作 |
|------|---------|---------|
| 通过 | 无 P0 待确认项，覆盖缺口均有处置 | 进入执行 |
| 有条件通过 | 存在不影响执行的待确认项或补测项 | 限期闭环后进入执行 |
| 不通过 | 需求不一致、关键场景未覆盖或风险不可接受 | 修订后重新评审 |

### 评审记录模板

```markdown
## 用例评审记录

**评审类型**：[走查 / 同行评审 / 干系人评审 / 正式评审]
**评审日期**：[YYYY-MM-DD]
**参会角色**：[产品 / UI / 前端 / 后端 / 测试]

### 结论

[通过 / 有条件通过 / 不通过]

### 问题与行动项

| 编号 | 类型 | 问题 | 提出人 | 归属角色 | 处置 | 截止时间 | 状态 |
|------|------|------|--------|---------|------|---------|------|
| RV_001 | 需求歧义 | 锁定 30 分钟是否含解锁尝试次数 | 产品 | 产品 | 补充需求说明 | 2026-11-05 | 待办 |
| RV_002 | 覆盖缺口 | 并发重复提交仅覆盖 1 条 | 后端 | 测试 | 补 2 条幂等用例 | 2026-11-06 | 待办 |

### 风险接受记录

| 风险 | 影响 | 接受人 | 理由 |
|------|------|--------|------|
| 第三方登录本期不测 | 上线后无法验证 | 产品 | 功能未上线 |

### 出口准则核对

- [ ] 所有 P0 待确认项已有结论
- [ ] 覆盖缺口均有处置（补用例 / 接受风险 / 移出范围）
- [ ] 行动项均有负责人与截止时间
```

**出口准则**（全部满足才算评审结束）：P0 待确认项清零、覆盖缺口有处置、行动项有责任人与时限、风险接受有记录人。

## 按角色检查清单（会前自查 + 会上提问）

| 角色 | 检查点 |
|------|--------|
| 产品 | 需求是否完整、无歧义、可测；验收标准是否明确；优先级是否与用例优先级一致 |
| UI | 主流程与分支路径是否覆盖；空态、异常态、加载态、超长文本是否覆盖 |
| 前端 | 交互与状态切换是否覆盖；兼容性与降级策略是否覆盖 |
| 后端 | 接口契约与错误码是否覆盖；并发、幂等、事务边界是否覆盖；外部依赖异常是否覆盖 |
| 测试 | 追溯矩阵是否完整；覆盖缺口是否有处置；不测范围是否有理由；用例是否可执行可判定 |

## 度量口径与常见误用

| 指标 | 正确口径 | 常见误用 |
|------|---------|---------|
| 需求覆盖率 | 已覆盖需求项 / 需求项总数 | 用「用例条数多」当作覆盖充分 |
| 场景覆盖率 | 已覆盖场景 / 识别场景 | 只统计正向流程 |
| 用例通过率 | 执行通过 / 已执行 | 用通过率代替需求覆盖率 |
| 缺陷发现率 | 本阶段发现缺陷 / 总缺陷 | 把用例评审问题当作产品缺陷 |
| 逃逸率 | 上线后缺陷 / 总缺陷 | 用单版本数据下结论 |

**原则**：评审阶段报告的是「设计覆盖度」，不是「执行通过率」；两者不能混用，也不能互相替代。

## 反例（不要做什么）

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|--------|-------------|----------|
| 1 | 用用例条数讲覆盖度 | 条数多不等于需求覆盖全 | 用需求追溯矩阵与需求覆盖率 |
| 2 | 用执行通过率代替需求覆盖率 | 评审阶段尚未执行，口径错位 | 汇报设计覆盖度，执行数据单列 |
| 3 | 只讲正向流程 | 干系人误以为异常场景已覆盖 | 按类型矩阵逐类说明 |
| 4 | 不说明不测范围 | 风险被隐藏，上线后争议 | 逐项列出不测项、理由与接受人 |
| 5 | 会前不发材料，会上现讲 | 参会人无法提前准备，会议变成宣讲 | 提前 1 个工作日发一页纸摘要与矩阵 |
| 6 | 评审会没有决策人 | 问题议而不决，结论无效 | 明确产品/技术负责人必须到场 |
| 7 | 结论不落行动项 | 问题散会即失，无法追踪 | 输出记录表，含负责人与截止时间 |
| 8 | 把评审会开成逐条读用例 | 时间被细节耗尽，重点无法讨论 | 会上只过缺口、风险与待确认项 |
| 9 | 覆盖缺口只写「未覆盖」 | 无法判断是遗漏还是有意排除 | 每项缺口给出补用例/接受风险/移出范围 |
