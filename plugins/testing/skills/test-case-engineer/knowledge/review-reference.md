# 评审模板与增量评审（按需）

> **何时阅读**：评审模式 R3 生成意见表/度量报告、进入修订闭环、或用户要求增量评审时读取。R1–R2 判定规则见 [review-mode.md](review-mode.md)。

## 评审意见表模板

```markdown
## 用例评审意见表

**评审范围**：[用例文件/模块]
**评审日期**：[YYYY-MM-DD]
**用例总数**：N 条
**整体评级**：[A 优秀 / B 合格 / C 需改进 / D 不合格]

| 维度 | 问题数 | 严重等级 | 典型问题 | 建议改进 |
|------|--------|---------|---------|---------|
| 覆盖度 | 2 | P0 | TC_005-TC_008 缺少异常类型（type=异常 的用例为 0 条） | 新增异常场景用例：网络断开/超时/依赖服务不可用 |
| 优先级合理性 | 0 | 未评估 | 缺少业务影响依据，当前只统计分布 | 补充业务风险说明 |
| 字段规范 | 1 | P0 | TC_002 expected_results 为空 | 补充最终业务结果 |
| 可执行性 | 1 | P1 | TC_004 仅写「功能正常」 | 改为可观察业务结果 |
| 冗余 | 0 | 候选 | TC_009 与 TC_010 前三步一致，尚未核实业务目标 | 核对条件及结果，不直接合并 |
| 溯源 | 1 | P0 | TC_011 的 test_point_id 不在测试点清单中 | 核对需求，补充对应测试点或删除该孤儿用例 |
| 语义一致性 | 1 | P0 | TC_003 内同一状态同时被肯定和否定 | 核对原文及抽取事实 |
```

## 改进建议清单模板

```markdown
## 改进建议清单（按用例 ID）

| 用例 ID | 问题维度 | 严重等级 | 具体问题 | 改进建议 |
|---------|---------|---------|---------|---------|
| TC_002 | 字段规范 | P0 | expected_results 为空 | 补充：「页面显示『用户名或密码错误』提示，3 秒后消失」 |
| TC_004 | 可执行性 | P1 | steps 含占位符「某用户名」 | 改为具体值「testuser@example.com」 |
| TC_006 | 字段规范 | 候选 | 标题语义可能不明确 | 结合业务语境确认，幂等性等术语不违规 |
| TC_009 | 冗余 | 候选 | 与 TC_010 前三步相同 | 核对是否同一业务规则，不因前置操作相同合并 |
| TC_011 | 溯源 | P0 | test_point_id 不在测试点清单 | 核对需求：若 TP_005 已删除则删除该用例；若遗漏则补 TP_005 |
```

## 评审度量报告模板

> 与生成模式效率度量对称：生成模式在阶段 4 输出效率度量，评审模式在 R3 输出评审度量，使效果可量化、可对比、可追踪。

```markdown
## 评审度量报告

| 指标 | 本次值 | 说明 |
|------|--------|------|
| 用例总数 | N 条 | 评审范围内的用例总数 |
| 问题用例数 | M 条 | 至少有 1 个已确认问题的用例数 |
| 通过率 | (N-M)/N * 100% | 通过率 = 无问题用例 / 总用例 |
| 问题总数 | K 个 | 已确认问题数，候选问题单独展示 |
| 问题密度 | K/N | 平均每条用例的问题数（基准：< 0.5 优秀 / 0.5-1.0 合格 / > 1.0 需改进） |
| 整体评级 | [A/B/C/D/未评估] | 空集合未评估；已确认 P0 为 D；否则采用阈值，并标注实际评审范围 |

**维度分布**：

| 维度 | 问题数 | 占比 | 主要严重等级 |
|------|--------|------|-------------|
| 覆盖度 | x | x% | P0 |
| 优先级合理性 | x | x% | P1 |
| 字段规范 | x | x% | P0 |
| 可执行性 | x | x% | P1 |
| 冗余 | x | x% | P2 |
| 溯源 | x | x% | P0 |
| 可维护性 | x | x% | P2 |
| 可自动化 | x | x% | P2 |
| 测试数据依赖 | x | x% | P2 |
| 语义一致性 | x | x% | P0 |

**严重等级分布**：

| 严重等级 | 问题数 | 占比 | 处置建议 |
|---------|--------|------|---------|
| P0 | x | x% | 必须修订后方可执行 |
| P1 | x | x% | 建议本次迭代修订 |
| P2 | x | x% | 可纳入下个迭代修订 |

**评审结论**：[总结最严重的 1-2 个系统性问题及改进方向]
```

**度量报告使用场景**：同模块多次评审趋势对比；跨模块横向对比定位问题集中模块；评审改进措施成效验证。

## 修订报告模板

```markdown
## 用例修订报告

**修订日期**：[YYYY-MM-DD]
**对应评审**：[评审日期 + 整体评级]
**修订范围**：M 条用例（修订）/ K 条用例（不修订，标注原因）

| 用例 ID | 修订前问题 | 修订动作 | 复审维度 | 复审结果 |
|---------|-----------|---------|---------|---------|
| TC_002 | expected_results 为空（P0） | 补充预期结果 | 字段规范、可执行性 | 通过 |
| TC_006 | title 含模糊词（P0） | 改为「登录-手机号错误密码-提示错误」 | 字段规范、冗余 | 通过 |
| TC_009 | 与 TC_010 重复（P2） | 不修订（纳入下迭代） | - | - |

**修订度量**：修订条数 x；复审通过率 x%；残留问题数 x（含未修订的 P1/P2）

**复审结论**：[修订后用例集整体状态，是否达到可执行标准]
```

## 增量评审子模式

> 仅评审本次新增/修改的用例，避免全量重复评审；借鉴 change-impact-analyzer 的 diff 模式。

**触发**：用户明确要求「增量评审」「只评审改动的用例」「评审本次新增」；或提供 git diff 范围 + 用例文件路径。

**工作流**：复用 R1–R3，仅 R1 解析范围不同。

```text
R1 解析 diff 用例 → R2 10 维度评审（仅变更用例）→ CHECKPOINT R3 输出增量评审意见
```

**R1 差异**：

> **安全提示**：执行 git diff 前，必须遵守 [../integrations/quickstart.md](../integrations/quickstart.md)「安全约束」的 git diff 范围安全规则。

1. 执行 `git diff <range> -- <用例文件路径>` 提取变更
2. 按用例 ID 匹配前后版本，识别新增（`+`）和修改的用例
3. 仅将变更用例纳入 R2；未变更用例不评审

**R2 差异**：
- 覆盖度/优先级：基于全量用例统计比例，但仅对变更用例输出问题
- 冗余：变更用例须与全量用例比对
- 字段规范/可执行性/溯源：仅检查变更用例

**R3 差异**：意见表标注「增量评审」+ diff 范围；度量报告「用例总数」= 变更用例数。

**增量失败模式**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 用例文件不在 git 仓库 | 提示确认路径，或改用全量评审 | 降级全量，标注「增量模式不可用，已转全量」 |
| diff 中无用例变更 | 提示本次无用例变更，确认是否评审全量 | 终止评审，输出「无用例变更」结论 |
| 变更用例无法从 diff 提取结构 | 列出可识别 ID，提示用户确认 | 仅评审可解析的变更用例，标注「部分变更用例无法解析」 |
