# 语义评审 Rubric（J 类规则）

> **定位**：`scripts/validate_cases.py` 之后的第二道闸门。脚本负责可布尔判定的 D 类规则；本文件覆盖脚本判不了的 J 类规则，由**独立上下文的评审者**执行。
> **与 review-mode.md 的区别**：review-mode 是面向评审会/干系人的 10 维度全面评审（含流程、度量、报告）；本文件只回答一个问题——**这批用例能不能交付**。
> **前置条件**：validator 已通过（0 error）。让评审者去挑格式错误是浪费，且会稀释它对语义问题的注意力。

## 使用方法

1. 把本文件与用例文件一起交给评审者
2. 评审者**只看产物**，不看生成过程、不看修改历史
3. 每条判定必须引用原文片段；引不出原文的判定视为无效
4. 不输出总分、不输出"整体良好"这类无法执行的结论

## 判定通则

- **只判可举证的**：说不清"哪一条、哪句话、为什么不对"，就不要报
- **区分缺失与错误**：缺失是"没有"，错误是"有但不对"，两者分列
- **不重复 D 类**：格式、词表、句长已由脚本判定，这里不再报
- **给改法**：每条问题必须给出可执行的修改方向，而不是"建议优化"

## J1 业务结果可判定性 `JUDGEABLE_RESULT`

**判定问题**：执行人只看这条结果，能否直接判 pass 或 fail，无需追问、无需自行解释？

**FAIL 条件**（满足任一）：
- 含评价词但无具体值或位置：`保存成功`、`功能正常`、`显示正确`
- 只描述动作、未描述可观察状态：`提交表单`
- 推测语气：`应生效`、`会被拦截`、`可以正常使用`
- 两种互斥结果并列作为通过条件：`提示错误或跳转首页`

**PASS 示例**：`输入框下方显示「验证码不正确」，输入框保持红色边框`
**不算 FAIL**：引用具体文案（`显示「保存成功」`）、具体的状态值（`status 由 pending 变为 paid`）、明确的空值/非空断言

**必须引用**：该条业务结果原文

## J2 测试点覆盖度 `COVERAGE`

**判定问题**：测试点清单里的每一项，是否都能指到至少一条用例？

**FAIL 条件**：
- 存在测试点无对应用例，且「裁剪说明」未写明理由
- 仅覆盖 Happy Path，反向/边界/权限缺失且无说明
- 用例数量显著低于测试点估算值（如估算 20 条实际 5 条）且无解释

**PASS 条件**：每个测试点或有用例覆盖，或在裁剪说明中写明未覆盖理由（如"低风险字段，本次不覆盖"）

**必须引用**：未覆盖的测试点编号 + 裁剪说明原文（若有）

**常见误判**：把「需求没写所以不测」当合规——需求缺失应记入原文问题清单，不等于裁剪合理

## J3 术语与动词一致性 `TERM_CONSISTENCY`

**判定问题**：同一对象、同一动作，全文是否只有一个说法？

**FAIL 条件**：
- 同一对象两种称呼：`弹窗` / `对话框`、`浮层` / `弹层`
- 同一动作两种动词：`点击` / `点选`、`输入` / `录入`
- 同一字段两种叫法：`昵称` / `用户昵称`

**PASS 例外**：界面本身存在两个不同按钮时，按界面原文区分不视为不一致

**必须引用**：冲突的两处原文 + 所在用例 ID

---

## J4 步骤可执行性 `STEP_EXECUTABLE`

**判定问题**：执行人照着步骤能否直接操作，不需要问作者？

**FAIL 条件**：
- 缺少操作对象或输入值：`填写相关信息`、`输入合法值`、`选择正确的选项`
- 占位话术：`按测试点要求执行`、`执行对应操作`、`验证相关功能`
- 用位置代替元素名：`点击左上角的按钮`
- 步骤内含条件分支：`如果按钮可点击则点击，否则刷新`

**PASS 示例**：`在「昵称」输入框输入 `测试用户``、`点击「保存」按钮`

**必须引用**：该步骤原文

---

## J5 预期与步骤对应 `EXPECT_STEP_ALIGN`

**判定问题**：每条预期是否对应步骤中真实发生的操作？

**FAIL 条件**：
- 预期描述了步骤中未出现的操作结果（凭空断言）
- 改状态的操作（新增/修改/删除/提交/发送）没有任何预期覆盖其直接后果
- 预期指向的字段或页面在步骤中从未出现过

**必须引用**：步骤原文 + 预期原文

**常见误判**：数据准备类步骤可以无断言，但需标注「准备」

---

## J6 拆分与合并合理性 `GRANULARITY`

**判定问题**：一条用例是否只有一个业务目标？同构场景是否做了不必要的拆分？

**FAIL 条件**：
- 一条用例含两个独立业务目标（失败时无法定位是哪一步出问题）
- 同一规则的数据变体被拆成多条完整用例，而非参数化
- 合并后无法指出「哪一步、哪个字段」导致失败

**必须引用**：标题 + 步骤中体现多目标的那几步

---

## J7 优先级业务依据 `PRIORITY_BASIS`

**判定问题**：优先级是否由业务影响推导，而非机械分配？

**FAIL 条件**：
- 全部用例同一优先级（如 10 条全 P0）且无风险说明
- P0 用例不含核心流程、资金、数据或权限边界
- 同类场景优先级互相矛盾且无解释

**PASS 条件**：优先级分布有依据，或分布异常但在交付说明中给出了理由

**必须引用**：优先级分布 + 至少 2 条存疑用例及其理由缺失之处

---

## J8 需求追溯完整性 `TRACEABILITY`

**判定问题**：用例**若填写了**追溯，能否反查到真实存在的需求或测试点？

> **必填性以 writing-rules.md 为准**：`需求追溯` 字段为非必填（字段说明表标「否」）。**完全缺省不判 FAIL**，只作为观察项记录；只有「填了但指错」才计入问题数。不要比主规则更严。

**FAIL 条件**：
- 追溯指向不存在的测试点编号或需求 ID
- 追溯填「待补充」但需求原文实际存在对应条目

**观察项**（不计入问题数）：全部用例均无追溯字段 → 在输出末尾单列提示，由交付方决定是否补

**PASS 条件**：追溯可对应，或需求本身无正式 ID 且已如实标注来源

**必须引用**：该用例的追溯字段原文 + 被指向对象的实际情况

## 输出格式

默认输出 markdown 表格：

```markdown
## 评审结果

用例 24 条 · 问题 6 条 · 覆盖缺口 2 项

| 用例 ID | 规则 | 原文引用 | 判定 | 修改建议 |
|---|---|---|---|---|
| TC_LOGIN_003 | JUDGEABLE_RESULT | 业务结果：`登录成功` | 无具体位置与值 | 改为 `页面跳转到 /home，右上角显示「测试用户」` |

### 覆盖缺口

| 测试点 | 状态 | 说明 |
|---|---|---|
| TP-05 | 无用例 | 裁剪说明为空，需补用例或写明理由 |

### 未覆盖的 J 类规则

- 无（全部 8 条已判）
```

用户要求 JSON 时，输出：

```json
{

  "issues": [

    }

```

## 禁止事项

- **禁止输出总分或等级**（如"质量 85 分""整体良好"）——无法执行
- **禁止改写用例**——评审者只给建议，改写由生成方执行
- **禁止无引用判定**——说不出原文位置的，不报
- **禁止重复 D 类问题**——格式、词表、句长由脚本负责
- **禁止为凑数报问题**——宁可报 2 条真的，不报 10 条虚的
