# 测试分层与交付形态

> **何时阅读**：阶段 2 必读；阶段 3 确定编排分组与输出类型时查阅。
> **覆盖范围**：E2E / API / 契约 / 集成 / 单元 五层定义、本 Skill 默认重心、禁止混层规则、L1/L2-A/L2-B/L3 编排组占比、默认输出类型、与上游策略的分层映射。

## 常见分层（简图）

```text
        /\
       /  \     E2E / 验收（少而精，用户旅程）
      /----\
     /      \   API / 集成 / 契约（服务行为、错误码、兼容）
    /--------\
   / 单元/组件  \（开发主导，函数/类/模块边界）
  /--------------\
```

| 分层 | 典型目标 | 谁主导 | 本 Skill 常见产出 |
|------|----------|--------|-------------------|
| **单元 / 组件** | 函数/类边界、分支、异常 | 开发 | **测点提示**（输入边界、异常路径） |
| **集成** | 多模块/DB/消息队列联调 | 开发/测试 | 关键路径的**接口级或环境级**步骤 |
| **API / 服务** | HTTP/RPC 行为与契约 | 测试（或开发） | **请求/响应/状态码/错误码** 可断言的用例 |
| **契约 / 消费者-提供者** | Schema 与版本兼容 | 视团队 | **字段、版本号、破坏性变更** 相关测试点 |
| **E2E / 功能验收** | 完整用户旅程、多端 | 测试 | **默认可执行场景用例**（本 Skill 默认重心） |

## 本 Skill 的默认重心

- **默认**：产出**可执行的场景级用例**，重心为 **E2E / 功能验收**（含必要 UI 步骤）
- 若用户或需求明确后端/接口，则**重心必须上移到 API**，禁止用纯 UI 步骤代替服务侧验证

## 禁止混层

- **禁止**：在一条「接口用例」里只写「打开页面点击」而无请求/断言
- **禁止**：在「E2E 用例」里堆砌大量底层字段而又无操作上下文
- 应拆条或分组，保持每条用例的分层一致性

## 分层选择简决策

1. 需求文档**仅描述接口/无界面** → 必须以 **API（+契约按需）** 为主
2. 需求**强依赖浏览器/多端流程** → 必须以 **E2E** 为主，API 作为辅助或回归子集
3. **重构无行为变更** → 必须使用回归清单，禁止强行补全所有分层
4. **不确定** → 必须在「存疑点」中列出，并在测试点表中标注分层列

## 编排组占比（L1 / L2-A / L2-B / L3）

根据需求类型选择用例的编排分组与占比，确定本次输出的层级重心：

| 分层 | 名称 | 关注点 | 适用场景 | 目标占比 |
|------|------|--------|----------|----------|
| **L1** | 单元层 | 核心算法、复杂计算逻辑 | 核心业务逻辑型需求 | 0-10% |
| **L2-A** | 业务场景层 | 跨接口业务闭环、状态机流转 | 复杂业务流程、异步任务 | 30% |
| **L2-B** | 接口契约层 | API 参数校验、DB 读写、第三方对接 | 所有后端功能 | 30% |
| **L3** | UI/E2E 层 | 用户旅程、交互体验、端到端闭环 | 前端样式、交互相关 | 40% |

**动态调整规则**：

| 需求类型 | 典型场景 | L2 占比 | L3 占比 |
|----------|----------|---------|---------|
| 核心业务逻辑型 | 积分规则、自动化营销、VIP 判定 | 70% | 30% |
| 数据集成型 | 对接新物流商、同步订单、数据报表 | 80% | 20% |
| 纯交互/UI型 | 首页改版、新增引导弹窗、样式优化 | 20% | 80% |

**分层选择决策**：
1. 需求涉及核心算法/复杂计算？→ 必须选择 L1 单元测试
2. 需求涉及跨接口业务闭环？→ 必须选择 L2-A 业务场景测试
3. 需求涉及 API/数据/第三方？→ 必须选择 L2-B 接口测试
4. 需求涉及 UI/交互/体验？→ 必须选择 L3 E2E 测试

## 默认输出功能测试用例

除非用户明确要求或需求内容明显涉及以下类型，否则只输出功能测试用例（`type: functional`）：

| 额外类型 | 触发条件 |
|----------|----------|
| performance | 需求提到响应时间、并发量、吞吐量要求 |
| security | 涉及认证、授权、敏感数据、支付 |
| compatibility | 需求提到多浏览器、多设备、多系统版本 |

当需要额外类型时，在功能测试用例之后独立成组追加。

## 与上游/内部分层体系的映射

本文件五层是 case 侧分层的权威定义。存在两套相邻分层体系，映射关系如下：

### strategy 三层 → case 五层

上游 test-strategy-engineer（见 [../../test-strategy-engineer/SKILL.md](../../test-strategy-engineer/SKILL.md)）输出经典三层（单元/接口/UI）分层比例时，按本表换算：

| strategy 三层 | case 五层去向 | 换算说明 |
|---|---|---|
| 单元 | 单元 | 1:1 对应 |
| 接口 | 集成 + API + 契约 | 三层合计承接 strategy 的"接口"占比，内部按需求特征分配 |
| UI | E2E / 验收 | 1:1 对应 |

### case 内部：五层定义 vs L1/L2-A/L2-B/L3 编排组

上方「编排组占比」的 L1/L2-A/L2-B/L3 是本文件五层的**用例编排分组视角**（按需求类型编排用例时的占比分组），非另一套分层标准：

| 编排组 | 对应本文件分层 |
|---|---|
| L1（单元层） | 单元 |
| L2-A（业务场景层） | 集成 / API（业务闭环） |
| L2-B（接口契约层） | API / 契约 |
| L3（UI/E2E 层） | E2E / 验收 |

其占比（L1 0-10% / L2-A 30% / L2-B 30% / L3 40%）为**编排目标**，非分层硬约束。

**优先级**：接收上游 strategy 分层比例时，按上方映射表换算后执行；无上游输入时，按「编排组占比」的默认比例执行。
