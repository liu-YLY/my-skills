# 团队测试规范与标准

> **何时阅读**：阶段 3 划分优先级与类型、阶段 4 复核覆盖基线时必读。写作格式以 [writing-rules.md](writing-rules.md) 为唯一权威源。

## 命名变体与超长标题例外

- 专项 ID 变体：性能 `TC_{模块}_PERF_{三位序号}`；安全 `TC_{模块}_SEC_{三位序号}`。
- **超长标题保留条件**（禁为凑 40 字截断或加省略号）：① 删词会导致同模块标题重名；② 含必要环境/版本标识（如弱网、v2 接口）；③ 执行人靠该条件快速区分场景。

## 优先级（P0–P3）

| 等级 | 业务风险定义 | 回归安排 |
|------|--------------|----------|
| **P0** | 核心主流程阻断、资金/关键数据损毁、核心权限或安全边界失效 | 发布准入必测 |
| **P1** | 高频支线、重要角色权限、核心异常拦截及明确指标的性能风险 | 变更与迭代回归 |
| **P2** | 影响可控、存在替代路径的一般校验或次要交互问题 | 按受影响范围回归 |
| **P3** | 低频边缘场景、纯体验细节 | 按需抽检 |

**定级三步法**：① 判失败后的业务后果（主流程/资金/数据/权限/影响面）→ ② 结合触发频率、历史缺陷与本次变更定回归必要性 → ③ 指定 P0–P3（高风险写明依据）。**严禁**从用例类型自动推导优先级（安全/性能同样可为 P0），**严禁**为迎合固定比例增删用例或强改等级（不支持 P3 的平台映射至 P2 并备注）。

## 用例类型选择

按**主要验证目标**单选（不为凑类型补造无需求依据的用例）：
- `functional`（业务功能正确性，默认） / `ui`（视觉布局渲染，有设计稿或前端改动时） / `security`（鉴权/越权/脱敏/注入，涉权限或敏感数据时） / `performance`（时延/吞吐/并发，需求给明确指标时） / `compatibility`（跨端/浏览器/版本，需求提兼容要求时） / `usability`（有明确交互规范时） / `accessibility`（有无障碍要求时） / `observability`（要求日志/指标/告警/trace 验收时）。

## 新功能覆盖与回归基线

- **新功能六项核对**（按焦点与风险取舍，缺输入标未评估）：① 至少 1 条完整 Happy Path；② 本次改动的有阈值字段取一组三点边界；③ 需求明确的角色权限差异；④ 明确的条件/配置联动；⑤ 关键取消/返回/刷新动作；⑥ 非焦点只留 1 条冒烟，无依据服务故障 0 条。
- **变更回归范围**：Bug 修复 → `修复点 + 关联 P0`；小功能迭代 → `变更功能全量 + 上下游 P0`；数据库/配置变更 → `受影响模块 P0 + P1`；大版本发布 → `P0 全量 + P1 抽样`。
