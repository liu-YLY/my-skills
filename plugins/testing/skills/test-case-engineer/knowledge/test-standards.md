# 团队测试规范与标准

> **何时阅读**：阶段 3 编写用例 + 阶段 4 自检。写作字段规则以 [writing-rules.md](writing-rules.md) 为唯一权威源；本文件只保留优先级、类型、测试策略与生命周期。
> **快速定位**：划分 P0–P3 →「优先级」；选类型 →「用例类型」；定回归范围 →「测试策略标准」。

## 命名规范

通用 ID 与标题规则见 [writing-rules.md](writing-rules.md)。补充变体：性能用例 `TC_{模块}_PERF_{三位序号}`（如 `TC_WEBHOOK_PERF_001`）；安全用例 `TC_{模块}_SEC_{三位序号}`（如 `TC_AUTH_SEC_001`）。

**超长标题例外**：标题长度是软指导，场景可区分性优先。满足任一条件可保留超长标题，并在用例备注记录原因：① 删除任一信息会导致同模块标题重复；② 标题包含必要的环境/前置条件标识（夜间模式、弱网、v2 接口）；③ 执行人员需要该信息快速识别场景。**禁止**为满足 40 字截断或加省略号。

## 优先级

| 等级 | 定义 | 回归安排 |
|------|------|----------|
| P0 | 核心流程不可用、重大资金或数据损失、关键安全边界失效等阻断风险 | 相关发布的准入检查 |
| P1 | 高频业务、重要权限、主要异常路径及高影响性能风险 | 相关变更及迭代回归 |
| P2 | 影响可控且有替代路径的一般业务风险 | 按受影响范围回归 |
| P3 | 低影响、低暴露、低回归必要性的场景 | 按风险和变更安排 |

测试类型与优先级独立；安全、性能、兼容性均可能属于 P0/P1。目标系统不支持 P3 时映射到 P2 并保留风险说明。分布只作为观察信息，不预设占比，不为比例增删或调整用例。

**三步法**：① 根据需求判断失败的业务影响（核心流程、资金、数据、权限、用户范围）；② 结合发生可能性、使用频率、历史缺陷、替代路径与本次变更确定回归必要性；③ 指定 P0–P3，高风险判断写明依据，不从 functional/security/performance 等类型自动推导。

## 用例类型

`functional`（功能正确性，默认）、`ui`（布局/视觉/渲染，需设计稿或前端改动）、`security`（认证/授权/数据保护/注入，涉权限或敏感数据）、`performance`（响应时间/并发/吞吐，需求给指标）、`compatibility`（多浏览器/设备/版本，需求提兼容要求）、`usability`（交互体验，有交互规范或要求）、`accessibility`（无障碍，需求有无障碍规范）、`observability`（日志/指标/告警/链路，要求可观测验收）。按主要验证目标选，不按技术实现；目标系统不支持时按实际类型映射。

## 测试策略标准

### 新功能覆盖基线

按需求与风险选择适用项；缺基线时标为未评估，不为凑类型补造规则：

1. **Happy Path**：至少 1 条完整正向流程
2. **字段校验**：只覆盖本次改动涉及校验的字段；有阈值取一组三点边界，无阈值不展开（见 [scope-discipline.md](scope-discipline.md)）
3. **权限差异**：需求明确的用户角色
4. **联动逻辑**：需求明确的条件联动
5. **辅助操作**：取消/返回/刷新
6. **范围核对**：焦点项全覆盖；非焦点内容只留 1 条冒烟，服务故障类默认 0 条

### 回归选择

| 变更类型 | 回归范围 |
|----------|----------|
| Bug 修复 | 修复场景 + 关联功能的 P0 用例 |
| 小功能迭代 | 变更功能全量 + 上下游 P0 用例 |
| 大版本发布 | P0 全量 + P1 抽样 |
| 数据库/配置变更 | 受影响模块的 P0+P1 |

## 用例生命周期

状态：`Draft`（新建待评审）→ `AI-Generated`（AI 生成待审核）→ `Active`（人工审核通过，可执行）→ `Obsolete`（需求变更失效）；`Blocked` 表示环境/依赖阻塞。人工编写走 `Draft → Active → Obsolete`。

轻量维护：AI 用例按功能模块批量维护；需求变更优先重生成受影响模块；P2/P3 允许过期自动归档；P0/P1 必须随需求同步更新。
