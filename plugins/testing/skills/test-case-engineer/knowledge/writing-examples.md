# 用例编写好/坏写法对照示例

> 本文件承载「编写与审核铁律」的行业优秀实践对照示例，由 [test-case-engineer-core.md](../test-case-engineer-core.md) 阶段 3 按需加载：写用例拿不准 title/steps/expected_results 格式时查阅。铁律规则条文本体仍在 writing-rules.md，本文件仅为教学示例。所有示例采用 YAML 结构化格式。

## title 好/坏写法对照

| 场景 | 好的 title | 坏的 title | 原因 |
|------|------------|------------|------|
| 登录功能 | `手机号登录 - 正确凭据成功跳转首页` | `验证登录功能` | 缺少具体行为和预期结果 |
| 表单提交 | `优惠券创建 - 满减金额低于阈值提示错误` | `验证优惠券创建` | 缺少边界条件和错误场景 |
| 权限控制 | `用户管理 - 普通用户无法访问管理员页面` | `验证权限` | 缺少具体角色和行为 |
| 状态流转 | `订单状态 - 已发货订单无法修改收货地址` | `验证订单状态` | 缺少具体状态和限制 |
| 跨版本迁移 | `套餐 V3 → V4 创建跟踪 - 额度不足时拒绝` | `V4 API 测试` | 缺少套餐、操作和边界 |
| 判定规则类 | `[判定规则]订单取消 - 已发货状态拒绝取消` | `订单取消测试` | 缺少状态约束与判定类别 |

## steps 好/坏写法对照

| 场景 | 好的 steps | 坏的 steps | 原因 |
|------|------------|------------|------|
| 登录 | `1. 输入手机号 13800138000`<br>`2. 输入密码 Abc12345`<br>`3. 点击 “登录” 按钮` | `1. 输入正确的手机号和密码`<br>`2. 点击登录` | 缺少具体值，「正确」是模糊词 |
| 表单 | `1. 在 “优惠券名称” 输入框输入 “满100减20”`<br>`2. 在 “使用门槛” 输入框输入 “100”`<br>`3. 在 “优惠金额” 输入框输入 “20”`<br>`4. 点击 “保存” 按钮` | `1. 填写优惠券信息`<br>`2. 保存` | 缺少具体字段和值 |
| 权限 | `1. 使用普通账号登录系统`<br>`2. 在地址栏访问 `/admin/users``<br>`3. 按回车键提交` | `1. 尝试访问管理员页面` | 缺少具体操作路径 |
| API 调用 | `1. 调用 POST /v4/trackings/create，请求体中 tracking_number 为 9400111899223856928499` | `1. 调用创建接口` | 缺少方法、路径和参数 |
| 数据查询 | `1. 查询 Redis 键 user:10001 的 consume 字段` | `1. 查询相关数据` | 缺少查询对象和字段 |

## expected_results 好/坏写法对照

| 场景 | 好的 expected_results | 坏的 expected_results | 原因 |
|------|----------------------|----------------------|------|
| 登录成功 | `1. 密码输入框显示圆点掩码`<br>`2. 页面跳转至首页，顶部显示用户名 “测试用户”` | `1. 登录成功` | 缺少具体表现 |
| 表单校验 | `1. 输入框下方显示红色提示 “优惠金额不能超过使用门槛”`<br>`2. 保存按钮保持置灰状态` | `1. 提示错误信息` | 缺少具体文案和UI状态 |
| 权限拦截 | `1. 接口返回 HTTP 403，响应体 code 为 NO_PERMISSION`<br>`2. 页面显示 403 错误页，标题为 “无权访问”` | `1. 无法访问` | 缺少具体错误码和页面表现 |
| 数据保存 | `1. 页面顶部显示绿色提示 “保存成功”`<br>`2. 数据库 user 表 status 字段值变为 “active”` | `1. 保存成功` | 缺少UI反馈和数据库验证 |
| 接口响应 | `1. 接口返回 HTTP 200，data.id 非空` | `1. 接口返回正常` | 「正常」是模糊词，缺少状态码和字段 |

## description 好/坏写法对照

| 场景 | 好的 description | 坏的 description | 原因 |
|------|------------------|------------------|------|
| 表单校验 | `追溯: WEBHOOK-123 / PRD§3.2 / TP-WEBHOOK-001`<br>`验证已填写其他必填项时清空 Endpoint URL，系统阻止提交并展示格式错误提示。` | `验证功能正常` | 缺少追溯和具体验证意图 |
| 状态流转 | `追溯: STORY-42 / TP-ORDER-012`<br>`验证订单处于已发货状态时，取消接口拒绝请求且订单状态保持不变。` | `验证订单状态` | 缺少条件与结果方向 |

## 完整 YAML 用例示例（好）

```yaml
test_cases:
  - id: "TC_WEBHOOK_ADD_001"
    title: "Endpoint URL 校验 - 为空时提示错误"
    priority: "P1"
    type: "functional"
    description: |-
      追溯: WEBHOOK-123 / PRD§3.2 / TP-WEBHOOK-001
      验证已填写其他必填项时清空 Endpoint URL，系统阻止提交并展示格式错误提示。
    preconditions:
      - "测试账号已登录并拥有创建 Webhook 的权限"
      - "已打开 “Add webhook” 弹窗"
    steps:
      - "填写 Version 和至少 1 个 Trigger，使 “Add endpoint” 按钮可点击"
      - "清空 “Endpoint URL” 输入框"
    expected_results:
      - "“Add endpoint” 按钮为可点击状态"
      - "输入框下方显示红色错误提示：“Wrong URL format!”；“Add endpoint” 按钮变为置灰状态"
    tags: [webhooks, validation, endpoint-url, boundary]
    auto: false
```

## 完整 YAML 用例示例（坏）

```yaml
test_cases:
  - id: "TC_001"                # 坏：ID 格式不规范，缺少模块/功能位
    title: "验证 Webhook 功能"   # 坏：缺少具体行为、条件、结果
    priority: "P0"
    type: "functional"
    description: "测试添加 Webhook 的功能"  # 坏：无追溯，未以「验证」开头，复述标题
    preconditions:
      - "环境正常"               # 坏：「正常」是模糊词
      - "已准备相关数据"          # 坏：「相关」是模糊词
    steps:
      - "填写对应内容"            # 坏：「对应」是模糊词，缺少具体字段和值
      - "点击保存并验证结果"       # 坏：一个步骤包含两个动作（保存 + 验证）
    expected_results:
      - "保存成功"                # 坏：缺少 UI 反馈和数据库验证
      - "功能正常"                # 坏：「正常」是模糊词
    tags: [test, webhook, 其他]   # 坏：首位非业务域，「其他」无筛选价值，大小写不统一
    auto: false
```
