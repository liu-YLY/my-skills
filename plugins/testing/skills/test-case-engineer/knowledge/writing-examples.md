# 用例编写好/坏写法对照示例

> 本文件承载「编写与审核铁律」的行业优秀实践对照示例，由 [test-case-engineer-core.md](../test-case-engineer-core.md) 阶段 3 按需加载：写用例拿不准 title/steps/expected_results 格式时查阅。铁律规则条文本体仍在 writing-rules.md，本文件仅为教学示例。

## title 好/坏写法对照

| 场景 | 好的 title | 坏的 title | 原因 |
|------|------------|------------|------|
| 登录功能 | `手机号登录 - 正确凭据成功跳转首页` | `验证登录功能` | 缺少具体行为和预期结果 |
| 表单提交 | `优惠券创建 - 满减金额低于阈值提示错误` | `验证优惠券创建` | 缺少边界条件和错误场景 |
| 权限控制 | `用户管理 - 普通用户无法访问管理员页面` | `验证权限` | 缺少具体角色和行为 |
| 状态流转 | `订单状态 - 已发货订单无法修改收货地址` | `验证订单状态` | 缺少具体状态和限制 |
| 跨版本迁移 | `套餐 V3 → V4 创建跟踪 - 额度不足时拒绝` | `V4 API 测试` | 缺少套餐、操作和边界 |
| 判定规则类 | `[判定规则]订单取消 - 已发货状态拒绝取消` | `订单取消测试` | 缺少状态约束与判定类别 |

## steps 好/坏写法对照

| 场景 | 好的 steps | 坏的 steps | 原因 |
|------|------------|------------|------|
| 登录 | `1. 输入手机号 13800138000`<br>`2. 输入密码 Abc12345`<br>`3. 点击 "登录" 按钮` | `1. 输入正确的手机号和密码`<br>`2. 点击登录` | 缺少具体值，"正确"是模糊词 |
| 表单 | `1. 在 "优惠券名称" 输入框输入 "满100减20"`<br>`2. 在 "使用门槛" 输入框输入 "100"`<br>`3. 在 "优惠金额" 输入框输入 "20"`<br>`4. 点击 "保存" 按钮` | `1. 填写优惠券信息`<br>`2. 保存` | 缺少具体字段和值 |
| 权限 | `1. 使用普通账号登录系统`<br>`2. 在地址栏访问 /admin/users`<br>`3. 按回车键提交` | `1. 尝试访问管理员页面` | 缺少具体操作路径 |
| API 调用 | `1. 调用 POST /v4/trackings/create，请求体中 tracking_number 为 9400111899223856928499` | `1. 调用创建接口` | 缺少方法、路径和参数 |
| 数据查询 | `1. 查询 Redis 键 user:10001 的 consume 字段` | `1. 查询相关数据` | 缺少查询对象和字段 |

## expected_results 好/坏写法对照

| 场景 | 好的 expected_results | 坏的 expected_results | 原因 |
|------|----------------------|----------------------|------|
| 登录成功 | `1. 密码输入框显示圆点掩码`<br>`2. 页面跳转至首页，顶部显示用户名 "测试用户"` | `1. 登录成功` | 缺少具体表现 |
| 表单校验 | `1. 输入框下方显示红色提示 "优惠金额不能超过使用门槛"`<br>`2. 保存按钮保持置灰状态` | `1. 提示错误信息` | 缺少具体文案和UI状态 |
| 权限拦截 | `1. 接口返回 HTTP 403，响应体 code 为 NO_PERMISSION`<br>`2. 页面显示 403 错误页，标题为 "无权访问"` | `1. 无法访问` | 缺少具体错误码和页面表现 |
| 数据保存 | `1. 页面顶部显示绿色提示 "保存成功"`<br>`2. 数据库 user 表 status 字段值变为 "active"` | `1. 保存成功` | 缺少UI反馈和数据库验证 |
| 接口响应 | `1. 接口返回 HTTP 200，data.id 非空` | `1. 接口返回正常` | "正常"是模糊词，缺少状态码和字段 |

## 需求追溯/业务背景 好/坏写法对照

| 场景 | 好的写法 | 坏的写法 | 原因 |
|------|------------------|------------------|------|
| 表单校验 | 需求追溯: `WEBHOOK-123 / PRD§3.2 / TP-WEBHOOK-001`<br>业务背景: `验证已填写其他必填项时清空 Endpoint URL，系统阻止提交并展示格式错误提示` | 业务背景: `验证功能正常` | 缺少追溯和具体验证意图 |
| 状态流转 | 需求追溯: `STORY-42 / TP-ORDER-012`<br>业务背景: `验证订单处于已发货状态时，取消接口拒绝请求且订单状态保持不变` | 业务背景: `验证订单状态` | 缺少条件与结果方向 |

## 完整用例示例（好）

```markdown
### TC_WEBHOOK_ADD_001: Endpoint URL 校验 - 为空时提示格式错误

- **优先级**: P1
- **类型**: functional
- **需求追溯**: WEBHOOK-123 / PRD§3.2 / TP-WEBHOOK-001
- **来源**: ai-generated
- **业务背景**: 验证其他必填项已填写时清空 Endpoint URL，系统阻止提交并提示格式错误

**前置条件**:
- 测试账号已登录并拥有创建 Webhook 的权限
- 已打开「Add webhook」弹窗

**测试步骤**:
1. 填写 Version 为 v4，Trigger 选择「订单创建」，Endpoint URL 填入 `https://example.com/hooks/orders`
2. 清空「Endpoint URL」输入框

**关键检查点**:
- 步骤 1 后：「Add endpoint」按钮由置灰变为可点击

**业务结果**:
- 「Endpoint URL」输入框下方显示红色提示「Wrong URL format!」
- 「Add endpoint」按钮重新变为置灰

**后置条件**:
- 关闭「Add webhook」弹窗，Webhook 列表未新增记录

**标签**: webhooks, validation, endpoint-url, boundary
```

## 完整用例示例（坏）

```markdown
### TC_001: 验证 Webhook 功能

- **优先级**: P0
- **类型**: functional
- **业务背景**: 测试添加 Webhook 的功能

**前置条件**:
- 环境正常
- 已准备相关数据

**测试步骤**:
1. 填写对应内容
2. 点击保存并验证结果

**业务结果**:
- 保存成功
- 功能正常

**标签**: test, 其他
```

坏在哪里：
- **ID**：`TC_001` 缺少模块/功能位，格式不规范
- **标题**：`验证 Webhook 功能` 缺少具体行为、条件、结果
- **需求追溯**：缺失，无法追溯需求和测试点
- **业务背景**：未以「验证」开头描述意图，只是复述标题
- **前置条件**：「环境正常」「已准备相关数据」是模糊词，无法直接准备
- **步骤 1**：「填写对应内容」缺少具体字段和值
- **步骤 2**：一个步骤包含两个动作（保存 + 验证），应拆分
- **业务结果**：「保存成功」缺少 UI 反馈和数据库验证；「功能正常」是模糊词
- **后置条件**：创建成功后未说明如何清理，重复执行会在列表中累积脏数据
- **标签**：首位 `test` 不是业务域；`其他` 无筛选价值

## 语气与信息密度对照

### 步骤：填充 vs 有效

| 填充型步骤 | 有效写法 | 问题 |
|-----------|---------|------|
| 确认当前已登录系统 | （删除） | 复述前置条件 |
| 打开浏览器，访问 Webhook 配置页面 | （删除） | 无信息量导航，已在前置条件中 |
| 找到「Add webhook」按钮并点击 | 点击「Add webhook」 | 「找到」不是业务动作 |
| 填写相关信息 | 填写 Version 为 v4，Trigger 选择「订单创建」 | 空泛动作，缺少字段与值 |
| 点击保存并确认结果 | 点击「保存」 | 验证动作混入操作 |
| 由于金额不足，因此点击提交 | 点击「提交」 | 原因属于业务背景 |

### 预期结果：评价 vs 观察

| 评价式预期 | 可观察预期 | 问题 |
|-----------|-----------|------|
| 保存成功 | 页面顶部显示绿色提示「保存成功」，列表新增一行「满100减20」 | 缺少位置与对象 |
| 功能正常 | 点击「导出」后下载 CSV，首行为表头「订单号,金额,状态」 | 无法判定 |
| 系统应拦截 | 接口返回 HTTP 403，响应体 code 为 ORDER_STATE_INVALID | 愿望式表达 |
| 页面无异常 | 页面标题为「订单详情」，状态标签显示「已发货」 | 无关事实 |

### 完整用例：啰嗦版 vs 精简版

**啰嗦版**（信息密度低，但没有明显错误）：

```markdown
### TC_WEBHOOK_ADD_001: 验证 Webhook 的 Endpoint URL 格式校验功能

- **优先级**: P1
- **类型**: functional
- **业务背景**: 测试添加 Webhook 时对 URL 格式的校验

**前置条件**:
- 测试账号已登录并拥有创建 Webhook 的权限
- 已打开「Add webhook」弹窗

**测试步骤**:
1. 确认当前已登录系统
2. 打开浏览器并访问 Webhook 配置页面
3. 找到「Add webhook」按钮并点击
4. 填写 Version 和至少 1 个 Trigger
5. 清空「Endpoint URL」输入框
6. 查看页面上的提示信息
7. 确认「Add endpoint」按钮是否可用

**业务结果**:
- 系统提示错误信息，功能正常
```

**精简版**（同样的测试点，只保留必要信息）：

```markdown
### TC_WEBHOOK_ADD_001: Endpoint URL 校验 - 为空时提示格式错误且按钮置灰

- **优先级**: P1
- **类型**: functional
- **需求追溯**: WEBHOOK-123 / PRD§3.2 / TP-WEBHOOK-001
- **业务背景**: 验证其他必填项已填写时清空 Endpoint URL，系统阻止提交并提示格式错误

**前置条件**:
- 测试账号已登录并拥有创建 Webhook 的权限
- 已打开「Add webhook」弹窗

**测试步骤**:
1. 填写 Version 为 v4，Trigger 选择「订单创建」
2. 清空「Endpoint URL」输入框

**业务结果**:
- 输入框下方显示红色提示「Wrong URL format!」
```

## 易读性对照（同一信息）

信息量相同，只改句式。判断标准：执行人能否一遍读完、不需要回读。

### 难读版

```markdown
### TC_PROFILE_NICKNAME_004: 修改昵称 - 超长时提示错误

- **优先级**: P1
- **类型**: functional
- **业务背景**: 验证在昵称输入框中输入超过长度上限的字符内容的情况下，系统对提交行为进行阻止并给出相应提示

**前置条件**:
- 账号 A 已登录，处于「修改昵称」页

**测试步骤**:
1. 在「昵称」输入框中输入由 21 个汉字组成的字符串「测试昵称测试昵称测试昵称测试昵称测试昵称测」（该字段的长度上限为 20 个字符），随后对「保存」按钮执行点击操作

**业务结果**:
- 系统应当对超出长度限制的输入进行拦截，并在界面上给出相应的错误提示信息
```

### 易读版

```markdown
### TC_PROFILE_NICKNAME_004: 修改昵称 - 超过 20 字时提示错误

- **优先级**: P1
- **类型**: functional
- **业务背景**: 验证昵称超过长度上限时，系统阻止保存并提示错误

**前置条件**:
- 账号 A 已登录，处于「修改昵称」页

**测试步骤**:
1. 在「昵称」输入框输入 `测试昵称测试昵称测试昵称测试昵称测试昵称测`（21 字，上限 20 字）
2. 点击「保存」

**业务结果**:
- 输入框下方显示「昵称不能超过 20 个字」
- 昵称仍为修改前的值
```

### 改了什么

| 位置 | 难读版 | 易读版 | 原因 |
|------|--------|--------|------|
| 业务背景 | 在…的情况下，系统对提交行为进行阻止并给出相应提示 | 系统阻止保存并提示错误 | 26 字条件从句 + 「对…进行」虚动词 |
| 标题 | 超长时提示错误 | 超过 20 字时提示错误 | 「超长」需读者回查上限，直接给阈值 |
| 步骤 1 | 输入 21 个汉字…，随后对「保存」按钮执行点击操作 | 输入 21 字。点击「保存」 | 一步两个动作，拆开；「执行点击操作」改为「点击」 |
| 业务结果 | 应当…进行拦截，并给出相应的错误提示信息 | 显示「昵称不能超过 20 个字」 | 愿望式 + 「相应的」无信息，改为具体文案 |
| 业务结果 | （未写状态） | 昵称仍为修改前的值 | 补一条可观察的未变更事实，信息不减反增 |

> 易读版没有删掉任何可判定信息：21 字、上限 20、具体文案、状态未变都在。区别只是把长句拆短、把抽象词换成事实。

## 独立性、验证与实现边界

| 场景 | 不要这样写 | 这样写 | 原因 |
|------|-----------|--------|------|
| 跨用例依赖 | 步骤 1：打开上一条用例创建的订单 | 前置条件：已存在订单 `ORD-20261031-001`，由 `TC_ORDER_ADD_001` 创建 | 依赖未声明，单跑必失败 |
| 状态变更无验证 | 步骤：点击「提交」<br>业务结果：（未写） | 步骤：点击「提交」<br>业务结果：页面显示「提交成功」，订单表 `status` 变为 `submitted` | 状态变了却没人检查 |
| 实现细节入用例 | 步骤：调用 `OrderService.create()` 写入 `t_order` 表 | 步骤：点击「提交订单」 | 业务用例绑定实现，重构即失效 |

> 纯准备步骤可以没有断言，但要标注：`1（准备）在后台创建 1 个待支付订单`。
