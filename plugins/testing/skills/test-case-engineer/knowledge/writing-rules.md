# 用例编写规则与格式标准（写作契约）

> **何时阅读**：阶段 3 编写用例时必读；本文件是写作规则的唯一权威源（格式/字段/标题·步骤·预期/句式/模糊词/术语/Tag/拆分合并）。
> **相邻**：好坏对照 [writing-examples.md](writing-examples.md)；动词与可读性细则 [readability.md](readability.md)（按需）；编排 [case-arrangement.md](case-arrangement.md)；失败语义 [failure-semantics.md](failure-semantics.md)。

## 通用用例格式

**块结构（强制）**：每条用例以 `### TC_{模块}_{功能}_{序号}: 标题` 起始。这是脚本校验的锚点；用列表、加粗或整表代替标题时，该用例不会被任何规则检查，等同于未校验。

新用例采用「业务结果 + 关键检查点」；不批量迁移历史用例，用户指定的输出载体可保留，但不要求步骤与结果数量相等。

```markdown
### TC_MODULE_FUNC_001: 被测对象 - 具体行为

- **优先级**: P0
- **类型**: functional
- **需求追溯**: Story-42 / TP-03
- **来源**: ai-generated
- **人工审核状态**: not-reviewed
- **业务背景**: 验证…

**前置条件**: 已登录为 A 类用户；已打开 "Add webhook" 弹窗

**测试步骤**:
1. 填写名称「订单通知」和地址 `https://example.com/hooks/orders`
2. 点击「Add webhook」提交

**关键检查点**: 步骤 2 后：弹窗关闭，列表出现「订单通知」记录

**业务结果**: 刷新后记录仍存在且地址未变；只新增一条记录

**后置条件**: 保留「订单通知」，供编辑用例使用
```

**紧凑表格模式（P2/P3 可选）**：同一 `### TC_xxx` 块内，把 ≥5 条验证逻辑同构的 P2/P3 用例合并为一张表；组头写共享元信息与前置条件，行内只写变化，表头为 `| 用例 ID | 输入值 | 操作 | 预期结果 |`。

约束：仅限 P2/P3 且验证逻辑同构，P0/P1 必须完整块；表头必须含「用例 ID」「操作」「预期结果」，缺一列即格式违规；单组 ≤10 行；每行独立 ID 且预期可判定；组内行计入用例集预算。**用一张表罗列全部用例（无块标题、跨组混排）属于格式违规。**

## 补充用例 ID 生成规则（强制）

格式 `TC_{模块}_{功能}_{三位序号}`。评审或阶段 4 补用例时，从已有 ID 提取模块与功能前缀，序号 = 相同「模块+功能」的最大序号 +1（已有 `TC_WEBHOOK_ADD_001/002` → 新增 `TC_WEBHOOK_ADD_003`）。

**禁止**：`TC_001`、`TC_NEW_001`、`TC补充_001`；序号跳跃；模块/功能缩写不一致（已有 `WEBHOOK` 却写 `WH`）。性能/安全 ID 变体见 [test-standards.md](test-standards.md)「命名规范」。

## 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| **ID / 标题** | 是 | `TC_{模块}_{功能}_{三位序号}`；标题规则见「标题」节 |
| **优先级** | 是 | P0–P3；定义见 [test-standards.md](test-standards.md) |
| **类型** | 是 | functional / ui / security / performance / compatibility / usability / accessibility / observability，按主要验证目标选 |
| **需求追溯** | 否 | Story ID、TP 编号、接口契约、设计稿或已关联缺陷 |
| **来源** | 否 | ai-generated / manual；ai-reviewed 不作为人工审核证明 |
| **追溯引用** | 否 | 可选 `trace_refs` 指向稳定产物 ID，`stable_ref` 标识当前输入/断言；长期身份用版本化产物 ID，不用列表位置或展示编号 |
| **人工审核状态** | 否 | not-reviewed / reviewed；reviewed 需真实审核依据，AI 自检不算 |
| **业务背景** | 否 | 「验证」开头一句话：条件+对象+动作+结果方向；>40 字须改写；不复述步骤 |
| **前置条件** | 否 | 陈述句列表：角色/权限、页面或调用条件、数据状态；不写「已准备相关数据」「账号/环境正常」 |
| **测试步骤** | 是 | 按业务操作组织，不要求每步独立断言 |
| **业务结果** | 是 | 最终可判定结果；结构化输出用 `expected_results` 字符串数组 |
| **关键检查点** | 否 | `checkpoints` 数组，每项含 `after_step`（从 1 开始）与 `expected_results` |
| **后置条件** | 条件 | 改变系统状态或共用环境时必填，写复位/清理动作或保留数据 |
| **标签** | 否 | 小写 kebab-case，1–5 个，首位是业务域 |

**后置条件写法**：默认不填；新增/修改/删除数据、占用资源、发送消息或共用环境时必填。写可执行动作或保留产物（`删除本次创建的 Webhook「订单通知」`、`保留订单 ORD-20261031-001 供退款用例使用`），不写「环境恢复正常」；下一条依赖本条产物时在此声明。

## 标题、步骤与预期

### 三条原则

1. **一句话一个事实**：标题说测试点，步骤说操作，预期说观察结果；同一事实只出现一次。
2. **每句都有定位价值**：删掉后仍能判断测什么、怎么执行、是否通过，这句就不该出现。
3. **用日常业务动作词**：输入、点击、选择、打开、刷新；不用「执行点击操作」「录入」「呈现」「触发」。

**深度分级**：焦点项写完整，非焦点内容只保留 1 条冒烟，不铺开中间校验（见 [scope-discipline.md](scope-discipline.md)）。

### 标题：第一眼看到测试点

只看标题，应能回答「测什么对象、在什么条件下、预期发生什么」；好坏对照见 [writing-examples.md](writing-examples.md)。

- 格式 `被测对象 - 具体行为/条件/结果`，建议 40 字以内；信息删除会造成同模块场景重复、或无法识别环境/版本时，可保留长标题，但**禁止**截断、`...` 或「等」隐藏关键条件（例外见 [test-standards.md](test-standards.md)「命名规范」）
- 可用 `[]` 标注「判定规则」「跨版本」等筛选类别，`→` 表示状态/版本迁移；英文产品文案保留原文
- 不以「验证」「测试」开头（`验证码`、`测试数据` 等业务词除外）；不写「功能」「逻辑」「场景」等纯抽象名词；不重复 ID 中已有的模块名与优先级。禁止：`验证 Width`、`验证布局`、`验证登录功能`

### 测试步骤：只保留有业务意义的操作

**删除测试**：删掉这一步后用例仍可执行且测试点不变，就删除（复述前置条件、无信息量导航、空泛动作、解释性文字、操作与验证混写均属填充）。

- 每步以动作开头，包含操作对象、值或路径；涉及输入/选择/配置必须写明具体值；按有业务意义的操作组织，允许一次填写一组表单并提交
- UI 步骤用控件/页面实际名称，不用「左上角按钮」「对应入口」等泛称
- 普通业务步骤用业务动作与接口名称；协议、路由或契约测试才写 HTTP 方法、路径、参数与认证条件。业务/UI 用例不写类名、表名、内部服务名、SQL 或选择器
- 数据步骤写明查询对象和字段，如 `查询 Redis 键 ... 的 consume 字段`
- 仅不属于被测行为的外部准备放 `preconditions`；被测登录、导航或数据准备保留在步骤中
- 禁止占位话术：`按测试点要求执行`、`执行对应操作`、`验证相关功能`
- 查询、刷新、查看消息等必要观察操作可写入步骤；可判定结果写入业务结果或检查点
- 禁止用 `if/else` 描述路径，每个条件分支独立成用例；步骤长度只作可读性提示，是否拆分依据业务目标、前置条件与失败隔离，不设数量阈值

### 业务结果与关键检查点：写观察到的事实

每条结果写成「在哪里 + 看到什么 + 什么值/状态」，证据可为 UI 状态/文案/路由、API 状态码/错误码/字段值、表/缓存/消息字段、业务状态迁移、事件/日志/trace。禁止三类填充：评价词（正常、成功、正确、符合预期）、愿望式（应生效、会被拦截）、无关事实（系统稳定、页面无异常）。

- 最终业务结果必须可判定；只在必要中间状态、后续入口或风险判断处设检查点
- 同一动作可关联页面、业务状态、消息或数据结果；不因证据层次不同强制拆分，不合并独立业务目标
- 单条结果 ≤100 字；必须与步骤中的实际操作直接对应，禁止为未发生的操作写预期；改变状态的操作至少一条结果覆盖直接后果，纯数据准备可无断言但步骤需标注「准备」
- 需求未给具体文案/数值/错误码时，不写「待补充」占位；用结构化事实作预期（出现错误提示、按钮置灰、字段值未变、列表未新增），并在「原文问题清单」标注缺失文案
- 自检：执行人员看到这条预期，能否直接判 Pass/Fail？

**业务背景与需求追溯**：

- 需求追溯记录需求 ID / Jira / 测试点编号 / 接口契约 / 设计稿 / 已关联缺陷
- 可选 `traceability` 原样消费：`sources` 为 `id/location/version/availability`（available/unreachable/missing/unknown），`artifacts` 为 `id/kind/version`，`links` 为 `upstream/downstream/confirmation/source/source_refs`（confirmed/candidate）
- 需求→风险→模型/场景→用例→执行证据用显式产物 ID 和版本关联；有依据且来源可达才标 confirmed，缺依据或仅文字相似标 candidate
- 来源不可达与业务结果未知分列；未读到来源不补造版本/确认关系；独立 skill 无完整图仍可输出并注明追溯未评估；来源变化只复核已确认关联的结论，候选关联单列，保留旧证据与版本
- 业务背景以「验证」开头；标题则不得以「验证」开头；不复述步骤，不写「验证功能正常」「验证符合预期」
- 异步流程分别说明受理状态与最终状态，等待依据需求约定的完成事件或时限，不编造 SLA；必要检查失败后停止依赖步骤，独立结果继续汇总

**测试点→用例映射**：同一流程不同测试数据合并为 1 条并参数化；同一规则的数据变体可参数化，每行写清条件与预期；独立目标、互斥流程或不能共存的前置条件必须拆分；同一字段多类校验按类拆分。

## 句式与结构（阈值）

- **句长**：逗号分隔构件以 20 字为目标，20–29 可接受，30–39 须语义清晰，超过 40 字必须改写；单条步骤或预期 ≤100 字
- 一句一个动作；动词直用；主动语态；名词前修饰不超过两层；拆分优先于压缩
- 步骤首词用动词（输入/点击/选择/打开/刷新），预期首词写位置（页面/接口/表/缓存/消息）；检查点就近写 `步骤 N 后：…`，不集中到文末
- 步骤 >7 条时按业务阶段分组，每组 ≤7 条；单条用例正文建议 ≤300 字；指代「其/该/此/这」必须有唯一指向，一条步骤最多 1 个需额外解释的术语
- 中文正文用全角标点；数字/版本/金额同一用例内形式一致，范围写 `1~2 天`；数字与英文单位间留空格（`16 GB`）；完整对照表与认知负荷细则见 [readability.md](readability.md)

## 禁用的模糊表达

以下表达不能单独构成步骤或预期（**本清单为唯一权威源**）：

**基础 15 词**：`正常`、`正确`、`符合预期`、`相关`、`对应`、`适量`、`多次`、`一些`、`大约`、`可能`、`频繁`、`边界值`、`最大`、`最小`、`等`。

**扩展词**：`很多`、`部分`、`大量`、`少量`、`随机`、`任意`、`一段时间`、`一会`、`一点`、`特殊`、`很长`、`较长`、`很短`、`较短`、`多个`、`几块`、`多条`、`数次`、`所有`、`大概`、`某些`、`超长`、`超小`、`超短`、`过低`、`过高`、`全部`、`缺省`、`默认`、`各模块`、`有的`、`一定范围`、`多于`、`少于`、`左右`、`上下`、`设备无异常`、`计数正常`、`长时间`、`错误信息`、`非法字符`。

**不判违规的业务术语**：`部分退款`、`部分成功`、`部分失败`、`部分取消`、`默认值`、`默认套餐`、`默认配置`、`正常订单`、`正常状态`、`边界值分析`、`最小权限`、`最大长度`、`所有角色`。

**判定口径**：看词是否掩盖输入、条件或结果。`状态为部分退款` 是明确业务状态，不违规；`部分功能可用` 掩盖范围，违规。新增术语沿用同一口径，并在评审模式登记。

替换示例：`输入正确的手机号` → `输入手机号 13800138000`；`输入超长内容` → `输入 101 个字符（上限 100）`。

不确定的规则不写成「可能」「待确认」后直接执行；在需求/测试点中标记待确认，确认后再落为可判定用例。已识别但口径未确认的边界保留在独立待确认清单（输入、问题、来源）；不能把两种互斥结果并列作为通过条件（如优惠上限已明确为 `min(订单×10%, 30)` 时，不得另造 27 元分支）。

## 术语与用词

同一概念全文只用一个词；界面有多个不同按钮时按界面原文区分。动词首选、对象称呼、术语解释与环境/版本写法见 [readability.md](readability.md)「术语与用词一致」。

## Tag 规范

小写 kebab-case，单条 1–5 个，首位必须是业务域，后续按筛选价值由宽到窄：

```text
业务域 → 功能/操作 → 关键对象或版本 → 资源/渠道 → 边界属性
```

示例：`webhooks, validation, endpoint-url, boundary`。

- 不重复 title 中没有筛选价值的信息；复用已有受控词表，新增前先检索相近模块
- 不在每条用例重复版本/发布名称；`boundary`、`security`、`compatibility` 仅在确实表达额外测试面时添加

## 拆分与合并

围绕清晰业务目标，在失败可定位与准备/执行/维护成本之间取舍。

**应拆分**：独立业务目标、互斥执行路径、不能共存的前置条件，或合并后失败无法隔离；不要仅因页面/接口/数据库等证据层次不同而拆。**可合并**：同一操作的相关结果（注册后的记录、欢迎邮件、初始积分，可用软断言汇总）；完整业务流程（保留必要检查点与最终结果）；同一规则的数据变体（每组有明确前置、输入、预期）；准备成本高且共享目标的流程（说明共享准备）。

**独立与失败**：用例默认独立可执行；必须串联时在前置条件声明依赖来源（`已存在订单 ORD-...，由 TC_ORDER_ADD_001 创建`），被依赖用例在后置条件声明保留，不写「执行上一条用例」。入口/前置检查失败后停止依赖步骤并标记未执行，无依赖结果继续检查；不为一次跑通跨过错误业务状态。

**信息归属**：业务规则放业务背景，执行前状态放前置条件，动作与输入放步骤，观察结果放业务结果/检查点，清理或保留数据放后置条件。

**认知负荷（软）**：单步一个决策点、单步字段 ≤5、步骤 ≤7、单组主数据；合并后若无法指出「哪一步、哪个字段」导致失败，说明粒度过粗，应拆分。

## 输出与证据边界

- 用例输出采用 Markdown（可直接阅读编辑、转测试管理工具、版本控制与 diff）；导入特定工具时用脚本或手动转换。编排见 [case-arrangement.md](case-arrangement.md)。
- 覆盖报告区分需求条目、模型转换、场景设计与实际执行，每层注明分母来源/版本与未评估项；沿用 `requirement_baseline` / `design_baseline` / `case_baseline` 语义，不改旧 transition/forbidden 分母。
- 无需求基线不算需求覆盖；无执行记录不算通过率；候选关联与待确认场景不混入已验证结果；空基线、不适用、缺输入分别表达；只有设计证据时写「已设计，未执行」。
