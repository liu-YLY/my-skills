## 分层测试策略

根据需求类型选择测试分层，确定用例的验证层级：

| 分层 | 名称 | 关注点 | 适用场景 | 目标占比 |
|------|------|--------|----------|----------|
| **L1** | 单元层 | 核心算法、复杂计算逻辑 | 核心业务逻辑型需求 | 0-10% |
| **L2-A** | 业务场景层 | 跨接口业务闭环、状态机流转 | 复杂业务流程、异步任务 | 30% |
| **L2-B** | 接口契约层 | API 参数校验、DB 读写、第三方对接 | 所有后端功能 | 30% |
| **L3** | UI/E2E 层 | 用户旅程、交互体验、端到端闭环 | 前端样式、交互相关 | 40% |

**动态调整规则**：

| 需求类型 | 典型场景 | L2 占比 | L3 占比 |
|----------|----------|---------|---------|
| 核心业务逻辑型 | 积分规则、自动化营销、VIP 判定 | 70% | 30% |
| 数据集成型 | 对接新物流商、同步订单、数据报表 | 80% | 20% |
| 纯交互/UI型 | 首页改版、新增引导弹窗、样式优化 | 20% | 80% |

**分层选择决策**：
1. 需求涉及核心算法/复杂计算？→ 必须选择 L1 单元测试
2. 需求涉及跨接口业务闭环？→ 必须选择 L2-A 业务场景测试
3. 需求涉及 API/数据/第三方？→ 必须选择 L2-B 接口测试
4. 需求涉及 UI/交互/体验？→ 必须选择 L3 E2E 测试

## 默认输出功能测试用例

除非用户明确要求或需求内容明显涉及以下类型，否则只输出功能测试用例（`type: functional`）：

| 额外类型 | 触发条件 |
|----------|----------|
| performance | 需求提到响应时间、并发量、吞吐量要求 |
| security | 涉及认证、授权、敏感数据、支付 |
| compatibility | 需求提到多浏览器、多设备、多系统版本 |

当需要额外类型时，在功能测试用例之后独立成组追加。

## 通用用例格式

每条测试用例采用 YAML 结构化格式输出。业务文本统一使用双引号，确保冒号、日期、金额和特殊字符不会被 YAML 误解析；`description` 使用 `|-` 多行文本；列表型字段即使只有一项也保持 YAML 列表。

```yaml
test_cases:
  - id: "TC_WEBHOOK_ADD_001"
    title: "Endpoint URL 校验 - 为空时提示错误"
    priority: "P1"
    type: "functional"
    description: |-
      追溯: WEBHOOK-123 / PRD§3.2 / TP-WEBHOOK-001
      验证已填写其他必填项时清空 Endpoint URL，系统阻止提交并展示格式错误提示。
    preconditions:
      - "测试账号已登录并拥有创建 Webhook 的权限"
      - "已打开 “Add webhook” 弹窗"
    steps:
      - "填写 Version 和至少 1 个 Trigger，使 “Add endpoint” 按钮可点击"
      - "清空 “Endpoint URL” 输入框"
    expected_results:
      - "“Add endpoint” 按钮为可点击状态"
      - "输入框下方显示红色错误提示：“Wrong URL format!”；“Add endpoint” 按钮变为置灰状态"
    tags: [webhooks, validation, endpoint-url, boundary]
    auto: false
```

`id`、`title`、`priority`、`type`、`preconditions`、`steps`、`expected_results`、`tags` 和 `auto` 是最小必需字段。对新增或实质修改的用例，`description` 也应补齐；历史文件可在其所属模块重构时渐进式补齐，不能因只改格式而改变已有业务事实。

## 补充用例 ID 生成规则（强制）

当评审模式或阶段 4 自检发现缺失用例需要补充时，**必须**按以下规则生成 ID：

**ID 格式**：`TC_{模块}_{功能}_{三位序号}`

**生成步骤**：
1. **确定模块缩写**：从已有用例 ID 中提取模块前缀（如 `TC_WEBHOOK_ADD_001` → `WEBHOOK`）
2. **确定功能缩写**：从已有用例 ID 中提取功能前缀（如 `TC_WEBHOOK_ADD_001` → `ADD`）
3. **确定序号**：扫描已有用例 ID，找到相同模块+功能的最大序号，新用例序号 = 最大序号 + 1

**示例**：
- 已有用例：`TC_WEBHOOK_ADD_001`, `TC_WEBHOOK_ADD_002`, `TC_WEBHOOK_EDIT_001`
- 补充新增用例：`TC_WEBHOOK_ADD_003`（最大序号 2 + 1）
- 补充编辑用例：`TC_WEBHOOK_EDIT_002`（最大序号 1 + 1）

**禁止**：
- 使用不规范格式：`TC_001`、`TC_NEW_001`、`TC补充_001`
- 序号跳跃：已有 001、002，新增用 005
- 模块/功能缩写不一致：已有 `WEBHOOK`，新增用 `WH` 或 `webhook`

## 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| **id** | 是 | `TC_{模块}_{功能}_{三位序号}`，全仓库唯一，规则见上方「ID 生成规则」 |
| **title** | 是 | `被测对象 - 具体行为/条件/结果`，建议 40 字以内；信息删除会造成重复或无法识别环境/版本时可保留长标题，禁止通过截断、`...` 或「等」隐藏关键条件 |
| **priority** | 是 | P0/P1/P2/P3，定义与比例见 [test-standards.md](test-standards.md) |
| **type** | 是 | functional / ui / security / performance / compatibility / usability / accessibility / observability；描述「主要验证目标」而非技术实现 |
| **description** | 应填 | `|-` 多行文本：第一行追溯（需求 ID / Jira / 测试点 / 接口契约 / 设计稿 / 缺陷）；第二行以「验证」开头描述条件、对象、动作和结果方向；不复述步骤 |
| **preconditions** | 否（建议） | 陈述句列表，覆盖角色/权限、页面或调用条件、数据状态；不写「已准备相关数据」「账号正常」「环境正常」 |
| **steps** | 是 | 动作开头的列表，包含操作对象、值或路径；每步一个核心动作；不超过 7 步 |
| **expected_results** | 是 | 与 steps 数量一致（一步一验），明确可观察证据；同一触发动作的紧密业务结果可合并多条断言 |
| **tags** | 是 | 小写 kebab-case，1–5 个，首位必须是业务域；规则见下方「Tag 规范」 |
| **auto** | 是 | 布尔值，标识是否已/适合纳入自动化，不替代优先级 |

## 编写与审核铁律

**title 规范**：
- 首选格式：`被测对象 - 具体行为/条件/结果`
- 必须包含：验证对象、用户行为（若存在）、条件与可观察结果
- 可使用分隔符与标记：`-` 分隔对象/条件/行为/结果；`[]` 标示「判定规则」「跨版本」「升级交互」等有筛选价值的类别；`→` 表示状态、版本或套餐迁移；英文产品文案保留原文（如 `Cancel downgrade`、`Add endpoint`）
- 建议不超过 40 字；信息一旦删除会造成同模块场景重复或无法识别环境/版本时，可保留长标题；禁止通过截断、`...` 或「等」隐藏关键条件
- 禁止：`验证 Width`、`验证布局`、`验证 Rounded 为 16px`、`验证登录功能`、`验证优惠券创建`

> title 好/坏写法对照示例见 [writing-examples.md](writing-examples.md)。

**steps 规范**：
- 每一步以动作开头，包含操作对象、值或路径
- 每一步仅包含一个核心动作；禁止 `修改并保存`、`点击并跳转`、`输入后提交`，应拆分为独立步骤
- UI 步骤使用控件/页面的实际名称，不使用「左上角按钮」「对应入口」等泛称
- API 步骤写明方法、路径、必要参数、认证方式或关键请求头
- 数据步骤写明查询对象和字段，如 `查询 Redis 键 ... 的 consume 字段`
- 涉及输入、选择、配置时必须明确具体值
- 纯准备动作放进 `preconditions`；步骤只保留会触发或观察被测行为的动作
- 禁止占位话术：`按测试点要求执行...`、`执行对应操作`、`验证相关功能`
- 禁止作为独立步骤：`查看 xxx 是否...`、`验证 xxx 是否...`、`检查 xxx 是否...`
- 禁止在步骤中使用 `if/else` 描述不同路径；每个条件分支应成为独立用例
- 不超过 7 步，超过 7 步必须按用户路径、状态分支或验证层次拆分为多条用例

> steps 好/坏写法对照示例见 [writing-examples.md](writing-examples.md)。

**expected_results 规范**：
- 必须明确、可验证、可定位，指明至少一类可观察证据：
  - **UI**：实际元素状态、文案、路由、加载态、错误态
  - **API**：HTTP 状态、业务错误码、响应字段和值
  - **数据**：表/缓存/消息/事件的字段和值
  - **业务状态**：状态迁移、生效时机、额度或金额变化
  - **可观测性**：事件名、属性、日志、trace 或告警
- 默认「一步一验」：每步后有对应的主要观察结果
- 同一触发动作存在不可分割的多个业务结果时，允许在该步骤对应的预期下合并多条紧密断言；不要将 UI、接口、数据库等彼此独立的验证硬塞在一条用例里
- 禁止使用：`结果正确`、`符合预期`、`配置正确`、`功能正常`、`应生效`、`与测试目标一致`
- 必须与 steps 中的实际操作直接对应；禁止生成 steps 中未发生操作的预期结果
- 自检：如果我是测试执行人员，看到这个 expected_results，能否直接判断 Pass 还是 Fail？

> expected_results 好/坏写法对照示例见 [writing-examples.md](writing-examples.md)。

**steps ↔ expected_results 一一对应（强制）**：
- `steps[N]` 和 `expected_results[N]` 数量必须一致
- 每步操作后立即写出对应的预期结果
- 预备动作上移到 preconditions

**description 规范**：
- 第一行记录追溯：需求 ID / Jira / 测试点编号 / 接口契约 / 设计稿 / 已关联缺陷
- 第二行以「验证」开头，描述条件、对象、动作和结果方向
- 不复述步骤；不写「验证功能正常」「验证符合预期」

**测试点→用例映射规则**：
- 同一流程不同测试数据 → 合并为 1 条用例，数据参数化
- 不同前置条件/预期结果/测试逻辑 → 拆分为独立用例
- 同一字段多类校验 → 按类拆分，每类 1 条

## 禁用的模糊表达

以下表达不能单独构成步骤或预期：`正常`、`正确`、`符合预期`、`相关`、`对应`、`适量`、`多次`、`一些`、`大约`、`可能`、`频繁`、`边界值`、`最大`、`最小`、`等`。

替换为可复现的事实：

| 不可执行表达 | 改为 |
|---|---|
| `输入正确的手机号` | `输入手机号 13800138000` |
| `连续多次提交` | `在 10 秒内连续点击“提交”按钮 2 次` |
| `输入超长内容` | `输入 101 个字符（字段上限为 100）` |
| `提示错误信息` | `输入框下方显示“Wrong URL format!”` |
| `接口返回正常` | `接口返回 HTTP 200，data.id 非空` |

不确定的规则不应写成「可能」或「待确认」后直接执行。应在需求/测试点中标记待确认，确认后再落为可判定用例。

## Tag 规范

Tag 使用小写 kebab-case，单条 1–5 个。第一个 Tag 必须是业务域；后续按筛选价值由宽到窄排列：

```text
业务域 → 功能/操作 → 关键对象或版本 → 资源/渠道 → 边界属性
```

示例：

```yaml
tags: [webhooks, validation, endpoint-url, boundary]
tags: [api-billing, api-v4, plan-v3, tracking-create, overage]
tags: [account-management, deletion, child-account]
```

规则：
- Tag 用于跨文件筛选，不重复 title 中没有筛选价值的信息
- 复用已有受控词表；新增 Tag 前先检索相近模块
- 不在每条用例重复版本/发布名称；这类归属放文件级 `metadata.tags`
- `boundary`、`security`、`compatibility` 等仅在确实表达额外测试切面时添加

## 用例拆分与合并策略

用例划分需在三个目标间寻求平衡：**单一验证目标**、**失败原因可隔离**、**执行与维护成本可控**。基础准则：原子化、互不干扰的场景是最基础的划分单元，再结合业务内聚性与复杂度决定是否合并或进一步拆分。

**以下场景必须拆分独立测试用例**：
- 默认值验证
- 配置修改验证
- 保存后刷新验证
- 权限验证
- 异常输入验证
- 边界值验证
- 验证的是不同的业务规则（如正确登录 vs 错误密码登录）
- 场景之间完全独立、无相互依赖且前置条件不同
- 某一边界条件历史上反复出现缺陷或属于关键高风险逻辑（需频繁单独回归）

**以下场景可合并为一条用例**：
- **同一业务操作触发的多个紧密结果**：如用户注册成功后同时验证"数据库新增记录 + 发送欢迎邮件 + 初始积分为0"，使用**软断言（soft assert）**一次执行所有检查，汇总全部失败。要求：检查点属于同一操作触发的结果。
- **端到端核心业务流程**：如登录→搜索→加购→下单→支付，保留为一条业务流程用例。控制步骤数在 5-8 个关键节点内，每节点设置明确检查点。若流程过长，按业务阶段拆分为多个中等粒度流程用例。
- **前置条件极其昂贵或难以重建**：如数据准备需长时间批处理或依赖难以复现的环境时，可在同一用例中沿流程验证多个关键节点以分摊成本。需在用例注释中说明合并原因，此类用例作为补充而非常态。
- **同一规则下的参数化变体**：如数值输入框边界值（-1、0、1、最大值、最大值+1），通过**数据驱动**将"相同逻辑、不同输入"组织在一起，测试方法本身仍只验证一条规则。

**基于复杂度主动拆分**：
- 用例步骤数 > 15 行 → 必须拆分
- 检查点 > 5 个且不共享同一触发条件 → 必须拆分（即使用软断言也不行）
- 用例中出现 if-else 条件分支模拟不同路径 → 按分支拆分为独立用例
- 同时验证页面展示、接口状态码、数据库字段值等不同层次的检查 → 按被测模块或验证层次拆分

**合并决策快速判断（5 步法）**：

| 步骤 | 问题 | 判断 |
|------|------|------|
| 1 | 两个场景验证的是同一个业务规则吗？ | 否 → 必须独立 |
| 2 | 合并后，一个场景失败是否会阻断其他场景的验证？ | 会（且无法用软断言解决）→ 独立 |
| 3 | 合并后是否需要软断言才能一次跑完所有检查？ | 是，且检查点属于同一操作触发的结果 → 可以合并 |
| 4 | 分开写是否会导致大量无法消除的重复准备？ | 是 → 考虑合并为流程用例，或用数据驱动方式组织 |
| 5 | 即使可合并，当前用例的步骤/检查点数量是否已显著增加维护成本？ | 是 → 按模块或层次拆分 |

**软断言说明**：当一条操作触发多个可同时验证的结果时，使用软断言在一次执行中全部验证，即使某一项失败也不会影响其他检查执行，失败输出能清晰指出哪一项不符合预期。

禁止为了减少用例数量而合并无关验证目标。

## 输出格式说明

用例输出采用 YAML 结构化格式，优势：
- 直接阅读和编辑，业务文本与字段边界清晰
- 转换为任意测试管理工具格式
- 版本控制和 diff 比较

导入特定测试管理工具时，必须使用脚本或手动转换。

## 效率度量输出（AI 生成模式必做）

阶段 4 自检完成后，输出效率报告：

```markdown
## 效率度量报告

| 指标 | 本次值 |
|------|--------|
| 用例总数 | X 条 |
| AI 生成 | Y 条 (Z%) |
| 人工补充 | W 条 |
| 预估传统工时 | N 人天 |
| 实际工时 | M 人天 |
| 工时节省 | (N-M)/N * 100% |
| 效率提升 | N/M 倍 |

**质量观察**：
- AI 生成用例中需修改的比例：约 A%
- AI 补充的异常/安全场景数量：B 条
```

**传统工时估算基准**：
- 低（单表单/单页面，3-5 字段）：0.5 人天
- 中（多表单/多页面，含联动/权限）：1-2 人天
- 高（复杂业务流程，多角色多状态）：3-4 人天
- 极高（跨系统集成，核心业务链路）：5+ 人天
