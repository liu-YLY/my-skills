# 用例编写规则与格式标准（写作契约）

> **何时阅读**：阶段 3 必读，写作规则唯一权威源。好坏对照见 [writing-examples.md](writing-examples.md)；动词与可读性细则见 [readability.md](readability.md)；编排见 [case-arrangement.md](case-arrangement.md)；失败语义与追溯契约见 [failure-semantics.md](failure-semantics.md)。

## 通用块结构与 ID 规范（强制）

每条用例必须以 `### TC_{模块}_{功能}_{三位序号}: 标题` 起始（脚本校验唯一锚点；用列表、加粗或整表代替标题等同未校验）。用户指定 YAML 等载体时字段语义与句法禁令同等生效。

```markdown
### TC_WEBHOOK_ADD_001: 新增 Webhook - 填写合法 HTTPS 地址提交后持久化生效

- **优先级**: P0
- **类型**: functional
- **需求追溯**: Story-42 / TP-01
- **来源**: ai-generated
- **人工审核状态**: not-reviewed
- **业务背景**: 验证管理员提交合法 HTTPS 地址可成功创建 Webhook

**前置条件**:
- 已登录管理员账号；已打开「Add webhook」弹窗

**测试步骤**:
1. 输入名称「订单通知」与地址 `https://example.com/hooks/orders`
2. 点击「Add webhook」提交并刷新列表页

**关键检查点**:
- 步骤 2 提交后：弹窗关闭，列表新增「订单通知」

**业务结果**:
- 刷新后「订单通知」仍存在且地址一致；列表仅新增 1 条记录

**后置条件**:
- 删除 Webhook「订单通知」
```

- **紧凑表格模式（仅限 P2/P3 同构组）**：同一 `### TC_xxx` 块内，可将 ≥5 条逻辑同构的 P2/P3 数据变体合并为 `| 用例 ID | 输入值 | 操作 | 预期结果 |`（≤10 行，每行独立 ID 且计入总预算）；P0/P1 必须完整块，**严禁用一张大表罗列全部用例**。
- **ID 续编规则**：从同模块已有 ID 提取前缀，`序号 = 同模块同功能最大序号 + 1`；禁止 `TC_001`、`TC_NEW_001`、跳号或缩写漂移（已有 `WEBHOOK` 禁写 `WH`）。性能/安全变体见 [test-standards.md](test-standards.md)。

## 字段契约速查

| 字段 | 必填 | 核心约束 |
|------|------|----------|
| **优先级 / 类型** | 是 | `P0–P3`；`functional`(默认) / `ui` / `security` / `performance` / `compatibility` / `usability` / `accessibility` / `observability` |
| **需求追溯 / 引用** | 否 | Story ID / TP 编号 / 接口契约；可选 `trace_refs` 绑版本化产物 ID（不用列表行号） |
| **来源 / 审核状态** | 否 | `ai-generated` / `manual`；未经真实人工审阅固定填 `not-reviewed` |
| **业务背景** | 否 | 「验证」开头一句话（≤40 字，条件+对象+结果方向），不复述步骤 |
| **前置条件** | 否 | 槽位：`[对象/角色] + [当前客观业务状态与关键属性值]` |
| **测试步骤** | 是 | 真实业务动作序列，含具体输入值，不要求步步配断言 |
| **关键检查点** | 否 | 仅在必要中间态设检查点，就近写 `步骤 N 后：…` |
| **业务结果** | 是 | 槽位：`[直接业务结果或错误提示]；[核心对象的状态或数值变化]` |
| **后置条件** | 条件 | 改写状态或共用环境时必填具体清理/保留动作（禁写「环境恢复正常」） |
| **标签** | 否 | 小写 kebab-case，1–5 个，首位为业务域（如 `webhooks, validation, boundary`），不重复无筛选价值的词 |

## 四大槽位纪律与脱水铁律

### 1. 冲突裁决与删词脱水测试

- **冲突裁决铁律**：**人类秒读精炼性 > 防御性免责解释**。默认除被测异常外其余服务、网络、配额均正常，执行人具备基本测试常识。
- **删词脱水测试（输出前必做）**：逐句自问——「删掉这半句话，懂基本常识的测试工程师是否仍能准备数据、执行操作并准确判定 Pass/Fail？」回答为「是」则立即删掉。
- **单条数据自包含**：角色特征、初始状态和具体输入值直接写在本条用例内；**严禁抽离到外部 `test-data.md` 再用 `夹具 M4`、`见数据表 S1` 等暗号跨文件引用**（需离线批量文件交 `test-data-generator`，用例正文仍须自包含可读）。

### 2. 标题：一眼定位测试点

- 格式 `被测对象 - 具体条件与预期方向`（建议 ≤40 字；删词会导致同模块重名或丢失关键环境标识时可超长，**严禁截断或用 `...`/`等` 隐藏条件**）。
- **禁止**以 `验证`、`测试` 开头（`验证码`、`测试数据` 除外）；禁止纯抽象词（`验证登录功能`）或重复 ID 模块名。英文 UI 原文保留。

### 3. 前置条件：可重建客观状态 + 四不写

按「可随时新建或重置的状态特征」定义（如「存在待支付订单 `ORD_01`（应付 100.00 元）」），不绑死跑一次即脏的唯一实例、不改全局配置或拨服务器时钟；禁止写「沿用上一条记录」（串联须显式写 `由 TC_xxx 创建` 并在上游后置条件声明保留）。

1. **禁默认无干扰废话**：服务可用、网络正常、余额/配额充足、无其他阻断、不先触发其他限制。
2. **禁执行过程叮嘱**：期间不重发、不重新登录、不手工改库/改有效期、不复用前组数据。
3. **禁取证与快照动作**：已记录原值/原数量、保存快照、计数已回读、由技术协作者配合。
4. **禁裸写底表列名**：业务/UI 用例写业务属性（「年付套餐总额度 100、已用 81」），严禁裸写 `ssdays=365, up_to=100, consume=81`。

### 4. 测试步骤：只留有业务意义的动作

- 每步动词开头（输入/点击/选择/打开/刷新，不用「执行点击操作/录入/呈现」），写清具体控件名与输入值；UI/业务用例不写类名、表名、SQL 或选择器（协议/契约测试才写 HTTP 方法、路径与请求体；数据验证写明查询键与字段）。
- **步骤删除测试**：复述前置条件、无信息量导航、占位废话（`按测试点要求执行`、`执行对应操作`）、`if/else` 分支混写一律删除或拆条。外部准备放前置，被测登录/导航留步骤。

### 5. 业务结果：只写可判定的观察事实

写成「在哪里 + 看到什么具体状态/文案/数值/错误码/数据变化」：
- **严禁冠行号前缀**：业务结果禁写 `步骤 1：`、`步骤 1～2：`（中间态放 `关键检查点` 用 `步骤 N 后：`）。
- **严禁防作弊说教与免责自辩**：禁写 `不用其他原因代替本例命中`、`不能以页面跳转冒充成功`、`X 秒仅为观察数据不代表 SLA`、`确认前不计入通过率`、`前端提示由 UI 用例另验`。
- **缺具体文案兜底**：需求未给精确文案/错误码时，禁写「待补充」；用结构化事实断言（如「拒绝提交并提示超时，账户状态保持未激活」），同时记入「原文问题清单」。异步流程分别写受理态与终态，不编造 SLA；上游传入 `traceability` 图时按 [failure-semantics.md](failure-semantics.md) 消费。

## 句长红线与禁用词表（机器门禁直拦）

- **硬红线**：除 `数据组：` 枚举外，单条前置、步骤、业务结果的有效汉字 **严格 ≤60 字**，且**最多含 1 个分号**（`>=2` 个分号直接报 error）；单分句目标 ≤20 字，步骤 >7 条按阶段分组，中文用全角标点，数字与英文单位留空格（`16 GB`）。
- **禁用模糊词**：`正常`、`正确`、`符合预期`、`应生效`、`相关`、`对应`、`多次`、`一些`、`部分`、`随机`、`任意`、`大约`、`超长`、`边界值`、`错误信息`、`非法字符`、`等`（须换成具体值，如 `输入 101 个字符`）。
- **合法业务词白名单**：`部分退款`、`部分成功`、`部分失败`、`部分取消`、`默认值`、`默认套餐`、`默认配置`、`正常订单`、`正常状态`、`边界值分析`、`最小权限`、`最大长度`、`所有角色`。
- **禁用说教黑名单**：`已回读`、`另验`、`另由`、`手工修改`、`技术协作`、`无其他阻断`、`不先触发`、`其余条件`、`不代表`、`不计入`、前置取证式 `已记录`/`快照`、反面免责式 `不用…代替`/`不能…冒充`。

## 拆分与合并准则

- **应拆分**：独立业务目标、互斥分支、前置互斥或合并后失败无法定位到具体步骤/字段；**不因 UI/接口/落库证据层次不同而强拆同一动作**。
- **应合并**：同一规则的等价输入变体（参数化或 `数据组：` 汇总）；同一操作触发的多层观察结果（如注册落库+发信+初始积分）；前置高昂的连贯主流程。入口检查失败即停后续依赖步骤，不跨错误状态硬跑。
