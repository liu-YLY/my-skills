## 通用用例格式

新用例采用「业务结果＋关键检查点」。不批量迁移历史用例；用户指定的输出载体可保留，但不要求步骤和结果数量相等。

```markdown
### TC_MODULE_FUNC_001: 被测对象 - 测试意图（具体行为）

- **优先级**: P0
- **类型**: functional
- **需求追溯**: Story-42 / TP-03
- **来源**: ai-generated
- **人工审核状态**: not-reviewed
- **业务背景**: 以「验证」开头，一句话描述条件、对象、动作和结果方向

**前置条件**:
- 已登录为 A 类用户
- 已打开 "Add webhook" 弹窗

**测试步骤**:
1. 填写名称「订单通知」和地址 `https://example.com/hooks/orders`
2. 点击「Add webhook」提交
3. 刷新 Webhook 列表

**关键检查点**（按需）:
- 步骤 2 后：关闭新增弹窗，列表出现名称为「订单通知」的记录

**业务结果**:
- 刷新后「订单通知」仍存在，地址为 `https://example.com/hooks/orders`
- 本次操作只新增一条记录

**后置条件**（按需）:
- 保留本次创建的 Webhook「订单通知」，供后续编辑用例使用

**标签**: 场景标签
```

### 紧凑表格模式（P2/P3 批量用例可选）

当同类 P2/P3 用例数量 ≥5 条（如字符类型等价类、多机型兼容矩阵），可将该组用例合并为一张紧凑表格，每条用例一行：

```markdown
### TC_PROFILE_NICKNAME_006: 修改昵称 - 字符类型等价类（紧凑组）

- **优先级**: P2
- **类型**: functional
- **需求追溯**: TP-PN-006
- **业务背景**: 验证白名单字符类型各自独立组成昵称时均被接受

**前置条件**: 账号 A 已登录，处于「修改昵称」页

| 用例 ID | 输入值 | 操作 | 预期结果 |
|---------|--------|------|----------|
| TC_..._006a | `测试用户`（纯中文） | 点击「保存」 | 保存成功，「昵称」行显示 `测试用户` |
| TC_..._006b | `testuser`（纯英文） | 点击「保存」 | 保存成功，「昵称」行显示 `testuser` |
```

> 示例仅展示 2 行，实际组内用例数不少于 5 条。

**使用约束**：
- 仅限 P2/P3 且验证逻辑同构的用例组；P0/P1 必须用完整块状格式
- 组内共享的前置条件/元信息写在组头部，行内只保留变化部分
- 单组行数不超过 10 行；跨验证逻辑的用例禁止合组
- 每行仍必须有独立 ID（可用字母后缀 `006a/006b`）与可判定的预期结果

## 补充用例 ID 生成规则（强制）

当评审模式或阶段 4 自检发现缺失用例需要补充时，**必须**按以下规则生成 ID：

**ID 格式**：`TC_{模块}_{功能}_{三位序号}`

**生成步骤**：
1. **确定模块缩写**：从已有用例 ID 中提取模块前缀（如 `TC_WEBHOOK_ADD_001` → `WEBHOOK`）
2. **确定功能缩写**：从已有用例 ID 中提取功能前缀（如 `TC_WEBHOOK_ADD_001` → `ADD`）
3. **确定序号**：扫描已有用例 ID，找到相同模块+功能的最大序号，新用例序号 = 最大序号 + 1

**示例**：
- 已有用例：`TC_WEBHOOK_ADD_001`, `TC_WEBHOOK_ADD_002`, `TC_WEBHOOK_EDIT_001`
- 补充新增用例：`TC_WEBHOOK_ADD_003`（最大序号 2 + 1）
- 补充编辑用例：`TC_WEBHOOK_EDIT_002`（最大序号 1 + 1）

**禁止**：
- 使用不规范格式：`TC_001`、`TC_NEW_001`、`TC补充_001`
- 序号跳跃：已有 001、002，新增用 005
- 模块/功能缩写不一致：已有 `WEBHOOK`，新增用 `WH` 或 `webhook`

## 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| **ID** | 是 | `TC_{模块}_{功能}_{三位序号}`，作为标题 |
| **标题** | 是 | `被测对象 - 具体行为/条件/结果`，建议 40 字以内（软指导）；信息删除会造成同模块场景重复或无法识别环境/版本时可保留长标题，禁止通过截断、`...` 或「等」隐藏关键条件 |
| **优先级** | 是 | P0/P1/P2/P3，定义与比例见 [test-standards.md](test-standards.md) |
| **类型** | 是 | functional / ui / security / performance / compatibility / usability / accessibility / observability；描述「主要验证目标」而非技术实现 |
| **需求追溯** | 否 | 需求 ID（Story ID）、测试点编号（TP 编号）、接口契约、设计稿或已关联缺陷 |
| **来源** | 否 | 用例来源：ai-generated / manual；历史 ai-reviewed 保留但不作为人工审核证明 |
| **追溯引用** | 否 | 可选 `trace_refs` 指向追溯图稳定产物ID；`stable_ref` 是当前输入/断言内容标识；长期身份使用显式版本化产物ID，不用列表位置或SM展示编号代替 |
| **人工审核状态** | 否 | not-reviewed / reviewed，独立于来源；reviewed 需记录真实审核依据，AI 自检不等于人工审核 |
| **业务背景** | 否 | 以「验证」开头描述条件、对象、动作和结果方向；不复述步骤 |
| **前置条件** | 否 | 陈述句列表，覆盖角色/权限、页面或调用条件、数据状态；不写「已准备相关数据」「账号正常」「环境正常」 |
| **测试步骤** | 是 | 按业务操作组织的有序步骤，不要求每步独立断言 |
| **业务结果** | 是 | 最终可判定的结果；结构化输出使用 `expected_results` 字符串数组 |
| **关键检查点** | 否 | `checkpoints` 数组，每项含 `after_step`（从 1 开始）与 `expected_results` 数组 |
| **后置条件** | 条件 | 改变系统状态或与其他用例共用环境时必填：写明复位、清理或需保留的数据，写法见下方「后置条件写法」 |
| **标签** | 否 | 小写 kebab-case，1–5 个，首位必须是业务域；规则见下方「Tag 规范」 |

**后置条件写法**：
- 默认不填；新增/修改/删除数据、占用资源、发送消息，或与其他用例共用环境时必填
- 写可执行的动作或需保留的产物，不写「环境恢复正常」这类评价：`删除本次创建的 Webhook「订单通知」`、`保留订单 ORD-20261031-001 供退款用例使用`
- 与下一条用例衔接：下一条依赖本条产物时，在此显式声明；无副作用时可省略

## 写作风格与信息密度

用例首先是给人读的文档，其次才是执行脚本。目标是执行人只扫标题、步骤、预期三处，就能说出这条用例测什么、怎么操作、看到什么算通过。

### 三条原则

1. **一句话一个事实**：标题说测试点，步骤说操作，预期说观察结果。同一事实只出现一次，不复述。
2. **每句话都要有定位价值**：删掉一句后，如果仍能判断测什么、怎么执行、是否通过，这句就不该出现。
3. **用日常业务动作词**：输入、点击、选择、打开、刷新；不用「执行点击操作」「录入」「呈现」「触发」这类机器腔。

### 标题：第一眼看到测试点

判断标准：只看标题，能否回答「测什么对象、在什么条件下、预期发生什么」。

| 能定位 | 不能定位 | 问题 |
|--------|---------|------|
| `手机号登录 - 验证码错误时提示「验证码不正确」` | `登录异常场景测试` | 没有具体条件与结果 |
| `删除账号 - 存在未完成订单时阻止删除` | `账号删除测试` | 没有条件与结果，只说明测试类别 |
| `Webhook 创建 - Endpoint URL 为空时按钮置灰` | `Webhook 表单验证` | 没有具体字段与行为 |

标题不以「验证」「测试」开头——那是业务背景字段的写法；不写「功能」「逻辑」「场景」等纯抽象名词，「XX 校验 - 条件」这类指明被测对象的写法可用；不重复 ID 中已有的模块名与优先级。

### 步骤：只保留有业务意义的操作

| 无意义填充 | 例子 | 处理 |
|-----------|------|------|
| 复述前置条件 | 「确认已登录系统」 | 删除，前置条件已有 |
| 无信息量导航 | 「打开浏览器，进入系统，找到菜单」 | 删除；导航本身是被测行为时才保留 |
| 空泛动作 | 「填写相关信息」「进行配置」 | 改为具体字段与值 |
| 解释性文字 | 「由于额度不足，因此点击提交」 | 原因移到业务背景，步骤只留动作 |
| 操作与验证混写 | 「点击保存并确认结果」 | 操作、结果分开写 |

**删除测试**：删掉这一步后，用例仍可执行且测试点不变，就删除。

### 预期结果：写观察到的事实，不写评价

每条结果写成「在哪里 + 看到什么 + 什么值/状态」：

- UI：`页面跳转到 /home，右上角显示「测试用户」`
- API：`接口返回 HTTP 422，响应体 error.code 为 PHONE_INVALID`
- 数据：`订单表 status 由 pending 变为 paid，paid_at 写入当前时间`

禁止三类填充：

- 评价词：正常、成功、正确、符合预期
- 愿望式：应生效、会被拦截、可以正常使用
- 无关事实：系统稳定、页面无异常、环境正常

### 语气对照

| 生硬 | 自然 |
|------|------|
| 对「登录」按钮执行点击操作 | 点击「登录」 |
| 于手机号输入域录入 13800138000 | 在「手机号」输入框输入 13800138000 |
| 系统呈现「保存成功」提示 | 页面顶部显示「保存成功」 |
| 若用户未登录则跳转登录页 | 未登录时访问该页面，跳转到登录页 |

### 句式：让一句话一次读懂

可读性首先是句子能不能一次解析。以下阈值为软预算，用于提示与改写，不作机械扣分。

**句长预算**：
- 逗号分隔的构件以 20 字以内为目标；20–29 字可接受；30–39 字须语义清晰；超过 40 字必须改写
- 单条步骤或预期不超过 100 字；超出时先删修饰，再拆句
- 拆分优先于压缩：拆成两步不丢信息，压成一句容易丢条件

**四条改写规则**：

| 规则 | 难读 | 易读 |
|------|------|------|
| 一句一个动作 | 点击「保存」并确认列表中出现记录 | 点击「保存」。列表出现「订单通知」记录 |
| 动词直用 | 对 Endpoint URL 输入框执行清空操作 | 清空「Endpoint URL」输入框 |
| 主动语态 | 提交请求被系统拦截 | 系统拦截提交请求 |
| 修饰不超过两层 | 在用于接收订单创建事件通知的 Webhook 配置弹窗中清空 Endpoint URL | 在「Add webhook」弹窗清空「Endpoint URL」 |

**指代与术语**：
- 「其」「该」「此」「这」必须有唯一指代；可能出现歧义时重复名词
- 一条步骤最多出现 1 个需要额外解释的术语；控件名称、产品原文、接口字段属于界面事实，不计入
- 首次出现的术语用一句话或括号解释；同一条用例内多次出现时只在首次解释
- 同一概念全文用一个词；界面本身有多个不同按钮时（如「保存」与「提交」），按界面原文区分，不视为同义词混用

**标点与数字**：
- 中文正文使用全角标点；英文原文、代码、字段值保留原样，不强制转换
- 数字、版本、金额在同一用例内保持同一形式；数值范围统一写 `1~2 天`
- 阿拉伯数字与英文单位之间留空格，如 `16 GB`、`200 ms`

### 结构：让人扫一眼就能定位

读者通常先扫标题，再扫步骤首词，最后看结果。结构服务于这条路径。

**固定顺序**：标题 → 元信息 → 前置条件 → 测试步骤 → 关键检查点 → 业务结果 → 后置条件 → 标签。不调换字段，不把检查点混进步骤。

**首词规则**：

| 位置 | 首词写什么 | 反例 |
|------|-----------|------|
| 标题 | 对象 + 条件，前 6–10 字可定位 | `关于 Webhook 的一些测试` |
| 步骤 | 动词：输入 / 点击 / 选择 / 打开 / 刷新 | `首先，我们需要…` |
| 预期 | 位置：页面 / 接口 / 表 / 缓存 / 消息 | `正确`、`成功` |

**就近原则**：
- 检查点紧跟对应步骤，写成 `步骤 2 后：…`；不集中到文末
- 同一动作的多条结果写在一起，不拆到不同段落
- 需要跨段引用时写步骤号，不写「如上」「见后文」

**分块与长度预算**（软）：
- 单条用例步骤超过 7 条时，按业务阶段分成若干组：每组前写一行阶段名（如 `准备`、`提交`、`校验`），组内编号连续，每组不超过 7 条；分块只改排版，不改变拆分判定
- 单条用例正文建议不超过 300 字（不含元信息）；超出时先删填充，再评估是否拆分
- 表格只用于同构对比（等价类、兼容矩阵、多组数据），不用于叙述流程；单元格不写超过 30 字的句子

**禁止**：
- 用整段文字叙述替代编号步骤
- 有序编号嵌套超过 3 层（`一、` → `（一）` → `1.` 即止）；用例正文一般只用一层
- 括号套括号；补充说明另起一句，或移到业务背景

### 与铁律的关系

可执行性保证用例能跑，可读性保证人能看懂。两者冲突时先保证可执行，再用最少的字表达；不得为了「好看」弱化可判定性。

## 编写与审核铁律

**title 规范**：
- 首选格式：`被测对象 - 具体行为/条件/结果`
- 必须包含：验证对象、用户行为（若存在）、条件与可观察结果
- 可使用分隔符与标记：`-` 分隔对象/条件/行为/结果；`[]` 标示「判定规则」「跨版本」「升级交互」等有筛选价值的类别；`→` 表示状态、版本或套餐迁移；英文产品文案保留原文（如 `Cancel downgrade`、`Add endpoint`）
- 建议不超过 40 字；信息一旦删除会造成同模块场景重复或无法识别环境/版本时，可保留长标题；禁止通过截断、`...` 或「等」隐藏关键条件
- 标题不以「验证」「测试」开头，不写「功能」「逻辑」「场景」等纯抽象名词（「XX 校验 - 条件」是指明被测对象的可用写法）；只看标题应能说出被测对象、触发条件与预期行为（见上方「写作风格与信息密度」）
- 禁止：`验证 Width`、`验证布局`、`验证 Rounded 为 16px`、`验证登录功能`、`验证优惠券创建`

> title 好/坏写法对照示例见 [writing-examples.md](writing-examples.md)。

**steps 规范**：
- 每一步以动作开头，包含操作对象、值或路径
- 按有业务意义的操作组织；允许填写明确的一组表单数据并提交，不必拆成每次输入或点击
- UI 步骤使用控件/页面的实际名称，不使用「左上角按钮」「对应入口」等泛称
- 普通业务步骤使用业务动作和接口名称；协议、路由或接口契约测试才写明 HTTP 方法、路径、参数及认证条件
- 数据步骤写明查询对象和字段，如 `查询 Redis 键 ... 的 consume 字段`
- 涉及输入、选择、配置时必须明确具体值
- 仅将不属于被测行为的外部准备放入 `preconditions`；被测登录、导航或数据准备流程应保留在步骤中
- 禁止占位话术：`按测试点要求执行...`、`执行对应操作`、`验证相关功能`
- 只保留改变状态或提供输入的操作：删除复述前置条件、无信息量导航、空泛动作、解释性文字，以及与操作混写的验证动作（见上方「写作风格与信息密度」）
- 查询、刷新、查看消息等必要观察操作可写入步骤；可判定的结果写入业务结果或关键检查点
- 禁止在步骤中使用 `if/else` 描述不同路径；每个条件分支应成为独立用例
- 单句超过 40 字或一步含两个以上动作时，按上方「句式」改写；这是表达层要求，不改变拆分判定
- 步骤长度只作可读性提示；是否拆分依据业务目标、前置条件与失败隔离，不设数量阈值

> steps 好/坏写法对照示例见 [writing-examples.md](writing-examples.md)。

**expected_results 规范**：
- 必须明确、可验证、可定位，指明至少一类可观察证据：
  - **UI**：实际元素状态、文案、路由、加载态、错误态
  - **API**：HTTP 状态、业务错误码、响应字段和值
  - **数据**：表/缓存/消息/事件的字段和值
  - **业务状态**：状态迁移、生效时机、额度或金额变化
  - **可观测性**：事件名、属性、日志、trace 或告警
- 最终业务结果必须可判定；只在必要的中间状态、后续操作入口或风险判断处设置关键检查点
- 同一业务动作可关联页面、业务状态、消息或数据结果；不因证据层次不同强制拆分，不合并独立业务目标
- 禁止使用：`结果正确`、`符合预期`、`配置正确`、`功能正常`、`应生效`、`与测试目标一致`
- 每条结果写成「在哪里 + 看到什么 + 什么值/状态」；不写评价词、愿望式表达与无关事实（见上方「写作风格与信息密度」）
- 单条结果不超过 100 字；超出时拆成多条可观察事实，不合并成一句
- 必须与 steps 中的实际操作直接对应；禁止生成 steps 中未发生操作的预期结果
- 自检：如果我是测试执行人员，看到这个 expected_results，能否直接判断 Pass 还是 Fail？

> expected_results 好/坏写法对照示例见 [writing-examples.md](writing-examples.md)。

**业务结果与关键检查点**：
- `expected_results` 表达最终业务结果；`checkpoints` 可选，一个检查点可含多个相关结果
- `after_step` 引用实际步骤；多个操作可以共用一次验收，同一动作也可验证多个结果
- 准备和导航不必逐项断言；必要检查失败时停止依赖它的后续操作，独立结果可继续检查并汇总
- 异步流程分别说明受理状态和最终状态，等待依据需求约定的完成事件或时限，不编造 SLA

**需求追溯与业务背景规范**：
- 需求追溯记录：需求 ID / Jira / 测试点编号 / 接口契约 / 设计稿 / 已关联缺陷
- 可选 `traceability` 原样消费：`sources` 为 `id/location/version/availability`（available/unreachable/missing/unknown），`artifacts` 为 `id/kind/version`，`links` 为 `upstream/downstream/confirmation/source/source_refs`（confirmed/candidate）。
- 需求→风险→模型/场景→用例→执行证据以显式产物ID和版本关联；结构化映射仍需关联依据及可达来源版本才标confirmed，缺依据或自然语言相似仅作candidate。
- 来源不可达与业务结果未知分列；未读到来源不补造版本/确认关系，独立Skill无完整图仍可输出并注明追溯未评估。
- 来源/需求变化只标记有已确认关联的受影响结论需复核，候选关联单列待核实；保留旧证据与版本，不覆盖旧执行结果或重跑无关流程。
- 业务背景以「验证」开头，描述条件、对象、动作和结果方向
- 不复述步骤；不写「验证功能正常」「验证符合预期」

**测试点→用例映射规则**：
- 同一流程不同测试数据 → 合并为 1 条用例，数据参数化
- 同一规则的数据变体可参数化，每行写清条件及预期；独立目标、互斥流程或不能共存的前置条件应拆分
- 同一字段多类校验 → 按类拆分，每类 1 条

## 禁用的模糊表达

以下表达不能单独构成步骤或预期（**本清单为唯一权威源，与 test-standards.md「模糊词禁用清单」取并集后统一维护，两处不再各自新增**）：

**基础 15 词**：`正常`、`正确`、`符合预期`、`相关`、`对应`、`适量`、`多次`、`一些`、`大约`、`可能`、`频繁`、`边界值`、`最大`、`最小`、`等`。

**扩展词（来自 test-standards.md，语义等价并入）**：`很多`、`部分`、`大量`、`少量`、`随机`、`任意`、`一段时间`、`一会`、`一点`、`特殊`、`很长`、`较长`、`很短`、`较短`、`多个`、`几块`、`多条`、`数次`、`所有`、`大概`、`某些`、`超长`、`超小`、`超短`、`过低`、`过高`、`全部`、`缺省`、`默认`、`各模块`、`有的`、`一定范围`、`多于`、`少于`、`左右`、`上下`、`设备无异常`、`计数正常`、`长时间`、`错误信息`、`非法字符`。

> 本文件是字段编写规则权威源。词语只有在掩盖输入、条件或结果时才构成问题；「幂等性」「默认套餐」「正常订单」等明确业务术语不因包含单字违规。test-standards.md 仅保留核对语境的说明，不再维护独立清单。

替换为可复现的事实：

| 不可执行表达 | 改为 |
|---|---|
| `输入正确的手机号` | `输入手机号 13800138000` |
| `连续多次提交` | `在 10 秒内连续点击“提交”按钮 2 次` |
| `输入超长内容` | `输入 101 个字符（字段上限为 100）` |
| `提示错误信息` | `输入框下方显示“Wrong URL format!”` |
| `接口返回正常` | `接口返回 HTTP 200，data.id 非空` |

不确定的规则不应写成「可能」或「待确认」后直接执行。应在需求/测试点中标记待确认，确认后再落为可判定用例。

**已识别但判定口径未确认的边界**：保留在独立的待确认场景清单，记录输入、待确认问题及来源；确认唯一验收口径后再生成可执行用例，不能把两种互斥结果并列作为通过条件。

例如：订单 300.00 元、9 折券、优惠上限 30.00 元，若规则已明确为 `min(订单金额 × 10%, 上限)`，优惠应为 30.00 元；不能无依据另造 27.00 元的分支。

## Tag 规范

Tag 使用小写 kebab-case，单条 1–5 个。第一个 Tag 必须是业务域；后续按筛选价值由宽到窄排列：

```text
业务域 → 功能/操作 → 关键对象或版本 → 资源/渠道 → 边界属性
```

示例：

```text
webhooks, validation, endpoint-url, boundary
api-billing, api-v4, plan-v3, tracking-create, overage
account-management, deletion, child-account
```

规则：
- Tag 用于跨模块筛选，不重复 title 中没有筛选价值的信息
- 复用已有受控词表；新增 Tag 前先检索相近模块
- 不在每条用例重复版本/发布名称；这类归属放模块级说明或测试计划
- `boundary`、`security`、`compatibility` 等仅在确实表达额外测试切面时添加

## 用例拆分与合并策略

围绕一个清晰业务目标，在失败可定位与准备、执行、维护成本之间取舍。

**应拆分**：独立业务目标、互斥执行路径、不能共存的前置条件，或合并后失败无法隔离。不要仅因页面、接口、数据库等证据层次不同而拆分。

**可合并**：
- 同一操作的相关结果，如注册后的账户记录、欢迎邮件和初始积分；独立检查可用软断言汇总
- 完整业务流程，如选择商品→下单→支付，保留必要的中间检查点和最终业务结果
- 同一业务规则的数据变体，每组数据具有明确前置条件、输入和预期
- 准备成本高且确实共享业务目标的流程；说明共享准备，避免合并无关目标

**失败处理**：必要的入口或前置检查失败后停止依赖步骤，标记后续未执行；与失败无依赖的结果可以继续检查。不能为追求一次运行而跨过错误业务状态。

**可读性检查**：步骤或结果较多时检查重复导航、无关目标、路径分支及失败定位能力；可以分业务阶段组织，不以固定数量强制拆分。

**信息归属（同一事实只写一处）**：

| 信息 | 唯一位置 | 常见错位 |
|------|----------|----------|
| 为什么做、业务规则 | 业务背景 | 写进步骤，如「由于额度不足，因此点击提交」 |
| 执行前状态 | 前置条件 | 写进步骤，如「确认已登录」 |
| 动作与输入值 | 测试步骤 | 写进前置条件，如「打开弹窗并填写地址」 |
| 观察到的结果 | 业务结果 / 关键检查点 | 写进步骤，如「点击保存并确认列表新增」 |
| 清理或保留的数据 | 后置条件 | 写进业务结果 |

- 前置条件只写状态，不写动作；被测登录、导航属于步骤
- 业务背景不复述步骤；步骤不复述前置条件
- 同一动作的多条结果合并写，不拆成多条步骤

**认知负荷约束**（软）：
- 一步一个决策点：一次提交、一次跳转、一次状态切换；同一表单的字段可一并填写，但不得跨页面、跨判断分支
- 单步涉及字段建议不超过 5 个；超出时按字段组分步，如「基本信息」与「通知配置」
- 一条用例步骤建议不超过 7 条；超出先按「结构」节分块，再评估是否拆分
- 一条用例建议只使用 1 组主数据；需要对比多组数据时改用参数化表格
- 合并后若无法指出「哪一步、哪个字段」导致失败，说明粒度过粗，应拆分

## 覆盖报告的证据边界

输出覆盖情况时区分需求条目、模型转换、适用场景设计和实际执行；每层注明分母来源/版本及未评估项，
沿用策略的requirement_baseline/design_baseline/case_baseline与已有模型覆盖语义，不改变旧transition/forbidden分母。
无需求基线不能计算需求覆盖；无真实执行记录不能计算执行通过率；候选关联和待确认场景不混入已验证结果。
同一基线与run下去重稳定ID，空基线、不适用、缺输入分别表达；只有设计证据时明确「已设计，未执行」。
