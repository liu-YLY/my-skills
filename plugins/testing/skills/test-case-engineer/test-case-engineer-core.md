# 测试工程师核心流程

> 四阶段：理解需求 → 提取测试点 → 编写用例 → 自检补全。写作细节见 knowledge/，本文件只保留流程、闸门与失败处理。

## 工作流概览

```
输入：需求文档/用户描述/代码变更
  ↓ 阶段 1：理解需求 → 需求理解文档（结构化）
  ↓ 阶段 2：提取测试点 → 测试点清单（Markdown 表格）
  ↓ 阶段 3：编写用例 → 测试用例（结构化块）
  ↓ 阶段 4：自检补全 → 最终用例 + 效率报告
```

后一阶段的输入是前一阶段的输出。阶段 3 的格式与字段见 [knowledge/writing-rules.md](knowledge/writing-rules.md)，分层与编排见 [knowledge/case-arrangement.md](knowledge/case-arrangement.md)。

## 阶段 1：理解需求

**目标**：理解业务背景、技术实现与产品现状。**输出**：需求理解文档。

### 信息收集（按优先级）

| 优先级 | 手段 | 做法 |
|--------|------|------|
| P0 | 项目知识库 | 扫描 `docs/`、`testing-tm-cases/`，读取相关文档 |
| P0 | 产品知识库 | 识别产品并加载 `knowledge/products/{product-id}.md` |
| P0 | 代码库 | 搜索模块实现、API 定义、数据模型、校验逻辑；必要时看控制器/服务层实际行为 |
| P0 | 已有用例 | 读同模块用例，继承风格、避免重复 |
| P1 | 公开文档 | 第三方服务文档、API 规范、竞品实现 |
| P2 | 追问用户 | 列出具体问题清单，不做假设 |

**产品知识加载**：识别产品归属并加载对应文件，业务规则/缺陷/清单/状态/模板/数据字典用于阶段 1–3；测试点「来源」列标注「产品知识-{章节名}」。无文件时按通用流程并标注「未找到产品知识文件」。识别方式见 [SKILL.md](SKILL.md)「产品知识库」。

**来源追踪**：执行期间每读取/搜索一个文件或文档，立即追加到「信息来源」。

**自检**：确认信息来源与业务目标，展示影响结论的存疑点；无阻塞信息则进入阶段 2。

**需求评审衔接**：已有问题清单直接消费：confirmed 进「原文问题清单」，candidate 进「待确认项」，不重复评审。

### 可测性与验收口径

- **日志与追踪**：能否用 request id / trace id 唯一定位一次调用
- **可观测性**：指标、告警、链路是否与验收口径一致
- **造数与配置**：测试账号、造数接口、mock、开关是否齐备
- **验收定义**：除界面外，是否要求后端状态、对账、消息投递等证据

### 失败模式与 Fallback

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 项目文档缺失/不完整 | 扫描代码库、注释与 README 提取逻辑 | 列「存疑点」要求补充；缺失段落回填「原文问题清单」（位置=文档名:章节，类型=缺失） |
| 代码库无权限/不可达 | 请求关键代码片段或 API 文档 | 基于需求推断标「待验证」；不可达位置回填「原文问题清单」（位置=路径，类型=缺失） |
| 已有用例风格不一致 | 取最近 3 个模块用例作参考基线 | 采用通用格式，阶段 4 统一校验 |
| 用户无法确认存疑点 | 列备选解释及各自影响 | 依赖未决规则的场景标「待确认」，与可执行用例分开；回填「原文问题清单」（位置=对话轮次#N，类型=模糊） |

### 需求理解输出模板

```markdown
## 需求理解

**功能概述**：[一句话]

**本次变更焦点**：
| 焦点项 | 需求依据 | 改动的行为 |
|--------|----------|------------|
| [焦点 1] | [PRD §x.y / Story-ID] | [从…变为…] |

**不在本次范围**：[需求未涉及、也不受本次改动影响的内容]
**需求追溯**：
| 条目 | 需求ID/PRD章节/Story | 备注 |
|------|----------------------|------|
| [能力点1] | [ID 或 章节号] | 无正式 ID 填「待补充」 |

**用户角色**：[所有涉及的用户类型/权限角色]
**业务规则**：1. [规则 1] 2. [规则 2]
**状态规则**：初始状态 / 状态切换 / 状态保存 / 状态互斥 / 非法状态
**配置联动规则**：上游配置 / 下游行为 / 配置优先级 / 配置冲突
**默认值规则**：[字段/功能的默认值及业务含义]
**异常规则**：[网络异常、接口超时、权限不足等处理逻辑]
**数据规则**：[校验规则、一致性要求、流转规则]
**风险分析**：高风险模块 / 高回归风险 / 必须重点测试范围
**待确认项**：[需求未明确处，标注「待产品确认」或「待需求补充」]

**原文问题清单**（阶段 1–4 累积，不另起章节）：
| 序号 | 原文位置 | 问题类型 | 问题描述 | 影响范围 | 处置 |
|------|---------|---------|---------|---------|------|
| 1 | [PRD §3.2 / req.md:L42 / 对话轮次#3] | 模糊/矛盾/缺失/错误 | [原文片段 + 问题] | [影响的测试点/用例] | [待确认 / 已按 X 理解 / 已标条件分支] |

**信息来源**：[实际参考的文件/文档/检索结果]
```

原文位置：需求用 `文件名:行号`/`PRD 章节`，代码用 `路径:行号`，口述用 `对话轮次#N`。

**焦点三档**（焦点 / 回归 / 范围外）的判定与用例待遇见 [knowledge/scope-discipline.md](knowledge/scope-discipline.md)。

### 业务系统识别

| 系统类型 | 识别特征 | 核心测试维度 |
|----------|----------|--------------|
| 通知/邮件 | Email、Notification、Message、Subscription | 发送/重复/失败，订阅/退订/黑名单，开关 |
| 状态机 | Enable/Disable、Toggle、Status、Publish/Draft | 初始/切换/保存/刷新后状态/互斥/非法流转 |
| 配置系统 | 全局配置、子配置、Feature Flag、多级配置 | 上游影响/下游行为/覆盖/优先级/冲突 |
| 支付/订单 | Payment、Order、Refund、Invoice | 金额精度/重复支付/部分退款/超时/状态流转 |
| 权限系统 | Role、Permission、Auth、Access Control | 角色矩阵/越权/Token 过期/敏感数据 |
| 搜索/筛选 | Search、Filter、Sort、Pagination | 特殊字符/空结果/大结果集/排序/组合 |
| 异步任务 | Job、Queue、Scheduler、Cron、Async | 触发/重试/死信/延迟/并发 |

识别后标注系统类型并把核心维度补进测试点清单；多系统逐一覆盖。

## 阶段 2：精准提取测试点

**目标**：不漏焦点、不留越界。**输出**：测试点清单（编号/测试点/维度/设计方法/优先级/用例数/需求引用/来源/裁剪说明）。

### 范围闸门（每个候选点必过）

1. **需求依据**：需求原文、变更说明或接口契约里有对应条目？
2. **变更影响**：本次改动会改变这条的预期结果？
3. **失败归属**：失败时由本次需求的责任方修？

任一为否即不落用例，在「裁剪说明」列写明理由。服务故障类（断网/5xx/超时/降级/依赖不可用）、边界值膨胀、非重点内容展开三类默认不写；需求本身要求容错时，容错条目属于焦点。详见 [knowledge/scope-discipline.md](knowledge/scope-discipline.md)。

### 风险与优先级（粗分级）

评估变更面（影响模块数）、业务影响（资金/合规/核心路径）、技术复杂度（新依赖、并发、分布式），辅助映射 P0–P3。

### 7 维度扫描

覆盖深度是扫描清单，不是用例数量下限；按业务风险与资金/权限/状态属性决定是否落用例，裁剪项写理由。

| 维度 | 检查内容 | 覆盖深度（按风险裁剪） |
|------|----------|----------------------|
| 正向功能 | 核心业务流程正常路径 | 每个涉及角色至少 1 条 Happy Path |
| 反向校验 | 异常/非法输入 | 只覆盖本次改动涉及校验的字段；等价输入合并为参数化一行 |
| 权限/角色 | 不同用户类型的可见内容与操作 | 只覆盖需求明确的角色 × 功能点，其余裁剪并写理由 |
| 状态联动 | 选项 A 变化时 B 的联动响应 | 每对联动关系 × 相关源状态 |
| 边界与限制 | 数量上限、长度限制、重复校验 | 仅对需求给阈值且本次改校验的字段取一组三点（临界内/临界/临界外），对称区间只取一端 |
| UI 交互 | 按钮状态、提示文案、跳转、加载态 | 仅当 UI 本身为被测对象时逐点覆盖 |
| 异常与容错 | 网络异常、并发、服务端错误 | 仅当需求要求容错/降级/重试时覆盖；默认 0 条 |

### 测试点设计原则（强制）

- **单一验证目标**：每条只验证一个核心目标；禁止「保存成功并且页面展示正确」；不堆叠正常+异常、默认+修改后、UI+数据、权限+展示。
- **要素完备**：必须含 [验证对象] + [操作/场景] + [预期结果方向]；禁止「验证 General updates 可以关闭」，须写清关闭后状态与保存行为。
- **核心业务优先**：数量与深度向焦点倾斜；非焦点只留 1 条冒烟；禁止大量低风险 UI 测试点（通知系统核心是发送/内容/退订，不是 Toggle UI）。

### 缺陷模式与产品知识补点

7 维度扫描后对照 [knowledge/bug-patterns.md](knowledge/bug-patterns.md)「缺陷模式→测试点映射」：只对焦点功能命中的模式补点。容错类仅当需求要求容错；输入类仅当字段面向公网或要求校验收敛；产品专项同样受范围闸门约束。

已加载产品知识时按表提取，并在「来源」列标注「产品知识-{章节名}」：

| 产品知识章节 | 提取规则 |
|--------------|----------|
| 业务规则与约束 | 每条规则至少 1 条正向 + 1 条反向 |
| 状态流转规则 | 每条合法流转 1 条正向、每条非法流转 1 条反向；状态机 skill 已输出场景时不重复建模 |
| 历史高频缺陷 | 命中焦点功能时补防御性测试点，未命中不补 |
| 专项检查清单 | 逐项判定是否涉及，涉及才补 |
| 数据字典与校验规则 | 只对焦点字段取点：有阈值取一组三点，格式/类型校验合并为参数化一行 |
| 性能基线 | 需求给出指标时作为预期阈值；未要求不生成性能用例 |

产品知识不是补点清单：未命中项写进裁剪说明（如 `产品知识-历史缺陷：本次未触及该模块`）。

### 设计方法决策树

- 输入域有需求阈值 → 只取一组三点，不做全区间穷举
- 多个条件组合 → 判定表/因果图
- 明确状态流转 → 状态迁移法
- 业务流程 → 场景法（基本流 + 备选流 + 异常流）

### 测试点清单模板

```markdown
## 测试点清单

| 编号 | 测试点 | 维度 | 设计方法 | 优先级 | 用例数（估） | 需求引用 | 来源 | 裁剪说明 |
|------|--------|------|----------|--------|-------------|----------|------|----------|
| 1 | Endpoint URL 必填校验 | 反向校验 | 等价类+边界值 | P0 | 3 | PRD §3.2 | 需求 | - |

**覆盖度自检**：7 维度均已判定适用性；缺陷模式命中/未命中已说明；有阈值字段取三点、无阈值已写裁剪；角色/权限与联动关系已覆盖或裁剪；越界候选已剔除并写清理由。
```

**阶段 2 自检**：核对需求/风险/待确认项；依赖未决规则的场景单列。

**阶段 2 机器校验**：测试点清单保存后运行 `python $SKILL_ROOT/scripts/validate_points.py <清单.md>`；0 error 方可进入阶段 3。

### 失败模式与 Fallback

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 测试点遗漏（阶段 4 发现） | 回溯 7 维度，只补焦点或需求条目要求的遗漏 | 标遗漏维度并用例标「待补充」；需求段落回填「原文问题清单」（类型=缺失） |
| 缺陷模式库无匹配 | 用通用模式（输入校验/状态/权限/数据/UI） | 仅输出 7 维度扫描结果，不强制补点 |
| 设计方法选择困难 | 优先场景法（基本流+备选流+异常流） | 多方法并用，阶段 4 去重 |
| 需求规则表述不清 | 列歧义点要求澄清 | 按最保守理解设计，歧义点回填「原文问题清单」（类型=模糊） |

## 阶段 3：编写测试用例

**输入**：需求理解 + 测试点清单。**输出**：测试用例，每条以 `### TC_{模块}_{功能}_{序号}: 标题` 块承载；表格仅用于块内同构数据组，**不得用整表罗列全部用例**。

### AI 生成模式（默认）

1. 三轮生成：基础正向/反向 → 补未覆盖测试点 → 按缺陷模式命中项补防御性用例
2. 若已加载产品知识：将业务规则、常见场景模板作为上下文注入
3. AI 生成 70%–90% 的基础用例
4. 人工审核业务逻辑、领域边界、优先级合理性，并补充 AI 遗漏的复杂业务逻辑用例

**产品知识注入**：用数据校验规则约束输入值、状态流转规则补全状态路径、测试数据与环境完善前置条件、常见场景模板作 Few-shot。

**来源标记**：AI 生成标 `source: ai-generated`，人工补充标 `source: manual`；人工审核状态单列，未经人工审阅不得声称已审核。

### 阶段 3 输出前自检

- 必填字段齐全；业务结果可判定，关键检查点指向实际步骤
- 标题能独立定位测试点（对象 + 条件 + 预期），不以「验证」「测试」开头；建议 40 字以内，信息不可删时可保留长标题
- 步骤只保留改变状态或提供输入的操作，无复述前置条件、无信息量导航与解释性文字
- 范围符合焦点分级：服务故障类为 0 条或每条有需求依据；非焦点内容只到冒烟级
- 正文无测试黑话/套话；预期为「位置 + 对象 + 状态/值」；模糊表达按 [knowledge/writing-rules.md](knowledge/writing-rules.md)「禁用的模糊表达」判断
- 编排符合 [knowledge/case-arrangement.md](knowledge/case-arrangement.md)
- 待确认场景与可执行用例分开交付，审核状态如实标记

### 失败模式与 Fallback

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| AI 生成质量不达标（覆盖率<80%） | 增加约束、补 Few-shot | 分批生成（单次 10–15 条），人工补剩余；反复遗漏点回填「原文问题清单」（类型=模糊） |
| 格式不合规 | 按通用格式重新输出 | 人工修正并标 `source: manual` |
| 业务结果不明确/检查点不可定位 | 对照业务目标补充判定证据 | 按 writing-rules 调整目标与步骤组织 |
| 标题超 40 字 | 精简为「对象 - 行为」 | 信息不可删时保留长标题，禁止截断或加省略号 |
| 需求与代码矛盾 | 列矛盾点要求澄清 | 保留需求期望与实现差异，不用实现覆盖验收；回填「原文问题清单」（类型=矛盾） |

## 阶段 4：自检与补全

**行为约束**：发现遗漏直接补进用例；若遗漏源于原文问题，同时在「原文问题清单」记录位置与描述，不另起章节。

### 机器校验（必做，交付闸门）

```bash
python $SKILL_ROOT/scripts/validate_cases.py <用例文件>
```

| 结果 | 行为 | 输出标记 |
|------|------|----------|
| 0 error | 可交付 | `✓ 脚本校验通过（0 error）` |
| 有 error | 逐条修复后重跑，**禁止交付** | `✗ 脚本校验未通过（N error）` |
| 脚本不可用 | 按 `validate_cases.py` 规则码人工核对 | `⚠ 未脚本校验（原因）` |

- 交付时贴出校验摘要（文件数/用例数/error 数），不得只写「已校验」
- 脚本只覆盖 D 类（格式/枚举/词表/句长/结构/编排）；J 类仍须人工或评审 agent 判定
- warning 不阻断交付，但须在交付说明列出未处理项及理由
- 不得把「脚本校验通过」写成「人工审核通过」「用例已执行」或「质量已达标」

### 语义评审（J 类）

满足任一条件时交给独立评审者：交付外部团队/进入正式测试计划、含 P0 用例、用例数 >20。

执行方式：调用 `test-case-reviewer` agent（`plugins/testing/agents/`），或在新上下文中按 [knowledge/review-rubric.md](knowledge/review-rubric.md) 的 J1–J9 判定。评审者只看产物，不看生成过程。输出带原文引用的 issue 列表；问题回填后**重新执行脚本校验**。

- 评审者不改写用例，只给修改方向
- 评审者不输出总分或等级
- 缺少测试点清单时，覆盖度判为「无法评估」，不得臆测

### 失败模式与 Fallback

| 触发条件 | 一线修复 | 仍失败兜底 |
|----------|----------|------------|
| 自检发现测试点遗漏 | 回溯 7 维度，只补焦点或需求要求的遗漏 | 标遗漏维度并用例标「待补充」；需求段落回填「原文问题清单」（类型=缺失） |
| 优先级分布异常且缺少风险依据 | 按三步法复核业务影响、发生可能性与回归必要性 | 保持有依据的优先级，在效率报告说明分布及依据；不为满足比例调整 |
| AI 覆盖率不足 | 补充 Prompt 中的测试点清单，重新生成 | 人工补充遗漏，标 `source: manual` |
| 格式不合规 | 对照编写铁律逐项修正 | 人工修正，标记格式问题供后续优化 |

### J 类自检清单

> D 类以脚本 error 清单为准，勿重复逐项核对。

```markdown
**覆盖与追溯**：测试点均有对应用例或裁剪理由；用例可追溯到测试点/需求
**范围**：用例可指到需求/变更点；服务故障类 0 条或有依据；非焦点只冒烟
**可执行性**：结果可判 pass/fail；预期与步骤对应；照做可执行
**一致性**：同一概念/动词全文统一
**粒度与编排**：一用例一目标；等价场景已合并或参数化；顺序符合策略
**遗漏扫描**：字段/按钮/链接、角色、取消/返回/刷新已扫；安全已对照；原文问题已回填
**产品知识**（有文件时）：高频缺陷/专项清单/状态流转/业务规则已覆盖或注明不适用
**优先级**：有业务影响依据，未为凑比例调整
```

**交付**：输出用例及未评估项；生成完成不等于人工审核或已执行。效率报告模板见 [knowledge/efficiency-metrics.md](knowledge/efficiency-metrics.md)。

## 模式切换

- **默认**：不允许跳过阶段 1/2 直接写完整用例
- **快速**：压缩阶段 1/4 的需求理解与人工自检，但必须输出测试点清单，文首声明未做完整理解；**阶段 4 脚本校验不得跳过**
- **回归验证清单**：纯重构无行为变更时使用，跳过阶段 1/2，直接输出 `| 序号 | 验证项 | 关联变更 | 优先级 |`
- **探索式**：额外输出探索章程，与测试点清单并列
- **评审**：独立于四阶段生成流程，对他人/已有用例做 10 维度评审（详见 [knowledge/review-mode.md](knowledge/review-mode.md)）
- **需求评审**：输入为 PRD/需求文档且要求找需求问题时使用，不进入四阶段（详见 [knowledge/requirement-review.md](knowledge/requirement-review.md)）
