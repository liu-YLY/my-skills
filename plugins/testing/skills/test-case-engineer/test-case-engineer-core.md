# 测试工程师核心流程

> 四阶段：`理解需求 → 提取测试点 → 编写用例 → 自检补全`。后一阶段消费前一阶段产物；写作细则见 [knowledge/writing-rules.md](knowledge/writing-rules.md)，范围取舍见 [knowledge/scope-discipline.md](knowledge/scope-discipline.md)，分层编排见 [knowledge/case-arrangement.md](knowledge/case-arrangement.md)。

## 阶段 1：理解需求

**目标**：厘清业务规则、变更焦点与可测边界。**输出**：需求理解文档。

### 信息收集优先级

1. **P0 项目/产品/代码/已有用例**：扫 `docs/`、`testing-tm-cases/`（见 [knowledge/project-knowledge.md](knowledge/project-knowledge.md)）；存在对应产品时加载 `knowledge/products/{product-id}.md`（无则标「未找到产品知识文件」）；搜索 API、数据模型与控制器/服务层实际校验逻辑；读取同模块已有用例继承 ID 前缀与风格。
2. **P1 公开规范**：第三方服务文档、协议标准。
3. **P2 追问用户**：列出具体阻塞问题，不做隐式假设。

- **来源与评审衔接**：每读取一个文件立即记入「信息来源」；上游已有需求评审结论时直接消费（`confirmed` 进「原文问题清单」，`candidate` 进「待确认项」），不重复评审。
- **可测性与缺料兜底**：核对 trace/request id、环境已实际交付的账号/造数接口/沙箱（**严禁虚构未交付的隔离 stub 或可控服务端时钟**）及后端状态/消息核验方式。缺文档扫代码，代码不可达标「待验证」；依赖未决规则的场景标「待确认」并与可执行用例分开；需求与代码矛盾时保留需求期望，不用实现覆盖验收，全部记入「原文问题清单」（位置格式：`文件名:行号` / `PRD §x.y` / `对话轮次#N`）。

### 需求理解输出模板

```markdown
## 需求理解

**功能概述**：[一句话]
**本次变更焦点**：
| 焦点项 | 需求依据 | 改动的行为 |
|--------|----------|------------|
| [焦点 1] | [PRD §x.y / Story-ID] | [从…变为…] |

**不在本次范围**：[需求未涉及且不受本次改动影响的内容]
**需求追溯**：[能力点 → Story ID / PRD 章节；无正式 ID 填「待补充」]
**核心规则提取**：
- **角色与权限**：[涉及的角色及可见/可操作边界]
- **业务与数据规则**：[计算/校验/默认值/一致性/上下游配置优先级]
- **状态与异常规则**：[初始/合法切换/互斥/终态；需求明确定义的拒绝/限流/幂等/重试规则，未定义不脑补底层故障]
**风险与待确认项**：[高风险点；未明确处标「待产品确认」]

**原文问题清单**（阶段 1–4 累积，不另起章节）：
| 序号 | 原文位置 | 问题类型 | 问题描述 | 影响范围 | 处置 |
|------|---------|---------|---------|---------|------|
| 1 | [PRD §3.2 / req.md:L42] | 模糊/矛盾/缺失/错误 | [原文片段 + 问题] | [影响的测试点] | [待确认 / 已按 X 理解] |

**信息来源**：[实际读取的文件/接口/文档路径]
```

**业务特征速查**：通知/邮件（发送·防重·退订·开关）、状态机（初始·切换·互斥·非法流转）、配置（优先级·覆盖·冲突）、支付/订单（分精度·重复支付·部分退款·超时）、权限（角色矩阵·越权·Token·脱敏）、搜索（特殊字符·空结果·排序）、异步任务（触发·重试·死信·并发）。

## 阶段 2：精准提取测试点

**目标**：不漏焦点、不留越界。**输出**：测试点清单表格。

### 范围闸门与 7 维度扫描

每个候选点必过三问：**① 有需求/契约依据？② 本次改动影响预期？③ 失败归本次责任方修且无需虚构工具即可复现？** 任一为否即不落用例，写入「裁剪说明」（服务故障默认 0 条、边界值不穷举、非焦点不展开，详见 [knowledge/scope-discipline.md](knowledge/scope-discipline.md)）。

| 维度 | 覆盖深度（扫描清单，非数量下限，按风险裁剪） |
|------|----------------------------------------------|
| 正向功能 | 每个涉及角色至少 1 条 Happy Path |
| 反向校验 | 只测本次改动涉及校验的字段；等价非法输入合并为参数化一行 |
| 权限/角色 | 只测需求明确的角色 × 焦点功能，其余裁剪并写理由 |
| 状态联动 | 每对明确联动关系 × 相关源状态 |
| 边界与限制 | 仅对有明确阈值且本次改校验的字段取一组三点（临界内/临界/临界外），对称区间取一端 |
| UI 交互 | 仅当 UI 本身为被测对象时逐点覆盖 |
| 异常与容错 | 仅当需求明确要求容错/降级/重试/幂等时覆盖；默认 0 条 |

**测试点三原则**：① **单一目标**（禁「保存成功且展示正确」，不混排正常+异常、UI+底层）；② **要素完备**（含 `[验证对象] + [操作/条件] + [预期方向]`，禁「验证开关可关闭」）；③ **焦点优先**（非焦点只留 1 条冒烟，禁堆砌低价值 UI 点）。

### 高危特征与产品知识补点（命中焦点才补）

- **高危缺陷特征触发速查**（复杂场景按需查 [knowledge/bug-patterns.md](knowledge/bug-patterns.md)）：
  - **输入框/表单**：前后端必填绕过、超长截断、特殊字符编码；面向公网时测 XSS/注入。
  - **状态/提交/并发**：终态非法回退、操作后刷新对比（防幽灵状态）；需求含幂等/防重时测重复提交或并发冲突。
  - **资金/配额/上限**：浮点分精度、重复扣款、部分退款边界（0/等于/大于支付）、**封顶临界三档**（低于/恰好等于/高于上限）。
  - **权限/时间/列表**：篡改资源 ID 水平越权、低权限直调 API 垂直越权、跨时区/过期临界点、空列表与末页删除分页。
- **产品知识映射**（已加载时在「来源」列标 `产品知识-{章节名}`，未命中项写裁剪说明）：业务规则（1 正 + 1 反）、状态流转（合法 1 正 + 非法 1 反，已用状态机 skill 不重算）、历史缺陷/专项清单（仅命中焦点时补）、数据字典（有阈值取三点，格式合并参数化）、性能基线（仅需求给指标时用）。
- **设计方法**：有阈值用三点边界值；多条件组合用判定表；状态迁移用状态法；业务主备异常流用场景法。

### 测试点清单模板与机器校验

```markdown
## 测试点清单

| 编号 | 测试点 | 维度 | 设计方法 | 优先级 | 用例数（估） | 需求引用 | 来源 | 裁剪说明 |
|------|--------|------|----------|--------|-------------|----------|------|----------|
| TP-01 | Endpoint URL 必填与 HTTPS 协议校验 | 反向校验 | 等价类 | P0 | 2 | PRD §3.2 | 需求 | HTTP 明文合并参数化 |

**覆盖度自检**：7 维度与高危特征已判适用性；有阈值字段取三点、无阈值已裁剪；越界候选已剔除并写理由。
```

保存后必跑 `python $SKILL_ROOT/scripts/validate_points.py <清单.md>`，**0 error** 方可进阶段 3。

## 阶段 3：编写测试用例

**输出**：以 `### TC_{模块}_{功能}_{序号}: 标题` 块承载（表格仅限块内同构 P2/P3 数据组，**严禁整表罗列全部用例**）。

1. **三轮生成**：核心正反向用例 → 补齐未覆盖测试点 → 补命中高危特征的防御性用例（若有产品知识，注入校验规则、状态路径与场景模板）。
2. **来源与审核诚实**：AI 生成标 `source: ai-generated`、人工补充标 `source: manual`；未经真实人工审阅，状态固定写 `not-reviewed`。
3. **落笔硬约束**：
   - 过 [knowledge/scope-discipline.md](knowledge/scope-discipline.md) 淘汰门：禁无依据服务故障、禁虚构夹具/可控时钟、禁同兜底逻辑按状态码机械裂变、禁把查配置/问口径写成用例。
   - 守 [knowledge/writing-rules.md](knowledge/writing-rules.md) 槽位与红线：单条数据自包含（禁外置 `test-data` 暗号表）；前置只写客观业务状态（禁默认无干扰废话、禁取证动作、禁过程叮嘱、禁裸写底表列名）；业务结果禁冠 `步骤 N：` 前缀、禁写防作弊说教与免责备注；单条有效汉字 **≤60 字、最多 1 个分号**，输出前逐句执行**删词脱水测试**。
   - 待确认场景单列，不混入可执行用例；体量大时按 10–15 条分批生成。

## 阶段 4：自检与补全

发现遗漏直接按编排位置补入用例（源于需求缺陷的同步记入「原文问题清单」）。

### 1. 机器校验（必做交付闸门）

```bash
python $SKILL_ROOT/scripts/validate_cases.py <用例文件>
```

- **0 error 方可交付**：贴出校验摘要（文件数/用例数/error 数），标记 `✓ 脚本校验通过（0 error）`；有 error 必须逐条修完重跑，禁止带病交付；脚本不可用时按规则码逐条人工核对并标 `⚠ 未脚本校验（原因）`。
- warning 须在交付说明列出保留理由；严禁把「脚本校验通过」冒充为「人工审核通过」或「用例已执行」。

### 2. J 类语义自检与独立盲评

- **常规自检**：测试点全覆盖或有裁剪理由；每条可指回需求/变更点；预期可直接判 Pass/Fail 且与实际步骤对应；全文术语动词统一；等价场景已合并；优先级有业务风险依据（**不为凑固定比例增删或调级**）。
- **独立盲评触发**：交付外部团队/正式测试计划、含 P0 用例或总数 >20 条时，调用 `test-case-reviewer` agent 或在新上下文按 [knowledge/review-rubric.md](knowledge/review-rubric.md)（J1–J9）只看产物盲评；修订回填后**必须重跑 `validate_cases.py`**。效率报告按需见 [knowledge/efficiency-metrics.md](knowledge/efficiency-metrics.md)，脚本排障见 [knowledge/anti-patterns.md](knowledge/anti-patterns.md)。

## 模式切换

- **默认**：完整执行阶段 1–4，禁止跳过阶段 1/2 直接写用例
- **快速**：压缩阶段 1/4 理解与人工自检，文首声明快速模式，必出测试点清单且**必跑阶段 4 脚本校验**
- **回归验证清单**：纯重构无行为变更时跳过阶段 1/2，直接输出 `| 序号 | 验证项 | 关联变更 | 优先级 |`
- **探索式**：并列输出探索章程（`**时间盒** / **范围** / **关注点** / **证据** / **退出条件**`）
- **评审**：独立于四阶段，对已有用例做 10 维度评审与修订闭环（见 [knowledge/review-mode.md](knowledge/review-mode.md)）
- **需求评审**：独立于四阶段，审查 PRD 可测性与矛盾缺失（见 [knowledge/requirement-review.md](knowledge/requirement-review.md)）
