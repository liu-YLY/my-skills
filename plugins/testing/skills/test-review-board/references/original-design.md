# 原版奖励重构评审是怎样组织的

原件是用户提供的 `reward-refactor-review.html`，页名为“奖励架构重构 · 业务与数据测试评审”。下面的“原稿”指该文件；同一轮整理中后来制作的普通券示例只用于说明取舍。

## 为什么先讲测试构思

重构评审要同时回答两个问题。对顾客和商家，原先能做的操作是否仍有相同结果？对迁移的数据，新旧规则、券、积分和历史记录能否继续对应？原稿开头先解释两条验证路径，再用脑图列出普通券、POS、VIP、Referral、公共规则、关联业务、性能与数据迁移。这样，开发可以追问数据，产品也能一直跟着业务走。

原稿显示 183 个测试点，其中业务 153 个、数据 30 个；1,180 条用例记录中有 2 条待删除，页面注明未执行。数字说明评审材料的范围。复用这种做法时，用当前材料重新计算，并保留记录的状态。原稿安排了一场 60 分钟的会议，先讲主流程，有分歧再展开；会议时长、模块数量和讲解次序均可随项目调整。

## 总览、流程和用例各解决一个问题

| 评审时读者要回答的问题 | 原稿做法 | 复用时的取舍 |
| --- | --- | --- |
| 这次评什么，哪些人要参与？ | 默认展开测试构思和范围脑图，业务与数据入口分开 | 模块多时保留范围总览。单模块把边界讲清即可 |
| 业务究竟在哪一步发生？ | 各模块按角色与行为展示。普通券图分商家、顾客、奖励系统、Shopify 四条泳道 | 按实际交接划角色。保留主线、异常发生位置、恢复去向与终态。只缩短会议中的浏览路径 |
| 这个动作要测什么？ | 点图上节点，右侧按环节或节点展示测试点；点与图有对应标识，可切换聚焦和全图 | 同屏显示动作、规则和可观察预期。跨多个节点的规则保留多处关联 |
| 这个预期究竟怎样验证？ | 从测试点打开右侧独立查阅区。先看到整组用例的编号和标题，可同时展开多张卡片，对照前置条件、测试步骤和预期结果 | 将“返回测试点”和切换相邻测试点放在面板头部。标题负责展开，另设“定位流程”回查当前用例对应的分支。详见[用例查阅区设计](case-reader.md) |
| 出现分歧后怎样找回？ | 既有测试点旁保留评审口径或提醒；修改记录可关联测试点或用例，标作改测试点、改用例、待确认等 | 把原规则与补充意见并列。讨论结束后能按原 ID 找回并确认。记录意见和改写源用例是两个动作 |

原稿用浅底、深色标题与浅蓝模块区分阅读层次。泳道列头标明责任方；正常和替代流转有不同线型和标签；选中测试点可强调关键节点、相连路径和上下游。图较长时，聚焦便于核对文字，全图便于判断走向。图表的颜色、编号、选中态要帮助读者找到对应内容。

制作交互图时，可按[泳道图取景与展示规则](swimlane-view.md)核对原版的双视图、上下游取景、泳道列头、稳定步骤号和键盘行为。

## 一个能检验设计好坏的场景

普通券原稿有 7 个讲解环节、4 条泳道、20 个流程节点、19 条连线，包含 35 个测试点和 253 条用例记录。沿商家配置向下看，顾客主动兑换和商家代兑都要进入资格校验；建码、发券扣分、购物车应用以及订单回写发生在不同位置。已领券仍涉及历史展示、使用、到期或撤销。若用“发起 → 成功／失败”概括这些环节，读者就无法判断失败后该核对哪一侧的数据。

| 用原件可以核实的事实 | 对设计的影响 |
| --- | --- |
| `TP-NOR-013` 关联“校验兑换条件”和“条件不满足”。结账页两条用例 `TC_RWD_NOR_013_05`、`_06` 分别写明余额 100 分兑换成功和 99 分被拒。 | 选择测试点应看到两个节点。以**用例级反向定位**区分这两条分支，是这次讨论提出的明确要求，细分依据来自原用例标题。 |
| `TC_RWD_NOR_021_01` 描述兑换成功后商品不适用；换回适用商品可重用原码。原图的“应用失败”节点已有这段说明。 | 原稿说明了恢复行为。后续示例将它补画成回到“购物车应用优惠”的线，标为依用例补绘。另一条从已领券直接到期检查的线依据 `TP-NOR-032`。两条均不计入原图 19 条连线。 |
| `TP-NOR-036` 单列“本地已退分，但 Shopify 删除优惠码失败”的结果。 | 画图时分别标出本地结果和外部结果，测试点要能追到两侧；“撤销失败”四个字不足以判定。 |
| `TC_RWD_NOR_010_07`、`_08` 保留了待删除说明。 | 可以计入原始记录数，展示状态与原因，并排除在可执行清单之外。 |

同样的区分也适用于其他业务。例如退款受理、账户实际入账和订单退款状态可能由不同系统完成。只有当前材料说明了这些步骤和结果，才把它们画进当前项目。

## 如何核对原件

有原 HTML 时，可以从 `case-catalog` 核对原用例，从 `presentation-map` 中的 `domains`、`modules`、`point_case_ids`、`case_annotations` 和 `deferred_cases` 核对结构和口径。泳道图的节点和边在各模块的 SVG 中，`review-flow-v9` 维护点到节点的关联。原图中也有定位到整个环节的入口；这类入口应如实标明关联粒度。

页面同时保留了早期说明和后续交互。例如旧说明仅提到普通券已加泳道，实际文件有八个模块泳道；修改记录的静态配置与最终页面脚本也有差异。整理设计时，以实际文件中的内容和可观察交互描述现状；需求来源或正式决定仍须引用相应材料。
