# 测试分层与契约

> **何时阅读**：选择测试层与验证方法时。

## 1. 按风险选层

先找能观察风险、且反馈成本最低的测试层，再看现有覆盖缺口。只有更高层能证明的协作或用户结果，才补到更高层。同一风险可以在不同层观察不同结果。

| 层级 | 能证明什么 | 示例 |
|------|-----------|------|
| 单元/组件 | 规则、分支和本方适配行为 | 金额边界、未知状态映射 |
| 接口/集成 | 请求响应、服务协作、真实持久化或副作用 | 订单与库存同事务、退款入账 |
| 端到端 | 关键流程能贯通，经 API、消息或实际 UI 到达 | 支付跳转后真的回到订单结果页 |

无界面就省略 UI。按需隔离不稳定、难配置或高成本的依赖，保留有助于观察风险的确定性组件。比例仅作投入示意，给出时注明是用例数还是工时，避免把数量当覆盖。

## 2. 跨系统契约

- 消费者可识别、双方能协作且能准备提供方状态时，考虑消费者驱动契约。用真实消费者代码向 mock 发请求并核对响应处理，再由提供方在对应状态重放并核对响应，记录双方版本和验证范围。
- 不可控第三方：按公开规范验证本方请求与响应适配，覆盖实际使用的分支。Mock 说明本方在假设响应下如何处理。可用 sandbox 时再核对实际交互，并注明环境和未验证范围。
- 涉及事务、消息投递或重复副作用时，契约通过不能代替对真实协作结果的验证。
