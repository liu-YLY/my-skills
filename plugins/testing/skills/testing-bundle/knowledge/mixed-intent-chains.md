# 混合意图链详细步骤流

> **何时阅读**：bundle 判定命中混合链后，按链号阅读对应章节；单意图不读。
> **通用约定**：每个转交点展示「中间结果 + 转交依据 + 未决事项」；已授权只读分析连续执行，仅在缺关键信息、范围变化或未授权写操作时暂停。用户要求一次交付时文末统一汇总。
> **安全提示**：涉及 git diff 或终端命令时，只在当次授权范围内读取，遵守 [test-case-engineer 安全约束](../../test-case-engineer/integrations/quickstart.md)。

## 链冲突裁定（多链命中）

优先级（高 → 低）：链 6/7（评审先于生成）→ 链 4（根因定位）→ 链 1/5（根因/建模先于用例）→ 链 3（性能内部完成；与链 4 冲突按用户主诉求）→ 链 2（策略先于用例）→ 链 9（上下文先于用例）→ 链 8（用例与规则确定后造数）。

- 高优先级链先执行，下游用例生成合并，避免重复转交 test-case-engineer
- 输出有依赖时按依赖串联（如链 7 证据可复用给链 6）
- 链 9 + 链 2：先出策略与前端上下文，再共用一次用例生成
- 链 8 + 链 1/2/5/9：共用一次用例生成，再转交 test-data-generator；用户未要求数据交付时不追加造数
- 无法判定 → CHECKPOINT 列候选链；用户授权「你来决定」按默认顺序；用户指定顺序优先

## 链 1：分析 Bug 并补充用例

`bug-analyzer 根因 → 防御性测试点清单 → CHECKPOINT → test-case-engineer 生成用例 → 根因 + 用例报告`

触发：Bug 根因信号 + 用例生成信号。

## 链 2：策略 + 分层用例

`test-strategy-engineer 策略/分层/优先级/准入准出 → CHECKPOINT → test-case-engineer 按层生成 → 策略 + 分层用例`

触发：项目级策略信号 + 用例生成信号。

## 链 3：性能测试 + 瓶颈分析

`performance 阶段 1–2 方案 → CHECKPOINT → 阶段 3 瓶颈定位（内部完成，不转交）→ 方案 + 瓶颈报告`

触发：性能测试信号 + 瓶颈/容量信号。

## 链 4：性能问题定位到代码缺陷

`performance 瓶颈定位 → CHECKPOINT → 阶段 4 判断指向代码层 → bug-analyzer → 瓶颈报告 + 代码根因 + 修复建议`

**链 3 vs 链 4**：含代码层/逻辑层/死锁/N+1/内存泄漏/连接泄漏/空指针/业务规则错误 → 链 4；含资源/CPU/IO/网络/架构/扩容/连接池不足/缓存未命中 → 链 3；两类都有 → 默认链 3，performance 阶段 4 按证据判断是否转交。

## 链 5：状态机建模 + 用例

`state-machine 模型 + 场景清单（需求明确/合理推理/待确认）→ CHECKPOINT → test-case-engineer 生成步骤级用例 → 模型 + 场景 + 用例`

触发：状态型信号 **且** 明确要求完整用例/步骤级落地。
- 只要场景/测试点 → 单意图 state-machine
- 只要用例 → 单意图 test-case-engineer
- 两者都有 → 链 5

## 链 6：评审 → 覆盖缺口验证

`test-case-engineer 评审 → R2 覆盖度 P0/P1（4 类场景缺失/异常用例为 0）→ CHECKPOINT → change-impact-analyzer 做 git diff × 用例交叉验证 → 意见表 + 度量 + 缺口 + 代码层验证 + 补充建议`

触发：评审信号 **且** 覆盖缺口/覆盖度验证/diff/回归风险信号。
- 只要评审 → 单意图 case-engineer 评审
- 只要覆盖验证 → change-impact-analyzer
- 两者都有 → 链 6

> change-impact-analyzer 随 testing plugin 整体安装；未安装时链 6 步骤 3 降级为 bundle 方向性指导（四阶段：收集输入→Diff 解析→交叉分析→生成报告）。

## 链 7：评审 → 风险用例根因反推

`test-case-engineer 评审 → 高风险用例（P0 集中/可执行性 P0/字段规范 P0）→ CHECKPOINT → 质量问题交回 case-engineer 修订；有实际故障证据才转 bug-analyzer，风险假设保留待验证 → 意见表 + 度量 + 风险清单 + 诊断 + 待验证场景`

触发：评审信号 **且** 根因/缺陷定位/风险分析/为什么会出问题信号。
- 只要评审 → 单意图 case-engineer
- 只要根因 → bug-analyzer
- 两者都有 → 链 7

## 链 8：用例编写/修订 → 离线数据

`test-case-engineer 用例（编号/场景或固定组合维度/字段与规则/来源/待确认）→ CHECKPOINT → test-data-generator 生成并独立校验（已有文件用 validate）→ 用例 + profile + 数据 + 校验报告，保留 case_ids/combination_id/验收映射`

触发：明确要求新编/修订用例 **且** 生成或校验对应离线数据。
- 已有用例/场景/矩阵只要准备数据 → 直接 test-data-generator，不重写用例或发明组合
- 只编写/评审用例 → test-case-engineer，不追加造数
- 压测/状态机/变更影响产物需要数据 → 按实际产物转交，不强制新增完整用例

数据：保留未决规则；数量、种子、输出位置按已有信息传递，缺省参数由 test-data-generator 处理；已有矩阵维度固定，辅助字段才随机。校验通过只表示已声明约束通过；未运行标 not_run，无法完成必需断言保留 incomplete；不导入数据库、不调用业务接口、不推导系统/压测通过。

## 链 9：前端准备 → 用例

`frontend-test-preparation 建/更新索引并映射需求 → 入口/前置（角色/权限/开关）/数据/步骤/检查点，标注代码推断/运行已验证/待确认 → CHECKPOINT → test-case-engineer 生成或修订 → 索引 + 准备记录 + 用例`

触发：前端准备信号 **且** 要求生成/修订用例。
- 只要前端准备 → 单意图 frontend
- 只要用例 → test-case-engineer
- 两者都有 → 链 9

**边界**：「测试前端功能」「测这个页面」按用例生成；前端准备的正确预期必须引用需求/设计/用户确认，代码现状只能作实现证据；缺运行条件只交付代码分析与待确认项，不把未执行标为通过，不扩大授权。
